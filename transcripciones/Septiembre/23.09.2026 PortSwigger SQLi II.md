**El mapa de las inyecciones: dónde encaja cada una**

Antes de meter una técnica nueva, el profesor rehace el esquema de siempre (navegador → HTTP/TLS sobre TCP/IP → servidor → ficheros de la web → base de datos) para ubicar cada inyección en su capa exacta. Esto es lo que responde a la gran duda de "tengo una web, ¿por dónde empiezo?".

- **XSS (Cross-Site Scripting):** ocurre en el **navegador**, inyecta **JavaScript**, y afecta a la zona entre el cliente y la IP pública (el front). Lo máximo que habilita es robar una cookie de sesión, por lo que en un CTF donde estás solo en la máquina no vale casi nada
    
- **SQLi:** ocurre en el **backend**, concretamente en la **base de datos**; no altera la plantilla, sino el resultado de la consulta
    
- **XXE:** ocurre también en el backend pero a nivel **documental** (inyección XML), y solía escalarse a un **LFI** recurriendo a un elemento externo
    
- **SSTI:** la pieza que faltaba. Inyecta directamente en la **template** (PHP, Python, Java, .NET…), que vive en un directorio del servidor, que a su vez corre sobre un sistema operativo. Si logras que la plantilla interprete tu texto como código, hablas con el **Linux** que hay detrás
    
- **La idea clave:** un mismo campo de texto reflejado puede ser vector de XSS, SQLi _o_ SSTI a la vez; la decisión de cuál probar depende de qué haya detrás (¿hace petición a base de datos? ¿se refleja el input? ¿qué lenguaje corre?)
    

---

**Qué es el SSTI y por qué el payload es una operación matemática**

Un SSTI aprovecha que los campos variables de una plantilla se rellenan en servidor _antes_ de enviar la respuesta al front. Si esas variables se rellenan con funciones de código en lugar de con datos, el motor de plantillas las ejecuta, exactamente igual que un SQLi ejecuta una query dentro de la consulta legítima.

- El payload de prueba universal es una operación aritmética como 7*7: si el campo devuelve **49**, el servidor ha _interpretado_ la expresión en lugar de tratarla como texto plano, confirmando el SSTI
    
- **La idea clave:** por eso los payloads de test son operaciones matemáticas y no <script/> buscamos evidencia de que hay un motor evaluando expresiones, no de que hay un navegador interpretando HTML
    
- Truco de detección avanzado (aportado en clase): existen payloads con muchos caracteres especiales donde el **carácter que "desaparece"** al procesarse revela qué tecnología de plantilla hay detrás, porque cada motor consume una sintaxis distinta

**Ecosistema y motor: cómo elegir el payload de detección**

Determinar qué payload lanzar es lo más complejo del SSTI, y para ello hay que conocer dos cosas: el **ecosistema** (el lenguaje) y el **motor** (el engine de plantillas concreto que corre sobre ese lenguaje).

- **La metáfora útil:** el ecosistema es como la marca "Audi" y el motor es el modelo concreto (A1, A2, A3…); un mismo lenguaje puede montar motores muy distintos, y cada uno pide su propia sintaxis
    
- Mapa mínimo de motores que merece la pena reconocer: **Python** → **Jinja2** (el más común, típico de **Flask**) y Mako; **PHP** → **Twig** (más conocido que Smarty); **Java** → **Thymeleaf**; **Ruby** → **ERB**; **Node.js** → varios; **.NET** → **Razor**
    
- Payloads de test según motor:
    
    - Jinja2 (Python/Flask): { {7*7} } → 49
        
    - ERB (Ruby): <%= 7*7 %> → 49
        
    - Razor (.NET): @(7*7) → 49
        
- **La idea clave:** vivimos en la época de la IA — antes había que probar payload por payload a ciegas; hoy basta con enumerar bien el lenguaje/motor y pedir el payload adecuado, o lanzar un **Intruder** de Burp con las opciones candidatas y ver cuál devuelve 49
    

---

**Los dos requisitos para que exista un SSTI**

Para que un SSTI sea explotable hacen falta exactamente las mismas dos condiciones que ya identificábamos para el XSS almacenado, y conviene tenerlas presentes al auditar cualquier formulario.

- Un **campo de input** donde introducir el payload
    
- Un **sitio donde ese input se refleja** de vuelta al usuario
    
- **La idea clave:** si además el input se guarda en base de datos y se muestra al recargar (como el full_name de un perfil), estamos ante la variante _stored_, que persiste igual que el XSS almacenado; el flujo es idéntico, solo cambia quién interpreta el dato

**Reconocimiento de la máquina: ping, TTL, Nmap y el servidor Werkzeug**

Retomando la metodología de red de la clase de OWASP API, el flujo arranca igual: un ping para confirmar que el host responde y que **ICMP** está activo, leyendo el **TTL** para deducir el sistema operativo.

- TTL observado de **63** → Linux (64 base menos un salto por la VPN de HackTheBox), como confirmamos con traceroute viendo el salto intermedio
    
- Sobre la metodología de Nmap, la decisión profesional es escaneo estándar primero (top 10.000 puertos, poca traza) y solo después -sC -sV sobre los puertos encontrados; el -p- se reserva para cuando el recurso visible se agota
    
- **La idea clave:** lanzar -p- de primeras dispara ~55.000 peticiones basura y mucho ruido; primero se agotan los recursos visibles y solo si son un callejón sin salida se barre el espectro completo
    
- El único puerto abierto (**80**) monta un servidor **Werkzeug + Python 3.9.2**. Buscarlo en Google revela que es el servidor de desarrollo típico de **Flask** → Python → apunta directamente a **Jinja2** como motor probable de un futuro SSTI
    
- **La metáfora útil:** ante un servicio desconocido _que tienes delante_, buscarlo cuesta 10 segundos y puede regalarte el vector; no se trata de estudiarse toda la informática, sino de investigar lo que ya sabes que existe en tu objetivo
    

```
ping <IP>
traceroute <IP>
nmap <IP>
nmap -sC -sV -p80 <IP>
```

**Enumeración web: rabbit holes y fuzzing de directorios en paralelo**

Con la web delante, la disciplina es _toquetearlo todo_ (todo cursor con "manita" es interactuable → hace una petición → es un potencial vector) mientras se deja un fuzzer de directorios corriendo de fondo para no perder tiempo.

- Buena práctica: lanzar **Feroxbuster** (o dirsearch/gobuster) de forma recursiva nada más entrar, en paralelo a la exploración manual
    
- Muchas funcionalidades resultan ser **rabbit holes** (madrigueras): buscadores fake con ?# que recargan la propia página, artículos sin implementar, un forgot password que responde igual exista o no el email (bloqueo deliberado de **enumeración de usuarios**), un /server-status en 403
    
- El hallazgo útil del fuzzing es un /signup que permite registrarse: se crea un usuario de prueba para entrar al área privada
    
- **La idea clave:** ante un login no hay que saltar directo al SQLi por inercia de "llevamos tres semanas con SQLi"; primero se enumera, y a veces el propio registro te da acceso

**Resolución de subdominios sin DNS: /etc/hosts y DNS hijacking**

Al entrar como admin aparece un engranaje que redirige a un subdominio (internal-administration...) sobre el **puerto 3000**, montado con **Flask**. Como en el laboratorio no hay acceso a los DNS de Internet, la resolución tiene que hacerla el propio atacante.

- La solución es editar /etc/hosts en Kali y mapear a mano la IP con goodgames.htb y cada subdominio; **no** vale el comodín *.dominio, hay que declarar cada nombre explícitamente
    
- **La idea clave:** resolver un nombre significa pasar de _name server_ a IP pública; sin acceso a esos servidores, _tú eres_ el DNS, y /etc/hosts es tu tabla de resolución local
    
- **La metáfora útil (contexto real):** ese mismo mecanismo, en manos ofensivas sobre una red pública (un Wi-Fi abierto en un Starbucks o un hotel), es un **DNS hijacking**: te haces pasar por el servidor DNS de la red, y cuando una víctima pide [bancox.com](http://bancox.com/) la rediriges a tu página de phishing. Por eso una red pública —y más si tú la levantas— es tan peligrosa
    

```
sudo nano /etc/hosts
# <IP>   goodgames.htb internal-administration.goodgames.htb
```

**Extracción de datos con UNION-based SQLi**

Como Minu señaló acertadamente, hacer solo el bypass desaprovecha el vector: el SQLi permite **volcar la base de datos** entera para reutilizar sus credenciales en el segundo login. El procedimiento con UNION SELECT es siempre el mismo.

- Se determina el número de columnas probando UNION SELECT 1,2,3,4... hasta que deja de dar error → aquí son **4 columnas**, y la que se refleja en el welcome es la **número 4**
    
- En ese campo reflejado se van colocando funciones: database() revela el nombre de la BD (**main**)
    
- Con information_schema se enumeran tablas y columnas hasta encontrar la tabla user con los campos id, email, password, name
    
- **La idea clave:** no se buscan los campos "a lo loco" aunque intuyamos que existen; se listan paso a paso (esquema → tablas → columnas → datos) porque así se descubre lo que realmente hay, no lo que suponemos
    
- Estos payloads son de plantilla: se memorizan, se buscan en Google, o se automatizan con **SQLMap** (esta máquina admite ambas vías)
    

```
' UNION SELECT 1,2,3,concat(table_name) FROM information_schema.tables WHERE table_schema='main';-- -
' UNION SELECT 1,2,3,concat(column_name) FROM information_schema.columns WHERE table_name='user';-- -
' UNION SELECT 1,2,3,concat(id,';',password,';',email,';',name) FROM user;-- -
```

**Crackeo de hash y reutilización de credenciales**

El volcado devuelve la contraseña del admin como un **hash MD5**. Aquí se aplica la teoría de reutilización de credenciales vista ayer.

- Pegar el hash en una herramienta de crackeo (o CrackStation/md5-online) identifica el algoritmo como **MD5** —débil— y lo rompe al instante
    
- Con admin + contraseña en claro se accede al **segundo login** del panel interno (el que _no_ era vulnerable a SQLi), confirmando que las credenciales estaban reutilizadas entre la web pública y el backend administrativo
    
- **La idea clave:** que el segundo login no tuviera SQLi no cierra la puerta; la enumeración del primero, bien exprimida, entrega las llaves del segundo

Con esta clase entendemos que una API o una web no se rompen con una sola bala, sino encadenando fallos, y ya sabemos ubicar cada inyección en su capa: el XSS en el navegador, el SQLi en la base de datos, el XXE en los documentos y —cerrando el círculo— el **SSTI en la propia plantilla del servidor**. Somos capaces de detectar un SSTI con el test del 7*7, de identificar el motor por el ecosistema (Jinja2 si es Python/Flask) y de evolucionarlo hasta un **RCE** subiendo por la jerarquía de objetos hasta os.popen. Hemos reforzado el reconocimiento de red que arrastramos desde la clase de OWASP API (ping, TTL, Nmap disciplinado), hemos exprimido un SQLi hasta volcar y reutilizar credenciales como planteamos ayer, y hemos visto por qué /etc/hosts nos convierte en nuestro propio DNS —con su reverso ofensivo, el DNS hijacking—. La máquina GoodGames deja la lección de fondo del máster: este perfil, encadenar vulnerabilidades sin CVE hasta el compromiso total, es exactamente lo que el mercado llama **AppSec** y lo que más se demanda.
