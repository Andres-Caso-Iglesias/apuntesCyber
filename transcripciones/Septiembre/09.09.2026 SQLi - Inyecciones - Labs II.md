**El debate sobre la carrera hacia la superinteligencia**

Se analiza el hilo de Jacob Kox (investigador que trabajó en OpenAI y Anthropic), quien renunció denunciando que ambas empresas compiten de forma poco responsable hacia una superinteligencia que se automejora, y que dentro de las propias compañías se reconoce en privado el riesgo aunque se minimice de cara a la prensa. El punto técnico de fondo es que cada nuevo modelo se entrena usando agentes del modelo anterior como generador de datos sintéticos, por lo que la capacidad se retroalimenta de forma acelerada generación tras generación.

- **La idea clave:** los modelos son cada vez más potentes, pero también cada vez más capados de cara al público (los casos de Mitos y GPT-5 se mencionan como ejemplos de lanzamientos que hubo que restringir tras detectar capacidades peligrosas), porque el propio nivel de potencia empieza a suponer un riesgo real si se pone en manos de cualquier usuario civil
    
- **La metáfora útil:** la calidad del aprendizaje de una IA depende de "qué profesor" (qué modelo) la entrena, igual que la formación de un alumno depende de qué profesor le da la clase; si cada modelo entrena al siguiente, se genera una cadena de mejora exponencial y autoalimentada
    
- Se conecta con la reflexión ya lanzada en clases anteriores sobre el ritmo de aparición de nuevos modelos: lo que hace un año y medio era un hito (conectar Claude a la terminal de Kali) hoy es una base que cualquier alumno del máster supera con creces
    
- En el debate posterior entre alumnos surgen varias posturas: que la IA es "una herramienta" y no un competidor mientras carezca de capacidad de razonamiento y decisión propia; que cada revolución tecnológica (máquina de vapor, [punto.com](http://punto.com/), telecomunicaciones) destruye empleos pero crea otros distintos; y que el verdadero riesgo no es que las grandes tecnológicas frenen el desarrollo, sino que dejen ventaja a actores maliciosos (grupos terroristas, cibercrimen organizado) que no se detienen ante ningún dilema ético
    
- **La idea clave para la práctica profesional:** la IA resuelve la ejecución de código, pero no resuelve por sí sola la arquitectura, el criterio de diseño ni la idea original de un producto — ese sigue siendo el valor diferencial del humano en el bucle (human in the loop)

**Diseño de arquitectura segura en Hetzner: segmentación de red real**

Se despliega en vivo la arquitectura que se había dibujado conceptualmente en la clase anterior: dos servidores en un proyecto de Hetzner, uno como Web Server (con IP pública, en la DMZ) y otro como BBDD Server, ambos conectados además por una red privada interna (rango 10.10.10.x/24). Solo el Web Server es accesible desde Internet; el servidor de base de datos no expone IP pública y únicamente es alcanzable desde el Web Server a través de la red interna.

- **La idea clave:** esto es segmentación de red aplicada en la práctica, el mismo principio que exigen normativas como **ISO 27001**, el Esquema Nacional de Seguridad, **DORA** o **NIS2** — nunca exponer directamente el recurso más sensible (la base de datos) a la red pública
    
- Se aclara un matiz legal importante: la ISO 27001 es una certificación voluntaria, no obligatoria; su ausencia no es sancionable, pero sí puede impedir la adjudicación de un contrato si el cliente la exige como requisito, y existen hasta 98 medidas compensatorias documentadas para justificar controles equivalentes sin tener la certificación formal
    
- Para la conexión a los servidores se generan un par de claves **SSH** (pública/privada) en lugar de usar contraseña: la clave pública se sube al servidor, la privada se queda en el equipo local, y la autenticación se produce por criptografía asimétrica sin necesidad de introducir contraseña en cada conexión

```
ssh-keygen
ssh root@<IP> -i <ruta_clave_privada>
```

**Firewalls de entrada y salida: bloqueo por defecto y excepciones mínimas**

Se configuran dos firewalls diferenciados. El del Web Server permite solo tres puertos de entrada (22 para SSH, 80 redirigido a 443, y 443 para el tráfico HTTPS), bloqueando todo lo demás por defecto (filosofía **zero trust**: bloquear todo y habilitar solo lo estrictamente necesario). El del servidor de base de datos solo acepta conexión desde la IP interna del Web Server, exclusivamente por el puerto 3306 de MySQL.

- **La idea clave:** un mismo puerto no puede alojar dos servicios distintos simultáneamente (con la excepción rara de un WebSocket sobre HTTPS), por lo que limitar los puertos abiertos limita directamente las superficies por las que un atacante podría establecer una reverse shell tras comprometer el servidor
    
- Además del tráfico de entrada, se bloquea también el tráfico de salida (outbound) no necesario, precisamente para impedir que, si el servidor es comprometido, pueda establecer una conexión saliente hacia el atacante (el mecanismo exacto de una reverse shell)
    
- **La idea clave:** siempre hay que distinguir entre reglas de tráfico entrante (inbound) y saliente (outbound); ambas se definen por IP, puerto y protocolo, y omitir el protocolo (TCP vs UDP) puede dejar una vía de escape aunque el puerto esté aparentemente controlado
    
- Se recupera aquí el concepto de NTP (Network Time Protocol) visto de forma tangencial: la sincronización horaria del servidor es crítica para ataques Kerberos como el Kerberoasting, ya que los tickets llevan timestamp y un desfase de milisegundos puede hacer que el ticket sea rechazado — de ahí que antes de lanzar un ataque contra Kerberos convenga sincronizar el NTP inmediatamente antes
    

```
IP + puerto + protocolo = regla de firewall (inbound/outbound)
```

**Despliegue de la base de datos con IA: de la infraestructura al dato**

Con la arquitectura de red ya asegurada, se pide a Claude que instale MySQL en el servidor de base de datos, añada la regla correspondiente al firewall interno y genere un script que cree una base de datos ficticia de un taller mecánico (varias tablas: clientes, empleados, vehículos, piezas, con miles de filas de datos de prueba). Después se genera una web mínima en PHP con un buscador que ejecuta consultas directas sobre esa base de datos.

- **La idea clave:** ese buscador, deliberadamente simple, es exactamente el tipo de endpoint vulnerable que da lugar a un SQL Injection: el parámetro que introduce el usuario se concatena directamente en una sentencia SELECT ... WHERE campo = $parametro sin ningún tipo de sanitización
    
- Esto conecta directamente con lo visto en la clase de OWASP API Top 10 sobre no confiar nunca en el frontend: aquí el propio backend PHP es el que construye la consulta insegura
    
- El uso deliberado de la IA en tareas repetitivas y de infraestructura (crear servidores, generar el script SQL, montar la web) libera tiempo para centrarse en lo que realmente importa: entender qué hace cada sentencia y por qué es explotable
    

---

**Sentencias SQL fundamentales para entender el SQL Injection**

Se recorren en la consola de MySQL las sentencias que sustentan cualquier ataque de inyección posterior, usando la base de datos del taller mecánico recién creada.

- SHOW DATABASES; lista las bases de datos disponibles en el servidor; siempre aparecen information_schema y performance_schema por defecto, además de las bases de datos propias
    
- USE <base_de_datos>; selecciona la base de datos activa sobre la que se ejecutan las siguientes consultas
    
- SHOW TABLES; lista las tablas (las "hojas de Excel" en filas y columnas) dentro de la base de datos seleccionada
    
- **La idea clave:** qué tabla interesa a un atacante depende del scope del ataque, igual que en una auditoría legítima: si el objetivo es acceder a la plataforma, interesa la tabla de empleados/usuarios; si el objetivo es competencia desleal, interesa la de clientes o precios de piezas
    
- SELECT * FROM empleados; sin condición devuelve todos los campos y permite descubrir los nombres reales de las columnas cuando no se conoce la estructura de la tabla de antemano
    
- SELECT nombre FROM empleados WHERE tarifa_hora < 45.30; filtra por condición una vez conocidos los nombres de columna
    
- ORDER BY siempre debe indicar explícitamente el campo de ordenación, incluso si ya se ha usado ese mismo campo en el WHERE; **la metáfora útil**: el SQL funciona como el inglés, donde el sujeto nunca se omite (a diferencia del español), y hay que especificar constantemente sobre qué campo se opera
    
- Los operadores lógicos (AND, BETWEEN...AND) permiten combinar condiciones; BETWEEN 40 AND 70 es equivalente a tarifa_hora > 40 AND tarifa_hora < 70, pero computacionalmente más ligero al tener menos operadores — relevante en la práctica cuando se optimizan consultas sobre grandes volúmenes de datos (big data)
    
- LIMIT restringe el número de filas devueltas, útil por ejemplo para acotar rápidamente a los primeros resultados tras un ORDER BY id cuando se sospecha que el ID más bajo corresponde al usuario administrador
    
- Las funciones de agregación y operaciones aritméticas dentro del SELECT (por ejemplo, salario_bruto_anual * 1.33 con un alias AS coste_empleado) permiten calcular valores derivados (como el coste de Seguridad Social de un empleado) sin modificar la base de datos
    

```
SHOW DATABASES;
USE taller_mecanico;
SHOW TABLES;
SELECT * FROM empleados;
SELECT nombre FROM empleados WHERE tarifa_hora < 45.30;
SELECT * FROM empleados WHERE tarifa_hora BETWEEN 40 AND 70 ORDER BY tarifa_hora ASC;
SELECT *, salario_bruto_anual * 1.33 AS coste_empleado FROM empleados;
```

- **La idea clave final:** estas mismas consultas son las que, mal formadas o mal saneadas en el backend, dan lugar a un SQL Injection; entender qué sentencia SQL se ejecuta realmente detrás de un formulario web es el paso previo indispensable para explotarla — y también para no dejarla vulnerable como desarrollador
    

---

Con esta clase queda tendido el puente entre teoría y explotación: ahora entendemos cómo se levanta una arquitectura segmentada con firewalls de entrada y salida bien definidos, por qué la sincronización NTP puede tumbar un ataque Kerberos aunque todo lo demás esté bien planteado, y cómo las sentencias SQL básicas (SELECT, WHERE, ORDER BY, BETWEEN, funciones de agregación) son la base sobre la que se construye cualquier inyección SQL. El debate inicial sobre la superinteligencia deja además una idea de fondo que atraviesa todo el máster: la IA acelera radicalmente la ejecución, pero el criterio de arquitectura, el scope de un ataque o auditoría, y la comprensión de lo que ocurre por debajo siguen siendo responsabilidad exclusiva del humano.
