**Metodología de mapeo en Burp: scope, crawler y coloreado de parámetros**

Antes de disparar ningún payload, la disciplina es siempre la misma: acotar y mapear. Se mete el laboratorio en **scope** (alcance) para que los filtros del historial solo muestren lo relevante, y se recorre la web entera pulsándolo todo para que el **crawler** pasivo de Burp construya el sitemap completo.

- **Mapear** significa pasar por todos los elementos: pulsar cada botón, rellenar cada formulario, visitar cada enlace, para que ningún punto de entrada quede sin registrar en el sitemap
    
- Tras el mapeo se ordena el sitemap por la columna **parámetros**, porque los parámetros (en la URL de un GET, en el body de un POST, o incluso en cookies y cabeceras) son los **entry points** de la aplicación
    
- **La idea clave:** una vulnerabilidad web existe porque el desarrollador no ha securizado lo que entra por un parámetro; por eso el parámetro es siempre el objetivo, y su ubicación determina _qué tipo_ de vulnerabilidad aparece
    
- Técnica de trabajo del profesor: **colorear** cada parámetro _nuevo_ que aparece (naranja la primera vez) e ignorar las repeticiones donde solo cambia el valor; así, en una web con decenas de peticiones, acabas enviando al Repeater solo los dos o tres parámetros realmente distintos que merece la pena testear

**Detección de SQLi y número de columnas: order by vs null**

La detección es trivial: si metes una comilla simple y la aplicación pasa de responder **200 OK** a **500 Internal Server Error**, has roto la consulta del backend y hay SQLi. Al meter una segunda comilla vuelve el 200 (has vuelto a cerrar las comillas). Confirmado el fallo, el primer paso de la metodología UNION es contar columnas, y hay dos métodos.

- **ORDER BY:** se incrementa el número hasta que da error; el error salta en n, luego hay n-1 columnas (si ORDER BY 3 peta, hay 2 columnas)
    
- **UNION SELECT null:** se añaden null hasta que deja de dar error; tiene la ventaja de ahorrarte un paso frente a order by, porque el null encaja con cualquier tipo de dato
    
- Segundo paso, tipo de dato: se sustituye cada null por una cadena de texto ('a') y se mira cuál devuelve 200; esa es la columna que podremos usar para **filtrar información**
    
- **La idea clave:** en ambos métodos, los payloads nunca llevan espacios sin codificar — hay que meter el + del URL-encode o usar Ctrl+U en Burp, y el olvido del + es el error más común y frustrante al hacerlo a mano
    

```
' order by 1-- -
' union select null,null-- -
' union select 'a','a'-- -
```

**information_schema: la base de datos que describe la base de datos**

Aquí está el corazón de la clase. Para descubrir la estructura a ciegas se usa information_schema, un esquema estándar presente en la mayoría de gestores (**PostgreSQL, MySQL, SQL Server**) que funciona como una base de datos _sobre_ la propia base de datos, con metadatos de qué tablas y columnas existen.

- Primero conviene sacar la **versión** del gestor (version() en PostgreSQL, @@version en Microsoft…), porque cada motor tiene su propia sintaxis de extracción en el cheat sheet de PortSwigger
    
- **La idea clave:** el render de Burp _engaña_ — a veces no pinta la página completa y parece que el payload ha fallado; hay que bajar en la respuesta cruda, donde aparece la última fila con el dato real (así se descubrió que era **PostgreSQL 12.22 sobre Ubuntu**)
    
- El proceso es en cascada: information_schema.tables → columna table_name para listar todas las tablas y localizar la de usuarios; luego information_schema.columns con un WHERE table_name='users' para sacar los nombres de las columnas (username, password); y por fin la consulta directa sobre la tabla real
    
- Detalle de PostgreSQL: los valores del WHERE van entre **comillas simples** o revienta la consulta
    

```
' union select null, table_name from information_schema.tables-- -
' union select null, column_name from information_schema.columns where table_name='users'-- -
' union select username, password from users-- -
```

**Oracle y su peculiaridad: el FROM DUAL obligatorio**

El tercer laboratorio introduce Oracle, y con él la razón por la que en SQLi el mundo se divide en **Oracle y no-Oracle**. Un union select que funciona perfecto en el resto de motores aquí falla sin motivo aparente.

- **La idea clave:** Oracle _obliga_ a que toda consulta SELECT tenga un FROM; cuando no necesitas consultar ninguna tabla real, se usa la tabla especial **DUAL** solo para que la consulta esté bien formada
    
- Para enumerar en Oracle cambian los nombres de los objetos: all_tables (con la columna table_name) en lugar de information_schema.tables, y all_tab_columns (con column_name) para las columnas
    
- Truco de localización del punto de inyección, el **Canary**: en vez de un 'a' genérico se inyecta una cadena única (el profesor usa su propio nombre) para identificar de un vistazo dónde se refleja en la respuesta; el nombre viene del concepto de _canary_ en despliegues de software, donde una versión nueva se prueba con un grupo pequeño para ver si "sobrevive"
    

```
' union select 'YUBA1','YUBA2' from dual-- -
' union select null, table_name from all_tables-- -
' union select null, column_name from all_tab_columns where table_name='USERS'-- -
```

**Blind SQLi por tiempo: cuando la aplicación no te devuelve nada**

El laboratorio final rompe con todo lo anterior. Aquí la inyección vive en la cookie TrackingId, la consulta no devuelve resultados y la aplicación no cambia ni por filas ni por errores. Es la variante más difícil y la que mucha gente pasa por alto.

- Recordando la clasificación de tipos: los **in-band** (UNION o error-based) sacan los datos en la misma respuesta; los **blind** no muestran nada, solo se observa el **comportamiento** de la aplicación
    
- La palanca es el **retardo temporal**: se fuerza a la base de datos a dormir con pg_sleep() (PostgreSQL); si la respuesta tarda esos segundos, la inyección funciona; si vuelve al instante, no hay SQLi
    
- **La idea clave:** el salto mental es dejar de _leer_ datos y empezar a _hacer preguntas de sí/no_; ya no ves la contraseña, la deduces obligando a la app a tardar cuando tu hipótesis es cierta
    

```
'|| pg_sleep(10)-- -
```

**El CASE WHEN: convertir el tiempo en respuestas verdadero/falso**

Sobre el retardo se construye la lógica condicional con CASE WHEN, la estructura que permite atar el "dormir" a una condición y así interrogar la base de datos dato a dato.

- La plantilla es fija y conviene apuntarla: SELECT CASE WHEN (condición) THEN pg_sleep(10) ELSE pg_sleep(-1) END — un sleep negativo no se ejecuta, así que **tarda = verdadero**, **instantáneo = falso**
    
- Se verifica primero lo básico (1=1 tarda, 1=0 no), y luego se sustituye por condiciones reales: comprobar si existe el usuario administrator, averiguar la **longitud** de su contraseña (length(password) > n), y finalmente extraer **carácter a carácter** con substring (¿el primer carácter es a? ¿es b?…)
    
- **La idea clave:** esto es tan lento a mano que se automatiza con **Intruder** — un ataque _cluster bomb_ con dos payloads (la posición del carácter, del 1 a la longitud, y el juego de caracteres a-z/0-9), ordenando luego por tiempo de respuesta para leer la contraseña completa
    
- El contraste visual es brutal: al iterar la longitud, las peticiones tardan 10 s mientras la condición es cierta y de golpe caen a milisegundos cuando se supera el tamaño real (19 caracteres en el lab), señalando el valor exacto
    

```
'|| (SELECT CASE WHEN (1=1) THEN pg_sleep(10) ELSE pg_sleep(-1) END)-- -
'|| (SELECT CASE WHEN (username='administrator' AND length(password)>1) THEN pg_sleep(10) ELSE pg_sleep(-1) END FROM users)-- -
'|| (SELECT CASE WHEN (substring(password,1,1)='a') THEN pg_sleep(10) ELSE pg_sleep(-1) END FROM users WHERE username='administrator')-- -
```

Con esta sesión afianzamos que un SQL Injection manual sigue siempre la misma columna vertebral —mapear en Burp, colorear parámetros, detectar con la comilla, contar columnas, identificar tipos de dato— y que a partir de ahí solo cambian los detalles del motor. Ahora sabemos extraer una estructura completamente desconocida usando information_schema (o all_tables/all_tab_columns en Oracle), entendemos por qué Oracle exige su FROM DUAL, y hemos dado el salto conceptual más importante del módulo: cuando la aplicación no devuelve nada, un **Blind SQLi por tiempo** con CASE WHEN y pg_sleep nos permite reconstruir cualquier dato preguntando por verdadero/falso y midiendo el retardo, automatizándolo con Intruder para que sea viable. Esta es exactamente la clase de SQLi que en la máquina GoodGames nos abrió el panel interno, y la que en un trabajo real marca la diferencia frente a depender de herramientas automáticas. Con esto cerramos el bloque de SQL Injection; el profesor apunta que lo siguiente empezará a tocar la parte normativa, ese otro lado del oficio que complementa al ofensivo.
