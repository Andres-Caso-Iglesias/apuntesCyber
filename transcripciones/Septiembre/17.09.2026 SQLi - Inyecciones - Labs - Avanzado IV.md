**Mentalidad de explotación: no hay un único camino a la reverse shell**

Se abre la clase con un debate sobre qué hacer cuando se tiene un SQL Injection pero la base de datos no contiene tablas de usuarios ni información directamente explotable. La respuesta habitual de "entonces me quedo sin nada" es el error conceptual que Castillo quiere corregir.

- **La idea clave:** el SQL Injection no garantiza una vía directa a la máquina ni una reverse shell; lo que sí garantiza es acceso total a la base de datos, y con ese acceso hay siempre varias opciones: escalar privilegios dentro de la aplicación modificando un campo de rol, leer archivos internos del sistema si el usuario de MySQL tiene permisos suficientes, o encontrar credenciales reutilizables en los archivos de configuración a los que se puede llegar a leer a través de ese acceso
    
- El ejemplo que se plantea: si tienes acceso a la base de datos pero no encuentras tabla de usuarios, puedes modificar el valor del campo de administrador de un usuario existente en vez de crear uno nuevo, lo que puede darte acceso a un panel con otras vulnerabilidades encadenables
    
- **La idea clave sobre el objetivo real:** muchas veces los alumnos están tan centrados en obtener una reverse shell que pasan por alto que la cadena de explotación tiene múltiples pasos intermedios, y que presionar hacia el paso final antes de tiempo es lo que los atasca

**Introducción a CMS: WordPress como objetivo frecuente**

Al cambiar a la máquina Torrija (VM local) por los problemas con HackTheBox, se descubre que la aplicación web aloja un WordPress, lo que sirve de excusa para introducir los conceptos básicos de auditoría de CMS.

- Un **CMS** (Content Management System) es un gestor de contenidos que permite crear y publicar en una web sin programar — WordPress, Drupal, Joomla; su popularidad es precisamente lo que los convierte en objetivo frecuente porque tienen versiones ampliamente distribuidas, plugins de terceros con sus propias vulnerabilidades y estructuras de carpetas predecibles
    
- La señal más directa de que hay un WordPress es el código fuente de la página: clases como wp-block, rutas bajo /wp-content/, referencias al generador de WordPress y la propia cadena Designed by WordPress aparecen siempre
    
- **La idea clave:** conocer la estructura de carpetas predefinida de un CMS (WP-admin, WP-content, WP-includes) equivale a conocer el mapa del edificio antes de entrar — si se consigue acceso como el usuario que desplegó la web, ya se sabe dónde buscar los archivos de configuración con credenciales
    
- Se menciona también que muchos administradores intentan ocultar la ruta de login (/wp-admin, /wp-login) como medida de seguridad por oscuridad, que como ya se sabe no ofrece protección real frente a un escaneo completo

**WPScan: enumeración específica de WordPress**

Se presenta **WPScan** como la herramienta equivalente a Nmap pero específica para WordPress, capaz de detectar versión del CMS, plugins instalados con sus versiones, y usuarios, sin necesidad de hacer fuzzing manual.

- El parámetro más importante es --enumerate ap (todos los plugins), al que se puede añadir vp (solo plugins vulnerables) o u (usuarios); la opción --plugins-detection aggressive fuerza una detección activa más completa aunque más ruidosa
    

```
wpscan --url http://torrija.thl/wordpress/ --enumerate ap --plugins-detection aggressive
```

- **La idea clave:** con WPScan se obtiene en un solo comando lo que llevaría mucho tiempo deducir manualmente: versiones exactas de plugins instalados, que son la principal superficie de ataque en WordPress, no tanto el core del CMS en sí en versiones recientes
    
- Se explica también la utilidad del archivo readme.html presente por defecto en cualquier WordPress: aunque parece un archivo inofensivo, revela la versión exacta del CMS y los requisitos mínimos de PHP y MySQL, lo que permite inferir rangos de versiones del entorno incluso cuando no se tienen otros indicios

**Búsqueda de CVEs y explotación de un LFI en un plugin de WordPress**

WPScan detecta el plugin **Web Directory Free v1.7.0.2**, con una vulnerabilidad conocida de Local File Inclusion no autenticada (CVE-2024-36473). Se trabaja el proceso completo de investigación de un CVE hasta su explotación.

- El flujo de búsqueda recomendado tiene dos vías en paralelo: buscar por nombre y versión del plugin (nombre + versión + exploit) y buscar directamente por el número de CVE, porque a veces una vía da resultados y la otra no
    
- **La idea clave:** si un CVE se marca como "authenticated" (requiere estar autenticado), es poco útil sin credenciales previas; si se marca como "unauthenticated", es directamente explotable desde el exterior sin ningún acceso previo — siempre leer esa distinción antes de invertir tiempo en un exploit
    
- Se descarga un script Python de GitHub y se ejecuta con los parámetros que indica su documentación: la URL del WordPress y el fichero a leer en el servidor
    

```
python3 CVE-2024-xxxxx.py --url http://torrija.thl/wordpress/ --file ../../punto punto/../etc/passwd
```

- Esto confirma el LFI: se obtiene el contenido de /etc/passwd, que revela los usuarios del sistema con su shell asignada (los que tienen /bin/bash son los relevantes: primo, premo, debian y root)
    
- **La metáfora útil:** un path traversal es la vulnerabilidad de detectar que puedes salir de la ruta prevista; el LFI es lo que haces con ello, leer archivos internos del servidor

**De LFI a credenciales SSH: fuerza bruta con Hydra**

Al comprobar que las claves SSH privadas de los usuarios no están accesibles (requieren privilegios que el usuario web no tiene), se concluye que la única forma de avanzar es fuerza bruta sobre el servicio SSH que se encontró abierto en el escaneo de NMap.

- **La idea clave sobre LFI sin adivinar rutas:** cuando no se conocen rutas de archivos interesantes, la alternativa es usar un diccionario de LFI (listas de rutas conocidas de sistemas Linux, archivos de configuración habituales, etc.) para intentar acceder a todo lo que pueda existir; si tampoco eso da resultado, la única opción es atacar por otro vector (en este caso, SSH)
    
- Se construye un fichero de usuarios con los encontrados en /etc/passwd y se lanza Hydra con el diccionario estándar de contraseñas contra el puerto 22
    

```
nano usuarios.txt
# primo, premo, debian, root
hydra -L usuarios.txt -P /usr/share/wordlists/rockyou.txt 192.168.0.204 ssh
```

- Hydra encuentra la contraseña del usuario primo (Casandra), lo que permite el acceso SSH

**Post-explotación: credenciales en wp-config.php y acceso a MySQL**

Una vez dentro de la máquina como usuario primo, el primer objetivo es el archivo de configuración de WordPress, que siempre contiene las credenciales de conexión a la base de datos.

- La ruta es invariable en cualquier instalación estándar de WordPress: /var/www/html/wordpress/wp-config.php; es el primer archivo al que hay que ir cuando se consigue acceso como el usuario que desplegó la web
    
- **La idea clave:** el usuario de la web (www-data, el usuario de servicio de Apache, o en este caso el propio usuario primo) es el que tiene permisos sobre la carpeta de WordPress, por lo que siempre habrá acceso a leer wp-config.php desde ese contexto
    
- Con las credenciales encontradas se accede a MySQL directamente desde dentro de la máquina (conexión a [localhost](http://localhost/), no al puerto expuesto al exterior), usando el parámetro --ssl-mode=disabled para sortear el error de conexión TLS
    

```
mysql -h localhost -u admin -p --ssl-mode=disabled
```

- Se repasan los comandos esenciales de reconocimiento dentro de MySQL, que son exactamente los mismos que se usan al explotar un SQL Injection desde fuera: SHOW DATABASES, USE nombre_db, SHOW TABLES, SELECT * FROM tabla
    
- Funciones de interés para exfiltración de contexto: user() o current_user() devuelven el usuario de MySQL, version() la versión del motor, hostname() el nombre del host, datadir() la ruta donde están almacenados los datos; son las mismas funciones que se inyectan en un UNION SELECT para sacar información sin tener acceso directo

**Escalada de privilegios con BPFTrace y GTFOBins**

Una vez dentro como primo, se comprueba qué binarios puede ejecutar con privilegios elevados mediante sudo -l, que devuelve que el usuario puede ejecutar /usr/bin/bpftrace como root.

- **La idea clave sobre GTFOBins:** ante cualquier binario que sudo -l permita ejecutar, el primer paso es siempre buscarlo en **GTFOBins** ([gtfobins.github.io](http://gtfobins.github.io/)), la base de datos de binarios Unix con técnicas documentadas para abusar de sus funciones en escaladas de privilegios
    
- BPFTrace es una herramienta de trazado del kernel de Linux; GTFOBins documenta que puede ejecutar comandos arbitrarios con privilegios de root si se tiene permiso de sudo sobre él
    

```
sudo bpftrace -e 'BEGIN { system("/bin/bash"); exit(); }'
```

- Con esto se obtiene una shell como root, completando la cadena completa: LFI → lectura de /etc/passwd → fuerza bruta SSH → acceso como primo → lectura de wp-config.php → acceso a MySQL → sudo -l → escalada vía GTFOBins
