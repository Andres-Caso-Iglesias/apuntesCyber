**La crisis de tokens: shadow reductions y demanda colectiva contra Anthropic**

Se explica que durante agosto varias plataformas de IA (entre ellas Anthropic) redujeron de forma no anunciada la cantidad de tokens disponible por suscripción, un fenómeno bautizado como "shadow reduction". Cuando Anthropic anunció además un recorte adicional del 50% para el 15 de septiembre, una parte de los usuarios (más de 1,5 millones, según se comenta) se sumó a una demanda colectiva alegando que se estaba entregando solo una fracción de lo prometido en el plan de pago.

- **La idea clave:** el modelo de negocio actual de las grandes IA es insostenible económicamente (pérdidas mensuales multimillonarias), por lo que los recortes de tokens son la consecuencia lógica de intentar hacer rentable un servicio que se ofrecía a pérdida para generar dependencia
    
- Tras la presión de la demanda, Anthropic frenó el recorte adicional del 50% previsto, pero el recorte de agosto ya se había aplicado y no se revirtió
    
- Se menciona también, como contexto geopolítico del sector, un movimiento coordinado entre Anthropic, OpenAI y otros actores hacia mensajes públicos de cautela sobre el desarrollo de la superinteligencia, en línea con el debate ya visto en la clase anterior sobre los riesgos denunciados por investigadores del sector

**Modelo híbrido de arquitectura IA: orquestador, skills y MCP servers**

Carlos presenta en detalle su propuesta de arquitectura para reducir drásticamente el consumo de tokens sin perder capacidad de trabajo. La idea central es no usar siempre el modelo más potente para todo, sino seleccionar el modelo adecuado según la complejidad de cada tarea, de forma similar a cómo un arquitecto diseña un plano y una cuadrilla de obreros lo ejecuta sin necesidad de que cada obrero sea también arquitecto.

- **La metáfora útil:** un modelo de razonamiento complejo (el "arquitecto") diseña la tarea y genera instrucciones claras; modelos más simples y baratos (los "obreros") ejecutan el trabajo repetitivo siguiendo esas instrucciones, sin necesidad de razonar desde cero cada vez
    
- Se establece una jerarquía de modelos por coste y potencia: Haiku para tareas simples de búsqueda o lectura, Sonnet y Opus para tareas de ordenación y análisis más complejos, y Fable para diseño visual o codificación avanzada — usar el modelo más potente para tareas triviales es, en palabras de Carlos, como "usar una bomba atómica para hacer un agujero en el jardín"
    
- El [**Claude.md**](http://claude.md/) actúa como _system prompt_ persistente: un archivo de instrucciones que define comportamientos fijos (qué no hacer, cómo actuar) y que se consulta en cada sesión antes de ejecutar cualquier tarea
    
- Las **skills** son archivos de instrucciones reutilizables (.md) para tareas repetitivas concretas (cómo hacer un research, cómo generar un documento con un estilo determinado), y un **MCP server** se define como un conjunto organizado de herramientas y skills disponibles para que un agente las use según la tarea que se le asigne
    
- **La idea clave:** el ahorro real de tokens no viene de usar un modelo más barato, sino de reducir la cantidad de información que hay que leer y escribir en cada interacción; por eso una bóveda de **Obsidian** bien estructurada, consultada como fuente de contexto en vez de releer todo el código o la documentación cada vez, es más determinante que la elección del modelo
    
- Se menciona también la herramienta **RTK**, que permite ejecutar ciertos comandos desde la propia terminal sin pasar por la IA, reduciendo así el consumo de tokens en tareas que no requieren razonamiento

**Ventana de contexto y viabilidad de modelos locales**

A raíz de una duda sobre si migrar a un modelo local tipo Kimi K3 para ahorrar tokens, se explica el concepto de ventana de contexto y por qué no cualquier hardware doméstico puede correr un modelo grande de forma útil.

- **La idea clave:** el contexto de una conversación (todo el historial que la IA "recuerda") se cachea en memoria RAM; un modelo con miles de millones de parámetros necesita mucha más memoria de la que tiene un portátil convencional (16-32 GB), por lo que intentar correrlo localmente con recursos insuficientes produce respuestas prácticamente inútiles
    
- La solución que se plantea para proyectos grandes con recursos limitados es la misma bóveda de Obsidian: en vez de depender de una ventana de contexto amplia, se consulta un documento externo estructurado que resume el estado del proyecto, permitiendo trabajar por partes pequeñas que sí caben en el contexto disponible
    
- Este razonamiento conecta con la inversión en hardware anunciada por Apple (Mac Studio con memoria unificada de gran capacidad), que Carlos plantea como base de una futura infraestructura propia de agentes locales hiperespecializados, cada uno con una única función (generación de PDFs, despliegue de servidores, envío de correos, etc.)

**Metodología de reconocimiento aplicada a una máquina real de HackTheBox**

Con una alumna voluntaria al mando de la terminal, se repasa la metodología de reconocimiento ya vista en clases anteriores, insistiendo en el razonamiento detrás de cada paso en lugar de la ejecución mecánica de comandos.

- El **ping** inicial confirma que el host está activo; un TTL de 63 (en vez de 64) se explica correctamente por el salto de red que introduce la propia VPN de conexión a HackTheBox, retomando directamente el concepto visto en la clase de reconocimiento de red
    
- El escaneo con nmap -sVC -p- --min-rate combina detección de versión de servicio (-sV) con scripts de reconocimiento (-sC) y barrido de todos los puertos (-p-); se explica que sin el flag de detección de versión, Nmap solo devuelve el nombre de servicio más habitual asociado a ese puerto (por ejemplo, asumir que el puerto 4566 es un servicio concreto sin comprobar realmente qué corre ahí mediante banner grabbing)
    
- **La idea clave:** el valor de --min-rate recomendado por Carlos (1500) se justifica porque coincide con la MTU máxima de un paquete Ethernet (1500 bytes), evitando fragmentación de paquetes y generando menos ruido de red durante el escaneo, aunque valores más agresivos también funcionan a costa de mayor detectabilidad
    
- **La idea clave sobre seguridad por oscuridad:** cambiar un servicio a un puerto no estándar no lo protege realmente; un escaneo de todos los puertos con detección de servicio lo revela igualmente, por lo que ocultar un puerto nunca sustituye a asegurar el servicio en sí

**Enumeración de directorios y descubrimiento de un formulario vulnerable**

Tras identificar un servidor web, se enumeran directorios y archivos con un fuzzer (FeroxBuster en este caso, elegido por preferencia personal sobre otras herramientas equivalentes), incluyendo la extensión PHP para descubrir archivos no listados por defecto.

- **La idea clave:** un archivo descubierto con tamaño 0 bytes normalmente no aporta nada explotable, y conviene priorizar el análisis en archivos con contenido real
    
- Se localiza un formulario de registro con un campo de texto libre (nombre de usuario) y un desplegable de país; el campo de texto refleja el valor introducido en la página, lo que constituye una señal inmediata de posible vulnerabilidad
    
- **La idea clave metodológica:** ante cualquier campo de texto reflejado en pantalla, las dos primeras pruebas sistemáticas son XSS (Cross-Site Scripting) y SQL Injection, probando los caracteres especiales de ambos ataques a la vez para detectar si existe algún tipo de filtrado (WAF) que bloquee uno de los dos

**XSS almacenado (stored) como vector más sigiloso que un SQL Injection**

Al comprobar que el campo de nombre de usuario refleja literalmente el texto introducido sin escapar comillas dobles, se demuestra un XSS funcional inyectando una etiqueta de script que cierra el contexto HTML anterior (por ejemplo, cerrando la comilla del atributo y la etiqueta <h1> antes de abrir el script).

- Se comprueba que el payload persiste tras recargar la página con el filtro de país correspondiente, confirmando que se trata de un XSS **stored** (almacenado) y no solo reflejado: cualquier usuario que visite esa misma vista de listado ejecutará el script inyectado
    
- **La idea clave:** un XSS almacenado suele ser preferible a un SQL Injection directo como vector de ataque inicial porque es más sigiloso — permite robar cookies de sesión de forma continua (mediante algo como capturar document.cookie y enviarlo a un servidor propio) sin tocar directamente la base de datos, evitando dejar rastro evidente en los logs de consultas
    
- Se detecta también un fallo de diseño típico: el desarrollador protegió correctamente el campo de texto libre (username) contra comillas simples, pero no protegió el parámetro del desplegable de país, asumiendo erróneamente que un <select> no puede manipularse — un error común es proteger solo lo que el usuario puede escribir directamente en el frontend, olvidando que cualquier parámetro de la petición HTTP puede modificarse con **Burp Suite** antes de llegar al backend
    

---

**SQL Injection basada en errores (error-based) sobre el parámetro country**

Al interceptar la petición POST del formulario con Burp Suite y sustituir el valor del parámetro país por una comilla simple, el servidor responde con un error PHP no controlado, revelando la ruta del servidor y el número de línea exacto donde falla la consulta.

- **La idea clave:** cuando falta un bloque try/catch que capture correctamente los errores de base de datos, un fallo de consulta se filtra directamente al usuario en forma de traza de error (stack trace), y ese mensaje de error es en sí mismo la confirmación de que existe una inyección SQL de tipo **error-based**
    
- Se comenta que estos errores de SQLi expuestos en producción a veces terminan indexados por buscadores, lo que permite localizar aplicaciones vulnerables mediante técnicas de Google Dorking dirigidas específicamente a mensajes de error de bases de datos
    
- Se retoma la metodología ya explicada en la clase anterior sobre ataques UNION: primero se determina qué base de datos existe, después qué tablas contiene, y solo entonces se extraen columnas y datos concretos
    
- Usando la sintaxis UNION SELECT database()-- inyectada en el parámetro vulnerable, se obtiene el nombre de la base de datos activa; posteriormente, consultando schema_name FROM information_schema (la tabla de metadatos que existe siempre en MySQL), se listan todas las bases de datos del servidor, descubriendo una base de datos personalizada llamada registration junto a las bases de datos por defecto (information_schema, performance_schema, mysql)
    
- **La idea clave:** no toda inyección admite un SELECT puro; como la consulta original es de tipo escritura (inserción de un nuevo registro), hay que forzar la unión con UNION SELECT en lugar de intentar un SELECT directo, que fallaría por no encajar con la consulta original — entender qué tipo de consulta hay detrás del formulario es indispensable antes de intentar inyectar cualquier payload
