**¿Qué es una API y por qué existe?**

Una **API** (Application Programming Interface) centraliza los métodos —las funciones del código— y expone únicamente los parámetros necesarios para invocarlos, evitando que el cliente tenga acceso directo a la lógica interna o a las consultas SQL subyacentes. El ejemplo usado en clase es una función verPrecio(idProducto) que, internamente, ejecuta un SELECT price FROM catalogo WHERE id_producto = var1; la API es la capa que permite invocar esa función sin exponer la consulta real.

- Toda API sigue, salvo excepciones, el **modelo cliente-servidor**: el cliente (la web o app, no el usuario) inicia la comunicación mediante una petición a un endpoint del tipo /api/v1/metodo
    
- **La idea clave:** el front interactúa con el back siempre a través de la API, aunque el usuario nunca vea explícitamente esa palabra en la interfaz
    
- Los dispositivos **IoT**, ya tratados en clases anteriores como vectores especialmente vulnerables, funcionan mayoritariamente por API, por lo que su superficie de exposición real es precisamente esa interfaz
    
- El boom de la IA ha llevado a que muchas herramientas publiquen documentación de su API antes privada, para facilitar integraciones (ejemplo real: **Polymarket**, que expone públicamente sus endpoints de get, post, options, delete, head y websockets)
    

---

**Anatomía de una petición y el ciclo de comunicación**

Toda petición a una API se compone de un método (get, post, etc.), una URL de endpoint y unas cabeceras (headers), que son las variables de autenticación o contexto que el servidor necesita para responder correctamente.

```
GET /api/v1/catalogo/abrigos HTTP/1.1
Host: zara.com
Origin: mi-ip
Authorization: <token>
```

- El ciclo completo es: el cliente construye la petición → viaja por la red → el servidor **autentica** (verifica quién eres) → el servidor **autoriza** (delega permisos concretos) → calcula la salida → devuelve la respuesta (código HTTP + cuerpo, normalmente JSON) → el cliente actualiza la plantilla visual
    
- **La metáfora útil:** es como entrar a una discoteca — primero el portero comprueba tu DNI (autenticación) y solo después te pone el sello que te da acceso a ciertas zonas (autorización); nunca al revés
    
- Para consultar el catálogo completo de respuestas HTTP posibles, recurso recomendado: [http.cat](http://http.cat/)
    

---

**Por qué las APIs móviles son especialmente vulnerables**

Cuando una aplicación se ejecuta en el navegador (como una web normal), el usuario nunca tiene acceso directo al código: el navegador actúa de intermediario y solo permite interactuar con lo que el desarrollador ha decidido exponer. En cambio, al descargar una app móvil, el ejecutable —con el código fuente embebido— pasa a estar en manos del usuario, lo que lo hace reversible mediante ingeniería inversa.

- **La metáfora útil:** es la diferencia entre ver una botella en pantalla (solo puedes hacer lo que el propietario permite) y tener la botella físicamente en la mano (puedes abrirla, rellenarla, rascar la etiqueta y descubrir qué contiene realmente)
    
- Herramientas como **dotPeek** permiten descompilar el ejecutable y encontrar llamadas a endpoints normalmente hardcodeadas, ampliando la superficie de exposición real de la aplicación
    
- Factores que agravan la inseguridad de Android frente a web: facilidad de descompilación, ecosistema abierto (instalación fuera de Google Play), fragmentación de dispositivos y versiones sin parches, y el riesgo del rooteo (que da acceso root y permite interceptar y modificar todo el tráfico de red)
    
- **La idea clave:** una vulnerabilidad en una librería de bajo nivel se propaga en cascada a todo lo que depende de ella — el caso de Log4j en Minecraft, o jQuery en WordPress, ilustra que la robustez del software propio no basta si sus dependencias son inseguras
    

---

**IDOR: el ataque estrella contra APIs**

El grueso práctico de la clase se centra en el **IDOR** (Insecure Direct Object Reference): cuando un endpoint expone un identificador (ID) iterable sin comprobar que el usuario tiene permiso real para acceder a ese recurso, es posible cambiar el ID y obtener datos que no deberían ser visibles.

- La metodología de auditoría web ya conocida (interactuar con la página → revisar código fuente → enumerar directorios con herramientas de Kali) se aplica igual a las APIs, porque **una API es, en esencia, un directorio más**: enumerar /api, /v1, /login sigue la misma lógica de fuerza bruta con diccionario
    
- **La idea clave:** el criterio del auditor marca la diferencia entre una simple paginación (cambiar pagina=3 por pagina=4 en un catálogo público) y un IDOR real (acceder a un expediente médico confidencial cambiando id=348 por id=347)
    
- Casos reales expuestos en clase: el ataque de Al-Qassec al sistema de salud madrileño y a la sanidad de Cantabria se realizó explotando IDOR en la API móvil, combinado con ausencia de rate limiting (permitiendo iterar millones de IDs con Burp Intruder)
    
- Como consecuencia práctica, se recuerda que los controles anti-inyección SQL implementados solo en el front no protegen si la petición se envía directamente a la API
    

---

**Otros vectores del OWASP API Top 10 mencionados**

Se repasan de forma rápida, en formato de preguntas al grupo, otros vectores que también pueden manifestarse a través de la API aunque la web "tradicional" parezca segura:

- **SQL Injection**: si el control anti-inyección solo está en el front, enviar la petición directamente a la API puede saltárselo
    
- **XXE** (XML External Entity): posible si la API procesa XML sin restricciones, permitiendo lectura de archivos
    
- **Information disclosure**: exponer endpoints internos (como /viewAllPedidos) que no deberían ser accesibles al usuario final
    
- **Bypass de autenticación** y **escalada de privilegios**: el caso real citado es un ataque a la web de la FIA donde un simple POST role=admin al endpoint de gestión de usuarios otorgó privilegios de administrador
    
- Se mencionan también buenas prácticas de mitigación comentadas por los alumnos con experiencia: uso correcto de **JWT** (evitando que viaje en texto claro), rate limiting, validación de esquemas de entrada, protección de rutas de frontend y CORS bien configurado
    
- Se advierte sobre **Supabase**, tecnología muy usada por defecto en desarrollos asistidos por IA, que suele dejar habilitados por defecto endpoints como /register sin restricciones

Sabemos identificar una API en las herramientas de desarrollador del navegador, entendemos por qué las apps móviles amplían drásticamente la superficie de ataque al exponer el ejecutable al usuario, y somos capaces de reconocer un IDOR como el patrón de vulnerabilidad más común y más dañino en este contexto, con ejemplos reales de alto impacto (Al-Qassec, la FIA) que demuestran que el fallo suele reducirse a "cambiar un número" en una petición mal protegida.
