**Configuración del laboratorio: adaptador puente como opción recomendada**

La fuente de la mayoría de los problemas de conectividad de días anteriores era la configuración de red de VirtualBox. La recomendación definitiva es usar adaptador puente en ambas máquinas, con una regla importante: la tarjeta de red seleccionada tiene que coincidir con la que se está usando en el host en ese momento.

- Si se va por cable, seleccionar la tarjeta Realtek (o equivalente ETH)
    
- Si se va por WiFi, seleccionar la tarjeta Intel WiFi (o equivalente WLAN)
    
- Ambas máquinas deben usar el mismo tipo de adaptador
    

El problema habitual con Red NAT es que VirtualBox puede asignar la misma IP a ambas máquinas, generando un conflicto de direccionamiento que hace que ninguna de las dos sea accesible desde la otra. Con adaptador puente ese problema desaparece porque ambas obtienen IPs del router real de la red local.

Si se cambia el adaptador con la máquina ya encendida, el cambio no se aplica automáticamente. La solución es o bien reiniciar la máquina, o bien bajar y subir la interfaz de red desde dentro de Metasploitable:

```
sudo ifdown eth0
sudo ifup eth0
```

**Tipos de auditoría y por qué el scope lo define todo**

Antes de hablar de herramientas, Gómez introduce el marco conceptual que da sentido a todo lo que se va a ver. En una auditoría real, el cliente no entrega una máquina para que se hackee libremente: entrega un objetivo concreto y un alcance definido.

Las cinco grandes ramas del pentesting son auditoría web, auditoría interna (directorio activo, redes corporativas), hacking WiFi, forense y Red Team. En cada una, el punto de partida es distinto y lo que está permitido atacar también.

En una auditoría externa o de superficie de exposición, el cliente entrega un dominio o un rango de IPs y dice "descúbreme qué tengo expuesto". Muchas empresas grandes, especialmente las que han crecido comprando otras empresas, no tienen un inventario actualizado de sus propios activos. El trabajo empieza por descubrir qué hay antes de atacar nada.

Si el scope es una URL concreta, atacar el FTP del mismo servidor sin autorización explícita es salirse del scope. Esto tiene consecuencias legales y contractuales. La diferencia entre enumerar activos y hackear sin autorización es exactamente esa línea.

- **La idea clave:** el hacking no empieza con herramientas, empieza con entender a qué se tiene autorización de atacar. Irse de scope en una auditoría real puede costar el contrato y, en algunos casos, tener consecuencias legales

**Fase 1 — Descubrimiento de la red: del ping al script**

El primer problema en cualquier auditoría es saber qué hay en la red. La secuencia recomendada va de menos a más ruido:

**Opción 1 — Ping manual**

El más silencioso. Un ping usa trazas ICMP y genera exactamente dos paquetes por host: uno enviado, uno recibido. El TTL de la respuesta identifica el sistema operativo:

- TTL 64 (o cercano hacia abajo): Linux
    
- TTL 128 (o cercano hacia abajo): Windows
    
- En HackTheBox, la VPN resta un salto: Linux aparece como 63, Windows como 127
    

El problema del ping es que muchos entornos tienen ICMP desactivado. AWS lo tiene deshabilitado por defecto. Si se hace un ping y no responde, puede significar que el host no existe o que tiene ICMP cortado: no se puede distinguir sin más información.

**Opción 2 — Script de descubrimiento con filtro de TTL**

Un oneliner en bash que itera de la .1 a la .254, hace ping a cada IP y filtra por TTL para separar Linux de Windows. Herramienta para generarlo: pedírselo directamente a Claude o ChatGPT especificando que filtre por TTL 64 y 128.

```
# Ejemplo de estructura básica
for i in $(seq 1 254); do
    ping -c 1 -W 1 192.168.1.$i | grep "ttl=" | awk '{print $7, "-> Linux/Windows según TTL"}'
done
```

**Opción 3 — Net-Discover**

Usa el protocolo ARP, que funciona enviando "¿quién tiene esta IP?" a toda la red y registrando quién responde. Genera exactamente 254 paquetes para un rango /24, cada uno de 42 bytes. Devuelve IP y dirección MAC, y la MAC incluye el fabricante (que puede dar pistas sobre el tipo de dispositivo).

```
sudo netdiscover -r 192.168.1.0/24
```

Limitación importante: ARP no funciona en AWS ni en entornos cloud que lo tienen deshabilitado. En esos casos hay que usar Nmap directamente.

**Opción 4 — Nmap con -sn**

El parámetro -sn indica a Nmap que haga descubrimiento de hosts pero no escanee puertos. Genera más tráfico que Net-Discover pero funciona en entornos donde ARP no está disponible.

```
sudo nmap -sn 192.168.1.0/24
```

**Opción 4 (último recurso) — Nmap sobre el rango completo**

Si nada de lo anterior ha funcionado, se lanza Nmap con todos los puertos sobre el rango completo añadiendo -Pn para omitir el ping previo y forzar el escaneo aunque no haya respuesta ICMP:

```
sudo nmap -p- -Pn 192.168.1.0/24
```

Esto genera decenas de miles de paquetes y tarda mucho. Se usa cuando no hay otra opción.

- **La idea clave:** siempre empezar por lo más silencioso. Net-Discover para descubrir hosts, TTL para identificar el sistema operativo, Nmap solo cuando ya se sabe a qué IP atacar. Lanzar Nmap a toda la red de entrada es la opción menos profesional y la que más alertas levanta

**Fase 2 — Enumeración de puertos: los dos comandos de Nmap**

Una vez identificada la IP objetivo, Gómez presenta su metodología de dos comandos que usa sistemáticamente.

**Primer comando — Descubrimiento rápido de puertos abiertos**

El objetivo es saber qué puertos están abiertos lo antes posible, sin preocuparse aún por versiones ni scripts.

```
sudo nmap -p- --min-rate 5000 IP_OBJETIVO
```

- -p- escanea todos los 65.535 puertos
    
- --min-rate 5000 fuerza al menos 5.000 paquetes por segundo, acelerando el escaneo considerablemente. El límite teórico del protocolo es 1.500 pero se puede forzar hasta 10.000. En entornos reales bajar esta velocidad; en laboratorio o CTF usar 5.000
    
- No lleva -sC ni -sV porque no interesa la profundidad aún, solo saber qué está abierto
    

El resultado es una lista limpia de puertos abiertos en pocos segundos.

**Segundo comando — Análisis en profundidad sobre los puertos encontrados**

Con la lista de puertos abiertos del primer comando, se lanza un segundo escaneo solo sobre esos puertos, ahora con detección de versiones y scripts:

```
sudo nmap -p 21,22,23,25,53,80,111,139,445,512,3306,5900 -sCV IP_OBJETIVO
```

- -p seguido de los puertos separados por comas
    
- -sCV combina -sC (scripts por defecto) y -sV (detección de versión). Son equivalentes a ponerlos por separado
    

Este comando tarda más pero genera la misma cantidad de paquetes que un Nmap básico, porque solo actúa sobre los puertos ya identificados como abiertos. El resultado incluye versiones exactas de cada servicio y los hallazgos de los scripts de Nmap (login anónimo FTP, configuraciones débiles, etc.).

Una advertencia sobre la fiabilidad: los nombres de servicio que muestra Nmap (FTP, HTTP, MySQL) son inferencias basadas en el puerto. En puertos no estándar pueden aparecer nombres incorrectos. El segundo comando con -sCV da más fiabilidad pero tampoco es infalible.

Razón adicional para hacer dos escaneos: los servicios a veces se caen y se reinician. Un escaneo lanzado a las 6 de la tarde puede mostrar puertos que no aparecen a las 7, o viceversa. En certificaciones como el OSCP, relanzar el escaneo tras una hora puede revelar servicios que antes no estaban visibles.

---

**El protocolo FTP como primer caso de estudio**

FTP (puerto 21) es el primer servicio que se analiza en detalle porque es conceptualmente sencillo y permite introducir la lógica de enumeración que se aplicará a todos los demás.

FTP es un gestor de archivos remoto: permite conectarse y transferir ficheros entre cliente y servidor. Lo que lo hace interesante para el atacante es que muchas implementaciones tienen configuraciones débiles por defecto.

Los tres únicos vectores de ataque sobre FTP son:

- **Sesión anónima:** muchos servidores FTP tienen habilitado el login anónimo, que permite conectarse sin credenciales. Es la primera prueba que se hace siempre
    
- **Versión vulnerable:** si la versión del servicio tiene una vulnerabilidad conocida, se puede explotar directamente. Nmap con -sCV revela la versión exacta, que luego se busca en SearchSploit o ExploitDB
    
- **Credenciales obtenidas por otro medio:** desde OSINT, credenciales filtradas, ingeniería social, phishing, o información extraída de otro puerto del mismo servidor
    

Si ninguno de estos tres vectores funciona, el FTP no ofrece más superficie de ataque de forma aislada. Pero aislado no significa irrelevante.

**La relación FTP-web como vector combinado**

Si el servidor tiene también el puerto 80 activo y la carpeta del FTP está dentro del directorio web, cualquier fichero subido vía FTP puede ser ejecutado a través del navegador. Este es el punto donde la combinación de dos servicios que por separado parecen inocuos se convierte en un vector de compromiso total.

El flujo es: acceso anónimo al FTP → subida de fichero PHP malicioso → ejecución del fichero a través del navegador → reverse shell con privilegios del servidor web.

- **La idea clave:** el FTP por sí solo raramente da acceso root. Lo que da es un punto de entrada para subir contenido que otro servicio puede ejecutar. La clave del hacking no es explotar un servicio, es entender cómo los servicios interactúan entre sí

**Recapitulación integrada**

Al cerrar esta sesión sabemos montar correctamente el laboratorio con adaptador puente, entendemos por qué el scope define qué se puede atacar y qué no, y tenemos una metodología clara de descubrimiento: primero ping o Net-Discover para localizar hosts con el mínimo ruido posible, luego dos pasadas de Nmap sobre la IP identificada para obtener puertos y versiones. Sobre el FTP hemos interiorizado que sus vectores son exactamente tres y que ninguno por sí solo garantiza el compromiso del sistema, pero que combinado con el puerto 80 puede convertirse en la puerta de entrada completa. La próxima sesión continúa con la enumeración de los servicios restantes de Metasploitable y los primeros exploits reales.
