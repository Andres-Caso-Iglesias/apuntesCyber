**Máquinas virtuales, disco y red: qué pasó con Metasploitable**

Una máquina virtual no es más que un ordenador que vive dentro de otro ordenador. Comparte los recursos del anfitrión (RAM, CPU y disco), pero con una diferencia crítica respecto al disco: mientras el disco del anfitrión es dinámico y distribuye el espacio según lo que se necesite en cada momento, el disco virtual es un tamaño fijo reservado desde el principio. Lo ocupe o no, ese espacio está bloqueado.

Metasploitable 2 se distribuye únicamente como fichero VMDK (Virtual Machine Disk), sin el OVA que simplifica la importación. La solución es crear una máquina nueva en VirtualBox, asignarle el VMDK ya existente como disco en lugar de crear uno nuevo, y dejarla con recursos mínimos: 512 MB de RAM y un solo núcleo son suficientes porque la máquina no tiene interfaz gráfica y va a permanecer en segundo plano esperando ser atacada.

Para montar el laboratorio correctamente hay que crear una Red NAT personalizada. El procedimiento es: Archivo → Herramientas → Red → Red NAT → Crear. Se le activa el DHCP para que asigne IPs automáticamente y se asigna esa misma red a ambas máquinas (Kali y Metasploitable) en su configuración de adaptador. Con esto quedan forzadas a verse entre sí.

```
# Verificar conectividad entre máquinas
ifconfig          # Ver IP en Metasploitable
ping 10.0.2.X     # Comprobar desde Kali
```

El TTL de la respuesta al ping ya da información del sistema operativo: 64 es Linux, 128 es Windows, 256 es Solaris o macOS.

- **La idea clave:** el problema de ayer no era de herramientas sino de conceptos. Si no se entiende que el disco virtual es fijo y que la red NAT tiene que crearse explícitamente antes de asignarla, las máquinas nunca van a verse. El laboratorio no falla, falla la configuración

**Redes e interfaces: por qué tenemos más de dos IPs**

Un ordenador no tiene una sola IP sino tantas como interfaces de red activas tenga. Las interfaces pueden ser físicas (Ethernet por cable, nomenclatura ETH), inalámbricas (WiFi, nomenclatura WLAN) o virtuales (VPN, nomenclatura TUN; conectores de máquinas virtuales). Cada conexión a una red diferente genera una interfaz nueva con su propia IP.

Los tipos de adaptador en VirtualBox tienen comportamientos distintos:

- **Red NAT:** conectividad tanto con otras máquinas virtuales de la misma red como con Internet. Es la opción más completa para el laboratorio
    
- **Adaptador puente:** expande la red local física del anfitrión a la máquina virtual, que obtiene una IP del tipo 192.168.X.X igual que cualquier otro dispositivo de la casa. En bridge aparecerán en Net-Discover todos los dispositivos del hogar (móvil, televisor, etc.)
    
- **Red interna:** visibilidad solo entre máquinas virtuales, sin salida a Internet. Útil para sandboxes de malware donde se quiere aislar el bicho
    

La diferencia entre proxy y VPN: un proxy hace un único salto a través de un servidor intermedio. Una VPN encapsula el tráfico y lo hace saltar por varios nodos antes de salir a Internet, funcionando como un conglomerado de proxys. Las VPN corporativas (Fortinet, Cisco, Checkpoint) crean un túnel para entrar en la red interna de una empresa desde fuera. Las VPN domésticas (Mullvad, NordVPN, ProtonVPN) enmascaran la IP pública del usuario.

- **La metáfora útil:** la VPN es como tintarse los cristales del coche. No cambia el coche ni el destino, pero nadie sabe quién va dentro

**Corrección del laboratorio: Web Investigation (preguntas 6-9)**

**Pregunta 6 — Tabla con datos de usuarios**

Desde el análisis anterior sabemos que el atacante volcó el information_schema. Yendo a Archivo → Exportar objetos → HTTP y buscando las peticiones que hacen referencia a information_schema, se identifica el paquete donde se consulta el TABLE_NAME. El follow del stream HTTP revela que la base de datos contiene tres tablas: admin, bugs y customers. La tabla que contiene datos de usuarios es customers.

**Pregunta 7 — Directorio al que accede sin autorización**

El atacante lanza un fuzzer de directorios: centenares de peticiones GET con nombres de carpetas habituales en sistemas Linux, ordenadas alfabéticamente. Las que empiezan por punto son carpetas ocultas (.mysql_history, .passwd). Las respuestas 404 se descartan. Un 403 Forbidden significa que el directorio existe pero el acceso está restringido. Un 301 Moved Permanently indica que existe y redirige a otro lado. Siguiendo la secuencia se localiza el primer 302 Found apuntando a /admin/login.php, que es el directorio al que accede exitosamente.

**Pregunta 8 — Credenciales del atacante**

Una vez localizado el panel de login, el atacante realiza intentos de autenticación mediante método POST. La señal para distinguir el intento exitoso del fallido es el Content-Length de la respuesta: mientras la respuesta es siempre el mismo mensaje de error (credenciales inválidas), el Content-Length es constante (291 bytes). En el momento en que cambia a 0 bytes y aparece un 302 redirigiendo a /admin/index.php con una cookie de sesión válida, sabemos que las credenciales han funcionado. Las credenciales son admin / admin123! (el %21 es la codificación URL del signo de exclamación).

**Pregunta 9 — Fichero malicioso subido**

Después del acceso al panel de administración, el atacante navega a la sección de uploads. Se observa una subida vía POST seguida de un GET al mismo fichero: primero lo sube, después lo ejecuta. El fichero tiene nombre con caracteres aleatorios y extensión .php. Tras el GET que lo ejecuta, el servidor devuelve un Internal Server Error: la shell PHP se ha ejecutado y ha abierto la conexión reversa. A partir de ese momento el tráfico pasa bruscamente de HTTP a TCP puro.

- **La idea clave:** el cambio brusco de HTTP a TCP en una captura forense web no es un artefacto ni un error. Es la firma de una reverse shell activa. Alguien ha subido un fichero que al ejecutarse ha generado una conexión TCP directa entre el servidor víctima y el atacante, saltando por encima de la capa de aplicación

**Reverse shell vs bind shell: la física del ataque**

Una vez dentro de un servidor web por capa de aplicación (HTTP), el objetivo es bajar a capa de transporte (TCP) para tener control directo. Esto se hace subiendo un fichero PHP que al ejecutarse spawna una terminal en el servidor y la conecta con la máquina del atacante.

Si el servidor víctima se conecta al atacante, es una **reverse shell**. Si el atacante se conecta al servidor víctima, es una **bind shell**. La reverse shell hace mucho menos ruido porque los firewalls monitorizan las conexiones entrantes mucho más que las salientes. Además, si el servidor sale por el puerto 443 o el 80, ningún firewall lo va a cortar.

La cadena completa de ataque de esta sesión tiene siete pasos: SQL Injection → volcado de information_schema → extracción de credenciales de administrador → acceso al panel → bypass del filtro de subida de ficheros → ejecución del PHP malicioso → reverse shell TCP.

- **La idea clave:** el hacking no es un único exploit. Es una cadena de vulnerabilidades donde cada paso abre la puerta al siguiente. Si una empresa arregla solo la SQL Injection pero deja el panel de subida sin validar extensiones, el atacante encuentra otro camino. La seguridad tiene que ser sistémica

**Net-Discover vs Nmap: cuánto ruido hace cada uno**

Interceptando con Wireshark en tiempo real mientras se lanzan herramientas, se puede medir exactamente el impacto de cada decisión.

**Net-Discover** funciona a través del protocolo ARP. Pregunta a cada IP del rango "¿quién tiene esta dirección?" y registra quién responde. Para un rango /24 envía exactamente 254 paquetes de 42 bytes. Solo generan tráfico de respuesta los hosts activos. Es el método más silencioso para descubrimiento de activos.

Limitación importante: Amazon Web Services tiene ARP deshabilitado por defecto. Si el examen final está en AWS, Net-Discover no funcionará y habrá que usar Nmap directamente sobre el rango.

**Nmap por defecto** (sin parámetros extra) escanea los 1.000 puertos más comunes. Para dos hosts genera aproximadamente 2.000 paquetes. El patrón es muy reconocible en Wireshark: peticiones al mismo host a todos los puertos en un orden no secuencial (primero los más comunes), con paquetes de longitud siempre idéntica.

**Nmap con todos los puertos** (-p-) genera 131.000 paquetes para dos hosts (65.535 puertos por host, multiplicado por dos porque las comunicaciones son bidireccionales). Completamente inviable para red team.

**El flujo correcto en una auditoría real:**

```
# Paso 1: descubrimiento silencioso de activos
sudo netdiscover -r 10.0.2.0/24

# Paso 2: escaneo básico rápido para ver puertos abiertos
nmap -Pn IP_OBJETIVO

# Paso 3: escaneo profundo solo sobre los puertos encontrados
nmap -Pn -p 21,22,80,445,3306 -sC -sV IP_OBJETIVO
```

El parámetro -Pn elimina el ping previo (host discovery), que usa ICMP. HackTheBox tiene ICMP deshabilitado para que los usuarios no se ataquen entre sí, por lo que sin -Pn el Nmap devuelve "host unreachable" aunque la máquina esté activa.

El parámetro -sC lanza los scripts por defecto de Nmap (en /usr/share/nmap/scripts/), que extraen información adicional de cada servicio: versiones más detalladas de SMB, comprobación de login anónimo en FTP, enumeración de certificados SSL, etc. Combinado con -sV (detección de versión), con solo 2.000 paquetes se obtiene la información suficiente para buscar exploits.

- **La metáfora útil:** hacer Nmap en dos fases es como reconocer un edificio antes de entrar. Primero miras cuántas puertas tiene desde fuera (descubrimiento de puertos), luego te acercas solo a las puertas abiertas y miras por el ojo de la cerradura (scripts y versiones). Intentar abrir todas las cerraduras de todas las puertas a la vez no solo hace ruido, también tarda una eternidad

**Seguridad por oscuridad: mover servicios a puertos no estándar**

Mover un servicio a un puerto no habitual (por ejemplo, SSH al puerto 52022 en vez del 22) se llama seguridad por oscuridad. No hace el servicio más seguro, solo lo oculta de los escaneos más superficiales. Un Nmap con -p- lo encuentra igualmente. En auditorías reales se encuentran servicios en puertos raros con frecuencia, incluyendo FTP con login anónimo en puertos por encima del 50000. La oscuridad no es seguridad.
