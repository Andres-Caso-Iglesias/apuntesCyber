---

**La máquina y el entorno**

La máquina vulnerable se importa directamente en VirtualBox desde el fichero .ova descargado. Se coloca en la misma red NAT que Kali para que ambas tengan visibilidad. La IP de la máquina víctima se descubre durante el reconocimiento, no se da de antemano.

---

**Fase 1 — Reconocimiento de red**

El punto de partida es siempre el mismo: estamos en la misma red que la víctima y no sabemos nada más. Para descubrir qué IPs están activas hay dos herramientas principales.

**Net-Discover** usa el protocolo ARP para descubrir activos en la red local. ARP es capa 2, no es ni TCP ni UDP, lo que lo hace más ligero y menos detectable que un escaneo de puertos. Se lanza contra un rango de red:

```
sudo netdiscover -r 10.0.2.0/24
```

**Nmap** puede hacer el mismo descubrimiento de activos pero a través de TCP, lo que genera más ruido. Net-Discover es preferible para el reconocimiento inicial en red local. AWS no acepta ARP, lo que es relevante para entornos cloud.

Una vez identificada la IP de la víctima, se pasa al escaneo de puertos.

---

**Fase 2 — Escaneo de puertos y servicios**

El escaneo se hace en dos fases. Primero los puertos más comunes para obtener resultados rápidos:

```
nmap -sC -sV 10.0.2.15
```

La flag -sC lanza los scripts de Nmap asociados a cada servicio (banner grabbing, detección de configuraciones débiles, etc.). La flag -sV detecta versiones. El resultado revela cuatro puertos: 21 (FTP), 22 (SSH), 80 (HTTP) y 9090 (HTTP).

Ante un resultado así, la metodología es clara: cada puerto es una superficie de ataque. Los servicios con login (FTP, SSH) tienen tres vectores posibles: fuerza bruta, versión vulnerable con CVE explotable, o mala configuración. Los servicios HTTP tienen su propia metodología.

Si el escaneo inicial no da suficiente información, se lanza a todos los puertos:

```
nmap -sC -sV -p- 10.0.2.15
```

Este paso, más ruidoso, se reserva para cuando los puertos comunes no ofrecen ningún vector. En un entorno real, se usa como último recurso antes de cerrar la auditoría.

---

**Puerto 21 — FTP anónimo**

Nmap indica Anonymous FTP login allowed. Esto es una mala configuración clásica: el servidor FTP acepta conexiones sin credenciales reales, bajo la cuenta de servicio FTP.

```
ftp -a 10.0.2.15
```

La flag -a indica login anónimo automáticamente. Una vez dentro, el contexto es importante: no se está en una shell de Linux completa, sino en la shell restringida del FTP. Los comandos disponibles son los que muestra help. No hay cat, no hay locate.

```
ls
cd pub
ls
get flag.txt
```

La flag se descarga con get (file transfer protocol significa que transfiere ficheros, no los abre). Una vez descargada, se lee desde la shell de Kali con cat. El protocolo FTP es bidireccional: get descarga, put sube. Si se tuviesen permisos de escritura y acceso a la carpeta de la web, subir un fichero PHP malicioso sería el siguiente paso.

- **La idea clave:** la cuenta de servicio FTP no es un usuario del sistema. Es una cuenta que solo puede interactuar con el servicio FTP, no con el sistema operativo subyacente. Esto aplica a todos los servicios: FTP, Apache, PostgreSQL, cada uno tiene su cuenta de servicio con sus propios permisos
    

---

**Puerto 80 — Auditoría web: enumeración completa**

Cualquier servicio HTTP se audita diferente a un servicio de red. No se buscan versiones vulnerables ni se lanza un exploit: se enumera la funcionalidad de la aplicación y se buscan fallos en esa funcionalidad.

**Paso 1 — Ver el código fuente del front**

El código fuente que se ve desde el navegador (click derecho, ver código fuente) es únicamente el front: HTML, CSS, JavaScript. No es el código del servidor. Aun así, puede contener comentarios con información sensible, rutas de directorios desconocidos, o referencias a APIs del backend.

**Paso 2 — robots.txt**

El fichero robots.txt indica a los crawlers de buscadores qué URLs no deben indexar. Precisamente por eso es donde los desarrolladores suelen listar las rutas que no quieren que aparezcan en Google, lo que lo convierte en una fuente de información para el atacante. Se accede directamente:

```
http://10.0.2.15/robots.txt
```

En esta máquina revela el directorio /passwords/, que contiene dos ficheros: flag.txt y passwords.html.

**Paso 3 — Enumerar directorios**

Independientemente de lo que haya en robots.txt, siempre se lanza un enumerador de directorios. La herramienta no importa (DirSearch, GoBuster, Feroxbuster, FFUF, DirBuster: todas hacen lo mismo), pero todas usan un diccionario. Por defecto, DirSearch trae uno propio. Si se quiere más cobertura, se especifica uno manualmente:

```
dirsearch -u http://10.0.2.15
```

Lo que diferencia los resultados entre herramientas es el diccionario que usa cada una por defecto. Con el mismo diccionario darían los mismos resultados.

**Paso 4 — Explotar la funcionalidad: Command Injection**

En el directorio cgi-bin hay una página que implementa un traceroute: el usuario introduce una IP y el servidor ejecuta el comando y muestra el resultado. Esta funcionalidad implica que el servidor está ejecutando un comando del sistema operativo con el input del usuario como argumento.

Si el desarrollador no valida que el input sea únicamente una IP, el atacante puede encadenar comandos adicionales usando el operador ;. En bash, el punto y coma ejecuta el segundo comando después de que termine el primero:

```
10.0.2.15; whoami
```

Si la aplicación ejecuta esto, el servidor devuelve el resultado del whoami. Eso confirma el Command Injection. En producción, el código correcto validaría que el parámetro sea exactamente una IP (cuatro números separados por puntos) y rechazaría cualquier otro carácter.

Con esta vulnerabilidad confirmada, se enumera el sistema de ficheros del servidor:

```
10.0.2.15; head -200 /etc/passwd
```

El fichero /etc/passwd lista todos los usuarios del sistema. Los que tienen /bin/bash al final son usuarios reales con shell propia. Los que tienen /nologin o /false son cuentas de servicio. En esta máquina aparecen: root, Rick, Morty y Summer.

Esto reduce el espacio de búsqueda para una fuerza bruta de infinito a cuatro usuarios conocidos.

Para ver todo el árbol de ficheros de la web:

```
10.0.2.15; tree /var/www/www
```

Esto revela la estructura completa y confirma que no hay más directorios ocultos que explorar.

- **La idea clave:** las consultas parametrizadas son la solución a SQL Injection, y la validación estricta del formato del input es la solución al Command Injection. El problema en ambos casos es el mismo: el servidor confía en lo que el usuario le envía sin comprobar que sea exactamente lo que espera recibir
    
- **La metáfora útil:** el desarrollador dejó una ventanilla que supuestamente solo acepta IPs. El atacante descubrió que si se mete por el hueco junto a la ventanilla, puede hablar directamente con el empleado de dentro
    

---

**Puerto 9090 — Cockpit Web Service**

El puerto 9090 aloja un panel de administración de servidor Linux llamado Cockpit. La enumeración de directorios no revela rutas nuevas. La única funcionalidad visible es un campo de nombre de usuario sin contraseña. Cockpit versión 161 con Fedora 26 tiene CVEs asociados, pero ninguno aprovechable sin autenticación previa. Se descarta como vector de entrada y se identifica como un rabbit hole.

Un rabbit hole es un camino que parece prometedor pero no conduce a ningún vector de explotación. Saber cuándo cortar y no seguir invirtiendo tiempo en algo sin salida es una habilidad tan importante como saber explotar vulnerabilidades.

---

**Puertos ocultos — Escaneo completo**

Al agotar todos los puertos comunes, se lanza el escaneo completo:

```
nmap -sC -sV -p- 10.0.2.15
```

Aparecen dos puertos adicionales: el puerto 22222 (SSH real, el 22 estaba filtrado) y el puerto 60000 (TCP con una reverse shell a medio implementar).

El puerto 60000 se prueba con NetCat:

```
nc 10.0.2.15 60000
```

El servidor responde con un banner: "Welcome to Rick's half-baked reverse shell". La shell es funcional pero completamente restringida: no permite moverse fuera del directorio actual. Se lee la flag disponible y se descarta como vector de escalada.

---

**Acceso al servidor — SSH con credenciales obtenidas**

Con los usuarios extraídos del /etc/passwd y la contraseña winter encontrada en passwords.html, se construye el acceso:

```
ssh Summer@10.0.2.15 -p 22222
```

El SSH estaba en el puerto 22222, no en el 22 estándar. La contraseña winter funciona para el usuario Summer. Acceso obtenido al servidor.

---

**Recapitulación integrada**

Esta máquina demuestra que el hacking real no requiere exploits sofisticados. Siete puertos, cada uno auditado sistemáticamente: FTP anónimo entregó una flag, el puerto 80 entregó usuarios del sistema y otra flag mediante Command Injection, y la combinación de usuarios y contraseña filtrada abrió el acceso SSH. Todo fue enumeración metódica, curiosidad ante cada funcionalidad y saber cuándo descartar un camino sin salida. El acceso inicial al servidor está conseguido. La próxima sesión completa la máquina con la fase de escalada de privilegios hasta root.
