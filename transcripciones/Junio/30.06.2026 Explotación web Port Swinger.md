**Burp Suite como framework de auditoría web**

La definición correcta de **Burp Suite** no es "un proxy" sino un framework de auditoría web: una colección de funcionalidades integradas que permiten realizar acciones sobre páginas web para auditarlas. El proxy es la dependencia crítica — sin él no funciona nada más — pero no es lo mismo que la herramienta en sí.

El proxy opera en el único punto donde el atacante tiene control total sobre la comunicación: el tramo entre el navegador (que corre localmente) y el servidor. El front, al correr en tu ordenador, está bajo tu control. El back, en el servidor, no lo está. El proxy se inserta justo antes de que el paquete salga del ordenador: la página cree que lo has enviado correctamente, pero Burp lo intercepta en texto claro antes de que entre en la capa TLS/HTTPS.

- **La idea clave:** la seguridad del front es completamente eludible porque el front corre en el ordenador del atacante. Cualquier validación, restricción de longitud de campo o sanitización de inputs que exista en el frontend puede ser saltada modificando el paquete después de que la página lo valide pero antes de que llegue al servidor
 
- **La metáfora útil:** Burp es el cartero corrupto que abre el buzón antes de que llegue el repartidor. Tú has metido correctamente el sobre con los calcetines, la página lo ha visto salir, pero Burp lo saca, le cambia el contenido, y lo que recibe la abuelita (el servidor) ya no son calcetines

**La cadena de seguridad: front, WAF y back**

Cuando un desarrollador pone controles en el front (longitud máxima de campos, sanitización de inputs, validaciones de tipo de archivo), esos controles son bypasseables con Burp. El atacante modifica el paquete después de que el front lo haya validado. Una vez superado el front, quedan dos variables: el **WAF** (Web Application Firewall) y el propio backend.

El WAF es bypasseable en la mayoría de implementaciones reales. Lo que sí importa es que el backend gestione bien los datos que le llegan, porque si el PHP del servidor no valida lo que recibe, el paquete modificado va a explotar algo. Las vulnerabilidades más comunes que aprovechan esta cadena son inyección SQL (si los parámetros no están sanitizados), file upload (si el servidor no valida el tipo real del fichero), y overflow de buffers por campos sin validación en el back.

**Configuración completa del stack: FoxyProxy + certificado CA + Burp**

Para interceptar tráfico HTTPS hay que resolver el problema del cifrado: el navegador normalmente rechaza un intermediario que no tenga un certificado válido. Burp genera su propia CA (autoridad certificadora) que hay que importar como de confianza en el navegador.

El flujo de configuración es el siguiente. Primero, con Burp abierto, navegar a localhost:8080 y descargar el certificado CA desde la esquina superior derecha. Segundo, importarlo en Firefox (o el navegador elegido) en about:preferences â†’ Certificados â†’ Administrar certificados â†’ Autoridades â†’ Importar. Tercero, instalar la extensión FoxyProxy y crear un nuevo proxy apuntando a 127.0.0.1 en el mismo puerto donde Burp está escuchando (comprobable en Burp â†’ Proxy â†’ Proxy settings â†’ Proxy listeners). Cuarto, desde FoxyProxy activar ese perfil cuando se quiera interceptar.

```
Burp listener: 127.0.0.1:8080
FoxyProxy â†’ nuevo proxy â†’ host: 127.0.0.1, puerto: 8080
Certificado CA: descargado de localhost:8080 â†’ importado en Firefox como autoridad de confianza
```

Un problema frecuente al configurar: si tanto el FoxyProxy como el proxy listener de Burp están en el mismo puerto, puede haber conflicto. La solución es cambiar uno de los dos (por ejemplo, mover Burp a 8081) y asegurarse de que FoxyProxy apunta al puerto correcto.

- **La idea clave:** sin el certificado CA instalado, el navegador detecta el proxy como un tercero no autorizado y bloquea la conexión HTTPS. Con el certificado, el navegador confía en Burp como si fuese el destino legítimo, y Burp puede leer y modificar el tráfico en texto claro antes de reenviarlo al servidor real

**Módulos de Burp Suite — mapa funcional**

La clase recorrió el mapa completo de módulos para que los alumnos sepan qué existe aunque no hayan usado todo todavía.

El **Proxy** es el corazón, con tres subfuncionalidades relevantes: Intercept (parar y modificar peticiones en tiempo real), HTTP History (historial de todo el tráfico interceptado, muy útil para revisar peticiones anteriores sin tener que repetirlas) y Target/Scope (filtrar qué dominio se quiere interceptar, imprescindible para no ahogarse en tráfico de Analytics, APIs de terceros y demás ruido).

El **Intruder** es el módulo de fuzzing y fuerza bruta. Los parámetros del paquete a iterar se marcan entre signos de dólar ($parámetro$), se carga un diccionario como payload, y Burp lanza las peticiones. Se recomienda fuzear un solo parámetro a la vez para poder interpretar las respuestas. Tiene cuatro modos: Sniper (un payload, una posición), Battering Ram (mismo payload en todas las posiciones), Pitchfork y Cluster Bomb (el más agresivo, para los que tengan la versión Pro). En la versión gratuita el Intruder funciona pero a velocidad reducida.

El **Repeater** permite reenviar la misma petición cuantas veces se quiera, modificando manualmente parámetros o cabeceras entre envío y envío, y comparar las respuestas. Es la herramienta de exploración quirúrgica: primero se entiende cómo responde la aplicación a distintos inputs antes de automatizar nada.

El **Decoder** convierte datos entre formatos: base64, URL encoding, HTML encoding, hex. En auditorías es frecuente encontrar tokens y cookies con doble encoding (por ejemplo, base64 dentro de URL encoding), que hay que decodificar en capas para ver su contenido real.

El **Comparer** compara dos fragmentos de texto o datos (por ejemplo, dos cookies de sesión) para buscar patrones. Ãštil en ataques de session hijacking o análisis de tokens.

- **La idea clave:** aunque en la versión gratuita el Intruder va lento, es perfectamente usable para fuerza bruta en CTFs. El límite de velocidad no es un impedimento real para las máquinas que se trabajan en el máster

**Cookies de sesión y session hijacking**

Cada vez que un usuario entra en una web, el servidor genera un session ID único y lo almacena en una cookie. Ese ID es lo que diferencia tu sesión de la de cualquier otro usuario simultáneo: el servidor no sabe quién eres, solo que el portador de ese ID tiene los permisos correspondientes. La cookie tiene una duración (habitualmente 30 días) y se invalida al limpiar la caché del navegador.

El vector de ataque práctico más actual no es iterar IDs (los IDs modernos son pseudoaleatorios y no se reciclan), sino el **robo de cookie de sesión vía phishing avanzado**. El flujo es: se crea una página de phishing que replica el login legítimo; cuando la víctima introduce sus credenciales, el atacante las reenvía en tiempo real al servidor real; si hay 2FA, se intercepta también mediante un iframe que se muestra a la víctima; una vez completado el login, el atacante captura la cookie de sesión generada y la usa en su propio navegador, obteniendo 30 días de acceso sin necesidad de credenciales ni 2FA.

- **La idea clave:** robar la cookie de sesión equivale a robar la sesión activa completa, bypaseando cualquier segundo factor de autenticación. El 2FA protege el proceso de login, no la sesión ya establecida

**Reconocimiento web metodológico — máquina Academy**

La máquina Academy (HackerLab) corre Apache 2.4.59 en Debian con PHP, puertos 22 y 80 abiertos. Por la misma razón de siempre: el puerto 22 (SSH) sin credenciales no lleva a ningún lado, así que se empieza por el puerto 80.

El primer paso al encontrar un servidor con HTTP es configurar la entrada DNS local. Si la aplicación web está configurada para responder a un hostname (no a una IP), acceder por IP directa puede dar una página diferente o rota. La solución es editar el archivo hosts del sistema operativo para mapear la IP al nombre de dominio. En Linux es /etc/hosts; en Windows es C:\Windows\System32\drivers\etc\hosts (requiere abrir el bloc de notas como administrador). Se añade una línea con el formato IP dominio, se guarda y a partir de ese momento el navegador pasa por el protocolo DNS local.

Con la página cargando correctamente, el flujo de reconocimiento es: lanzar dirsearch (o equivalente con SecLists + script PowerShell en este caso) en segundo plano mientras se explora manualmente la página, instalar Wappalyzer para identificar tecnologías, y consultar HackTricks para ver la metodología específica del CMS detectado.

**Wappalyzer** identifica la tecnología principal como **WordPress**. Esto cambia la metodología: ya no buscamos vulnerabilidades genéricas de Apache sino que entramos en la metodología específica de WordPress.

**WordPress — metodología de auditoría y WPScan**

WordPress no suele ser vulnerable en su núcleo. Las vulnerabilidades están en los plugins, desarrollados por terceros con control de calidad variable. La cadena de dependencias es: motor WordPress â†’ tema â†’ plugins â†’ librerías de cada plugin.

Los archivos y rutas relevantes que siempre se comprueban en un WordPress: index.php (redirige a la home, confirma que funciona), license.txt (revela versión exacta de WordPress si no se ha limpiado), wp-activate.php (a veces permite registros o acciones administrativas si está mal configurado), /wp-login.php (panel de login, vector de fuerza bruta), /wp-admin/ (panel de administración), /wp-content/uploads/ (directorio de subidas, si hay archivos ejecutables ahí podríamos ejecutarlos).

Los roles de usuario en WordPress siguen un sistema de permisos equivalente a Linux: Administrador (rwx), Editor (rw), Autor (w), Contribuidor (w), Suscriptor (r). Conocer el rol obtenido tras comprometer una cuenta determina qué acciones son posibles.

**WPScan** es la herramienta de referencia para auditoría de WordPress. Requiere Ruby para instalarse (en Kali: sudo apt install wpscan; en Mac: gem install wpscan). Con una API token gratuita expone CVEs de plugins y temas instalados. Sin token solo lista los plugins sin CVEs. Sus funciones principales son enumeración de plugins, enumeración de usuarios (explotando el information disclosure del login, ya visto en Mr. Robot), y fuerza bruta de contraseñas sobre el login de WordPress.

- **La idea clave:** la diferencia entre WPScan con y sin API token es la diferencia entre saber que existe un plugin y saber que ese plugin tiene una vulnerabilidad crítica conocida. Registrarse para obtener el token gratuito es obligatorio para usar WPScan de manera profesional

**SecLists y diccionarios de referencia**

**SecLists** es el repositorio de referencia para todos los diccionarios usados en auditorías web: contraseñas (RockYou y variantes), directorios (directory-list-2.3-medium.txt es el estándar), fuzzing de subdominios, parámetros, y más. Se descarga como ZIP desde GitHub y se descomprime localmente. El diccionario directory-list-2.3-medium.txt es el que utilizan por defecto DirSearch, GoBuster y DirBuster, y es el punto de partida para cualquier enumeración de directorios.
