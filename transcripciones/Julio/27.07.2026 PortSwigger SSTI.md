**Qué es SSTI y por qué ocurre**

Las aplicaciones web no muestran contenido estático: cada usuario ve datos dinámicos que se generan en tiempo real. Para eso existen los motores de plantillas, que son sistemas que toman un formato fijo con variables y los rellenan con datos reales antes de enviar la respuesta al navegador. Un ejemplo simple sería una plantilla que dice hola, {{nombre}} y que el motor convierte en hola, Carlos cuando el usuario con ese nombre inicia sesión.

El problema aparece cuando el valor que rellena esa variable viene directamente de una entrada del usuario sin sanitizar. Si en lugar de un nombre, el usuario puede inyectar una expresión matemática o una llamada a funciones del sistema, el motor la evaluará como código propio. Eso es SSTI.

La diferencia entre el caso seguro y el vulnerable se reduce a una línea de código en el backend:

- Seguro: render(template="hola {{nombre}}", nombre=entrada_usuario) — los datos llegan como parámetro separado del template, nunca como parte del template en sí.
 
- Vulnerable: render(template="hola " + entrada_usuario) — la entrada del usuario se concatena directamente en la cadena que el motor va a evaluar.
 
- **La metáfora útil:** es como la diferencia entre darle a alguien una receta con un ingrediente a rellenar (seguro), y darle la receta en blanco para que la escriba él entero (vulnerable). En el segundo caso, puede escribir lo que quiera

**La señal de detección: el famoso cuarenta y nueve**

La detección de SSTI se reduce a inyectar 7*7 con la sintaxis del motor sospechado y observar si la respuesta muestra 49 en lugar del texto literal. Si el motor evalúa la expresión matemática y devuelve el resultado, ha ejecutado código arbitrario del atacante. Eso es todo. No hace falta más para confirmar la vulnerabilidad.

El payload de detección genérico, que mezcla sintaxis de todos los motores principales en una sola cadena, se llama polyglot. Al enviarlo, el motor que esté activo reconocerá sus propios delimitadores, evaluará la expresión, y el resultado revelará qué caracteres han desaparecido o qué valor ha calculado, permitiendo identificar el motor por eliminación.

Las tres fases de explotación de SSTI son siempre las mismas: detectar que existe (el cuarenta y nueve), identificar el motor concreto (ERB, Tornado, Jinja2, FreeMarker, Twig...), y explotar con la sintaxis correcta para ese motor.

- **La idea clave:** el cuarenta y nueve no es el fin, es la confirmación de que hay ejecución. Lo que interesa es escalar de esa operación matemática a whoami, a leer ficheros, a borrar ficheros, o a abrir una reverse shell
 

---

**Motores principales y sus sintaxis**

Los motores más habituales en auditorías reales, con su sintaxis de detección:

ERB (Ruby): la operación matemática va entre <%= y %>. Si al enviar el polyglot se comen los caracteres <, %, = y > pero no las llaves dobles, es ERB.

Tornado y Jinja2 (Python): usan doble llave, {{ 7*7 }}. Si da cuarenta y nueve con esta sintaxis, es Python. Para distinguir Tornado de Jinja2, Jinja2 permite acceder a la jerarquía de clases de Python desde la propia plantilla, mientras que Tornado es más restrictivo.

FreeMarker (Java): usa ${ 7*7 }. Más habitual en aplicaciones empresariales de banca y sector público.

Twig (PHP): usa la misma sintaxis de doble llave que Jinja2, pero el comportamiento al intentar acceder a objetos internos varía.

No hace falta memorizar ninguna de estas sintaxis. Lo que hay que saber es que existen diferencias y que cuando se detecta el motor, HackTricks o PayloadsAllTheThings tienen los one-liners de explotación para cada uno.

**Laboratorio 1 — ERB Ruby: producto sin stock como vector**

La tienda de PortSwigger tiene productos con stock y productos sin stock. Al lanzar el Intruder sobre el parámetro de product ID iterando del uno al veinte, aparece una anomalía: el producto uno devuelve código 302 con tamaño de respuesta diferente a todos los demás. Ese producto redirige al home con un parámetro message en la URL que contiene el mensaje de error desafortunadamente este artículo no está en stock.

El valor del parámetro message se refleja directamente en la página. Al inyectar el polyglot, los caracteres <%= y %> desaparecen del output, lo que confirma que el motor es ERB de Ruby. El laboratorio además lo indica explícitamente en el enunciado.

Con <%=7*7%> se confirma el cuarenta y nueve. A partir de ahí, la sintaxis ERB para ejecutar comandos de sistema usa system():

```
<%=system("rm /home/carlos/morale.txt")%>
```

El espacio entre rm y la ruta se codifica como + al URL-encodear el parámetro, lo que causó problemas durante la resolución hasta que se identificó el error. Una vez enviado con el encoding correcto, el servidor devuelve true confirmando que el fichero ha sido borrado.

**Laboratorio 2 — Tornado Python: escape de la variable y ejecución**

Este laboratorio añade una capa de complejidad: la vulnerabilidad no está en un campo de texto libre sino en la variable user.name que se inyecta en el template del backend. La diferencia conceptual con el laboratorio anterior es importante: en el laboratorio uno el atacante controla directamente el valor que entra en el template; aquí el template tiene {{ user.name }} hardcodeado y lo que controla el atacante es el valor almacenado en el campo preferred name del perfil.

Al forzar un error con el polyglot en ese campo, el stack trace revela que el backend usa Tornado de Python.

El punto técnico crítico de esta clase es la necesidad de escapar del contexto de la variable antes de inyectar. Por detrás el template hace algo como {{ user.name }}. Si el atacante solo cambia user.name por {{ 7*7 }}, lo que el servidor recibe es {{ {{ 7*7 }} }}, que es sintaxis inválida y puede dar error o comportarse de forma inesperada. La forma correcta es cerrar primero el contexto existente y luego abrir el propio:

```
}}{{7*7}}
```

Esto hace que el template quede como {{ }}{{7*7}}{{ ... }}, donde el primer bloque cierra correctamente el de la variable y el segundo inyecta la expresión del atacante. El resultado en los comentarios del blog donde se refleja el nombre del autor pasa de mostrar Peter Winner a mostrar 49.

El paralelismo con SQL Injection es exacto: igual que se cierra la consulta con una comilla antes de inyectar el payload, aquí se cierra el bloque de plantilla con }} antes de inyectar el propio.

Para escalar a RCE en Tornado (Python), hace falta importar el módulo os:

```
}}{% import os %}{{os.system("rm /home/carlos/morale.txt")
```
