Se cubren los seis casos canónicos de la vulnerabilidad, con énfasis en el razonamiento detrás de cada bypass.

**Qué es path traversal y cómo detectarlo**

Path traversal no es una vulnerabilidad del servidor ni del front ni del puerto: es una vulnerabilidad del fichero PHP que hace la llamada a un archivo del sistema. Cuando una aplicación web carga una imagen, un PDF o cualquier recurso, está haciendo internamente una llamada a una ruta del servidor. Si esa ruta contiene una variable controlada por el usuario y no está correctamente sanitizada, el atacante puede sustituir el nombre del archivo por una ruta que apunte a ficheros arbitrarios del sistema.

La forma de detectarlo es observar en Burp Suite las peticiones que contienen parámetros como filename=, file=, path= o cualquier nombre que sugiera que el valor es el nombre de un archivo. Estas peticiones no siempre aparecen en la URL visible: pueden estar en peticiones que se lanzan en segundo plano al cargar imágenes o recursos de la página, que solo se ven interceptando con Burp.

El fichero de referencia para validar la vulnerabilidad es siempre /etc/passwd en Linux porque es universalmente conocido, está en la misma ruta en todos los sistemas y tiene permisos de lectura para cualquier usuario. Una vez confirmado que hay path traversal, el siguiente paso es el LFI (Local File Inclusion): buscar otros ficheros del sistema que contengan información útil, como claves privadas, ficheros de configuración de bases de datos, o credenciales en texto plano.

- **La metáfora útil:** el desarrollador ha dejado una puerta abierta que da a la calle, pensando que nadie saldría a la calle porque la puerta es pequeña. Path traversal es agacharse para pasar

**Caso 1 — Sin validación (el más simple)**

La aplicación carga imágenes con un parámetro filename=9.jpg. Al interceptar la petición en Burp y modificar el valor por ../../../etc/passwd, el servidor devuelve el contenido del fichero sin ninguna restricción. No hay filtros, no hay validaciones, la variable llega directamente a la función de lectura de ficheros.

```
/image?filename=../../../etc/passwd
```

Este caso existe en producción con más frecuencia de lo que debería.

---

**Caso 2 — Bloqueo de punto punto barra, bypass con ruta absoluta**

El servidor detecta la secuencia ../ y la rechaza, devolviendo un error. Sin embargo, si en lugar de navegar hacia atrás con ../ se proporciona directamente la ruta absoluta del fichero, el servidor la acepta porque el código de validación no contempla ese caso:

```
/image?filename=/etc/passwd
```

Esto ocurre porque el desarrollador protegió el parámetro contra el path traversal relativo, pero olvidó que una ruta absoluta también puede apuntar a cualquier fichero del sistema. El servidor interpreta la ruta absoluta ignorando el contexto desde el que debería servirse el fichero.

---

**Caso 3 — Eliminación no recursiva de punto punto barra**

El servidor elimina las secuencias ../ del valor del parámetro antes de procesarlo. Si el atacante envía ../, queda vacío. La solución es anidar la secuencia de modo que al eliminar la interior quede la exterior intacta:

```
/image?filename=....//....//....//etc/passwd
```

El servidor elimina ../ de cada ....// y lo que queda es ../../../etc/passwd. Este caso ilustra por qué los filtros que eliminan cadenas sin validar el resultado son insuficientes.

```
Entrada: ....//....//....//etc/passwd
Filtro: elimina ../
Resultado: ../../../etc/passwd
```

---

**Caso 4 — Bypass con URL encoding**

El servidor bloquea los caracteres ../ como texto plano. Sin embargo, si el mismo parámetro se envía con los caracteres codificados en URL, el backend puede no aplicar el mismo filtro:

```
/image?filename=%2e%2e%2f%2e%2e%2f%2e%2e%2fetc%2fpasswd
```

Si el servidor decodifica el valor antes de procesarlo pero el filtro actúa sobre el valor sin decodificar, el bypass funciona. Si el backend decodifica una vez, se puede necesitar doble codificación:

```
/image?filename=%252e%252e%252f%252e%252e%252f%252e%252e%252fetc%252fpasswd
```

La lógica del doble encoding: %25 es el carácter % en URL encoding, por lo que %252e se decodifica primero a %2e y luego a .. El filtro solo ve la primera codificación y no reconoce el patrón.

---

**Caso 5 — Validación de ruta de inicio (requiere prefijo)**

El servidor valida que el valor del parámetro empiece por una ruta conocida, por ejemplo /var/www/html/images/. Si el valor no empieza por esa cadena, la petición es rechazada. El bypass consiste en incluir el prefijo requerido y luego navegar hacia atrás desde ahí:

```
/image?filename=/var/www/html/images/../../../etc/passwd
```

El servidor ve que el valor empieza por el prefijo esperado y lo acepta, sin verificar que el path resultante después de resolver los .. sigue dentro del directorio permitido.

---

**Caso 6 — Validación de extensión con null byte**

El servidor valida que el valor del parámetro termine con una extensión de imagen como .jpg o .png. El bypass utiliza un null byte (%00) que actúa como terminador de cadena en algunos lenguajes y entornos:

```
/image?filename=../../../etc/passwd%00.png
```

El servidor ve que el valor termina en .png y lo acepta. Pero cuando la ruta llega al sistema operativo, el null byte termina la cadena ahí, y lo que realmente se lee es ../../../etc/passwd. Este bypass funciona principalmente en aplicaciones antiguas que usan funciones de C por debajo o en ciertos contextos PHP.

---

**De path traversal a LFI — qué buscar después**

Una vez confirmado que hay path traversal, el siguiente paso es buscar ficheros útiles. SecLists incluye diccionarios específicos de LFI en Fuzzing/LFI/ con rutas organizadas por sistema operativo. Se puede lanzar Intruder de Burp con ese diccionario apuntando al parámetro vulnerable para automatizar la búsqueda.

Los ficheros más relevantes en Linux son /etc/passwd (usuarios del sistema), /home/usuario/.ssh/id_rsa (clave privada SSH), ficheros de configuración de bases de datos como config.php o database.yml, y ficheros de log que pueden contener credenciales en texto plano.

- **La idea clave:** path traversal no es el fin sino el principio. El objetivo es escalar de leer /etc/passwd a obtener acceso al sistema, ya sea vía clave privada SSH, credenciales reutilizadas, o información de configuración que abra otra vía de entrada

**Recapitulación integrada**

Los seis casos de path traversal que se han visto en esta sesión (sin validación, ruta absoluta, eliminación no recursiva, URL encoding simple, URL encoding doble, prefijo requerido y null byte) representan el espectro completo de contextos que se encontrará en auditorías reales y en certificaciones web. El denominador común de todos es el mismo error conceptual: el desarrollador filtra una representación concreta del ataque sin proteger la semántica subyacente. La semana que viene se abrirá el módulo de SQL Injection siguiendo la misma estructura: primero los casos más simples, luego los contextos con validación, y finalmente los blind SQLi que son donde la técnica realmente se complica.
