**Repaso de SSTI — el diagrama que faltaba ayer**

Castillo arrancó con el diagrama que no dio tiempo a hacer en la sesión anterior. El flujo completo de SSTI en tres pasos: la entrada del atacante llega al motor de plantillas, el motor lo procesa, y la salida reflejada al cliente puede ser o bien el valor esperado (caso seguro) o bien el resultado de haber ejecutado una expresión (caso vulnerable). El cuarenta y nueve como salida de siete por siete es la señal inequívoca de que el motor ha ejecutado código.

El poliglot (la cadena de caracteres que mezcla sintaxis de todos los motores) se usa cuando no se sabe qué motor hay por detrás. Cada motor solo entiende su propia sintaxis y descarta el resto. Lo que desaparece del output es exactamente lo que ese motor ha procesado. Si los caracteres <%= y %> no aparecen en la respuesta, el motor es ERB de Ruby. Si desaparecen las llaves dobles, es Tornado o Jinja2 de Python. La analogía: como si alguien dijera una misma frase en siete idiomas y el oyente solo reaccionara al que entiende.

Tres vías para detectar el motor sin el poliglot: forzar un error con caracteres raros (el stack trace revela el framework), lanzar el Intruder de Burp con un diccionario de payloads SSTI y comparar longitudes de respuesta, y revisar lo que reveló el Nmap (si dice servidor Python, el motor será Tornado o Jinja2).

- **La idea clave:** la detección del motor no es opcional. El mismo síntoma (cuarenta y nueve) puede requerir payloads radicalmente distintos dependiendo de si es ERB, Tornado, FreeMarker o Twig. Detectar primero, explotar después

**El concepto que bloqueó a media clase ayer — cerrar la expresión**

La parte que costó el día anterior fue el laboratorio dos: cuando por detrás el servidor ya tiene una expresión abierta del tipo {{ user.name }}, inyectar directamente {{ 7*7 }} produce {{ {{ 7*7 }} }}, que es sintaxis inválida y peta.

Castillo lo explicó con la analogía del SQL Injection, que es el equivalente exacto. En SQLI, la consulta por detrás es:

```
SELECT * FROM users WHERE name = 'entrada'
```

Si el atacante mete directamente or 1=1 sin cerrar primero la comilla, el resultado es una consulta malformada. La práctica correcta es cerrar la consulta primero con una comilla, y luego añadir el payload. Pues en SSTI ocurre exactamente lo mismo: si el servidor ya tiene {{ user.name }}, el atacante debe primero cerrar esa expresión con }}, y luego abrir la suya propia:

```
}}{{ 7*7 }}
```

Esto produce en el backend: {{ }}{{ 7*7 }}{{ ... }}, donde el primer bloque es la expresión vacía cerrada y el segundo es la del atacante. La expresión vacía es potencialmente problemática (algunos motores no aceptan expresiones sin contenido), por lo que la forma más robusta es incluir el [user.name](http://user.name/) original antes de cerrar:

```
user.name}}{{ 7*7 }}
```

La regla general que queda fijada: cuando se está dentro de una expresión preexistente y no se sabe cuánto hay después, siempre cerrar primero y abrir una nueva. Igual que en SQLI, cerrar la consulta antes de inyectar. La analogía es directa y deliberada.

**Escalada a RCE en Tornado — el import OS**

Una vez confirmado el cuarenta y nueve, la escalada a RCE en Tornado (Python) requiere importar el módulo os. Si se intenta usar os.system("whoami") sin importar primero, el motor da error de nombre no definido. La sintaxis completa en una sola expresión:

```
}}{% import os %}{{ os.system("whoami") }}
```

El {% import os %} usa la sintaxis de bloque de Tornado para importar el módulo, y el {{ os.system(...) }} usa la sintaxis de expresión para ejecutarlo y reflejar el output. Cuando el output aparece como Carlos 0, el cero es el código de retorno del comando, no un error: significa que se ejecutó con éxito. Con este vector ya disponible, el objetivo del laboratorio (borrar morale.txt) se resuelve sustituyendo whoami por rm /home/carlos/morale.txt, con el espacio codificado como + en el URL encoding.

**Máquina Casa Paco — metodología antes que vulnerabilidades**

La máquina Casa Paco de HackerLab es un restaurante ficticio con página web minimalista. Castillo la eligió expresamente por ser fácil, con el objetivo de demostrar que la metodología web correcta no depende de la complejidad de la vulnerabilidad.

El flujo completo de reconocimiento: netdiscover para encontrar la IP (192.168.0.184, identificada como PC Systemic en la red), ping con TTL 64 confirma Linux, nmap -p 22,80 --svc descubre SSH versión 9.2 y Apache 2.4.62 en Debian. El Nmap ya revela que hay un redirect hacia casapaco.thl, lo que obliga a añadir la entrada en /etc/hosts antes de poder acceder a la web. Lección: cuando hay virtual hosting y el Nmap no puede resolver el dominio, relanzarlo después de añadir la entrada en /etc/hosts puede revelar información adicional que antes no se capturaba.

En la web: Wappalizer no da nada relevante, control U muestra HTML puro sin comentarios útiles, el menú tiene directory listing activo (vulnerabilidad en sí misma, aunque no sea el vector principal), y la funcionalidad de "pedido para llevar" acepta dos campos: nombre y plato.

---

**Command Injection — el vector más simple**

Al interceptar la petición del pedido con Burp, la respuesta incluye literalmente el texto "salida del comando" antes del campo del plato. La máquina no intenta disimular lo que está haciendo. Cuando el campo plato recibe id, la respuesta devuelve el resultado de ejecutar id en el sistema: www-data.

Esto es command injection básico: el valor del parámetro se pasa directamente a una función de ejecución de comandos del sistema operativo sin sanitización. No hace falta SSTI, no hace falta path traversal, no hace falta ningún bypass. El campo acepta comandos del sistema.

Los caracteres que bloquea el filtro de la máquina: ls, pwd, cat y bash. El mensaje de bloqueo "no intente hackearme" enmascara los errores pero no impide la ejecución. Los comandos no bloqueados incluyen id, whoami (aunque con sintaxis diferente al id), y el acceso a /etc/passwd.

- **La idea clave:** el mensaje de error personalizado que dice "no intente hackearme" en lugar del error real de Python/Tornado no significa que la vulnerabilidad no exista. Significa que el desarrollador intentó ocultar la información de diagnóstico, pero si el campo ejecuta comandos, sigue ejecutando comandos aunque no lo anuncie

**El mensaje metodológico de Castillo al cierre de la semana**

La razón por la que eligió esta máquina no fue técnica sino pedagógica. La clase llevan semanas viendo SSRF, SSTI, path traversal con bypasses complejos, whitelist encoding doble. El riesgo es que al llegar a una máquina real, el cerebro busca automáticamente la vulnerabilidad más sofisticada y pasa por alto lo obvio.

La realidad del pentesting: el noventa y nueve por ciento de los hackeos reales en España no son vulnerabilidades técnicas avanzadas sino credenciales robadas, ingeniería social, o configuraciones absurdamente inseguras que nadie revisó. En máquinas de certificación, la vulnerabilidad que parece más fácil suele ser la correcta. La metodología que funciona es: revisar todo metódicamente, probar lo básico primero, no asumir que tiene que ser complejo, y no descartarse a uno mismo porque la solución parezca demasiado sencilla.
