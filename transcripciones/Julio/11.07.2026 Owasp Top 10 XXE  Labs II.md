OWASP Top 10 — XXE y Escalada de Privilegios Completa — Máquina Nike (HackerLab) II

Esta sesión la imparte Carlos Castillo, que retoma la máquina Nike donde la dejó Carlos Gómez la semana anterior. El tono es diferente al habitual: más pausado, con énfasis en el razonamiento progresivo y en hacer visible el proceso mental del auditor, no solo los comandos. La clase consolida el vector XXE desde la detección hasta la explotación completa, y recorre las cuatro escaladas de privilegios de la máquina: Java, Python con library hijacking, logrotate y DD. Conecta directamente con las sesiones anteriores de XXE, rbash bypass y movimientos laterales vistas con Carlos Gómez.

---

**Metodología antes de atacar — reconocimiento pasivo y activo**

Antes de lanzar herramientas, Castillo insistió en algo que se suele saltar: mirar la web como lo haría un auditor real antes de tocar nada. Con **web** se puede extraer tecnologías, emails y metadatos que luego pueden ser útiles en otras fases. En esta máquina no aparece nada valioso, pero la práctica importa: en aplicaciones grandes, un email visible en el código fuente puede ser el usuario que da acceso a todo.

El reconocimiento activo empieza con nmap -sCV para confirmar puertos 22 y 80, Apache en Debian (regla: Apache = Linux, IIS = Windows). El puerto 22 se descarta sin credenciales. Gobuster con los ajustes correctos para capturar errores 500 encuentra upload.php, datos.php y el directorio uploads.

- **La idea clave:** un código 500 en un fichero PHP es una señal de actividad en el backend, no un error que ignorar. Significa que el fichero existe, recibe la petición y algo dentro rompe cuando no obtiene lo que espera
 

---

**Confirmación de XXE — razonamiento paso a paso**

Se hizo especial énfasis en no ir directo al payload. La secuencia correcta es la siguiente.

Primero se envía cualquier dato al endpoint: el error start tag expected, not found confirma que el servidor espera un elemento con apertura de etiqueta, es decir, XML o HTML. El header Accept: application/xml en la petición original lo confirma.

Segundo paso: se envía un XML mínimo sin ningún payload malicioso. Si el servidor devuelve el cuerpo del XML en el response, la ejecución es **reflected**: el servidor ha parseado el contenido y lo ha devuelto. Eso significa que lo ha ejecutado en el backend.

Tercer paso: se declara una entidad XML apuntando a un fichero del sistema:

```

<?xml version="1.0" encoding="UTF-8"?>
<!DOCTYPE test [
 <¡ENTITY ent SYSTEM "file:///etc/passwd">
]>
<test><name>&ent;</name></test>
```

El servidor devuelve el contenido de /etc/passwd en el response. La vulnerabilidad es XXE into LFI.

- **La metáfora útil:** ir al grano es lanzar el payload final sin saber si el servidor lo acepta. El razonamiento correcto es apretar de menos a más: ¿llega al servidor? ¿Lo parsea? ¿Lo ejecuta? ¿Lo refleja? Solo cuando cada pregunta tiene respuesta afirmativa tiene sentido pasar al siguiente nivel
 

---

**LFI a través de XXE — qué más se puede leer**

Del /etc/passwd se extraen los usuarios con shell activa: mike, n, pilon, maci y root. La presencia de cuatro usuarios intermedios antes de root anticipa cuatro movimientos laterales.

Castillo amplió el alcance teórico del LFI: no solo /etc/passwd. Con acceso de lectura al sistema se puede intentar leer claves privadas SSH en /home/usuario/.ssh/id_rsa, el historial de comandos en .bash_history, o cualquier fichero de configuración conocido. En este caso, leer datos.php (que externamente da 500) via XXE es posible porque el usuario www-data sí tiene permisos de lectura dentro del servidor web, aunque el acceso externo falle.

Como datos.php contiene código PHP con caracteres < y >, leerlo directamente rompe el parser XML. La solución es el wrapper base64:

```
php://filter/convert.base64-encode/resource=/var/www/html/datos.php
```

El response devuelve una cadena en base64 que se decodifica en el Decoder de Burp. El fichero contiene usuarios y contraseñas. Hydra con estos diccionarios locales sobre SSH encuentra las credenciales de mike.

---

**Bypass de rbash**

Al conectarse como mike por SSH, la shell asignada es /bin/rbash, que impide cambiar de directorio, usar rutas con barra, redirigir salidas y ejecutar comandos con rutas absolutas. El bypass es trivial: SSH permite especificar la shell al conectarse, antes de que se cargue el perfil del usuario:

```
ssh mike@IP bash
```

Una vez dentro con bash, se estabiliza la terminal con export TERM=xterm para tener una shell funcional.

---

**Primera escalada: Java (mike â†’ n)**

sudo -l como mike muestra que puede ejecutar /usr/bin/java como el usuario n. GTFOBins confirma que Java permite spawnear una shell compilando un fichero .java con un ProcessBuilder que invoca la shell del sistema.

Puntos críticos que costaron tiempo en la sesión anterior y que Castillo repasó:

- El fichero .java debe compilarse antes de ejecutarse. javac [Shell.java](http://shell.java/) genera Shell.class, que es el ejecutable real.
 
- El nombre de la clase dentro del fichero debe coincidir exactamente con el nombre del fichero. Si la clase se llama Shell, el fichero debe llamarse [Shell.java](http://shell.java/) con S mayúscula.
 
- Todo debe hacerse en /tmp porque el directorio home de mike solo tiene permisos para el propietario, y n no puede acceder a él.
 

El comando final es sudo -u n /usr/bin/java Shell, ejecutado desde /tmp. Genera una shell como n.

---

**Segunda escalada: Python con library hijacking (n â†’ pilon)**

sudo -l como n muestra que puede ejecutar python3 /opt/[suma.py](http://suma.py/) como el usuario pilon. El fichero [suma.py](http://suma.py/) es propiedad de n, por lo que se puede modificar directamente. Se sobrescribe su contenido con:

```
import os
os.system("/bin/bash")
```

Al ejecutar sudo -u pilon python3 /opt/[suma.py](http://suma.py/), Python carga el script modificado y genera una bash con los privilegios de pilon.

La diferencia con la escalada anterior es importante: aquí no hace falta crear ningún fichero nuevo. El fichero ya existe, ya es el que debe ejecutarse, y el propietario es n, por lo que tiene permisos de escritura. La única operación necesaria es sobrescribir su contenido.

- **La idea clave:** cuando sudo -l obliga a ejecutar un script concreto y ese script es tuyo, no hace falta dar ninguna vuelta. Lo modificas y ya
 

---

**Tercera escalada: logrotate (pilon â†’ maci)**

sudo -l como pilon muestra que puede ejecutar logrotate como maci. logrotate es una herramienta de gestión de logs que rota, comprime y elimina ficheros de log según una configuración. La escalada explota que el parámetro -m permite especificar un script que se ejecuta después de cada rotación, y que ese script corre con los permisos del usuario que invoca logrotate.

La cadena de preparación requiere varios ficheros en /tmp:

- Un fichero de log vacío o con contenido arbitrario (el objetivo de la rotación).
 
- Un fichero de configuración .conf que apunta al log anterior, establece parámetros como size 0 y missingok, y en la directiva postrotate ejecuta el comando deseado: copiar /bin/bash a /tmp/macibash y darle el bit SUID con chmod u+s.
 

Una vez ejecutado sudo -u maci /usr/sbin/logrotate -m /tmp/[shell.sh](http://shell.sh/) /tmp/test.log /tmp/test.conf, la bash copiada tiene SUID de maci. Ejecutar /tmp/macibash -p da una shell como maci.

Castillo fue explícito sobre el nivel de esta escalada: es avanzada, poco habitual en entornos reales, y no merece la pena obsesionarse con ella. Lo valioso es entender el patrón general, no memorizar los parámetros de logrotate.

---

**Cuarta escalada: DD (maci â†’ root)**

sudo -l como maci muestra que puede ejecutar dd. dd es una herramienta de copia de bloques de datos que en GTFOBins aparece con capacidad de escalada de privilegios vía SUID. El mecanismo es similar al de logrotate: se usa la capacidad de escritura arbitraria de dd para modificar un fichero del sistema al que normalmente no se tendría acceso. La sesión se cerró antes de ejecutar esta parte por limitación de tiempo.
