Esta sesión la imparte Carlos Gómez y tiene una estructura diferente a las anteriores: arranca con la explicación teórica más completa del máster sobre la arquitectura de una aplicación web, usando una página vulnerable propia construida en directo como soporte visual. La segunda mitad resuelve la máquina Injected de HackerLab, que combina enumeración de directorios, credenciales hardcodeadas con hash MD5, RCE desde un panel de administración y escalada de privilegios via sudo -l con find. Conecta y cierra el ciclo de todo lo visto en el módulo web.

---

**Una página web es una carpeta expuesta en un servidor**

Este es el concepto central que vertebra toda la sesión. Carlos lo materializó creando en directo el proyecto ciberlab con la siguiente estructura:

```
/var/www/html/ciberlab/
â”œâ”€â”€ public/ â† raíz de la URL
â”‚ â”œâ”€â”€ index.php
â”‚ â”œâ”€â”€ assets/
â”‚ â”œâ”€â”€ includes/
â”‚ â””â”€â”€ uploads/
â””â”€â”€ data/ â† base de datos, nunca expuesta
 â””â”€â”€ db.sqlite
```

La clave del diseño está en que public y data están al mismo nivel jerárquico bajo ciberlab, pero el servidor Apache solo sirve public. Esto significa que desde la URL solo se puede navegar hacia adelante: assets, includes, uploads. Para llegar a data habría que subir un nivel de directorio, y eso únicamente es posible si existe una vulnerabilidad de path traversal.

Lo que el servidor expone no son pestañas ni secciones: son ficheros PHP. Cada URL diferente corresponde a un fichero diferente. La barra de navegación del front simplemente contiene enlaces a estos ficheros.

- **La idea clave:** lo que hace vulnerable a una aplicación web no es el servidor, ni el puerto, ni la base de datos, ni el front. Lo que es vulnerable son los ficheros PHP, que son lo que programan las personas, y donde pueden introducirse errores de validación
 

---

**Qué hay detrás de cada funcionalidad**

El front de la página no hace nada: es HTML y CSS, no tiene backend. Lo que parece un botón de "enviar" que no va a ningún lado es exactamente eso: cartón piedra. El único momento en que hay comunicación con el servidor es cuando se llama a un fichero PHP.

Las funcionalidades críticas de cualquier aplicación web tienen siempre un PHP detrás:

- **Login:** login.php hace una consulta SQL a la base de datos para verificar credenciales.
 
- **Trabaja con nosotros:** trabaja.php acepta un XML (candidatura) y lo procesa.
 
- **Subida de ficheros:** un PHP recibe el fichero y lo guarda en uploads/.
 

La vulnerabilidad siempre está en el PHP, no en sus dependencias. Si el PHP del login no filtra correctamente la entrada, es vulnerable a SQL Injection. Si el PHP de candidaturas no valida el XML, es vulnerable a XXE. Si el PHP de subida no comprueba la extensión, es vulnerable a file upload bypass.

- **La metáfora útil:** el programador es como el portero del banco. El cliente no ataca la caja fuerte directamente, ataca al portero. Si el portero (el PHP) no tiene instrucciones claras de qué no dejar pasar, cualquiera puede entrar
 

---

**XXE demostrado en la aplicación propia**

En trabaja.php hay un formulario que acepta una candidatura en XML. El código PHP usa libxml_load_string() sin deshabilitar las entidades externas, lo que habilita XXE. Al enviar un payload con una entidad que apunta a file:///etc/passwd, el servidor devuelve el contenido del fichero en la respuesta.

La función PHP que permite mitigar esto sin modificar la lógica de negocio es libxml_disable_entity_loader(true), que impide que el parser XML resuelva entidades externas. Sin esta línea, cualquier fichero al que tenga acceso el usuario www-data es legible desde el exterior.

---

**SQL Injection demostrado en la aplicación propia**

En login.php, la consulta SQL se construye concatenando directamente la entrada del usuario:

```
SELECT id, username FROM users WHERE username='$username' AND password='$password'
```

Si el campo de usuario recibe ' OR '1'='1' --, la query resultante ignora la contraseña y devuelve el primer usuario de la tabla, dando acceso sin credenciales válidas. La mitigación es usar prepared statements, que separan el código SQL de los datos y hacen imposible que la entrada del usuario modifique la estructura de la query.

**Máquina Injected — reconocimiento**

netdiscover encuentra la IP .12. Ping con TTL 64 confirma Linux. nmap -sCV descubre puertos 22 y 80. Apache 2.4 en Debian.

Dirsearch con extensiones PHP y HTML encuentra login.php. El diccionario por defecto no incluye la palabra backup, por lo que no aparece backup.php. Al añadir el diccionario directory-list-2.3-medium.txt, aparece backup.php.

backup.php devuelve el mensaje "Bounced directory, backup comprometido, acceso no autorizado detectado" y en el código fuente muestra una ruta credentials/ con un fichero HTML que contiene un hash. El hash solo usa caracteres de la a a la f y dígitos del 0 al 9: rango hexadecimal, que identifica MD5. CyberChef confirma MD5. El hash corresponde a la contraseña qwerty.

Login con admin / qwerty da acceso al panel de administración.

---

**RCE desde el panel y obtención de shell**

El panel tiene una funcionalidad de ejecución de comandos en el sistema. Al ejecutar whoami devuelve www-data. Al ejecutar cat /etc/passwd se identifican los usuarios con shell activa: root y nolen.

Sin contraseña para nolen, la opción es una reverse shell. Con un listener de Netcat en la máquina atacante y un payload de reverse shell en el campo de comandos, se obtiene una conexión. La shell obtenida es inestable, se estabiliza con el método Python TTY:

```
python3 -c 'import pty; pty.spawn("/bin/bash")'
```

---

**Escalada de privilegios — sudo con find**

sudo -l como nolen devuelve que puede ejecutar /usr/bin/find como cualquier usuario sin contraseña. GTFOBins para find bajo la técnica sudo muestra el payload de escalada:

```
sudo find . -exec /bin/sh \; -quit
```

Al ejecutarlo sin especificar usuario (es decir, como root), se spawnea una shell como root. El ID confirma que se ha escalado correctamente.

La distinción conceptual que se fijó: sudo -l da un permiso de ejecución delegado (cualquier usuario puede ejecutar ese binario como root si está en la lista). El SUID es un bit en el propio fichero que hace que cualquiera que lo ejecute lo haga como root, independientemente del sudo. Cuando el vector de escalada viene de sudo -l, se usa la técnica sudo en GTFOBins. Cuando viene de find / -perm -4000, se usa la técnica SUID.

- **La idea clave:** el mismo binario puede tener dos caminos de explotación distintos dependiendo de cómo se haya descubierto. sudo -l â†’ técnica sudo. find -perm -4000 â†’ técnica SUID. Son vectores diferentes aunque el binario sea el mismo
