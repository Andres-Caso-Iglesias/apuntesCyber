Esta sesión la imparte Carlos Castillo y tiene dos partes bien diferenciadas. La primera es una explicación conceptual densa sobre la diferencia entre fuerza bruta, password spraying y fuzzing, con especial atención a los rate limits y por qué el directory listing no es una fuerza bruta. La segunda es la resolución de la máquina "I Want to be a Web Star" de HackerLab, en la que el vector de escalada de privilegios es un script hijacking mediante una tarea programada (cronjob).

---

**Anatomía de una URL â€” repaso estructural**

Una URL tiene componentes diferenciados que conviene tener claros porque determinan qué técnica de ataque se aplica a cada parte. El protocolo (https://) indica la capa de transporte y su variante segura. El dominio incluye el TLD (.es, .com, .mx) que indica la procedencia. El directorio comienza con la primera barra (/admin, /wordpress). El interrogante introduce los parámetros, y dentro de cada parámetro la variable es la clave y el valor es lo que sigue al =. Cuando hay múltiples parámetros se separan con &, sin interrogante entre ellos.

Esta estructura es la base de todas las técnicas de enumeración web: directory listing itera sobre los directorios, fuzzing puede colocarse en cualquiera de las posiciones (directorio, parámetro, variable), y la fuerza bruta itera sobre el valor de una variable contra el mismo endpoint.

---

**Fuerza bruta, password spraying y directory listing â€” por qué son cosas distintas**

La distinción entre estas tres técnicas no es académica: tiene consecuencias directas sobre si el sistema objetivo levanta alertas o bloquea la IP.

Un **rate limit** siempre es un número de intentos dividido por una unidad de tiempo. El ejemplo habitual es tres intentos fallidos cada cinco minutos por usuario. Lo que activa el bloqueo es saturar ese ratio sobre el mismo endpoint.

Una **fuerza bruta** lanza múltiples valores contra el mismo endpoint (por ejemplo, el parámetro de contraseña en /wp-login.php para el usuario admin). Como cada intento golpea el mismo punto, el sistema detecta fácilmente el patrón y bloquea. Además, el espacio de búsqueda es exponencial: antes de llegar a contraseñas de catorce caracteres alfanuméricos hay que probar todas las combinaciones de uno, dos, tres... trece caracteres, lo que puede llevar de minutos a cientos de millones de años según la longitud y el juego de caracteres.

El **password spraying** invierte la lógica: se prueba una misma contraseña contra todos los usuarios del sistema, uno a uno, esperando entre intentos. Como cada usuario es un endpoint diferente, el ratio de intentos por endpoint es mínimo y no activa el rate limit. La razón por la que funciona en auditorías reales es que las personas usan contraseñas predecibles basadas en el nombre de la empresa o el año. En la demostración, con cuatro variaciones (nombre de empresa + año actual/anterior, con y sin signo de exclamación), se obtuvo acceso al veinticinco por ciento de los usuarios de un directorio activo real.

El **directory listing** no es fuerza bruta porque cada directorio que se prueba es un endpoint diferente. Lanzar peticiones a /admin, /uploads, /config, /dev son peticiones a cuatro endpoints distintos, no cuatro intentos sobre el mismo. Los sistemas no aplican rate limit por volumen de directorios probados porque el comportamiento normal de un navegador ya genera decenas de peticiones a rutas diferentes al cargar cualquier página.

- **La idea clave:** el rate limit se activa por intentos repetidos sobre el mismo punto, no por volumen total de peticiones. Cambiar de endpoint entre cada intento es el principio que hace que el directory listing y el password spraying no levanten alarmas mientras que la fuerza bruta clásica sí lo hace
 

---

**Fuzzing â€” la técnica más versátil**

El fuzzing es la generalización del directory listing. En lugar de simplemente iterar sobre rutas, permite colocar el payload en cualquier posición de la URL: subdominios, directorios, parámetros o valores de variables. Esto abre posibilidades que el directory listing estándar no cubre:

- Subdominios ocultos: [FUZZ.dominio.com](http://fuzz.dominio.com/)
 
- Directorios no incluidos en diccionarios estándar: dominio.com/FUZZ
 
- Parámetros ocultos en endpoints conocidos: dominio.com/api?FUZZ=valor
 
- Variables de parámetros conocidos: dominio.com/search?q=FUZZ
 

La herramienta de referencia es ffuf. Herramientas complementarias como x8 permiten específicamente la enumeración de parámetros ocultos, que es un vector que el directory listing convencional no cubre.

El diccionario recomendado para CTFs y certificaciones es rockyou.txt. Para directory listing, el estándar es directory-list-2.3-medium.txt de SecLists. SecLists es el repositorio de referencia para todos los diccionarios de enumeración web.

**Explotación â€” webshell a reverse shell**

La shell web encontrada en /dev permite ejecutar comandos en el servidor. Se verifica con whoami (resultado: www-data) y ls.

Se comprueba que el servidor tiene Python disponible (python -v) y NetCat instalado (ls /bin | grep nc). Con estos dos elementos se puede establecer una reverse shell. En [revshells.com](http://revshells.com/) se selecciona la opción Python con socket y subprocess, se sustituye la IP por la de la máquina atacante y el puerto por 4444.

```
nc -lvnp 4444
```

Al ejecutar el payload Python desde la webshell, Netcat recibe la conexión y se obtiene una shell interactiva como www-data.

---

**Escalada de privilegios â€” script hijacking por cronjob**

Con la shell obtenida se ejecuta sudo -l. El resultado indica que el usuario www-data puede ejecutar como el usuario scriptmanager sin contraseña:

```
sudo -u scriptmanager -i
```

Una vez como scriptmanager, se accede al directorio /scripts que contiene dos ficheros: [test.py](http://test.py/) (propiedad de scriptmanager) y test.txt (propiedad de root).

El contenido de [test.py](http://test.py/) abre test.txt en modo escritura y escribe el string "testing 123". La clave de la escalada está en que test.txt es propiedad de root, pero [test.py](http://test.py/) lo puede modificar porque quien ejecuta [test.py](http://test.py/) es root a través de un cronjob. Esto se confirma observando que la fecha de modificación de test.txt cambia periódicamente aunque nadie lo haya modificado manualmente.

El ataque consiste en modificar [test.py](http://test.py/) para que en lugar de escribir texto en test.txt, establezca una conexión reversa a la máquina atacante. Se coloca Netcat a la escucha en un nuevo puerto, se reemplaza el contenido de [test.py](http://test.py/) con un payload de reverse shell en bash, y cuando el cronjob ejecuta [test.py](http://test.py/) como root, la conexión llega con privilegios de root.

```
nc -lvnp 4440
```

Al ejecutarse el cronjob, se obtiene shell de root y se puede leer la flag final.

- **La idea clave:** cuando un fichero ejecutable es propiedad de un usuario con menos privilegios pero es ejecutado periódicamente por un proceso con más privilegios (un cronjob de root), modificar ese fichero es equivalente a ejecutar código como root. La vulnerabilidad no está en el sistema operativo sino en la configuración: un fichero que root ejecuta pero que otros usuarios pueden escribir
 
- **La metáfora útil:** es como dejar las llaves del coche en el bolsillo del abrigo que cuelga en el recibidor. El coche es de root, pero cualquiera que entre al recibidor puede coger las llaves

**Recapitulación integrada**

Esta sesión cierra el ciclo de metodología web básica conectando los conceptos de enumeración con la explotación real. El reconocimiento sistemático (dirsearch + inspección manual + Wappalyzer) llevó a descubrir una webshell en /dev, que permitió el compromiso inicial como www-data. La enumeración de sudo abrió el movimiento lateral a scriptmanager. El análisis de permisos en /scripts reveló el vector de escalada: un cronjob de root ejecuta un fichero que scriptmanager puede modificar. Reemplazar ese fichero con una reverse shell produce una shell de root. El patrón se repetirá en máquinas más complejas, con vectores de escalada más elaborados, pero la lógica es siempre la misma: encontrar qué ejecuta root que podamos controlar nosotros.
