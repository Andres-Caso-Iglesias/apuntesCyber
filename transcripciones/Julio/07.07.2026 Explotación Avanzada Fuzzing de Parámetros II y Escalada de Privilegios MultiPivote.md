**Repaso de la sesión anterior â€” fuzzing de parámetros y LFI**

La sesión arranca con un repaso estructurado. Cuando encontramos un fichero PHP en una enumeración de directorios, la pregunta correcta no es qué hace la página, sino qué parámetros acepta. Un fichero PHP interactúa con el backend, por lo que los parámetros que le enviamos pueden desencadenar comportamientos no documentados. Esta técnica no tiene sentido sobre ficheros HTML, que son puramente de presentación en el front y nunca llegan al servidor.

El proceso de la sesión anterior fue: enumerar directorios con dirsearch (con extensiones -x php,html,txt,py), encontrar index.php y db.php, construir un fuzzer en Python con Claude para detectar qué parámetros acepta index.php mediante peticiones POST, identificar el parámetro backdoor, pasarle el valor db.php y obtener credenciales: usuario shark con contraseña.

Adicionalmente, ese mismo parámetro era vulnerable a **path traversal**: en lugar de db.php, se puede pasar ../../../../etc/passwd, navegando hacia atrás en el árbol de directorios hasta la raíz y leyendo ficheros arbitrarios del sistema. Esto es un **Local File Inclusion** (LFI): el código PHP tiene una función file_open() o equivalente que acepta una variable de usuario sin sanitizar, permitiendo leer cualquier fichero al que tenga acceso el proceso web.

- **La idea clave:** el número de ../ no tiene límite superior efectivo. Una vez se supera la profundidad real del árbol, el sistema se queda en la raíz y no puede retroceder más. Por eso es práctica estándar poner nueve o más combinaciones ../: garantiza llegar a la raíz independientemente de dónde esté el fichero PHP

**Permisos en Linux â€” tabla de referencia**

Antes de entrar en la escalada, se hizo un repaso completo de permisos porque es imprescindible para entender cuándo un fichero es explotable.

El listado largo (ls -la) muestra cuatro bloques en cada entrada. El primer carácter indica el tipo: - para fichero, d para directorio, s para SUID, l para enlace simbólico. Los siguientes nueve caracteres son tres tríos de bits, siempre en el orden rwx, que representan los permisos de owner (propietario), group (grupo) y others (el resto).

Cada posición es un bit binario: r vale 4, w vale 2, x vale 1. La suma de los activos da el número octal de ese trío. Las ocho combinaciones posibles son:

- 0 = --- (ningún permiso)
 
- 1 = --x (solo ejecución)
 
- 2 = -w- (solo escritura)
 
- 3 = -wx (escritura y ejecución)
 
- 4 = r-- (solo lectura)
 
- 5 = r-x (lectura y ejecución)
 
- 6 = rw- (lectura y escritura)
 
- 7 = rwx (todos los permisos)
 

Cuando se llama a chmod 755 fichero, se están asignando permisos rwx al propietario, r-x al grupo y r-x al resto. El chmod 777 es una mala práctica de seguridad que da todos los permisos a todo el mundo.

- **La idea clave para escalada:** si un usuario tiene permiso de **escritura** sobre un fichero que puede **ejecutar suplantando a otro usuario** (via sudo -l), tiene escalada de privilegios garantizada. Escritura + ejecución delegada = control total del proceso que ejecuta ese fichero

**Obtención de shell SSH y primera enumeración**

Con las credenciales del usuario shark obtenidas via LFI, se establece una sesión SSH directa. SSH es la mejor shell posible en una auditoría: estabilizada, con soporte completo de terminal, sin los problemas de una reverse shell por webshell. Una buena práctica de persistencia es generar un par de claves RSA en la máquina víctima (ssh-keygen), guardar la privada localmente y usar la pública como authorized key para reconectar sin contraseña.

El primer comando al entrar siempre es whoami, el segundo pwd. A estos se añade uname -a, que muestra la versión exacta del kernel de Linux. Esta información es valiosa porque permite buscar CVEs de escalada de privilegios de kernel, que últimamente salen con mucha frecuencia. En este caso la máquina era reciente y parcheada, por lo que la vía de kernel no era aplicable.

Lectura del fichero /etc/passwd mediante el LFI reveló los usuarios con sesión bash activa: root, shark, vvbered, lusei, username3. La presencia de múltiples usuarios con shell indica un entorno de escalada en escalera, donde hay que pivotar de uno en uno antes de llegar a root.

**Primera escalada: modificación de ejecutable (shark â†’ vvbered)**

sudo -l como shark revela que puede ejecutar el binario /home/shark/bof suplantando a vvbered. El fichero bof es ejecutable compilado de 32 bits. Al hacer cat bof aparece contenido ilegible, porque está compilado a código máquina. Al ejecutarlo con ./bof responde "overflow me", sugiriendo un buffer overflow como vector previsto. Sin embargo, ese vector no es necesario.

La clave es más simple: shark es el propietario del fichero bof, por lo que tiene permiso de escritura. Si puede escribir sobre él y ejecutarlo suplantando a vvbered, puede reemplazar su contenido:

```
echo bash > bof
sudo -u vvbered ./bof
```

Al ejecutar bof como vvbered, el sistema llama a bash, que se ejecuta con el contexto de vvbered. La escalada es inmediata.

- **La idea clave:** no hace falta entender qué hace un ejecutable para explotarlo. Si puedes escribir sobre él y ejecutarlo bajo otro usuario, sustituye su contenido por bash y obtén la shell directamente

**Segunda escalada: fuerza bruta controlada con Hydra (vvbered â†’ lusei)**

En el directorio home de vvbered aparece un fichero [rubiales.zip](http://rubiales.zip/) propiedad de root. Como vvbered tiene permisos de lectura (columna others), se puede descomprimir, pero está protegido con contraseña. Se utiliza zip2john para extraer el hash del ZIP y se rompe con john --wordlist=/usr/share/wordlists/rockyou.txt hash. La contraseña obtenida es princess, que descomprime el ZIP y revela un fichero passwords.txt con trece contraseñas.

Cruzando este listado de contraseñas con el listado de usuarios extraído del /etc/passwd, se hace una fuerza bruta con Hydra sobre SSH:

```

```

Con solo cuatro usuarios y trece contraseñas, el espacio de búsqueda es cincuenta y dos combinaciones máximo. Hydra encuentra las credenciales de lusei en segundos. Esta es la única situación en la que la fuerza bruta está justificada: cuando el espacio de búsqueda es finito, conocido y pequeño.

Cuando username3 ejecuta [rubiales.py](http://rubiales.py/) via sudo -u username3 python3 [rubiales.py](http://rubiales.py/), Python busca la librería psutil siguiendo el PATH del usuario que invocó el comando (lusei), encuentra el fichero malicioso antes que la librería real, y ejecuta bash con los privilegios de username3.

- **La idea clave:** cuando un script importa una librería por nombre relativo (no ruta absoluta), es vulnerable a library hijacking. Si el atacante controla algún directorio que aparezca antes en el path de búsqueda, puede sustituir cualquier librería por código propio que se ejecutará con los privilegios del usuario que corre el script

**Cuarta escalada: modificación directa del script (username3 â†’ root)**

sudo -l como username3 muestra que puede ejecutar /usr/bin/sh como root. La shell sh es diferente a bash: es más primitiva, con comandos distintos. Para ejecutar código en ella se usa exec("comando"). Con exec("id") se confirma que somos root.

Alternativamente, Manu resolvió esta escalada por una vía diferente: como lusei tiene permisos de escritura sobre [rubiales.py](http://rubiales.py/), renombró el original (mv [rubiales.py](http://rubiales.py/) [a.py](http://a.py/)), creó uno nuevo llamado [rubiales.py](http://rubiales.py/) con import os; os.system("bash"), y al ejecutarlo via sudo -u username3 python3 [rubiales.py](http://rubiales.py/) obtuvo shell de username3 directamente, sin necesidad de library hijacking.

**Teoría: Path Traversal, LFI y RFI**

Al final de la clase se explicó el marco conceptual de estas tres vulnerabilidades encadenadas.

El **path traversal** es la capacidad de navegar fuera del directorio previsto usando secuencias ../. Cuando un parámetro acepta un nombre de fichero y no sanitiza estas secuencias, el atacante puede salir del directorio raíz de la aplicación y acceder a cualquier parte del sistema de ficheros.

El **Local File Inclusion** (LFI) es la consecuencia: el código lee o ejecuta un fichero local que no debería ser accesible desde la aplicación web. La mitigación correcta es usar rutas absolutas hardcodeadas en el código, no variables de usuario.

El **Remote File Inclusion** (RFI) es más peligroso y más raro: el parámetro vulnerable acepta una URL, y el servidor hace una petición HTTP a esa URL y ejecuta o incluye el resultado. Si el atacante controla un servidor remoto con una reverse shell, puede conseguir RCE completo sin necesidad de subir ningún fichero al servidor objetivo. La mitigación es no permitir que parámetros controlados por el usuario sean pasados a funciones de lectura de ficheros o URLs.
