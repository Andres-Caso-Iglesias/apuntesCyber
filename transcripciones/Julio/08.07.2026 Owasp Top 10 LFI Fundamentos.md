**Escalada de privilegios — mapa mental consolidado**

Antes de entrar en la máquina, Carlos fijó el esquema mental que debe aplicarse automáticamente al obtener acceso a una máquina Linux. Los comandos que se lanzan siempre, en este orden:

- whoami — quién soy
 
- pwd — dónde estoy
 
- uname -a — versión del kernel (buscar CVEs de privilege escalation)
 
- sudo -l — qué puedo ejecutar como otro usuario (sudoers)
 
- find / -perm -4000 -type f 2>/dev/null — ficheros con bit SUID
 

Si sudo -l devuelve algo y el fichero tiene permiso de escritura para el usuario actual, hay escalada. Si sudo -l no da nada útil, se analiza el listado de SUIDs contra GTFOBins.

La diferencia crítica entre sudoer y SUID, que es el concepto más importante de esta clase:

- **Sudoer (sudo -l):** yo, como usuario concreto, tengo permiso para ejecutar un fichero específico suplantando a otro usuario. Solo yo puedo hacerlo, y solo ese fichero.
 
- **SUID (bit s):** cuando cualquier usuario ejecuta ese fichero, se ejecuta como root, independientemente de quién lo invoque. No es un permiso del usuario, es un atributo del fichero.
 
- **La metáfora útil:** el sudoer es tener una llave de la casa de alguien. El SUID es que la puerta se abre sola para cualquiera que llegue.

**Path Traversal y LFI — repaso conceptual con demostración**

Se consolidó el concepto con una demostración en bash. Un script Python o PHP que hace open(fichero) siendo fichero una variable de usuario es vulnerable si no sanitiza las secuencias ../. El atacante puede navegar hacia atrás en el árbol de directorios añadiendo tantos ../ como quiera: una vez alcanzada la raíz, el sistema no puede retroceder más, por lo que poner nueve o más secuencias garantiza llegar a / sin errores.

```
../../../../../../../../../../../etc/passwd
```

Esto no es un RCE porque no se ejecuta ningún comando: es simplemente una función de lectura de fichero a la que se le pasa una ruta que escapa del directorio previsto.

El LFI (Local File Inclusion) es la consecuencia: se puede leer cualquier fichero del sistema al que tenga acceso el proceso web. Los ficheros que siempre se leen cuando se detecta un LFI son /etc/passwd (usuarios con bash activo), config.php (credenciales de base de datos), php.ini y phpMyAdmin (configuración del servidor PHP). El RFI (Remote File Inclusion) es la variante más peligrosa: el parámetro acepta una URL externa, y el servidor hace la petición y ejecuta el contenido, lo que permite inyectar una reverse shell desde un servidor controlado por el atacante.

- **La idea clave:** la vulnerabilidad no está en el LFI en sí sino en la falta de validación del parámetro. La mitigación correcta es usar rutas absolutas hardcodeadas, no variables de usuario como argumento de funciones de lectura de ficheros

**Máquina Banco — reconocimiento inicial**

La máquina Banco (HackerLab) expone los puertos 22 (SSH) y 80 (HTTP Apache 2.4.66 en Debian). Se descartó el puerto 22 por ausencia de credenciales. Al acceder al puerto 80 aparece un panel de login.

El primer paso antes de intentar ningún ataque es revisar el código fuente de la página (Ctrl+U). En este caso, el código fuente tenía hardcodeada la contraseña de acceso al panel en texto claro, junto con la referencia al fichero descargar.php. Este hallazgo ilustra uno de los errores más comunes en desarrollo web: dejar credenciales en el frontend porque "solo lo ve el código fuente".

Con las credenciales obtenidas del código fuente se accede al panel autenticado. En el panel hay un botón de descarga de un PDF. Interceptando esa petición con Burp Suite se observa que hace un POST a descargar.php con el parámetro archivo=sobre_nosotros.pdf.

Adicionalmente, el propio código fuente de descargar.php (obtenido vía LFI) contenía un comentario de desarrollo que decía literalmente "Punto crítico de vulnerabilidad LFI — concatenamos directamente la entrada del usuario a la ruta, un atacante puede usar path traversal".

**Explotación — path traversal y LFI**

Con el parámetro archivo identificado como vector, se aplica path traversal en el Repeater de Burp:

```
archivo=../../../../../../../../etc/passwd
```

El servidor devuelve el contenido de /etc/passwd. Del listado de usuarios con /bin/bash, se identifican los que tienen sesión activa: root y vvbered.

A continuación se lee config.php via LFI:

```
archivo=../../../../../../../../var/www/html/config.php
```

El fichero de configuración expone las credenciales de la base de datos: usuario vvbered con su contraseña, usuario admin con la suya, y usuario root de MySQL. Como el usuario de sistema identificado en /etc/passwd también se llama vvbered, se prueba la misma contraseña para SSH y funciona: la reutilización de credenciales entre el servicio de base de datos y la cuenta del sistema permite el acceso.

**Desglose de una petición HTTP en Burp Suite**

Con la petición interceptada en el Repeater, se hizo un recorrido completo línea a línea. En el **request**:

La primera línea indica el método HTTP (POST), la ruta del recurso (/descargar) y la versión del protocolo HTTP (1.1). El **host** es la IP o dominio del servidor. El **User-Agent** identifica el navegador y sistema operativo del cliente, y es el parámetro que usan muchos anti-bots y páginas de phishing para filtrar peticiones (si no es Android, no muestran el contenido). El **Accept** lista los formatos de respuesta que acepta el cliente, incluyendo application/xml, lo que es relevante para ataques XXE. El **Content-Type** especifica el formato del body del POST; en este caso application/x-www-form-urlencoded indica que los parámetros van en formato de formulario web. El **Content-Length** es el tamaño en bytes del body, y muchos WAFs lo usan para filtrar payloads anómalos. El **Origin** indica el dominio desde el que se origina la petición, y algunas aplicaciones solo aceptan peticiones desde [localhost](http://localhost/). El **Referer** indica desde qué URL viene la petición.

En el **response**: el código de estado (200 OK), la fecha, la versión del servidor (que es la que usa Nmap para banner grabbing), y el Content-Length de la respuesta (útil para detectar si un ataque de fuerza bruta ha tenido éxito por diferencia de tamaño de respuesta).

- **La idea clave:** los headers HTTP no son decoración. Cada campo puede ser tanto un vector de información para el atacante como un vector de ataque en sí mismo (User-Agent falso, Origin manipulado, Content-Type para bypass de filtros)

**Escalada de privilegios — SUID, LSATTR y CHATTR**

Con acceso como vvbered, el flujo estándar:

sudo -l devuelve error: el usuario no tiene permisos de sudo. Se lanza el find de SUIDs:

```
find / -perm -4000 -type f 2>/dev/null
```

El listado devuelve comandos habituales (sudo, su, mount, passwd) más dos inusuales: lsattr y chattr. Inusuales porque son comandos de gestión de atributos de ficheros, que normalmente no necesitan SUID. Se buscan en GTFOBins: ambos aparecen bajo "privilege escalation" con la técnica SUID.

lsattr lista los atributos extendidos de ficheros. El atributo i (immutable) hace que un fichero no pueda ser modificado, borrado, renombrado ni enlazado, ni siquiera por root, mientras esté activo. chattr -i fichero elimina ese atributo.

Se lanza lsattr -R / 2>/dev/null (o el equivalente con find) para encontrar el único fichero inmutable del sistema: /usr/local/bin/[backup.sh](http://backup.sh/), propiedad de root con permisos rwxrwxrwx para others. La lógica es: si hay un SUID en chattr, en esta máquina hay algo inmutable que no debería poder tocarse normalmente. Hay que buscarlo.

Se quita la inmutabilidad con:

```
chattr -i /usr/local/bin/backup.sh
```

Se modifica el fichero con echo "/bin/bash" > /usr/local/bin/[backup.sh](http://backup.sh/), se le da el bit SUID con chmod +s /bin/bash, y se espera a que el cronjob de root ejecute el script. Cuando se ejecuta, el bin/bash se lanza como root. Accediendo con /bin/bash -p se obtiene shell de root.

- **La idea clave:** la escalada no es ejecutar el fichero uno mismo, sino dejar preparado el payload y esperar a que root lo ejecute a través de una tarea programada. El atacante no necesita ejecutar nada como root: basta con que root lo haga por él, sin saberlo

**Recapitulación integrada**

Esta sesión cierra el ciclo de la máquina Banco y consolida tres vectores encadenados: path traversal habilitó el LFI, el LFI permitió leer config.php con credenciales, las credenciales dieron acceso SSH, y la misconfiguration del SUID en chattr + la tarea programada de root completaron la escalada. El esquema mental de los cinco comandos iniciales (whoami, pwd, uname -a, sudo -l, find SUID) es el procedimiento estándar que se aplicará en todas las máquinas a partir de ahora. La distinción sudoer vs SUID, y la comprensión de que la escalada via cronjob no requiere ejecutar nada directamente como root, son los dos conceptos que quedan abiertos para el módulo de escalada de privilegios de septiembre.
