La particularidad de esta sesión es que Chema, un alumno, lleva el peso de la explotación guiado por Carlos, lo que convierte la clase en un ejercicio de metodología razonada en voz alta. Se consolidan conceptos clave: la diferencia entre webs nativas y CMS, la cadena de dependencias de plugins, el uso de WPScan con y sin API, la lógica del file upload como vector de ataque, y la diferencia operativa entre bind shell y reverse shell.

**Webs nativas vs CMS y la cadena de dependencias**

Antes de tocar herramientas, Carlos establece una distinción que cambia cómo se audita una web. Una web nativa (PHP, .NET, Java, Go) se audita directamente sobre su código y configuración. Un CMS como WordPress funciona como un motor con tres capas independientes: el propio WordPress (motor), el tema o plantilla (carcasa visual), y los plugins (accesorios funcionales). Cada capa puede tener vulnerabilidades propias, pero la distribución real del riesgo es claramente asimétrica: el núcleo de WordPress rara vez tiene vulnerabilidades explotables sin autenticación previa, mientras que los plugins, desarrollados mayoritariamente por comunidades sin revisión de seguridad formal, concentran la inmensa mayoría de los vectores de ataque.

La cadena va más lejos: cada plugin tiene librerías, cada librería tiene dependencias de segundo nivel, cada dependencia tiene componentes de tercer nivel. Cualquier eslabón de esa cadena puede ser vulnerable. Esto conecta directamente con lo explicado en la sesión de OWASP Top 10 sobre la categoría de fallos en la cadena de suministro, que ahora cobra un sentido práctico concreto.

- **La idea clave:** tener un plugin vulnerable instalado no implica necesariamente estar expuesto a esa vulnerabilidad. Si la función de código afectada no está accesible desde ningún endpoint de la web, el vector no es explotable. La auditoría web consiste en determinar no solo qué vulnerabilidades existen, sino cuáles son alcanzables desde el exterior
 
- **La metáfora útil:** el WordPress es un coche. El tema es la carrocería, los plugins son los accesorios. Una rueda que explota en el monte no representa ningún riesgo si el coche solo circula por autopista

**Enumeración web â€” la importancia del contexto de ruta**

El primer paso práctico es el reconocimiento. Net-Discover localiza la máquina en la red, Nmap revela puertos 22 y 80, y el navegador muestra un Apache. Se lanza DirSearch sobre la raíz y aparece el directorio /wordpress, que confirma la presencia de un CMS.

Aquí Carlos introduce un concepto que causará errores concretos en exámenes si no se interioriza: el hecho de que una web tenga WordPress en un subdirectorio no convierte toda la web en WordPress. Una misma instalación de Apache puede alojar simultáneamente un WordPress en /wordpress, un Drupal en /drupal y una aplicación PHP nativa en la raíz. Lanzar WPScan contra la raíz en lugar de contra /wordpress producirá resultados incorrectos o nulos, exactamente igual que lanzar un exploit contra una tecnología en la ruta equivocada.

La segunda lección de enumeración es el escaneo recursivo. DirSearch con -r lanza automáticamente un nuevo escaneo sobre cada directorio encontrado, descubriendo así /wp-content/uploads que no aparecería en un escaneo de primer nivel sobre la raíz. La regla general: siempre -r en DirSearch, igual que siempre -sV en Nmap.

```
dirsearch -u http://academy.thl/wordpress -r -w /usr/share/wordlists/dirb/common.txt
```

**WPScan â€” enumeración del ecosistema WordPress**

WPScan es la herramienta específica para auditar WordPress. Sin API key, detecta la versión de WordPress, el tema y lista plugins, pero no indica si tienen vulnerabilidades conocidas. Con API key (gratuita, registro en [wpscan.com](http://wpscan.com/)), consulta su base de datos de CVEs y muestra las vulnerabilidades asociadas a cada componente detectado.

La secuencia de análisis sigue la misma lógica de capas que se describió antes:

Apache 2.4.59: sin vulnerabilidades explotables sin autenticación. WordPress 6.5.3: cinco CVEs detectados con API, todos requieren rol de contributor o superior para ser explotados. Sin acceso autenticado previo, se descartan. Tema Twenty Twenty-Four: sin vulnerabilidades. Plugins: ninguno detectado sin API. Con API, se detectan plugins con CVEs, pero todos requieren roles que aún no tenemos.

La conclusión del análisis de vulnerabilidades en componentes es que en este momento no hay ningún vector de ataque explotable desde el exterior sin credenciales. La auditoría se desplaza hacia el vector de autenticación.

```
wpscan --url http://academy.thl/wordpress --enumerate ap --api-token TU_TOKEN
```

**Enumeración de usuarios y fuerza bruta con WPScan**

El panel de login de WordPress expone información sensible: si el usuario no existe dice exactamente "el nombre de usuario no está registrado en este sitio", mientras que si existe pero la contraseña es incorrecta, el mensaje cambia. Este information disclosure permite enumerar usuarios válidos antes de hacer fuerza bruta, reduciendo el espacio de búsqueda de bidimensional (usuario Ã— contraseña) a lineal (solo contraseña sobre usuario conocido).

WPScan tiene funcionalidad nativa para esto. El parámetro --enumerate u lanza enumeración de usuarios. Para la fuerza bruta, se usa el diccionario RockYou, que es el estándar en CTFs y certificaciones:

```
wpscan --url http://academy.thl/wordpress --enumerate u
wpscan --url http://academy.thl/wordpress --passwords /usr/share/wordlists/rockyou.txt
```

La fuerza bruta es el último recurso, no el primero. Antes de lanzarla siempre se intenta agotar otras vías: enumeración pasiva, OSINT, ingeniería social, credenciales por defecto, reutilización. Una fuerza bruta sobre un servicio en producción puede generar bloqueos de IP, alertas en el SIEM del cliente y, en el peor caso, una denegación de servicio no deseada.

En la demostración, WPScan encuentra el usuario dylan con la contraseña password1, confirmando el acceso al panel de administración.

**File Upload como vector de RCE â€” los dos requisitos**

Con acceso autenticado al panel de WordPress, se activa la vulnerabilidad que Carlos ya había introducido teóricamente en sesiones anteriores. La explotación por file upload requiere exactamente dos condiciones que deben cumplirse simultáneamente:

La primera es tener una vía de subida de ficheros que deposite el contenido en un directorio accesible por URL. En este caso, el plugin WP File Manager o el editor de temas de WordPress sirven como vía de subida. El directorio /wp-content/uploads es el destino natural.

La segunda es poder ejecutar ese fichero accediendo a él por navegador. Si el directorio es accesible y el servidor tiene PHP habilitado, navegar a [http://academy.thl/wordpress/wp-content/uploads/shell.php](http://academy.thl/wordpress/wp-content/uploads/shell.php) ejecuta el código PHP del fichero.

Si alguna de las dos condiciones falla (no se puede subir, o el directorio no es accesible por URL, o el servidor no interpreta PHP en esa ruta), el ataque no funciona aunque la otra condición se cumpla.

Las webshells PHP están disponibles por defecto en Kali en /usr/share/webshells/php/. Para este tipo de ataque se usa la reverse shell en lugar de una bind shell porque el objetivo es que el servidor se conecte al atacante, no al revés, lo que habitualmente bypasea las reglas de firewall que bloquean conexiones entrantes al servidor pero no las salientes.

---

**Configuración y ejecución de la reverse shell**

Antes de ejecutar la shell, hay que modificar dos parámetros en el fichero /usr/share/webshells/php/php-reverse-shell.php: la IP del atacante (la IP de la Kali, obtenida con ifconfig) y el puerto de escucha. Luego hay que poner Netcat a escuchar en ese puerto antes de navegar a la URL que ejecuta el fichero:

```
nc -lvnp 1234
```

Al acceder por navegador al fichero PHP subido, el servidor ejecuta el código, que establece una conexión TCP saliente hacia la IP y puerto especificados. En el listener de Netcat llega la shell como usuario www-data.

El cambio de HTTP a TCP en el tráfico capturado con Wireshark marca el momento exacto en que se abandona el contexto web y se pasa a la terminal directa. A partir de ese punto, el WAF ya no intercepta nada: el WAF opera sobre HTTP y la comunicación ahora es TCP puro.

La segunda vía disponible, útil cuando no hay un uploadder accesible, es el editor de temas de WordPress en Apariencia â†’ Editor. Modificar la plantilla 404.php para insertar código PHP consigue el mismo efecto: navegar a cualquier URL inexistente del WordPress ejecuta la plantilla modificada.

- **La idea clave:** la diferencia entre una bind shell y una reverse shell no es técnica sino de dirección de la conexión. En la bind shell, el atacante se conecta al servidor (requiere que el puerto esté abierto hacia el exterior). En la reverse shell, el servidor se conecta al atacante (solo requiere que el servidor pueda hacer conexiones salientes, lo cual casi siempre está permitido). En entornos con firewall restrictivo, la reverse shell es el camino habitual

**Regla general sobre tecnologías web y extensiones de fichero**

La clase deja establecida una correlación que hay que memorizar para cualquier auditoría: Apache en Linux implica PHP. IIS en Windows implica [ASP.NET](http://asp.net/) (.aspx). Subir una reverse shell en el lenguaje equivocado (una shell .aspx en un servidor Apache/PHP) produce un fichero inerte que el servidor no interpreta. Identificar el stack tecnológico antes de elegir el tipo de payload es un prerequisito, no un detalle.
