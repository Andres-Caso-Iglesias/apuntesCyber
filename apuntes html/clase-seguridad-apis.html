        01Qué es una API y cómo se comunica

        Una API es el contrato por el que dos programas se hablan sin conocerse por dentro. Uno pide algo concreto, el otro responde con datos o con un error. Nada más, y nada menos.

        La idea en una frase

        API son las siglas de Application Programming Interface, interfaz de programación de aplicaciones. Es un conjunto de reglas que define qué puede pedir un programa a otro, con qué formato y qué va a recibir a cambio. La palabra importante es interfaz: una frontera pública detrás de la cual se esconde la implementación.

        La analogía habitual es la carta de un restaurante. La carta lista lo que puedes pedir y a qué precio. Tú no entras en la cocina ni necesitas saber cómo se prepara cada plato: haces tu comanda con el lenguaje de la carta y la cocina te devuelve el plato. Si mañana cambian de proveedor o de receta, la carta puede seguir igual. La API es esa carta entre programas.

        Cliente y servidor

        Casi toda API web sigue el modelo cliente-servidor:

        • El cliente es quien inicia la conversación: una app de móvil, una página web en el navegador, otro servidor, un dispositivo IoT, un script.
        • El servidor (o backend) es quien tiene los datos y la lógica de negocio. Escucha peticiones, decide si quien pide tiene permiso, hace el trabajo y responde.

        El cliente no guarda la base de datos ni las reglas de negocio. Solo sabe qué endpoints existen y qué enviar. Esto tiene una consecuencia de seguridad que repetiremos toda la clase: el cliente no es de fiar. Cualquiera puede abrir las herramientas de desarrollo del navegador, interceptar el tráfico de su móvil o escribir su propio cliente y enviar exactamente lo que quiera.

        Cómo funciona una llamada, paso a paso

        1. El cliente construye una petición: un método (por ejemplo GET), una URL de endpoint, unas cabeceras (entre ellas la de autenticación) y, si procede, un cuerpo con datos.
        2. La petición viaja por la red, normalmente sobre HTTPS, hasta el servidor.
        3. El servidor autentica (quién eres) y autoriza (qué puedes hacer), valida la entrada y ejecuta la lógica: consulta la base de datos, llama a otros servicios, calcula.
        4. El servidor devuelve una respuesta: un código de estado (200, 404, 500), cabeceras y un cuerpo, casi siempre en JSON.
        5. El cliente interpreta la respuesta y actualiza la pantalla o continúa su flujo.

        Para qué se usan

        Las APIs son el tejido conectivo del software actual. Algunos usos concretos:

        • Separar frontend y backend. La web y la app de móvil son solo pantallas; toda la lógica vive detrás de una API.
        • Integrar servicios de terceros. Pagos (Stripe, Redsys), mapas, envío de SMS y correo, identidad (Google, Microsoft), IA.
        • Automatizar. Scripts e integraciones que crean recursos, exportan datos o disparan procesos sin intervención humana.
        • Conectar sistemas internos. En una arquitectura de microservicios, cada servicio expone una API y los demás la consumen.
        • Abrir un ecosistema. Una plataforma publica su API para que otros construyan encima (extensiones, apps, integraciones).

        Nota

        API es un término amplio. Hay APIs de sistema operativo, APIs de librerías y APIs de red. En esta clase, salvo que se diga otra cosa, hablamos de APIs web: las que se consumen por HTTP y sirven a aplicaciones web y móviles.

        Ejemplos cotidianos

        • Abres una app del tiempo. La app llama a GET /forecast?lat=40.4&lon=-3.7 y pinta la respuesta.
        • Pagas con el móvil. La app de la tienda llama a la API de la pasarela de pago, que a su vez llama a la del banco.
        • Inicias sesión con Google en una web. Esa web usa la API de identidad de Google por debajo.
        • Publicas una foto. La app sube el archivo con POST /media y luego crea la publicación con POST /posts.

        02La API troncal en web y móvil

        Web, iOS y Android suelen ser tres carcasas distintas sobre la misma API. Esa API troncal concentra los datos y las reglas, y por eso concentra también el riesgo.

        Qué es una API troncal

        Se llama API troncal (o backbone, o core API) a la API central que sirve a todos los clientes de un producto. En vez de programar la lógica de negocio tres veces, una para la web y una por cada plataforma móvil, se implementa una sola vez en el servidor y los tres clientes la consumen.

        Ventajas para quien construye el producto:

        • Una sola fuente de verdad. Las reglas de precios, permisos o validación viven en un único sitio.
        • Coherencia. Web y móvil enseñan lo mismo porque preguntan a lo mismo.
        • Evolución más barata. Un cambio de negocio se hace en el backend y llega a todos los clientes.

        Por qué concentra el riesgo

        • Un solo punto que proteger y un solo punto que fallar. Un control de autorización que falta en la troncal deja expuestos a todos los clientes.
        • La app móvil es pública. El binario de una app se puede descompilar. Las URLs de los endpoints, las claves incrustadas y los formatos de datos quedan a la vista de cualquiera que se lo proponga.
        • El cliente no aplica la seguridad, solo la muestra. Que la app oculte un botón no impide llamar al endpoint que hay detrás. La comprobación tiene que estar en la troncal.
        • Endpoints "internos" que no lo son. Funciones pensadas para el panel de administración acaban accesibles desde la misma API que usan los clientes normales.

        Aviso

        No metas secretos en una app móvil. Cualquier clave, token o URL "oculta" dentro del binario se puede extraer. Los secretos viven en el servidor.

        Por estilo o protocolo:

        Por quién puede consumirla:

        • Pública o abierta. Cualquiera puede registrarse y usarla, con o sin clave.
        • De socios. Solo para empresas con un acuerdo. Acceso controlado y con contrato.
        • Privada o interna. Solo para los sistemas y equipos de la propia organización. Ojo: "interna" describe la intención, no siempre la exposición real en la red.

        Y una distinción de contexto que conviene no mezclar: API de sistema operativo (llamadas del sistema, SDK de Android o iOS, acceso a cámara o ubicación) frente a API web (HTTP entre cliente y servidor). En esta clase el foco está en las segundas.

        API polimórfica

        Se habla de API polimórfica cuando un mismo endpoint cambia de comportamiento, de forma de la respuesta o de campos según un parámetro, el tipo de cliente, el rol del usuario o una cabecera. Ejemplos:

        • GET /me devuelve un objeto con más o menos campos según si quien pregunta es usuario normal o administrador.
        • POST /search acepta un cuerpo cuya estructura varía: a veces un texto, a veces un objeto con filtros complejos.
        • El mismo endpoint responde HTML, JSON o CSV según la cabecera Accept.

        El polimorfismo es cómodo, pero pasa factura en seguridad:

        • Superficie difícil de razonar. Si un endpoint hace muchas cosas, es fácil que una de esas ramas se quede sin comprobación de autorización.
        • Validación inconsistente. Cada forma del cuerpo necesita su propio esquema; alguna se olvida.
        • Filtrado de datos frágil. "Devuelve todo y que el cliente decida qué campos enseña" es justo el patrón de la vulnerabilidad API3, exposición excesiva de datos.
        • Escalada por parámetro. Si añadir ?view=admin o role=admin cambia lo que devuelve, hay que autorizar esa rama, no solo aceptarla.

        Nota

        Regla práctica con endpoints polimórficos: cada variante de entrada necesita su propio esquema de validación y cada variante de salida necesita su propia comprobación de "quién puede ver esto".

        03Endpoints, llamadas y formatos

        Para atacar o defender una API hay que leer con soltura una petición HTTP: la ruta, el método, las cabeceras, el cuerpo y el código de estado que vuelve.

        Qué es un endpoint

        Un endpoint es una dirección concreta de la API que representa una operación sobre un recurso. Anatomía de una URL de endpoint:

        • Host: el servidor de la API. A menudo un subdominio api..
        • Versión: /v1, /v2. Permite cambiar la API sin romper a los clientes antiguos.
        • Recurso y colección: /pedidos es la colección, /pedidos/42 es un elemento.
        • Identificador: el 42. Si es un número correlativo y predecible, invita a probar el 43. Aquí nace la vulnerabilidad API1.
        • Parámetros de consulta: filtros, paginación, orden. También son entrada de usuario y hay que validarlos.

        Llamadas: métodos HTTP

        MétodoIntenciónCambia datos
        GETLeer un recurso o una lista.No
        POSTCrear un recurso o disparar una acción.Sí
        PUTReemplazar un recurso entero.Sí
        PATCHModificar algunos campos de un recurso.Sí
        DELETEBorrar un recurso.Sí

        Un patrón de ataque clásico es cambiar el método sobre una ruta que sí puedes leer: si GET /admin/usuarios te responde, prueba DELETE /admin/usuarios/5. Si el control de acceso solo cubría el GET, tienes un problema. Esto es API5.

        Cabeceras

        Las cabeceras son metadatos de la petición y de la respuesta. Las que más importan en seguridad:

        • Authorization: lleva las credenciales. Casi siempre Bearer <token>.
        • Content-Type: en qué formato va el cuerpo (application/json, multipart/form-data).
        • Accept: en qué formato quiere el cliente la respuesta.
        • Cookie: sesión, cuando la API usa cookies en vez de token.
        • X-Forwarded-For, User-Agent, cabeceras X- a medida: útiles, pero nunca de fiar como control de seguridad.

        Autenticación: cómo se prueba quién eres

        MecanismoCómo viajaNotas
        BasicAuthorization: Basic base64(user:pass)Base64 no es cifrado. Solo aceptable sobre HTTPS y a ser posible ni así.
        API keyCabecera o parámetro con una clave fijaIdentifica a una aplicación o proyecto, no a un usuario. No sirve como autenticación de personas.
        Bearer / JWTAuthorization: Bearer eyJ...Token firmado con datos del usuario y una caducidad. Hay que validar firma y expiración en cada petición.
        OAuth 2.0Flujo que termina entregando un token de accesoEs un marco de autorización delegada, no de autenticación por sí solo.
        mTLSCertificado de cliente en el propio TLSHabitual entre servicios y en entornos B2B regulados.

        Aviso

        Autenticar (quién eres) no es autorizar (qué puedes hacer). La mayoría de fallos graves de APIs son de autorización: el token es válido, pero se usa para acceder a datos u operaciones que no corresponden a ese usuario.

        Formatos de datos

        • JSON: el formato por defecto de las APIs web. Legible y compacto.
        • XML: en SOAP y sistemas heredados. Su parser mal configurado abre la puerta a ataques XXE.
        • form-urlencoded: campo=valor&otro=valor. Formularios web clásicos.
        • multipart/form-data: subida de archivos. Cuidado con tamaño, tipo real y nombre del archivo.
        • Protobuf: binario, en gRPC. Eficiente, no legible a simple vista.

        Códigos de estado que hay que reconocer

        CódigoSignificaLectura para seguridad
        200 / 201Todo bien. Creado, en el 201.Si una petición manipulada devuelve 200, mira qué te devolvió.
        301 / 302Redirección.Redirecciones abiertas y saltos de HTTPS a HTTP.
        400Petición mal formada.La validación de entrada rechazó algo. Bien.
        401No autenticado.Falta credencial o es inválida.
        403Autenticado pero sin permiso.El control de autorización funcionó.
        404No existe.A veces se usa en vez de 403 para no revelar que el recurso existe.
        429Demasiadas peticiones.Hay límite de tasa. Su ausencia es la vulnerabilidad API4.
        500Error del servidor.Si trae traza de pila o detalles internos, es fuga de información (API7).

        04Superficie de ataque y principales peligros

        Una API publica de forma explícita lo que una web tradicional escondía entre páginas. Esa transparencia es cómoda para integrarse y cómoda para atacar.

        Por qué las APIs son hoy el objetivo

        • Exponen lógica y datos directamente. Detrás de GET /clientes/42 hay datos personales sin la capa de presentación que los envolvía en una web.
        • Están documentadas. La misma documentación que ayuda a un integrador legítimo ayuda a quien busca fallos.
        • Son predecibles. Si existe /v1/pedidos, probablemente exista /v1/facturas. Si el id es 42, existe el 41.
        • El cliente es inspeccionable. Herramientas de desarrollo del navegador, un proxy como Burp o mitmproxy, o descompilar la app: todo el "contrato" queda a la vista.
        • Automatización trivial. Un bucle de veinte líneas recorre miles de identificadores en minutos.

        Superficie de ataque de una API

        Todo lo que un cliente puede tocar es superficie:

        • Cada endpoint y cada método sobre ese endpoint.
        • Cada parámetro: de ruta, de consulta, del cuerpo, y cada cabecera que el servidor lea.
        • Los flujos de autenticación: registro, inicio de sesión, recuperación de contraseña, refresco de token, cierre de sesión.
        • Versiones antiguas que siguen vivas y entornos de pruebas accesibles desde fuera.
        • Servicios de terceros integrados y los webhooks que llegan desde fuera.
        • Mensajes de error, cabeceras de respuesta y metadatos que se filtran sin querer.

        Familias de peligro

        • Autorización rota. El caso más común y más grave. Acceder a objetos o funciones de otros. Lo desarrolla API1 y API5.
        • Autenticación débil. Fuerza bruta sin límite, tokens mal validados, recuperación de contraseña floja. API2.
        • Exposición de datos. Devolver más de lo necesario y confiar en que el cliente filtre. API3.
        • Consumo sin límites. Sin límite de tasa ni de tamaño, una API se cae o se usa para fuerza bruta. API4.
        • Manipulación de objetos. Enviar campos que no deberías poder tocar. API6.
        • Configuración descuidada. Cabeceras, CORS, TLS, errores verbosos, servicios por defecto. API7.
        • Inyección. Datos del usuario que acaban en una consulta o un comando. API8.
        • Inventario perdido. No saber cuántas APIs y versiones tienes desplegadas. API9.
        • Ceguera. Sin registro ni alertas, el ataque pasa desapercibido durante meses. API10.

        Nota

        Un modelo de amenazas sencillo para cualquier endpoint: ¿qué recurso toca? ¿quién debería poder tocarlo? ¿qué pasa si cambio el id, el método, un campo del cuerpo o una cabecera? ¿queda registro de lo que hice?

        05OWASP API Security Top 10: panorama

        OWASP es una comunidad abierta de seguridad de software. Su Top 10 de APIs, edición 2019, es la lista de referencia de los diez riesgos más críticos y específicos de las APIs.

        Qué es y qué no es

        El OWASP API Security Top 10 no es un estándar de certificación ni una checklist exhaustiva. Es un consenso de la industria sobre dónde suele estar el fuego en las APIs, pensado para formar a quien desarrolla, diseña y opera. La edición de 2019 se construyó a partir de datos públicos de bug bounty y bases de vulnerabilidades, más la experiencia de profesionales de pruebas de intrusión.

        Cada riesgo se puntúa con la metodología de riesgo de OWASP en cuatro ejes: explotabilidad, prevalencia de la debilidad, detectabilidad de la debilidad e impacto técnico, cada uno de 1 a 3. La probabilidad real y el impacto sobre tu negocio los pones tú.

Esta clase usa la edición 2019 porque su desglose es más didáctico para empezar. Los conceptos se trasladan casi uno a uno.

        06Recorrido por API1 a API10

        Una ficha por riesgo, con la misma estructura: qué es, un ejemplo con petición y respuesta reales, el impacto y cómo se previene.

        API1:2019

        Autorización rota a nivel de objeto

        Crítica
        Explotabilidad
        Prevalencia
        Detectabilidad
        Impacto técnico

        Qué es

        También llamada BOLA o IDOR. La API usa un identificador que envía el cliente para decidir a qué objeto acceder, pero no comprueba que ese usuario tenga derecho sobre ese objeto concreto. Cambiar el id por el de otro devuelve sus datos.

        Ejemplo

        Impacto

        Lectura, modificación o borrado de datos de cualquier usuario. En el peor caso, toma de control de cuentas.

        Prevención

        • Comprobar la propiedad del objeto en cada endpoint que recibe un id, contra las políticas del usuario autenticado.
        • Preferir identificadores aleatorios (UUID) frente a correlativos. No es un control por sí solo, pero reduce el barrido.
        • Centralizar la comprobación en una capa que sea difícil de saltarse por olvido.
        • Escribir pruebas automáticas de autorización y no desplegar si fallan.

        API2:2019

        Autenticación de usuario rota

        Crítica
        Explotabilidad

        Qué es

        Fallos en el propio mecanismo de identidad: permite fuerza bruta sin límite ni bloqueo, acepta contraseñas débiles, no valida bien los tokens (firma, caducidad, alg:none), o trata "recuperar contraseña" con menos rigor que "iniciar sesión".

        Ejemplo

        Impacto

        Toma de control de cuentas, lectura de datos personales y acciones sensibles en nombre de la víctima.

        Prevención

        • Límite de tasa estricto y bloqueo o captcha en login y en recuperación de contraseña.
        • Usar librerías y estándares probados para tokens y almacenamiento de contraseñas. No reinventar.
        • Validar firma y expiración de cada JWT. Rechazar alg:none y algoritmos no esperados.
        • Autenticación multifactor donde sea posible. Las API keys identifican apps, no personas.

        API3:2019

        Exposición excesiva de datos

        Alta
        Explotabilidad
        Prevalencia
        Detectabilidad
        Impacto técnico

        Qué es

        La API serializa el objeto entero de la base de datos y lo envía, confiando en que la pantalla del cliente muestre solo lo que toca. Quien mira el tráfico ve todo lo demás.

        Ejemplo

        Impacto

        Fuga de datos personales y de información interna útil para encadenar otros ataques.

        Prevención

        • Nunca confiar en el cliente para filtrar. Devolver solo los campos necesarios, elegidos a mano.
        • Evitar to_json() genérico sobre el modelo. Definir respuestas explícitas por endpoint.
        • Validar la respuesta contra un esquema, errores incluidos.
        • Clasificar los datos personales y revisar qué endpoints los devuelven.

        API4:2019

        Falta de recursos y de limitación de tasa

        Media
        Explotabilidad
        Prevalencia
        Detectabilidad
        Impacto técnico

        Qué es

        La API no pone topes: ni de frecuencia de peticiones, ni de tamaño del cuerpo, ni de número de registros por página, ni de memoria o tiempo por operación. Un cliente puede tumbarla o abusar de operaciones caras.

        Ejemplo

        Impacto

        Denegación de servicio y coste. También habilita la fuerza bruta de otros endpoints.

        Prevención

        • Límite de peticiones por cliente y por ventana de tiempo, y respuesta 429 con cabeceras de reintento.
        • Validar en servidor el tamaño de size, del cuerpo, de arrays y de cadenas.
        • Topes de memoria, CPU, procesos y tiempo por operación (contenedores ayudan).
        • Paginación con máximo fijo, no confiable al parámetro del cliente.

        Autorización rota a nivel de función

        Alta
        Explotabilidad
        Prevalencia

        Impacto técnico

        Qué es

        La diferencia con API1 es el objeto: aquí lo que no se comprueba es el acceso a una función completa, normalmente administrativa. Un usuario normal la alcanza cambiando la ruta (/users por /admins) o el método (GET por POST o DELETE).

        Ejemplo

        Impacto

        Acceso a funcionalidad no autorizada. Las funciones administrativas son el objetivo preferido.

        Prevención

        • Denegar por defecto. Cada función exige un permiso explícito para un rol concreto.
        • Que los controladores administrativos hereden de una base que aplica la comprobación de rol.
        • No asumir que una ruta es "de admin" por su path. Revisar endpoint por endpoint.

        Asignación masiva

        Media
        Explotabilidad
        Prevalencia

        Impacto técnico

        Qué es

        El framework vincula automáticamente todo el JSON entrante a los campos del objeto. Si el cliente añade una propiedad interna que el desarrollador no pensaba exponer (is_admin, credit_balance, verified), se guarda igual.

        Ejemplo

        Impacto

        Escalada de privilegios, manipulación de datos y elusión de controles de negocio.

        Prevención

        • Lista blanca de campos que el cliente puede modificar. Nada fuera de ella se vincula.
        • Usar objetos de transferencia (DTO) por endpoint en vez del modelo de base de datos.
        • Definir y validar el esquema de entrada de forma explícita.

        Configuración de seguridad incorrecta

        Media

        Qué es

        Cualquier ajuste inseguro en la pila: TLS ausente, CORS que acepta cualquier origen, cabeceras de seguridad que no se envían, métodos HTTP de más, servicios con credenciales por defecto, parches sin aplicar y, muy a menudo, errores verbosos que devuelven trazas de pila.

        Ejemplo

        Impacto

        Desde fuga de detalles internos hasta compromiso total del servidor.

        Prevención

        • Proceso de endurecimiento repetible y revisión de configuración en toda la pila, nube incluida.
        • Respuestas de error con esquema fijo, sin trazas ni datos internos.
        • Solo los métodos HTTP necesarios. CORS con lista de orígenes concreta.
        • TLS en todo. Cabeceras de seguridad. Parches al día. Comprobación automática y continua.

        Qué es

        Datos del cliente que llegan sin sanear a un intérprete: SQL, NoSQL, comando de sistema, LDAP, parser de XML. El intérprete ejecuta lo que no debía.

        Ejemplo

        Impacto

        Lectura y borrado de datos, denegación de servicio y, con inyección de comandos, control del host.

        Prevención

        • Separar datos de comandos: consultas parametrizadas, nunca concatenación.
        • Validar tipo y forma de cada parámetro. Un id es una cadena, no un objeto.
        • Una librería de validación única y mantenida. Escapar según el intérprete de destino.
        • Limitar el número de registros afectados y devueltos.

        API9:2019

        Gestión inadecuada de activos

        Media

        Detectabilidad
        Impacto técnico

        Qué es

        No saber qué APIs, versiones y entornos tienes expuestos. Versiones antiguas sin parchear, hosts de pruebas accesibles desde internet, documentación desfasada y sin plan de retirada.

        Ejemplo

        Impacto

        Acceso a datos sensibles y, a veces, al servidor, a través de la puerta que nadie vigila.

        Prevención

        • Inventario de todos los hosts de API con entorno, acceso de red y versión.
        • Inventario de servicios integrados y del flujo de datos.
        • Documentación generada de forma automática y publicada solo a quien corresponde.
        • Plan de retirada por versión. No usar datos de producción fuera de producción.

        API10:2019

        Registro y monitorización insuficientes

        Info
        Explotabilidad

        Impacto técnico

        Qué es

        La API no registra lo que importa, o lo registra sin detalle, o nadie mira esos registros. Sin alertas, un ataque puede durar meses. Los estudios de brechas hablan de más de 200 días de media para detectarlas, y casi siempre lo avisa alguien de fuera.

        Ejemplo

        Impacto

        El atacante tiene todo el tiempo del mundo para pivotar, mantener persistencia y exfiltrar.

        Prevención

        • Registrar autenticaciones fallidas, accesos denegados y errores de validación, con detalle suficiente para identificar al actor.
        • Formato apto para un gestor de logs. Tratar los logs como datos sensibles y garantizar su integridad.
        • Monitorización continua de infraestructura y de la API. Un SIEM que agregue todo.
        • Cuadros de mando y alertas para detectar y responder pronto.

        07Ataques en la práctica

        Los fallos reales rara vez vienen solos. Estos tres recorridos encadenan varias debilidades hasta un impacto concreto, con la respuesta de la aplicación en cada paso.

        Cómo leer la respuesta de una aplicación

        • Código de estado. ¿200 donde esperabas 403? Mira el cuerpo antes de descartar.
        • Tamaño y forma. Una respuesta más larga de lo normal suele traer campos de más.
        • Diferencias. Compara la respuesta legítima con la manipulada. Lo que cambia es la pista.
        • Cabeceras. Access-Control-Allow-Origin, Set-Cookie, ausencia de X-RateLimit.
        • Tiempos. Una ruta que tarda de más puede estar ejecutando algo caro o una inyección ciega.

        Recorrido 1 · Marketplace de comercios

        De un id predecible a la facturación de toda la plataforma

        Combina API3 (la respuesta trae el id interno de la tienda), API1 (no se comprueba la propiedad) y API4 (no hay límite de tasa para el barrido).

        Recorrido 2 · App de finanzas personales

        De invitado a administrador

        Combina API3 (la invitación devuelve el rol) y API5 (crear invitaciones no comprueba rol).

        Recorrido 3 · Cámaras de videovigilancia

        Un vigilante con acceso a todo el recinto

        Combina API3 (la respuesta trae cámaras fuera de su ámbito) y API1 (el token de acceso en vivo no se valida contra el usuario).

        08Defensa en profundidad

        Ningún control basta solo. La idea es apilar capas de forma que, si una falla, la siguiente contenga el daño.

        Las capas, de fuera adentro

        • Borde. TLS obligatorio, pasarela de API, límite de tasa, WAF o firewall de API para todas las versiones, no solo la actual.
        • Autenticación. Estándares probados, MFA, tokens de vida corta con refresco, validación de firma y expiración en cada petición.
        • Autorización. Denegar por defecto. Comprobar propiedad de objeto (API1) y permiso de función (API5) en cada endpoint, en una capa central.
        • Validación de entrada. Esquema por endpoint y por variante. Tipos estrictos. Consultas parametrizadas (API8). Lista blanca de campos (API6).
        • Salida. DTO explícitos. Nunca serializar el modelo entero (API3). Validar también la respuesta.
        • Observabilidad. Registro con detalle, monitorización y alertas (API10). Inventario y retirada de versiones (API9).

        Autorización a nivel de objeto

        API1: comprobar la propiedad, no solo la sesión

        Asignación masiva

        API6: vincular solo lo permitido

        Límite de tasa y de tamaño

        API4: topes en el servidor, no en la interfaz

        Nota

        El hilo común de casi todas las mitigaciones: la decisión de seguridad se toma en el servidor, con lo que el usuario realmente es, no con lo que la app dice que es ni con lo que el cliente envía.

        09Pruebas de seguridad de APIs

        Probar una API es, sobre todo, interceptar tráfico legítimo y repetirlo cambiando una cosa cada vez. El resto es método y paciencia.

        Método en cinco pasos

        1. Descubrir. Reúne endpoints: documentación, Swagger u OpenAPI, tráfico de la app, JavaScript del frontend, el binario descompilado, versiones antiguas (v1, beta., staging.).
        2. Mapear roles. Consigue al menos dos cuentas de usuario normal y una de administrador. Anota qué puede hacer cada una.
        3. Interceptar. Pon un proxy entre el cliente y la API y captura peticiones reales para tenerlas como base.
        4. Manipular una variable. Cambia el id (API1), el método (API5), un campo del cuerpo (API6), un parámetro de tamaño (API4), el tipo de un valor (API8), la versión de la ruta (API9). Repite con el token de otra cuenta o sin token.
        5. Comparar. Diferencia entre la respuesta legítima y la manipulada. Documenta con petición, respuesta e impacto.

        Herramientas habituales

        HerramientaPara qué
        Burp Suite / OWASP ZAPProxy de interceptación, repetición de peticiones, fuzzing, comparador de respuestas.
        Postman / Hoppscotch / InsomniaConstruir y organizar colecciones de peticiones, probar flujos con distintas cuentas.
        mitmproxyInterceptar tráfico de apps móviles y de scripts desde consola.
        ffuf / feroxbusterDescubrir endpoints y parámetros ocultos por fuerza bruta de diccionario.
        NucleiPlantillas para detectar configuraciones incorrectas y exposiciones conocidas (API7, API9).
        jwt_toolAnalizar y manipular JWT: alg:none, firma débil, caducidad (API2).
        Escáneres OpenAPI (Schemathesis, APIsec)Generar casos de prueba a partir del contrato de la API.

        Laboratorios para practicar sin meterte en un lío

        • crAPI (OWASP): API deliberadamente vulnerable centrada en el Top 10 de APIs.
        • vAPI: colección de retos, uno por cada punto del Top 10, con Postman incluido.
        • OWASP Pixi (DevSlop): app web y API vulnerables para practicar interceptación.
        • Juice Shop (OWASP): aplicación moderna con una API con muchos fallos encadenables.
        • PortSwigger Web Security Academy: laboratorios guiados y gratuitos, varios de ellos de API.

        Peligro

        Probar una API que no es tuya y sin permiso por escrito es un delito. Todo lo de esta clase se practica en tus propios laboratorios o dentro de un contrato de pruebas de intrusión o un programa de bug bounty con alcance claro.

        Checklist rápida por endpoint

        • ¿Responde sin token? ¿Con el token de otra cuenta?
        • ¿Qué pasa si cambio el id por uno que no es mío?
        • ¿Acepta otros métodos HTTP de los previstos?
        • ¿Puedo añadir campos al cuerpo y que los guarde?
        • ¿Hay tope de tamaño, de página y de frecuencia?
        • ¿La respuesta trae campos que la interfaz no muestra?
        • ¿El error revela versiones, rutas o credenciales?
        • ¿Existe una versión anterior de esta ruta sin los mismos controles?
        • ¿Queda registro de lo que acabo de hacer?

        10Ejercicios por tipo de aplicación

        Dieciséis ejercicios agrupados por sector. Cada uno describe un endpoint y una respuesta; el objetivo es identificar el fallo del Top 10, explotarlo sobre el papel y proponer la mitigación. Pistas y solución van plegadas.

        Formato sugerido en clase: se plantea el enunciado, cinco minutos en parejas, se abren las pistas si hace falta y se comenta la solución en común. La columna de dificultad orienta el orden.

        Comercio electrónico

        Contexto: TiendaLuz, marketplace con web y app. API troncal en api.tiendaluz.com/v2. Cuentas de comprador y de vendedor.

        Ejercicio 1

        Básico E-commerce

        La app descarga la factura de un pedido con GET /api/v2/orders/48213/invoice. La respuesta es un JSON con importe, nombre, dirección y NIF del comprador. Los identificadores de pedido son correlativos. ¿Qué riesgo del Top 10 es y cómo lo demuestras?

        1. ¿La API comprueba de quién es el pedido, o solo que hay sesión?
        2. Prueba 48212 y 48214 con tu propio token.

        API1, autorización rota a nivel de objeto. Con un bucle sobre el rango de identificadores se descargan las facturas de todos los compradores, con datos personales. Demostración: dos peticiones con tu token, una a tu pedido y otra al id contiguo; si ambas devuelven 200 con datos que no son tuyos, está confirmado.

        Mitigación: comprobar order.buyer_id == req.user.id (o la política que corresponda) antes de responder; identificadores UUID; prueba automática de autorización.

        Ejercicio 2

        Intermedio E-commerce

        El pago se confirma con POST /api/v2/checkout. Un GET previo del carrito devuelve, entre otros, {"items": [...], "subtotal": 89.90, "discount_pct": 0, "total": 89.90}. Reenvías el POST añadiendo "discount_pct": 90 y la respuesta es 201 con "total": 8.99. Nombra el fallo y la defensa.

        1. ¿Quién debería fijar el descuento, el cliente o el servidor?
        2. El campo estaba en la respuesta del carrito. ¿Eso lo convierte en editable?

        API6, asignación masiva. El checkout vincula todo el cuerpo, incluido un campo de precio que solo debería calcular el servidor. Es también un fallo de lógica de negocio.

        Mitigación: lista blanca de campos aceptados en el checkout (solo cart_id, dirección, método de pago). El descuento y el total se recalculan siempre en servidor a partir de reglas y cupones validados.

        Ejercicio 3

        Intermedio E-commerce

        El endpoint POST /api/v2/coupons/validate comprueba si un código de cupón existe y devuelve su valor. No pide autenticación y no tiene límite de tasa. Los cupones tienen formato LUZ-XXXX con cuatro caracteres alfanuméricos. ¿Qué dos riesgos se combinan y qué haces?

        1. ¿Cuántas combinaciones hay de cuatro caracteres? ¿Cuánto tardarías sin límite de tasa?
        2. Piensa en el endpoint como un oráculo de "cupón válido / no válido".

        API4 (sin límite de tasa) más API3 (la respuesta confirma validez y valor). El espacio es pequeño, del orden de un millón y medio de combinaciones; sin límite se recorre en minutos y se cosechan cupones reales.

        Mitigación: límite de tasa por IP y por token en el endpoint; respuesta neutra que no distinga "no existe" de "existe pero no aplica"; validar el cupón solo dentro del checkout, no en un endpoint suelto; códigos más largos y de un solo uso.

        Banca y fintech

        Contexto: NeoPagos, app de cuentas y transferencias. API en api.neopagos.com/v1. Roles: titular, autorizado y aprobador de empresa.

        Ejercicio 4

        Intermedio Banca

        GET /api/v1/accounts/ES7620770024003102575766/transactions devuelve el movimiento de esa cuenta. El IBAN va en la ruta. Con tu token, cambias el IBAN por el de otra cuenta que conoces y recibes 200 con sus movimientos. Clasifícalo y propón defensa.

        1. El IBAN es un identificador de objeto como cualquier otro.
        2. ¿Es más difícil de adivinar que un id correlativo? ¿Basta con eso?

        API1. Que el IBAN sea largo no es un control de acceso: los IBAN se comparten en facturas, recibos y contratos. La API debe comprobar que la cuenta pertenece al usuario o que este es autorizado de ella.

        Mitigación: resolver siempre la cuenta a través de la relación usuario-cuenta (SELECT ... WHERE iban = ? AND owner_id = ?); registrar y alertar sobre accesos a cuentas ajenas; nunca aceptar el IBAN como prueba de titularidad.

        Ejercicio 5

        Avanzado Banca

        Recuperación de contraseña: POST /api/v1/otp con el teléfono envía un código de 6 dígitos por SMS; POST /api/v1/otp/verify lo comprueba. No hay bloqueo tras fallos ni caducidad corta del código. Describe el ataque completo y todas las capas de mitigación.

        1. Un millón de combinaciones, sin límite por intento ni por cuenta.
        2. ¿Cuánto vive el código? ¿Se invalida al primer fallo tras varios intentos?

        API2 con apoyo de API4. Ataque: pedir el OTP para el teléfono de la víctima y lanzar un script multihilo contra /otp/verify probando de 000000 a 999999. Sin límites, se acierta en minutos y se obtiene la sesión o el token de reseteo.

        Mitigación en capas: máximo 5 intentos por código y luego invalidarlo; caducidad de 2 a 5 minutos; límite de tasa por cuenta, por teléfono y por IP; código de 8 dígitos o alfanumérico; retardo creciente entre intentos; alerta al usuario y al SOC ante muchos fallos; tratar recuperación con el mismo rigor que el login.

        Ejercicio 6

        Avanzado Banca

        Una transferencia de empresa se crea con POST /api/v1/transfers (rol autorizado) y se aprueba con POST /api/v1/transfers/{id}/approve (rol aprobador). Con una cuenta solo de rol autorizado, llamas a /approve sobre una transferencia que tú mismo creaste y responde 200 "state": "executed". ¿Qué falló?

        1. ¿La comprobación de rol está en el endpoint /approve o solo en el botón de la app?
        2. Piensa también en la segregación de funciones: quien crea no debería aprobar.

        API5, autorización rota a nivel de función. El endpoint de aprobación no verifica el rol; la app se limitaba a esconder la acción. Además rompe el principio de doble control.

        Mitigación: denegar por defecto y exigir rol approver en /approve; comprobar que el aprobador es distinto del creador; registrar quién aprueba cada transferencia; pruebas de autorización por rol en el pipeline.

        IoT y wearables

        Contexto: PulseBand, pulsera de actividad con app y nube. Los dispositivos hablan con api.pulseband.io.

        Ejercicio 7

        Básico IoT

        Interceptando el tráfico de la pulsera ves PATCH /api/v1/profile con la cabecera X-User-Id: 54796 y un cuerpo con peso y altura. Cambias la cabecera a 54795 y la respuesta es 200: has editado el perfil de otra persona. Clasifícalo.

        1. ¿De dónde debería salir la identidad del usuario, de una cabecera que el cliente controla o del token?

        API1. La identidad se toma de una cabecera manipulable en vez del token autenticado. El id de usuario del cuerpo o de la cabecera no es una credencial.

        Mitigación: ignorar X-User-Id; derivar el usuario del token; el endpoint /profile actúa siempre sobre req.user.id. Para editar a otro, un endpoint administrativo con su propia autorización.

        Ejercicio 8

        Avanzado IoT

        El firmware expone POST /api/CONFIG/restore que recibe un appId como parámetro. Descompilando ves que el servidor hace system("restore.sh /tmp/backup.bin " + appId). Envías appId=x; /sbin/reboot. Explica el fallo y la corrección.

        1. El valor del usuario acaba dentro de una llamada al shell sin ningún filtro.
        2. ¿Qué hacen ;, && y $(...) en una línea de comandos?

        API8, inyección de comandos. El appId se concatena a una orden de shell. Con metacaracteres se ejecuta lo que quieras con los privilegios del proceso: reiniciar, abrir un shell, borrar el dispositivo.

        Mitigación: no llamar al shell; usar execFile o equivalente con argumentos como lista, sin intérprete; validar appId contra un patrón estricto (por ejemplo, solo [a-z0-9-]{8,32}); ejecutar con el mínimo privilegio; firmar y autenticar la operación de restore.

        Red social

        Contexto: Corrillo, red social con perfiles, publicaciones y mensajes directos. API en api.corrillo.app, con host beta.corrillo.app para pruebas.

        Ejercicio 9

        Básico Red social

        GET /api/users/marina_g devuelve el perfil público, pero el JSON incluye email, phone, last_login_ip y birthdate. La app solo pinta el nombre y la biografía. ¿Riesgo y arreglo?

        1. Que la app no lo muestre no significa que no viaje.
        2. Un solo GET por usuario y tienes un censo con datos personales.

        API3. Serialización genérica del modelo. Combinado con enumeración de alias, permite recolectar datos personales a escala.

        Mitigación: DTO de perfil público con solo alias, nombre, bio y avatar; los campos sensibles solo en GET /api/users/me; validación de esquema de salida; límite de tasa en el listado de perfiles.

        Ejercicio 10

        Intermedio Red social

        El límite de tasa del reseteo de contraseña está implementado en una pasarela delante de api.corrillo.app. Descubres que beta.corrillo.app ejecuta la misma API, incluido el reseteo, pero sin esa pasarela delante. ¿Qué riesgo del Top 10 lo describe mejor?

        1. El fallo no es solo la fuerza bruta; es que exista un host gemelo sin los mismos controles.
        2. ¿Está inventariado ese host? ¿Debería estar accesible desde internet?

        API9, gestión inadecuada de activos, que a su vez reabre API2. Un host de pruebas con la misma lógica y sin los controles del de producción es una puerta trasera involuntaria.

        Mitigación: inventario de todos los hosts con su entorno y exposición; los entornos de prueba no accesibles desde internet o detrás de VPN; los controles de seguridad en la propia API, no solo en una pasarela externa; datos de prueba, nunca de producción.

        Ejercicio 11

        Intermedio Red social

        Los mensajes directos se leen con GET /api/conversations/91043/messages. El id de conversación es un entero. Con tu token, restas y sumas al número y obtienes conversaciones ajenas. ¿Cómo lo clasificas y qué propones más allá de "usar UUID"?

        1. El UUID dificulta el barrido pero no autoriza nada.
        2. ¿Es el usuario participante de esa conversación?

        API1. La defensa real es comprobar participación: WHERE conversation_id = ? AND ? IN (participants). El UUID es una mejora complementaria, no la solución. Añade registro de accesos y alerta ante patrones de enumeración.

        SaaS B2B multiinquilino

        Contexto: Facturia, SaaS de facturación con varias organizaciones (inquilinos) en la misma API api.facturia.com/v1. Roles: propietario, administrador y miembro.

        Ejercicio 12

        Intermedio SaaS B2B

        Con una cuenta de rol miembro, pruebas rutas por analogía y das con GET /api/v1/admin/users/export, que devuelve un CSV con todos los usuarios de tu organización, sus roles y sus últimos accesos. Nadie te paró. ¿Qué riesgo es?

        1. La ruta lleva /admin/, pero eso no aplica ningún control por sí solo.
        2. ¿El endpoint comprueba el rol del token?

        API5. Endpoint administrativo sin comprobación de rol. La convención de nombres /admin/ no es un control.

        Mitigación: middleware que exija rol admin u owner en todo /admin/*; denegar por defecto; pruebas por rol; y como capa extra, límite de tasa y alerta en endpoints de exportación masiva.

        Ejercicio 13

        Avanzado SaaS B2B

        Las peticiones llevan una cabecera X-Org-Id: 3391 que el frontend rellena con la organización activa. El backend la usa para filtrar los datos. Cambias la cabecera a 3390 con tu mismo token y ves las facturas de otra empresa. Clasifícalo y explica por qué es especialmente grave en SaaS.

        1. La organización activa debería salir de la relación usuario-organización en servidor, no de una cabecera.
        2. Un solo fallo así rompe el aislamiento entre todos los clientes del producto.

        API1 entre inquilinos. En SaaS es de los peores casos: expone datos de todas las organizaciones y suele desembocar en incidente notificable y pérdida de contratos.

        Mitigación: nunca confiar en X-Org-Id; derivar la organización del token o de la membresía del usuario; filtrar toda consulta por org_id comprobado; pruebas automáticas de aislamiento entre inquilinos; separación de datos por esquema o base cuando el riesgo lo justifique.

        Ejercicio 14

        Intermedio SaaS B2B

        Un id de factura no numérico provoca 500 con una traza que incluye el framework, la versión, la ruta del proyecto y una línea REDIS_URL=redis://:p4ss@cache.internal:6379. Además, la respuesta trae Access-Control-Allow-Origin: * y Access-Control-Allow-Credentials: true. Enumera los problemas.

        1. La traza filtra información. ¿Qué haría alguien con esa cadena de Redis?
        2. Allow-Origin: * junto con Allow-Credentials: true es una combinación inválida y peligrosa.

        API7. Tres cosas: error verboso que revela pila y credenciales de Redis; validación de entrada floja (el id no numérico no se rechazó con un 400 limpio); CORS mal configurado que, con * y credenciales, o lo ignora el navegador o, si se refleja el origen, deja que cualquier web haga peticiones autenticadas.

        Mitigación: manejador de errores que devuelve un cuerpo genérico con id de correlación; sin trazas ni secretos en la respuesta; secretos fuera del código y rotados si se han expuesto; CORS con lista blanca de orígenes y Allow-Credentials solo con origen explícito; validar el tipo del id.

        Videovigilancia

        Contexto: VigiaCloud, cámaras conectadas para empresas. API en api.vigiacloud.com/v2, con v1 heredada.

        Ejercicio 15

        Intermedio Videovigilancia

        Un vigilante con acceso solo al edificio A llama a GET /api/v2/sites/111/cameras. La respuesta lista todas las cámaras del recinto, con un live_token por cámara. Con GET /api/v2/stream?token=<el de otra cámara> ve el vídeo en directo de zonas restringidas. Identifica los fallos.

        1. La lista devuelve más de lo que el vigilante puede ver.
        2. El live_token no está atado al usuario que lo pide.

        API3 (la lista trae cámaras y tokens fuera del ámbito del usuario) más API1 (el stream acepta cualquier live_token sin comprobar a quién pertenece).

        Mitigación: filtrar la lista de cámaras por los permisos del usuario en servidor; no incluir tokens de cámaras que no puede ver; emitir el live_token ligado al usuario y a la cámara, de vida corta; en /stream, validar que el token corresponde a esa cámara y a ese usuario.

        Ejercicio 16

        Avanzado Videovigilancia

        La app usa api.vigiacloud.com/v2, que exige token y filtra por cliente. Cambiando v2 por v1 en la URL, GET /api/v1/cameras responde 200 sin token y devuelve todas las cámaras de todos los clientes con sus URLs RTSP. ¿Qué riesgo es y cuál es el plan?

        1. La versión vieja quedó viva y comparte base de datos con la nueva.
        2. ¿Se puede apagar v1 hoy? ¿Qué clientes la usan todavía?

        API9. Versión heredada sin los controles de la actual, conectada a los mismos datos. Impacto directo sobre la privacidad de todos los clientes.

        Plan: inventariar quién consume v1 a partir de los logs; si nadie, retirarla ya; si hay clientes, ponerle autenticación y filtrado equivalentes de forma inmediata y darles fecha de migración; alertar sobre cualquier acceso a v1; incluir el descubrimiento de versiones en el proceso de despliegue.

        Nota

        Patrón repetido en los dieciséis: el cliente envía un identificador o una bandera, y el servidor lo cree sin comprobar. La pregunta de examen siempre es la misma: ¿este usuario, con su token, tiene derecho a este objeto o a esta función?

        11Buenas prácticas, glosario y referencias

        El resumen accionable de las tres horas, un glosario para fijar el vocabulario y las fuentes para seguir.

        Para quien desarrolla

        • Autoriza en cada endpoint: propiedad del objeto y permiso de la función, en una capa central, denegando por defecto.
        • Devuelve solo los campos necesarios con un DTO explícito. Nunca serialices el modelo entero.
        • Acepta solo los campos previstos con una lista blanca. Valida tipo y forma de todo lo que entra.
        • Usa consultas parametrizadas siempre. Nunca construyas comandos ni consultas concatenando entrada.
        • No inventes autenticación ni gestión de tokens. Usa estándares y valida firma y expiración.
        • Pon límites: de tasa, de tamaño de cuerpo, de página, de tiempo y memoria por operación.
        • Trata "recuperar contraseña" con el mismo rigor que "iniciar sesión".
        • Que los errores no cuenten nada de dentro. Cuerpo genérico con id de correlación.
        • Escribe pruebas de autorización y de aislamiento, y bloquea el despliegue si fallan.

        Para quien opera (DevSecOps)

        • Mantén un inventario vivo de APIs, versiones y entornos. Retira lo que no se usa.
        • Endurecimiento repetible y revisión de configuración en toda la pila, nube incluida.
        • Registra autenticaciones fallidas, accesos denegados y errores de validación con detalle para identificar al actor.
        • Monitoriza y alerta. Un SIEM que agregue los logs de toda la pila.
        • Protege también las versiones antiguas con la pasarela y el firewall de API, no solo la actual.
        • Nada de datos de producción en entornos que no son de producción.
        • Seguridad continua en el pipeline: escaneo del contrato, pruebas de intrusión, no una revisión anual.
        • Entrega los hallazgos donde trabaja el equipo, no en un PDF, con su escenario de ataque.

        Glosario

        API
        Contrato por el que dos programas se comunican por HTTP: qué se puede pedir, con qué formato y qué se recibe.
        API troncal
        API central que sirve a todos los clientes de un producto (web, iOS, Android). Concentra lógica y riesgo.
        Endpoint
        Dirección concreta de la API que representa una operación sobre un recurso.
        Método HTTP
        Verbo de la petición: GET lee, POST crea, PUT reemplaza, PATCH modifica, DELETE borra.
        Autenticación
        Probar quién eres. No implica permiso para nada concreto.
        Autorización
        Decidir qué puede hacer un usuario ya autenticado. Origen de la mayoría de fallos graves.
        JWT
        Token firmado con datos del usuario y una caducidad. Hay que validar firma y expiración en cada petición.
        BOLA / IDOR
        Autorización rota a nivel de objeto: cambiar un id y acceder a datos de otro. API1.
        BFLA
        Autorización rota a nivel de función: alcanzar una función administrativa sin permiso. API5.
        Asignación masiva
        El servidor vincula campos del cuerpo que no debería aceptar del cliente. API6.
        Exposición excesiva de datos
        Devolver el objeto entero y confiar en que el cliente oculte lo sensible. API3.
        Límite de tasa
        Tope de peticiones por cliente y ventana de tiempo. Responde 429 al superarse.
        Inyección
        Entrada no confiable interpretada como consulta o comando. API8.
        CORS
        Reglas que dicen qué orígenes web pueden leer respuestas de la API. Mal configurado, es fuga. API7.
        API polimórfica
        Un endpoint que cambia de comportamiento o de forma según un parámetro, un rol o una cabecera.
        SIEM
        Sistema que agrega y correla logs y eventos de seguridad para detectar y responder.
        DTO
        Objeto de transferencia: estructura definida a mano para la entrada o la salida de un endpoint, distinta del modelo de datos.
