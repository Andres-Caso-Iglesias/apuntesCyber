        01Qué es la enumeración web y por qué importa

        Antes de explotar nada hay que saber qué existe. La enumeración es la fase de reconocimiento activo donde descubres la superficie real del objetivo: tecnologías, endpoints, archivos, subdominios y cualquier grieta que el propio servidor te muestre sin darse cuenta.

        La idea en una frase

        Enumeración es el proceso de mapear toda la superficie de ataque de una aplicación web de forma metódica. No es adivinar, no es probar cosas al azar: es recopilar información concreta que te permita decidir por dónde seguir y por dónde no.

        En la metodología de pruebas de penetración, la enumeración viene después del reconocimiento pasivo (OSINT, DNS, redes sociales) y antes de la explotación. Es el puente entre "sé que existe este dominio" y "sé que hay un endpoint vulnerable en el que puedo trabajar".

        Por qué es la fase más importante

        • Define el alcance. Cuanto más sepas de la superficie, más rutas de ataque encontrarás.
        • Ahorra tiempo. Un directorio mal configurado o un subdominio olvidado puede ser la entrada directa.
        • Reduce ruido. En vez de lanzar miles de peticiones a ciegas, sabes exactamente qué probar.
        • Revela errores humanos. Archivos de backup, versiones de prueba, paneles de administración expuestos.

        Enumeración vs. reconocimiento pasivo

        • Reconocimiento pasivo: recopilar información sin interactuar directamente con el servidor. DNS, WHOIS, redes sociales, certificados SSL públicos, GitHub, Google Dorks.
        • Enumeración activa: enviar peticiones al servidor para descubrir qué hay detrás. Fuzzing de directorios, probes de tecnología, bruteforce de subdominios.

        La enumeración activa deja rastro en los logs del servidor. En un entorno de pruebas autorizado eso no importa; en producción, un auditor responsable lo hace con cuidado y dentro del alcance acordado.

        Qué buscas cuando enumeras

        • Tecnologías: servidor web, framework, lenguaje, base de datos, CMS, CDN.
        • Endpoints y rutas: paths de la API, formularios, acciones ocultas.
        • Archivos y directorios: backups, configuraciones, paneles de admin, logs expuestos.
        • Subdominios: servicios internos, entornos de prueba, paneles de terceros.
        • Parámetros: campos de formulario, query strings, variables de sesión.
        • Información filtrada: comentarios HTML, headers HTTP, mensajes de error verbosos.

        Aviso

        Enumerar un sitio sin permiso es ilegal en la mayoría de jurisdicciones. Todo lo de esta clase se practica en laboratorios propios, máquinas de HTB/THM, o dentro de un contrato de pruebas con alcance definido.

        02Fingerprinting tecnológico

        El primer paso es saber con qué estás tratando. El servidor te dice más de lo que crees con cada respuesta que devuelve.

        Cabeceras HTTP

        Cada respuesta HTTP lleva cabeceras que revelan información tecnológica. Las más reveladoras:

        • Server: nombre y versión del servidor web (Apache, nginx, IIS).
        • X-Powered-By: framework o lenguaje del backend (PHP, ASP.NET, Express).
        • X-AspNet-Version: versión exacta de ASP.NET.
        • X-Generator: CMS que genera la página (WordPress, Drupal).

        Probes de tecnología

        Ciertas rutas solo existen si el servidor ejecuta una tecnología concreta:

        Ruta probeSi devuelve 200Qué confirma
        /wp-login.phpWordPressCMS WordPress instalado
        /administrator/JoomlaCMS Joomla instalado
        /user/loginDrupalCMS Drupal instalado
        /elmah.axdASP.NETPanel de errores expuesto
        /actuator/healthSpring BootActuator expuesto
        /.envPHP/LaravelVariables de entorno filtradas
        /server-statusApacheMod_status habilitado
        /phpinfo.phpPHPInfo de PHP expuesta

        Cookies y tokens

        • PHPSESSID → PHP
        • JSESSIONID → Java
        • ASP.NET_SessionId → ASP.NET
        • connect.sid → Express (Node.js)
        • csrftoken → Django
        • _rails_session → Ruby on Rails

        Error pages

        Las páginas de error suelen revelar la tecnología. Si provocas un error intencionadamente, la respuesta puede mostrar el framework, su versión, trazas de pila y rutas del servidor.

        Nota

        Una buena defensa es personalizar las páginas de error y suprimir las cabeceras identificativas. Pero en la práctica, muchas aplicaciones olvidan hacerlo.

        HerramientaQué hace
        whatwebIdentifica tecnologías, CMS, frameworks a partir de la respuesta HTTP.
        WappalyzerExtensión de navegador que detecta tecnologías en tiempo real.
        BuiltWithBase de datos de tecnologías web. Útil para reconocimiento pasivo.
        httpxProbe HTTP rápido que masajea headers, status codes y tecnologías.

        03Descubrimiento de directorios y archivos

        Detrás de la página principal hay una estructura de archivos que el servidor no muestra pero que existe. Encontrarla es cuestión de saber qué buscar y cómo buscarlo.

        La estructura oculta

        • Archivos de administración: /admin/, /phpmyadmin/, /wp-admin/
        • Backups: /backup.zip, /db.sql, /site.tar.gz
        • Configuraciones: /.env, /config.php, /wp-config.php.bak
        • Logs: /debug.log, /access.log
        • Archivos de test: /test.php, /phpinfo.php
        • Directorios de versiones: /.git/, /.svn/, /.hg/
        • Servicios internos: /jenkins/, /grafana/, /kibana/

        Cómo funciona el descubrimiento

        El método más habitual es el fuzzing de directorios: enviar peticiones GET a rutas candidatas con una lista de nombres conocidos y observar qué responde. No es solo 404 vs. 200; hay que leer el tamaño de la respuesta, el código de estado y el contenido.

        Wordlists

        WordlistIdeal paraNotas
        common.txt (dirb)Inicio rápido~4600 entradas. Cubre lo básico.
        directory-list-2.3-medium.txtBúsqueda amplia~220.000 entradas. Más lento pero más completo.
        raft-medium-directories.txtEquilibrio~20.000 entradas. Buen punto de partida.
        big.txtBúsqueda exhaustiva~20.000 entradas con variantes de nombres.

        Filtrar ruido

        La mayoría de servidores devuelven 200 para casi todo (página personalizada de error). Estrategias:

        • Tamaño de respuesta: la página de error personalizada tiene un tamaño fijo. Filtra por tamaño diferente.
        • Código de estado: descarta 404, pero presta atención a 301, 302, 403.
        • Regex sobre el contenido: busca "not found", "error", "404" en el body.
        • Recursividad: si encuentras /admin/, repite el fuzzing dentro.

        Extensiones y sufijos

        • /config, /config.php, /config.php.bak, /config.php~, /config.php.old
        • /backup, /backup.zip, /backup.tar.gz, /backup.sql
        • /.git/HEAD, /.git/config

        Peligro

        Un archivo .env expuesto puede contener credenciales de base de datos, claves de API y tokens secretos. Un repositorio .git expuesto permite reconstruir todo el código fuente.

        04Enumeración de subdominios

        Un dominio como ejemplo.com es solo la puerta principal. Detrás hay docenas de subdominios: mail, api, staging, dev, vpn, cada uno con su propia superficie de ataque.

        Por qué los subdominios importan

        • Amplían la superficie. Un subdominio de prueba puede tener la misma base de datos que producción pero sin los controles.
        • Son predictibles. Si existe api.ejemplo.com, quizás exista staging-api.ejemplo.com.
        • Pueden estar abandonados. Un servidor olvidado nunca se parchea.
        • Son la entrada a servicios internos. VPN, Jenkins, Grafana, Jira.

        Fuentes de subdominios

        FuenteCómo funcionaNotas
        DNSConsultas directas a registros A, CNAME, MX, TXT.Rápido pero solo lo que está en DNS.
        crt.shCertificados SSL/TLS públicos.Excelente fuente, actualizada y gratuita.
        Google Dorkssite:*.ejemplo.comLo que Google ha indexado.
        Wayback MachineHistorial de la web.Útil para servicios descontinuados.
        Bruteforce DNSProbar miles de nombres posibles.Rápido con subfinder o amass.
        VirusTotal, ShodanBases de datos de subdominios conocidos.Datos agregados de múltiples fuentes.

        Subdomain takeover

        Cuando un subdominio apunta (CNAME) a un servicio de terceros que ya no está dado de alta, puedes reclamar ese subdominio:

        • legacy.ejemplo.com → CNAME → algo.s3.amazonaws.com
        • El bucket de S3 no existe o fue eliminado
        • Tú creas el bucket y el subdominio ahora apunta a tu contenido

        Herramientas como subjack o nuclei con templates de takeover automatizan esta detección.

        Nota

        La enumeración de subdominios es una de las fases con mayor retorno de inversión. Un subdominio de staging sin autenticación puede darte acceso completo al sistema.

        05Descubrimiento de parámetros y endpoints

        Los endpoints de una API o las acciones de un formulario son la superficie donde se concentran las vulnerabilidades. Saber qué parámetros aceptan es mitad del trabajo.

        De dónde salen los parámetros

        • JavaScript del frontend: llamadas fetch/axios, rutas de router SPA, variables de configuración.
        • Formularios HTML: campos visibles y ocultos (<input type="hidden">).
        • Documentación de la API: Swagger/OpenAPI, WADL, WSDL.
        • Archivos JS y CSS: rutas, endpoints, parámetros hardcodeados.
        • Historial del navegador: peticiones anteriores, parámetros de URL.
        HerramientaQué hace
        katanaCrawler que sigue enlaces JavaScript y extrae endpoints y parámetros.
        gauObtiene URLs de Wayback, Common Crawl, OTX.
        waybackurlsExtrae URLs del Wayback Machine.
        LinkFinderAnaliza JavaScript para encontrar endpoints y parámetros.
        paramspiderMinera parámetros de dominios de Wayback y Common Crawl.

        El JavaScript como mina de oro

        En aplicaciones modernas (SPA, React, Vue, Angular), casi toda la lógica vive en JavaScript. El archivo bundle.js contiene:

        • Todas las rutas de la API que la app consume
        • Parámetros de cada endpoint
        • Funciones de validación (qué espera el servidor)
        • Variables de entorno hardcodeadas
        • Lógica de autorización del lado del cliente (que no es seguridad)

        06Información filtrada: lo que el servidor no debería decirte

        Cada petición que haces devuelve más información de la que necesitas. Headers, cookies, mensajes de error, páginas de defecto: todo son migas que, juntas, revelan el mapa completo.

        Comentarios HTML

        Los desarrolladores dejan comentarios en el código fuente que viajan al navegador:

        • <!-- TODO: cambiar la clave antes de production -->
        • <!-- Versión anterior en /v1/backup -->
        • <!-- Usuario de test: admin / test123 -->
        • <!-- API key de desarrollo: sk_test_xxx -->

        Robots.txt y sitemap.xml

        /robots.txt lista las rutas que el dueño no quiere que se indexen. Paradójicamente, eso te dice exactamente qué hay:

        • Disallow: /admin/ → existe un panel de administración
        • Disallow: /api/internal/ → hay una API interna
        • Disallow: /backup/ → hay una carpeta de backups

        Archivos de configuración expuestos

        • /.env: variables de entorno, credenciales, claves de API
        • /wp-config.php.bak: configuración de WordPress con credenciales de BD
        • /.git/config: repositorio con historial de commits
        • /web.config: configuración de IIS con connection strings

        Google Dorks

        • site:ejemplo.com filetype:sql → bases de datos volcadas
        • site:ejemplo.com filetype:env → archivos de entorno
        • site:ejemplo.com intitle:"index of" → directory listing
        • site:ejemplo.com inurl:admin → paneles de administración
        • site:ejemplo.com filetype:pdf password → documentos con contraseñas

        Aviso

        Si encuentras un archivo .env o credenciales en una prueba de penetración, documenta el hallazgo pero no uses esas credenciales a menos que el contrato de alcance lo incluya explícitamente.

        08Caso práctico: enumeración de un objetivo

        Un recorrido completo desde el dominio hasta la superficie de ataque, encadenando las técnicas de las secciones anteriores.

        Escenario

        Objetivo: tiendaluz.com

        E-commerce con tienda online, app móvil y panel de proveedores. API troncal. Tienes acceso a Burp y a una wordlist estándar.

        Paso 1

        Subdominios

        Paso 2

        Fingerprinting y directorios

        Paso 3

        Explotación del hallazgo

        Peligro

        El staging tiene credenciales de producción. Un atacante real tendría acceso a la base de datos de todos los clientes.

        09Ejercicios de enumeración

        Doce ejercicios para practicar cada técnica. Cada uno describe un objetivo y un escenario; tu trabajo es enumerar, encontrar y clasificar los hallazgos.

        Formato sugerido: 10 minutos por ejercicio, parejas, se abren las pistas si hace falta y se comenta la solución en común.

        Ejercicio 1

        Básico Fingerprinting

        Haces un curl -I a https://blog.ejemplo.com y recibes: Server: Apache/2.4.52 (Ubuntu), X-Powered-By: PHP/8.1.10, Set-Cookie: PHPSESSID=.... ¿Qué sabes ya del objetivo? ¿Qué próximos pasos?

        1. Apache 2.4.52 en Ubuntu: ¿tiene CVEs conocidos?
        2. PHP 8.1.10: ¿es la versión actual?
        3. PHPSESSID confirma PHP. Prueba probes de WordPress, Laravel.

        Sabemos: Apache 2.4.52, PHP 8.1.10, sesiones PHP. Descarta ASP.NET, Java, Node.js.

        Próximos pasos: probes de CMS (/wp-login.php), fuzzing con extensiones .php, buscar /phpinfo.php y /.env.

        Ejercicio 2

        Básico Directorios

        ffuf contra https://tienda.ejemplo.com. Filtras 404 de 4840 bytes. Obtienes: /admin → 302, /backup.zip → 200 (234 KB), /robots.txt → 200, /.git/HEAD → 200. ¿Cuáles son prioritarios?

        1. Un .zip de 234 KB puede ser un volcado de BD.
        2. .git/HEAD permite reconstruir el código fuente.
        3. El 302 de /admin sugiere login.

        1: .git/HEAD → git-dumper. 2: backup.zip → descargar y analizar. 3: /admin → probar bypass. 4: /robots.txt → buscar más rutas.

        Ejercicio 3

        Intermedio Subdominios

        Subdominios de empresa.com: api, staging, dev, vpn, ci. El staging devuelve 200 sin auth. ¿Qué haces?

        1. Staging sin auth es el hallazgo más directo.
        2. Fingerprinting antes de fuzzing.
        3. ¿ci.empresa.com es Jenkins o GitLab CI?

        1: Fingerprinting de staging. 2: Fuzzing de directorios (.env, .git, admin). 3: Revisar ci.empresa.com (Jenkins credenciales por defecto). 4: Documentar staging sin auth como impacto directo.

        Ejercicio 4

        Intermedio JavaScript

        En index.js: fetch('/api/v2/admin/export?format=csv'), localStorage.getItem('debug_token'), URL hardcodeada: https://internal-api.ejemplo.com/v1/users. ¿Qué haces?

        1. /admin/export: probar con token normal.
        2. debug_token: probar como header o parámetro.
        3. internal-api: acceder directamente.

        Admin export: probar GET con token normal → API5 si funciona. debug_token: probar como Bearer o ?debug=true → puede desactivar controles. internal-api: acceder directamente → endpoint interno expuesto.

        Ejercicio 5

        Avanzado Cadena completa

        Encuentras /.git/HEAD. Reconstruyes el repo. En el historial hay un config/database.yml eliminado con credenciales de producción. Describe la cadena de explotación.

        1. git log --all --full-history muestra commits eliminados.
        2. git show <commit>:config/database.yml recupera el archivo.
        3. Las credenciales siguen válidas si no se rotaron.

        Cadena: 1) Detectar .git/HEAD. 2) git-dumper. 3) git log del archivo. 4) git show para recuperarlo. 5) Conectar a la BD. 6) Si es remota, probar SSH/VPN. 7) Explotar la BD.

        Ejercicio 6

        Intermedio Google Dorks

        Escribe consultas Google Dorks para: a) Archivos .env de empresas financieras, b) Directorios abiertos con backups, c) Paneles de admin de WordPress.

        1. filetype:env busca archivos .env indexados.
        2. intitle:"index of" busca listados de directorio.
        3. inurl:wp-admin busca paneles de WordPress.

        a) filetype:env "DB_PASSWORD" "banco" OR "fintech"

        b) intitle:"index of" "backup" "sql" OR "zip"

        c) inurl:wp-admin site:*.banco.com

        Ejercicio 7

        Intermedio Fuzzing

        404 personalizado de 4840 bytes. Encuentras /server-status (200, 12KB) y /phpinfo.php (200, 45KB). ¿Qué información extraes de cada uno?

        1. /server-status muestra IPs, rutas, uptime.
        2. /phpinfo.php muestra versión PHP, módulos, variables de entorno.

        server-status: IPs de clientes, peticiones activas, rutas, uptime. phpinfo.php: versión PHP exacta, módulos, rutas del sistema, variables de entorno (credenciales), disabled_functions.

        Ejercicio 8

        Avanzado Subdomain takeover

        legacy.empresa.com tiene CNAME a algo.s3.amazonaws.com. Al acceder: 404 NoSuchBucket. ¿Es susceptible a takeover?

        1. El bucket de S3 no existe.
        2. Si creas el bucket, el tráfico va a ti.

        Sí. Crear bucket en S3, configurar website hosting, subir contenido. legacy.empresa.com serviría tu contenido. Impacto: suplantación de identidad, robo de cookies.

        Ejercicio 9

        Básico Crawling

        katana con JS produce 340 URLs. 45 contienen parámetros. ¿Cómo reduces el ruido y cuáles priorizas?

        1. Filtrar tracking (utm_, fbclid).
        2. Priorizar endpoints POST y parámetros de ID.

        Filtrar: eliminar utm_, fbclid, gclid. Agrupar por path. Priorizar: 1) search=, q= → SQLi/XSS. 2) id=, user= → IDOR. 3) file=, path= → traversal. 4) url=, redirect= → SSRF.

        Ejercicio 10

        Intermedio Headers

        curl -I devuelve: Access-Control-Allow-Origin: *, Allow-Credentials: true, Strict-Transport-Security: max-age=0, X-Content-Type-Options: ausente. ¿Qué problemas?

        1. Allow-Origin: * con credenciales = CORS roto.
        2. HSTS max-age=0 desactiva HTTPS obligatorio.

        CORS: Origin: * con credenciales permite leer respuestas autenticadas. HSTS: max-age=0 permite MITM. MIME sniffing: sin nosniff, el navegador puede interpretar archivos ambiguos como JS.

        Ejercicio 11

        Avanzado Cadena completa

        Startup.com: staging (Laravel), .env con credenciales BD, .git con API key de Stripe en commit eliminado. Diseña el plan completo.

        1. Credenciales BD → datos de usuarios.
        2. API key Stripe → fraudes o consulta de transacciones.
        3. APP_KEY Laravel → firmar tokens de sesión.

        1: Conectar a BD con .env. 2: Extraer usuarios (emails, hashes). 3: Usar APP_KEY para firmar token admin. 4: Acceder al panel. 5: Usar API key Stripe: listar clientes, ver transacciones, hacer cargos. Impacto: fraude financiero, robo de datos.

        Ejercicio 12

        Avanzado Workflow completo

        Tienes 3 horas para enumerar objetivo.com. Diseña tu plan minute a minute.

        1. No empieces por fuzzing sin saber las tecnologías.
        2. Si encuentras .env o .git, priorízalo.
        3. La recursividad en fuzzing consume mucho tiempo.

        0:00-0:20 Subdominios (subfinder+httpx) + whatweb. 0:20-0:50 Fuzzing directorios. 0:50-1:10 Revisar .env/.git/admin. 1:10-1:40 Crawling katana. 1:40-2:10 Fuzzing subdominios. 2:10-2:40 Análisis JS. 2:40-3:00 Documentación.

        Nota

        El patrón repetido en todos los ejercicios: primero saber qué hay, luego decidir por dónde atacar. La enumeración no es un paso que se completa; es un proceso iterativo.

        10Glosario, referencias y recursos

        Glossario

        Glosario de términos

        Crawl
        Recorrer recursivamente un sitio web siguiendo enlaces para descubrir páginas y endpoints.
        Dork
        Consulta avanzada en un motor de búsqueda para encontrar información específica expuesta.
        Fingerprinting
        Técnica para identificar tecnologías del servidor: framework, lenguaje, versiones.
        Fuzzing
        Envío masivo de peticiones con variaciones para descubrir rutas, parámetros o comportamientos ocultos.
        Heap dump
        Vuelco de memoria del servidor que puede contener datos sensibles como tokens o credenciales.
        IDOR
        Insecure Direct Object Reference: acceso a recursos de otro usuario cambiando un ID en la petición.
        Spidering
        Recorrido automático de un sitio web para construir un mapa completo de sus páginas y enlaces.
        Subdomain takeover
        Captura de un subdominio cuyo registro DNS apunta a un servicio externo no reclamado.
        Virtual host
        Configuración del servidor web que aloja múltiples dominios en la misma IP.
        Wayback Machine
        Archivo histórico de la Web que almacena versiones pasadas de páginas web.
        Wordlist
        Lista de palabras predefinida usada para fuzzing de directorios, subdominios o contraseñas.
        Zone transfer
        Transferencia de zona DNS que revela todos los registros si el servidor está mal configurado.
