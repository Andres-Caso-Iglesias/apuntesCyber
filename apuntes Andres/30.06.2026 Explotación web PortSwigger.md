## ① Burp Suite — Definición correcta

> [!important] Burp Suite NO es "un proxy"
> Burp Suite es un **framework de auditoría web**: una colección de funcionalidades integradas que permiten realizar acciones sobre páginas web para auditarlas. El proxy es la **dependencia crítica** — sin él no funciona nada más — pero no es lo mismo que la herramienta en sí.

### Por qué funciona el proxy

El proxy opera en el **único punto** donde el atacante tiene control total sobre la comunicación: el tramo entre el navegador (que corre localmente) y el servidor.

```
[Front - NAVEGADOR - tu ordenador] → [PROXY - Burp] → [Back - SERVIDOR]
     (control total)              (intercepta aquí)     (sin acceso)
```

> [!important] La idea clave
> La seguridad del front es **completamente eludible** porque el front corre en el ordenador del atacante. Cualquier validación, restricción de longitud de campo o sanitización de inputs que exista en el frontend puede ser **bypasseda** modificando el paquete después de que la página lo valide pero antes de que llegue al servidor.

> [!important] La metáfora de Carlos
> Burp es el **cartero corrupto** que abre el buzón antes de que llegue el repartidor. Tú has metido correctamente el sobre con los calcetines, la página lo ha visto salir, pero Burp lo saca, le cambia el contenido, y lo que recibe la abuelita (el servidor) ya no son calcetines.

## ② La cadena de seguridad: Front → WAF → Back

| Capa | Ubicación | Control del atacante | Bypasseable |
|---|---|---|---|
| **Front** | Tu ordenador | Total | Sí (siempre) |
| **WAF** | Antes del servidor | Ninguno | Generalmente sí |
| **Back** | Servidor | Ninguno | Depende de la implementación |

### Qué controles pone el Front (y cómo se bypassean)

| Control del Front | Cómo se bypassea con Burp |
|---|---|
| Longitud máxima de campo (ej: 25 chars) | Modificar el paquete después de la validación |
| Sanitización de inputs | Enviar datos crudos al servidor |
| Validación de tipo de archivo | Cambiar Content-Type en el request |
| Bloqueo de caracteres especiales | Inyectar después de la validación |

> [!important] El WAF
> El **WAF** (Web Application Firewall) es bypasseable en la mayoría de implementaciones reales. Lo que sí importa es que el **backend** gestione bien los datos que le llegan, porque si el PHP del servidor no valida lo que recibe, el paquete modificado va a explotar algo.

## ③ Configuración completa del stack: FoxyProxy + Certificado CA + Burp

### Flujo de configuración

```
1. Burp abierto → Proxy → Proxy Settings → Proxy Listeners
   (verificar puerto: 127.0.0.1:8080)

2. Navegar a http://localhost:8080 → CA Certificate → Descargar

3. Importar certificado en Firefox:
   about:preferences → Certificados → Administrar certificados
   → Autoridades → Importar → Seleccionar CA Certificate

4. Instalar FoxyProxy → Nuevo proxy:
   Host: 127.0.0.1
   Puerto: 8080 (el mismo que Burp)
   Nombre: Burp Suite

5. Activar FoxyProxy cuando se quiera interceptar
```

> [!important] Problema frecuente
> Si tanto el FoxyProxy como el proxy listener de Burp están en el mismo puerto, puede haber **conflicto**. La solución es cambiar uno de los dos (por ejemplo, mover Burp a 8081) y asegurarse de que FoxyProxy apunta al puerto correcto.

> [!important] Sin certificado CA
> Sin el certificado CA instalado, el navegador detecta el proxy como un tercero no autorizado y **bloquea la conexión HTTPS**. Con el certificado, el navegador confía en Burp como si fuese el destino legítimo.

## ④ Módulos de Burp Suite — Mapa funcional

### Proxy (el corazón)

| Sub-función | Qué hace |
|---|---|
| **Intercept** | Parar y modificar peticiones en tiempo real |
| **HTTP History** | Historial de todo el tráfico interceptado |
| **Target/Scope** | Filtrar qué dominio se quiere interceptar |

### Intruder (fuzzing y fuerza bruta)

| Modo | Descripción |
|---|---|
| **Sniper** | Un payload, una posición (el más usado) |
| **Battering Ram** | Mismo payload en todas las posiciones |
| **Pitchfork** | Payloads paralelos en múltiples posiciones |
| **Cluster Bomb** | El más agresivo (solo versión Pro) |

> [!important] Cómo usar el Intruder
> 1. Intercept → Capturar petición
> 2. Clic derecho → Send to Intruder
> 3. En **Positions**: seleccionar parámetro a fuzear → Add
> 4. En **Payloads**: cargar diccionario
> 5. Ejecutar ataque
> 6. Analizar respuestas (longitud, código HTTP)

> [!important] Recomendación
> Fuzear **un solo parámetro a la vez** para poder interpretar las respuestas correctamente.

### Repeater (exploración quirúrgica)

Reenviar la misma petición cuantas veces se quiera, modificando manualmente parámetros o cabeceras entre envío y envío, y comparar las respuestas.

### Decoder (decodificación)

| Formato | Uso |
|---|---|
| **Base64** | Tokens, cookies |
| **URL Encoding** | Parámetros en URLs |
| **HTML Encoding** | Caracteres especiales |
| **Hex** | Datos binarios |

> [!important] Doble encoding
> En auditorías es frecuente encontrar tokens y cookies con **doble encoding** (por ejemplo, base64 dentro de URL encoding), que hay que decodificar en capas para ver su contenido real.

### Comparador (análisis de patrones)

Comparar dos fragmentos de texto o datos (por ejemplo, dos cookies de sesión) para buscar patrones. Útil en ataques de session hijacking o análisis de tokens.

## ⑤ Cookies de sesión y Session Hijacking

### Qué es una cookie de sesión

Cada vez que un usuario entra en una web, el servidor genera un **session ID único** y lo almacena en una cookie. Ese ID es lo que diferencia tu sesión de la de cualquier otro usuario simultáneo.

| Concepto | Descripción |
|---|---|
| **Session ID** | Identificador único de sesión |
| **Duración** | Habitualmente 30 días |
| **Invalidación** | Al limpiar la caché del navegador |
| **Hard Reset** | Ctrl+Shift+R (borra caché y cookies) |

### Flujo de autenticación con 2FA

```
Login → User/Pass → ¿Correcto?
  ├─ No → Pedir credenciales otra vez
  └─ Sí → Pedir 2FA
        ├─ Incorrecto → Pedir 2FA otra vez
        └─ Correcto → Cookie de sesión (30 días de acceso)
```

### Ataque moderno: Robo de cookie vía phishing avanzado

```
1. Crear página de phishing que replica el login legítimo
2. Víctima introduce credenciales
3. Atacante reenvía credenciales en tiempo real al servidor real
4. Si hay 2FA → mostrar iframe con formulario de 2FA
5. Víctima introduce 2FA
6. Atacante captura la cookie de sesión generada
7. Usar cookie en propio navegador → 30 días de acceso
```

> [!important] La idea clave
> Robar la cookie de sesión equivale a **robar la sesión activa completa**, bypaseando cualquier segundo factor de autenticación. El 2FA protege el proceso de **login**, no la sesión ya establecida.

> [!warning] Ejemplo práctico
> Si robas las cookies de autenticación de Outlook de alguien y las pones en tu navegador, entras a la cuenta **sin contraseña y sin 2FA**. Las cookies son el vector de acceso más peligroso en aplicaciones web modernas.

## ⑥ Qué controles de seguridad pone el Front

| Control | Ejemplo | Bypasseable con Burp |
|---|---|---|
| **Longitud de campo** | Máximo 25 caracteres | Sí |
| **Sanitización de inputs** | Bloquear comillas simples | Sí |
| **Validación de tipo** | Solo aceptar PDF | Sí |
| **Expresiones regulares** | Solo números, solo letras | Sí |
| **Bloqueo de caracteres** | Bloquear `;`, `--`, `union` | Sí |

> [!important] La lección
> **Nunca** confíes en la validación del frontend. Siempre debe haber validación en el backend. El frontend es para UX, no para seguridad.

### WordPress — Rutas importantes

| Ruta | Qué contiene |
|---|---|
| `/index.php` | Home (redirige) |
| `/license.txt` | Revela versión exacta de WordPress |
| `/wp-login.php` | Panel de login (vector de fuerza bruta) |
| `/wp-admin/` | Panel de administración |
| `/wp-content/uploads/` | Directorio de subidas (¿archivos ejecutables?) |
| `/wp-activate.php` | Registro/acciones administrativas |

### Roles de WordPress

| Rol | Permisos equivalentes |
|---|---|
| **Administrator** | rwx (control total) |
| **Editor** | rw (editar/eliminar cualquier contenido) |
| **Author** | w (escribir contenido propio) |
| **Contributor** | w (escribir, no publicar) |
| **Subscriber** | r (solo leer) |

### WPScan — Herramienta de referencia

```bash
# Instalación
sudo apt install wpscan        # Kali
gem install wpscan              # Mac

# Enumeración de plugins (sin token)
wpscan --url http://academy.local --enumerate ap

# Enumeración de plugins (con token → ve CVEs)
wpscan --url http://academy.local --api-token TU_TOKEN --enumerate ap

# Enumeración de usuarios
wpscan --url http://academy.local --enumerate u

# Fuerza bruta de contraseñas
wpscan --url http://academy.local --passwords /usr/share/wordlists/rockyou.txt --usernames admin
```

> [!important] Token de API
> La diferencia entre WPScan **con** y **sin** API token es la diferencia entre saber que existe un plugin y saber que ese plugin tiene una **vulnerabilidad crítica conocida**. Registrarse para obtener el token gratuito es obligatorio para usar WPScan de manera profesional.

## ⑨ Notas de clase — Lo que Carlos quiso que quede claro

1. **Burp Suite es un framework**, no solo un proxy
2. **El front corre en tu ordenador** → siempre puedes modificarlo
3. **El WAF es bypasseable** en la mayoría de casos
4. **El certificado CA es obligatorio** para HTTPS
5. **FoxyProxy** reenvía tráfico a Burp en el puerto configurado
6. **El Intruder** sirve para fuzzing y fuerza bruta
7. **El Repeater** es para exploración quirúrgica
8. **Las cookies de sesión** son el vector de acceso más peligroso
9. **El 2FA** protege el login, no la sesión
10. **WordPress** se vulnera por plugins, no por el núcleo
11. **WPScan** requiere API token para ver CVEs
12. **La metodología es independiente del entorno** — se puede hacer desde Windows
