## ② Arquitectura de deployment

Carlos mostró en directo cómo funciona la cadena completa de un proyecto real.

### Flujo

```
[DESARROLLADOR] → [GITHUB] → [SERVIDOR PRODUCCIÓN]
     │                │                │
  IDE (Cursor,      Contenedor       Hetzner
  VS Code, etc)    de código         IP pública
```

| Paso | Qué pasa |
|---|---|
| 1. Desarrollo | Escribes código en tu IDE |
| 2. Push a GitHub | Subes cambios con Git |
| 3. Deploy al servidor | SSH + comandos Git pull en el servidor |
| 4. Publicación | El puerto se abre y la web está accesible |

### GitHub — El contenedor

GitHub es un repositorio de código, como una estantería:
- Cada balda es un proyecto
- Cada libro es un fichero
- Tiene documentación automática (README.md)
- Permite colaboración múltiple

### Hetzner — El servidor

| Concepto | Detalle |
|---|---|
| Proveedor | Hetzner (Alemania) |
| Precio | 7€/mes (subió de 4.95€) |
| Acceso | IP pública + claves SSH |
| Panel | 9 servidores con IPs diferentes |

### SSH — La conexión

```powershell
# Generar clave SSH
ssh-keygen -t rsa -b 4096

# Conectar al servidor
ssh root@178.62.197.94
```

## ③ Caso de uso real — Startup LaTeX → PHP

Carlos mostró el caso de **Luis Martín**, un contacto que tenía un SaaS hecho en LaTeX + Obsidian.

### El problema

| Herramienta | Qué hacía bien | Qué hacía mal |
|---|---|---|
| **Obsidian** | Estructura de conocimiento | No sirve para web |
| **LaTeX** | Documentos bonitos | No sirve para clientes |

### La solución

Migrar todo a **PHP** para tener libertad de movimiento:
- Crear una landing page
- Crear una aplicación web
- Conectar con clientes reales
- Crear una comunidad

### Lo que Luis tenía montado

- Servidores en Hetzner
- Claves SSH para cada herramienta
- Panel de control con 9 servidores
- Documentación completa
- Estructura de proyecto con Docker

### Lo que Carlos le hizo

```bash
# Clonar el proyecto
git clone [repo-url]

# Instalar dependencias
composer install

# Configurar base de datos
cp .env.example .env

# Generar clave de aplicación
php artisan key:generate

# Ejecutar migraciones
php artisan migrate

# Iniciar servidor
php artisan serve
```

> [!important] La metáfora
> Luis tenía un coche con motor de F1 (LaTeX) pero sin ruedas (no podía ser web). Carlos le puso las ruedas correctas (PHP) para que pudiera rodar.

## ④ Knowledge Bases vs Machine Learning

### Cuándo SÍ es Machine Learning

| Caso | Por qué |
|---|---|
| Detectar patrones en mamografías | Aprende algo que no se le enseñó |
| Bot de Tetris que mejora | Al principio no sabe, luego aprende |
| Redes neuronales con autoaprendizaje | Genera conexiones nuevas |

### Cuándo NO es Machine Learning

| Caso | Por qué |
|---|---|
| Buscar info en internet | Es deep research, no aprendizaje |
| Mapear info en Obsidian | Es indexación |
| Crear skills para un agente | Es documentación |
| Configurar AWS según la doc | Es ejecutar instrucciones |

> [!important] La regla
> ML es cuando el algoritmo **aprende a hacer algo que al principio no sabía**. Si ya sabes hacerlo y solo lo documentas, no es ML.

### Flujo de Deep Research

```
1. 1 a N subagentes buscando en internet (usar Haiku, no Opus)
2. El "jardinero" poda información redundante
3. El "conector" lee, entiende y crea relaciones
4. El resultado es un grafo con pesos
```

## ⑤ Optimización de tokens — La estrategia de Carlos

| Estrategia | Ejemplo |
|---|---|
| **Skills pregeneradas** | Frases hechas del personaje |
| **A/B testing con admin** | Aceptar o rechazar respuestas |
| **Vector database** | Cada respuesta aceptada = positivo |
| **Reducción de recorrido** | Solo leer las skills necesarias |

### El proyecto del chatbot de persona conocida

```
1. Desintegrar personalidad (tono, gestos, respuestas)
2. Crear bóveda de conocimiento en Obsidian
3. Generar skills a partir del grafo
4. El agente se comporta como la persona
5. Aprendizaje continuo con validación
```
