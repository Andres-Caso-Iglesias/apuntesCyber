## ① OWASP API Security Top 10 — El framework de auditoría de APIs

Al igual que el OWASP Top 10 para web, el **OWASP API Security Top 10** es el estándar que clasifica las vulnerabilidades más comunes en APIs.

### Las 10 categorías del API Top 10

| # | Categoría | Resumen |
|---|---|---|
| API1 | **Broken Object Level Authorization** | IDOR: acceder a datos de otro usuario modificando un ID en la URL |
| API2 | **Broken Authentication** | Autenticación de usuario rota: login débil, tokens predecibles |
| API3 | **Broken Object Property Level Authorization** | Exposición excesiva de datos: la API devuelve más información de la necesaria |
| API4 | **Unrestricted Resource Consumption** | Falta de rate limiting: no se limitan peticiones |
| API5 | **Broken Function Level Authorization** | Autorización rota a nivel de función: acceder a rutas de admin sin permisos |
| API6 | **Unrestricted Access to Sensitive Business Flows** | Asignación masiva: modificar campos que no deberías |
| API7 | **Server Side Request Forgery (SSRF)** | Configuración incorrecta del servidor |
| API8 | **Security Misconfiguration** | Configuraciones inseguras por defecto |
| API9 | **Improper Inventory Management** | Inyecciones: SQLi, XXE en APIs |
| API10 | **Unsafe Consumption of APIs** | Consumo inseguro de APIs externas |

> [!important] Diferencia clave con el OWASP Top 10 web
> El API Top 10 se enfoca en **objetos** (usuarios, mascotas, documentos) y **funciones** (endpoints), no en páginas web. Las APIs son como cajones: cada endpoint es un cajón que puedes abrir, modificar o borrar.

## ② Métodos HTTP — La clave para entender las APIs

### Los 6 métodos HTTP

| Método | Función | Ejemplo |
|---|---|---|
| **GET** | Leer/obtener un recurso | `GET /api/users/1` |
| **POST** | Crear un recurso | `POST /api/users` |
| **PUT** | Reemplazar un recurso completo | `PUT /api/users/1` |
| **PATCH** | Modificar algunos campos | `PATCH /api/users/1` |
| **DELETE** | Borrar un recurso | `DELETE /api/users/1` |
| **OPTIONS** | Ver métodos habilitados | `OPTIONS /api/users` |

> [!important] PUT vs PATCH
> **PUT** reemplaza todo el recurso. **PATCH** modifica solo algunos campos. Ejemplo: con PUT cambias nombre Y contraseña de golpe; con PATCH cambias solo el nombre.
>
> `PATCH role admin` → Escalada de privilegios si no está protegido.

### La petición HTTP

```
GET /api/users/1 HTTP/1.1
Host: example.com
Authorization: Bearer <token>
Content-Type: application/json
```

### Cabeceras importantes

| Cabecera | Qué hace |
|---|---|
| `Authorization` | Lleva las credenciales (JWT, token) |
| `Content-Type` | Formato del body (JSON, XML, etc.) |
| `Accept` | Formato que espera el cliente |
| `Cookie` | Sesión cuando se usa cookie en vez de token |
| `X-Forwarded-For` | IP real del cliente (proxy) |

## ③ JWT (JSON Web Token) — Autenticación en APIs

### Qué es un JWT

Un JWT es un token que se genera después del login y se usa en la cabecera `Authorization: Bearer <token>` para autenticar cada petición.

### Estructura de un JWT

```
eyJhbGciOiJIUzI1NiJ9.eyJ1c2VyX2lkIjozLCJyb2xlIjoiYWRtaW4ifQ.XXXXX
```

- **Header** (eyJ...): Algoritmo de firma
- **Payload** (eyJ...): Datos del usuario (ID, rol, etc.)
- **Signature** (XXX...): Firma para verificar integridad

### Cómo funciona

1. El usuario hace login con usuario/contraseña
2. El servidor genera un JWT con la información del usuario
3. El cliente envía el JWT en cada petición
4. El servidor verifica el JWT y ejecuta la acción

> [!important] Vulnerabilidad común
> Si el JWT no está bien implementado, se puede modificar el payload (por ejemplo, cambiar el `role` de `user` a `admin`) y reenviarlo. El servidor debe verificar la firma siempre.

## ④ IDOR (Insecure Direct Object Reference)

### Qué es

**IDOR** es cuando puedes acceder a datos de otro usuario simplemente cambiando un ID en la URL.

```
GET /api/users/1  → Datos de Ana (tu usuario)
GET /api/users/2  → Datos de otro usuario (¡acceso no autorizado!)
GET /api/users/3  → Datos del admin (¡acceso completo!)
```

### Ejemplo real

> [!important] Caso Verstappen
> Los datos de Max Verstappen fueron filtrados desde la página de la FIA usando IDOR: se registraban como usuario normal, hacían un GET al endpoint de usuarios, veían que el campo `role` era `user`, y hacían un PUT para cambiarlo a `admin`.

## ⑤ Métodos de escalada de privilegios en APIs

### Escalada vía PATCH/PUT

```
PATCH /api/users/1
{
  "role": "admin"
}
```

### Escalada vía tokens

Si consigues el token de un admin (por ejemplo, haciendo login con `admin/admin123`), puedes usarlo para acceder a endpoints restringidos.

### Bypass de controles de acceso

A veces el control de acceso está solo en el frontend (el navegador no muestra el botón), pero el backend no valida. Con Burp Suite puedes enviar la petición directamente.

---

## ⑥ Borrado de recursos — DELETE

### Peligro del DELETE

`DELETE` borra recursos permanentemente. Si no está protegido, puedes borrar usuarios, productos, archivos, etc.

### Control de acceso por método

> [!important] Cada método tiene su propio control
> El endpoint puede permitir GET a cualquier usuario, pero DELETE solo a admins. Si el backend no valida el rol por cada método, tienes un problema.

---

## ⑦ Enumeración de usuarios con Intruder

### Técnica de fuzzing

En Burp Suite, puedes usar **Intruder** para iterar sobre IDs de usuarios:

```
GET /api/users/1  → 200 OK (Ana existe)
GET /api/users/2  → 200 OK (Otro usuario existe)
GET /api/users/3  → 200 OK (Admin existe)
GET /api/users/4  → 404 Not Found
```

Al ver las diferencias en la longitud de respuesta, sabes cuántos usuarios hay.

---

## ⑧ Opciones (OPTIONS) — Enumeración de métodos

Cuando lanzas un `OPTIONS` a un endpoint, te devuelve qué métodos HTTP acepta:

```
OPTIONS /api/pets
→ Allow: GET, POST, PUT, DELETE, OPTIONS
```

Si ves `DELETE` o `PUT` habilitados, ya sabes qué puedes probar.

## ⑨ Cómo se usa Burp Suite en APIs

### Configuración

1. Activar **Foxy Proxy** en el navegador (apunta a Burp: 127.0.0.1:8080)
2. Abrir Burp Suite → Proxy → Intercept
3. Navegar por la web: Burp captura las peticiones
4. Clic derecho → **Send to Repeater** para modificar y reenviar

### Repeater

Herramienta para reenviar peticiones modificadas. Ideal para probar:
- Cambiar IDs
- Cambiar tokens
- Probar métodos diferentes
- Modificar roles

### Intruder

Herramienta para fuzzing: automatiza envío de peticiones con variaciones (IDs, payloads, etc.)

## ⑩ Notas de clase

- **Las APIs no son más que funciones web** que viajan por HTTP.
- **OPTIONS es tu mejor amigo** para enumerar qué métodos están habilitados.
- **PUT y PATCH** son los menos atacados porque la gente solo conoce GET y POST.
- **Cada método tiene su propio control de acceso**: no basta con proteger GET si PUT está abierto.
- **El JWT contiene información del usuario**: si puedes modificar el payload, puedes escalar privilegios.
- **IDOR es una de las vulnerabilidades más comunes** en APIs: siempre verificar que el usuario solo accede a sus propios datos.
- **Hack the Box liberará claves VIP el lunes** para empezar a hacer máquinas premium.
