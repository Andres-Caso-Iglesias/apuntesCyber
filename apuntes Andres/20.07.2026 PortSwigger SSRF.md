## ① SSRF €” Qué es y por qué importa

### Definición Core

**SSRF (Server-Side Request Forgery)** ocurre cuando una aplicación web hace una petición HTTP a una URL que puede ser controlada, total o parcialmente, por el atacante. La clave es que **la petición la hace el servidor, no el navegador del usuario**. El servidor tiene acceso a recursos que el atacante no puede alcanzar directamente: `localhost`, redes internas, servicios sin autenticación que solo escuchan en interfaces internas, y endpoints de metadatos de proveedores cloud.

### El Vector de Detección

Es el mismo que en Path Traversal: buscar en Burp Suite parámetros que contengan URLs o partes de URLs, como `url=`, `api=`, `endpoint=`, `redirect=`, `fetch=` o `resource=`. Cualquier parámetro que sugiera que el servidor va a hacer una petición a partir de ese valor es un candidato a SSRF.

- **La metáfora útil:** el servidor es el empleado con tarjeta de acceso que puede entrar en salas donde tú no puedes. Si consigues decirle al empleado a qué sala ir y qué traerte, no necesitas la tarjeta.

## ② Caso 1 €” SSRF contra el propio servidor (`localhost`)

### El Escenario

La aplicación de la tienda tiene un panel de administración en `/admin` que **no está accesible desde el exterior**: solo responde a peticiones provenientes de `localhost`. Hay una funcionalidad de "comprobar stock" que hace una petición al backend usando un parámetro `stockApi` con la URL de la API interna.

### Explotación

Al interceptar esa petición en Burp y modificar el valor por `http://localhost/admin`, el servidor hace la petición a sí mismo, y como el origen de la petición es el propio servidor, el panel de administración responde con el contenido completo. El response de la aplicación incluye el HTML del panel interno con los usuarios del sistema.

Para completar el laboratorio se encadena la petición: primero se obtiene la URL del endpoint de borrado de usuarios del HTML del panel, y luego se hace una segunda petición SSRF apuntando a esa URL:

```
stockApi=http://localhost/admin/delete?username=carlos
```

El servidor ejecuta la petición de borrado como si viniera del propio sistema, con todos los privilegios que eso implica.

> [!important] La idea clave
> Los paneles de administración que solo escuchan en `localhost` asumen que `localhost` es confiable. SSRF rompe esa asunción porque el atacante puede hacer que el servidor hable con sí mismo.

## ③ Caso 2 €” SSRF contra infraestructura interna

### El Escenario

En este caso la aplicación hace peticiones a un servidor interno en la red `192.168.0.0/24`. El atacante no conoce qué IP exacta ni qué puerto expone el servicio administrativo. Se usa el **Intruder de Burp** para hacer un escaneo de hosts y puertos dentro de la red interna.

### Metodología

1. Se itera sobre las IPs del rango `192.168.0.1` a `192.168.0.255`, buscando respuestas con código distinto de 404. La respuesta diferente delata el host activo.
2. Una vez identificada la IP, se itera sobre los puertos más comunes (en este laboratorio se da el rango 8000 a 9000 para acotar) buscando la misma diferencia de respuesta.
3. El panel administrativo encontrado responde a peticiones sin autenticación porque asume que nadie puede llegar a él desde el exterior. SSRF lo convierte en accesible.

> [!important] La idea clave
> Los servicios internos sin autenticación son el objetivo más valioso de SSRF. Asumen que la red interna es confiable, y SSRF convierte al servidor público en un pivote hacia esa red.

## ④ Caso 3 €” SSRF contra metadatos de AWS

### El Endpoint Mágico

En entornos cloud, las instancias EC2 de AWS exponen un endpoint de metadatos en la dirección `169.254.169.254`. Esta es una dirección **link-local** (no enrutable fuera de la instancia) que devuelve información sobre la instancia sin ningún tipo de autenticación: nombre de la instancia, región, rol de IAM asignado, y lo más crítico, las **credenciales temporales del rol**.

### Navegación del Árbol de Metadatos

```bash
# 1. Índice de categorías disponibles
stockApi=http://169.254.169.254/latest/meta-data/

# 2. Profundizar hasta credenciales IAM
http://169.254.169.254/latest/meta-data/iam/security-credentials/

# 3. Obtener nombre del rol asignado a la instancia
# 4. Última petición con el nombre del rol
http://169.254.169.254/latest/meta-data/iam/security-credentials/nombre-del-rol
```

La última petición devuelve las credenciales temporales: `AccessKeyId`, `SecretAccessKey` y `Token`. Con estas tres credenciales se puede autenticar contra cualquier servicio de AWS con los permisos que tenga asignados el rol de la instancia.

> [!important] La idea clave
> El endpoint de metadatos de AWS es el objetivo más crítico de SSRF en entornos cloud. Las credenciales IAM obtenidas pueden dar acceso a S3, RDS, Lambda, o cualquier otro servicio que el rol tenga permitido. En auditorías de aplicaciones cloud, SSRF siempre debe apuntar a este endpoint.

## ⑤ Bypasses de Filtros SSRF

Se cubrieron los bypasses más comunes para cuando el servidor intenta bloquear peticiones a direcciones prohibidas.

### Cuando el servidor bloquea `127.0.0.1` literalmente
- Representación decimal de la IP: `2130706433` (que es `127.0.0.1` en decimal)
- Forma abreviada: `127.1`
- Forma octal: `0177.0.0.1`
- Todas son representaciones válidas de `localhost` que algunos parsers no reconocen como equivalentes.

### Cuando el servidor bloquea `localhost` como palabra
- Usar `127.0.0.1` directamente, o viceversa.

### Cuando el servidor bloquea el dominio directamente
- Usar un dominio propio que resuelva a la IP bloqueada. Si el atacante controla un DNS, puede registrar un dominio que apunte a `127.0.0.1` y el servidor resolverá el dominio sin saber que la IP es `localhost`.

### Cuando hay una redirección abierta en la aplicación
- Encadenar con SSRF: el parámetro vulnerable apunta a la URL de la redirección abierta, que a su vez redirige al destino interno. Si el servidor sigue redirecciones automáticamente, llega al destino interno sin que el filtro de SSRF lo detecte.

## ⑥ SSRF Ciego

### Qué es

El **SSRF ciego** ocurre cuando el servidor hace la petición pero el resultado no aparece en el response de la aplicación. La petición se ejecuta en el backend, pero la respuesta queda en el servidor y el atacante no la ve directamente.

### Detección: Burp Collaborator

Un servidor externo controlado por el atacante que registra cualquier petición que reciba. Al apuntar el parámetro vulnerable a la URL del Collaborator, si el servidor hace la petición, el Collaborator la registra aunque el atacante no vea nada en el response de la aplicación. Esto confirma que hay SSRF aunque sea ciego.

### Explotación

Más compleja, se verá en sesiones avanzadas: requiere encadenar con otras vulnerabilidades o usar técnicas out-of-band para exfiltrar datos.

## ⑦ Recapitulación Integrada

SSRF completa el cuadro de vulnerabilidades que convierten al servidor en aliado del atacante:

| Vulnerabilidad | Qué hace el servidor por el atacante |
|----------------|--------------------------------------|
| **Path Traversal** | Lee ficheros locales |
| **XXE** | Parsea XML externo con consecuencias locales |
| **SSRF** | Hace peticiones de red que el atacante no puede hacer directamente |

→

Los tres vectores comparten la misma raíz: una función del servidor acepta entrada de usuario sin validar y la usa para acceder a un recurso. La semana que viene se entra en **SQL Injection** siguiendo la misma estructura progresiva: desde los casos más simples hasta blind SQLi y técnicas out-of-band.

```
¿Veo un parámetro que sugiere que el servidor va a hacer una petición?
 │
 │”œ─ Probar localhost / 127.0.0.1 / 169.254.169.254 / [::1]
 │
 │”œ─ Si responde 200 + HTML admin → SSRF confirmado, explotar
 │
 │”œ─ Si responde 400/403 "blocked" → Filtro activo (Blacklist)
 │ │”œ─ Encoding (1x/2x/3x)
 │ │”œ─ IP alternativa (127.1, decimal, octal, IPv6)
 │ │”œ─ DNS trick (lvh.me, dominio propio → 127.0.0.1)
 │ ┘─ Redirect chain
 │
 │”œ─ Si timeout / 500 / sin cambio visible → Blind SSRF candidate
 │ ┘─ Collaborator / Interactsh
 │
 ┘─ Si red interna expuesta → Intruder para fuzzing IPs/puertos
```

> [!note] La regla de oro
> En cloud, **SIEMPRE** probar `169.254.169.254` (AWS) / `metadata.google.internal` (GCP) / `169.254.169.254` con header `Metadata: true` (Azure) como primer intento. SSRF + Metadata = Cloud Admin.
